2024 年 1 月，Asahi Linux 承諾 Thunderbolt 會在年內到位；兩年後的 Linux 7.3 進度報告，把那句承諾直接稱為「mistake」，同時開始把有限度的 Thunderbolt 支援交給使用者。

Asahi 7.3 進度與 4 KiB 頁面難題

Asahi Linux 在 11 月 7 日發表 Linux 7.3 的進度報告，署名作者是 James Calligeros。報告的項目很雜：macaudio 與 AVD 兩個大型 driver 送上了郵件列表，M3 不再需要 EXPERT 旗標，Thunderbolt 開始出貨，x86 遊戲脫離 VM 執行的實驗有了結果，麥克風處理的速度提高到將近兩倍。把這些項目並排讀，會看到同一個模式反覆出現：Apple 的每一個自家設計，都要有人替 Linux 付一筆工程帳，而這份報告有大半篇幅，是在交代這些帳各自怎麼付、付到哪裡、哪幾筆還欠著。

上游化：兩個大 driver 與一個流程轉向

這個週期有兩個主要 driver 送上郵件列表，macaudio 和 AVD。macaudio 難在 Apple 的音訊子系統，作者形容它「rather special」，說光是為了正確支援它，就需要對 ALSA 核心做相當多的修改。Apple 使用的喇叭與耳機放大器，是上游本來就有支援的那幾款的特殊變體，對應的 driver 也得做不小的改動。團隊先前已經長篇討論過這些工作，這次終於能把主要 driver 送去審查。driver 與 Devicetree 的改動約 3100 行，文章稱它是整個 patchset 中相當大的一塊。

AVD 的規模更大。AVD driver 與相關的 Devicetree 改動約 13000 行，但這個 driver 在下游樹裡只待了不到三個月，就已經上了郵件列表。作者說這是團隊至今針對主要 SoC 元件最短的上游週期，並認為這對將來轉向 upstream-first 開發是好兆頭。兩個 driver 並排看，合理的推測是 macaudio 的成本主要花在修改既有的核心與放大器 driver，AVD 的成本則花在 driver 本身；文章沒有直接做這個比較，這只是從兩段敘述拼出來的讀法。

同一個週期，M4 Pro、M4 Max 與 M5 的初始 Devicetree 也上了列表，作者歸功於 Yureka。這批 Devicetree 的範圍很窄，只夠把 SoC 開到 TTY，更完整的啟用工作還在進行。流程上的轉變反而更關鍵：新裝置需要的 TI USB-PD 與 SPMI driver 改動，以及 Thunderbolt 的初始支援，都是先在上游開發，再回到下游樹。作者說團隊已經開始在能做到的地方改採 upstream-first，並且很高興看到這個方向開始見效。

M3 轉正，M4 與 M5 靠多開 VM 繼續逆向

上一份報告透過 installer 的 EXPERT 旗標，開放了 M3 系列的初步支援。這次的消息是，早期使用者回報的問題幾乎沒有，所以 M3 支援正式開放，不再需要 EXPERT 旗標。M3 也同時有了幾項改進，最主要的是啟用 DCP；作者說這除了帶來效能與電池續航的改善，還讓 M3 裝置能啟用睡眠，MacBook 瀏海周圍的區域也變得可用。m1n1 與核心的更新，依文章說法會在報告發表後的幾天內釋出。

M3 與 M1、M2 之間目前最明顯的落差是 GPU。作者的說法是，Apple 的 GPU 團隊似乎遵循 tick-tock 模式，M3 的 GPU 與 M1、M2 上的設計有非常大的差異。負責逆向的是另一群新的貢獻者，今年的 XDC 上，Alyssa Millburn、Anna Maniscalco 與 TellowKrinkle 公開了進度：m1n1 已經能成功初始化 M3 的 GPU，團隊也畫出了一個三角形。作者同時提醒，Apple 又做了幾個「interesting choices」，要整合進上游 Mesa 需要可觀的工程投入。

逆向工程這條線的難度，則隨著 Apple 疊上更多層而上升。上一期預告過，m1n1 能虛擬化啟用 SPTM 的 macOS 版本，使 M4 系列的逆向成為可能。M5 帶來的新問題是，支援 M5 的 macOS 版本全都要求使用 Exclaves。文章對 Exclaves 的描述是：在 Secure Kernel 控制的隔離環境中執行的小型應用程式，M5 系列以後的 macOS 用它處理敏感工作，例子是把鏡頭使用中的指示畫到螢幕上。XNU 透過 SPTM 與 Secure Kernel 及 Exclaves 溝通，用的是另一套叫 Tightbeam 的 IPC 協定；就像 SPTM 一樣，XNU 找不到執行中的 Exclaves 就會 panic。作者認為整體概念和 Arm 自家的 TrustZone 很像。

有些 Exclaves 可以靠改命令列設定繞過去，但作者預測，這個辦法不會一直有效。Sven 因此換了問法：能不能直接把這一整套放進 m1n1？第一個嘗試是把 Secure Kernel 與 Exclave userspace 放進另一個 VM，和 SPTM、macOS 並排。這個做法成功了，m1n1 現在能在 EL1 下開出三個 VM，於是 M4 與 M5 系列機器上的 macOS 都能虛擬化並逆向。

圖中的三個方塊，對應文章列出的三個元件，右邊那個因為是這次才加進去的而特別標色。從結果推測，這個做法的重點是讓 m1n1 補齊 macOS 預期存在的所有元件，而不是改動 macOS 去遷就 m1n1；文章沒有明說這是設計原則，只說第一個嘗試就成功了，團隊也沒有交代之後是否還要為更多元件再開 VM。

Thunderbolt：兩年沒消息，因為 Intel 的假設全被打破

Thunderbolt 是這份報告裡最有故事的一段。2024 年 1 月，團隊犯了作者所說的錯，承諾年內支援；之後兩年，他們對 Thunderbolt 幾乎什麼都沒說。作者現在給的答案是，它已經在郵件列表上，而且 patchset 是先送上游的，團隊另外把它併進下游核心，並且已經在出貨給使用者。

作者先交代背景。Thunderbolt 原本由 Apple 與 Intel 共同開發，硬體的設計與製造由 Intel 負責。Intel 以文章形容為「(mostly) reasonable」的價格，把控制器賣給任何想要的人，其他廠商於是沒有動機自己設計。直到最近，大致與標準移交給 USB-IF 同時，AMD 這類公司才開始自製控制器。Apple 當然也不例外，而且是比多數廠商更早動手的一家，理由是它在推動大部分矽智財的內製化。

Apple 的控制器是一顆執行 RTKit 的 Cortex-M3，搭配一個專屬的 Thunderbolt/USB4 router；每一個支援 Thunderbolt 的 USB-C 連接埠各有一組，所有 Apple Silicon Mac 皆然。這帶來第一個麻煩。市面上其他現存的 Thunderbolt 控制器全由 Intel 供應，Linux 核心的 Thunderbolt 子系統實際上就是圍繞它們設計的，對機器的硬體拓樸、硬體能力、某些暫存器與共享記憶體區域的存取方式，都帶著許多假設。作者的評語是 Apple 的控制器打破了其中許多假設，後面還附了一聲帶諷刺的「Great.」。

第二個麻煩是控制器與 PMGR 的耦合很奇怪。每個控制器的 reset 線，是靠設定或清除 PMGR MMIO 範圍中段的一組位元來拉高或放開；沒有別的硬體區塊是這樣運作的，團隊花了一段時間，才意識到那些對 PMGR 看似隨機的寫入不是雜訊。處理這一切的是 Sven，作者說他為這件吃力不討好的工作投入了將近 5 年，期間還做著其他同樣出色的工作。

出貨的功能有明確的邊界。目前只支援 USB3、XDomain 與 Thunderbolt Networking：可以接 USB 裝置，也可以把兩台 Thunderbolt 電腦連起來互相 ping，文章的說法是大概就這樣。PCIe 與 DisplayPort 的 tunnelling 還沒有，而大多數 Thunderbolt dock 都需要這兩項，作者在後面補了一句「Yet」與「Watch this space」。依這個範圍推斷，靠 dock 接螢幕和擴充裝置的用法，暫時還走不通；只想接 USB 裝置，或讓兩台機器直連組網的人，則已經可以試。

4 KiB 頁面：macOS 一句話做到的事，Linux 為什麼做不到

第二段分量重的是遊戲。作者的出發點是，在 Asahi Linux 上玩商用 PC 遊戲本來就相當痛苦，因為需要的軟體堆疊極為複雜：要把 x86/amd64 的 binary 轉成 arm64，還得快到足以低延遲遊玩；多數情況下還要處理 Windows API；而且幾乎所有遊戲都內建了 4 KiB 記憶體頁面大小的假設，用來啟用某些效能最佳化。

過去幾年，這些問題有一部分已經解決。FEX 進步很多，二進位轉譯的效能與可靠性，在多數情況下已經不太需要考慮。WINE 的 ARM64EC 支援也成熟可靠，FEX 因此只需轉譯遊戲本身的 binary，不必轉譯 WINE 整個 Windows API 實作。剩下 4 KiB 頁面大小這件事，由 muvm 負責：它用一個搭配 DRM Native Context 的薄 VM，向 x86/amd64 應用程式呈現 4 KiB 的頁面大小。

muvm 最初的假設是，DRM Native Context 能讓 VM 內的 GPU 效能接近原生，這個假設沒有成立。文章給的代價是約 20%，視工作負載而定。為了遷就 VM 而做的各種工程，也帶來其他問題：muvm 不能使用 Wayland，I/O 效能偏慢，對某些種類的輸入裝置也處理得吃力。

作者坦承，這是 macOS 完勝的地方。XNU 允許使用者空間的行程以任意的頁面粒度映射自己，所以 Rosetta 只需要告訴 XNU，替它的子行程映射 4 KiB 頁面。Linux 沒有這個彈性，所有頁面都必須以和核心相同的粒度映射。去年團隊曾預告 Windows 遊戲可以在 muvm 之外執行，但那個版本依賴 FEX 內部的醜陋 hack，後來為了可維護性與轉譯正確性已經移除。即使當時，相容性也時好時壞，許多（多半較舊的）軟體仍然拒絕運作。

轉機來自 Android。Android 正從 4 KiB 頁面轉向 16 KiB 頁面，原因不止一個；Google Play 現在要求應用程式為 16 KiB 系統建置，更新後沒能在這類系統上通過測試的應用程式，不會獲准上架。那些不再更新的應用程式怎麼辦？Google 工程師 Kalesh Singh 與 Frederick Mayle 今年在 Linux Plumbers Conference 的演講談的就是這件事，他們的解法很直接：修改 Linux，讓使用者空間能夠映射 4 KiB 頁面。

他們加進 Android 核心的功能叫 P3S，全名 Per Process Page Size。在 ARM64 上，頁表粒度由 Translation Control Register（TCR）裡的位元控制。P3S 追蹤每個行程頁表的粒度，每當切換到頁表大小不同的行程，就把對應的位元寫進 TCR。文章的效能論證是：這只是一次暫存器寫入，而對頁面大小為原生的行程又是 no-op，所以效能代價實質上為零。這是設計層面的推論，文章沒有附上量測數字。下面的圖用一串示意的行程切換，標出這個機制何時要動 TCR。

圖中的行程序列是示意，不是量測。對照文章的描述，要看的只有一件事：只有目標行程的頁表粒度與原生不同，才會有那一次暫存器寫入；原生行程之間的切換不多做任何事。至於 4 KiB 行程底下的子行程，文章說它們會繼承 shim 設下的 4 KiB 頁面大小，所以遊戲啟動後衍生出的行程，也落在同一條規則裡。

換個角度看，muvm、macOS 與 P3S 三條路，是把「遊戲假設 4 KiB，核心卻用 16 KiB」這個落差，放在不同的層去吸收。muvm 把落差放在 VM 的邊界上，代價是文章給的約 20% 效能損失，以及 Wayland、I/O 與輸入裝置的種種限制。macOS 把落差放在核心的映射機制裡，XNU 本來就允許行程自選粒度，Rosetta 要做的只是開口要求。P3S 則把落差放在行程切換的那一刻，用一次暫存器寫入處理。三者的差別在於落差由誰負責、什麼時候付錢；這是把文章的三段敘述放在同一個框架下的整理，框架本身不是作者的說法。

作者把 P3S 的 patchset 重新套到 Asahi 的樹上，順手修了幾個 bug，文章說這組 patchset 大致可以乾淨地 rebase 到主線 Linux 上。結果是四款遊戲在 muvm 之外跑了起來。前兩款作者自己就承認不算有說服力：Star Wars Battlefront 是 22 年前一款很簡單的 Direct3D 9.0 遊戲，搭配 WineD3D；Wolfenstein 系列的 The New Order 是高度最佳化的 OpenGL 遊戲，又是 64 位元，會走 WINE 的 ARM64EC 路徑，大幅減少 FEX 要做的工作。

所以他們接著挑了更糟的：要是 32 位元，讓 FEX 與 WINE 更吃力，還要用到 DXVK，程式本身又糟糕到在真正的 Windows 上都不太能正常運作，要靠社群 patch 與命令列參數才能在現代電腦上啟動。那就是 Grand Theft Auto IV。最後連 Bethesda 的遊戲也試了，Fallout 系列的 New Vegas 同樣搭配 DXVK，在 muvm 之外跑了起來。

效能的結論有保留。Battlefront 與 Wolfenstein 基本上毫無瑕疵地執行，後者在 M2 Max 的 Mac Studio 上達到 144+ FPS；GTA IV 則「not fantastic」，但比使用 muvm 時大幅改善。作者另外提到兩個副產品：完全不用 VM，應該能消除幾類 bug，而除錯 GPU driver 也應該容易許多。圖上標色的是效能最不理想的那一款，也是作者特意挑來加壓的案例。

P3S 為什麼還不出貨

演示做完，才是帳單。作者說，一如以往有個代價，而且遺憾的是這次很大。目前的方案寫死了 16 KiB 主機與其上的 4 KiB 行程，這剛好符合 Google 的商業需求，但在核心記憶體管理的核心程式碼裡，加入針對特定頁面大小的 kludge，並不適合放進上游。團隊不確定 Google 是否打算把這個做法一般化並送上游，還是它會一直是只存在於 Android 的 patchset。

第二個限制在使用者空間。P3S 靠檢查 binary 的 metadata，讀取各個 section 的頁面對齊來運作。這符合 Google 的用法，因為 P3S 被設計成給對齊 4 KiB 的應用程式使用的 fallback 機制。但現代的 arm64 binary 是對齊 64 KiB 的，這樣才能保證與所有原生頁面大小的系統相容，所以必須有一個 shim 來強制啟用 P3S。shim 觸發 P3S 之後，它的所有子行程都會繼承 4 KiB 的頁面大小。

兩邊的使用情境因此並不相同。Google 的 P3S 靠 binary 自己宣告的對齊 metadata 判斷要不要介入，是被動的 fallback，目標是那些來不及改成 16 KiB 的舊應用程式。Asahi 想要的是由自己指定哪些行程使用 4 KiB，而現代 arm64 binary 的 metadata 不會替它說出這個需求，所以必須在外面多包一層 shim。這個差異來自文章兩段敘述的合併，也就是 metadata 檢查，加上需要 shim 強制啟用，作者本人沒有用這樣的語言總結。也正因為還得寫這層 shim，團隊才說在 Google 的態度明朗之前，不值得先投入實作。

表裡 muvm 的「上游前景」一格寫「文章未討論」，因為作者談上游問題時，針對的只有 P3S 這組 patchset。把兩欄並排看，P3S 的優勢很集中：它拿掉了 VM 這一層；合理的推測是 muvm 的 Wayland、I/O 與輸入裝置限制都來自 VM，所以脫離 VM 之後不再適用，文章明說的則只有「消除 VM 應該能減少幾類 bug」。它的代價也同樣集中在剛才那兩條，寫死的頁面大小組合，和需要 shim。

團隊的決定是現在不出貨。他們不想把這個功能放進下游樹，讓使用者開始依賴一個前景如此不確定的東西；實作 shim 的力氣，也要等到弄清楚 Google 打算怎麼處理這組 patchset 之後才值得花。團隊已經去信向 Google 提問，希望很快有更多消息。這個取捨的結構很清楚：功能能展示，遊戲脫離 muvm 的成果就在眼前，但出貨之後的維護責任落在 Asahi 身上，而 patchset 的命運掌握在別人手上。

報告前面談上游化時，作者把 upstream-first 當作方向。合理的推測是，這個決定與那個方向出自同一個考量：不把尚未確定能進上游的東西交給使用者。文章沒有把兩者明確連起來，這是我讀出來的關聯。

麥克風、Fedora 與授權

麥克風這一節是整份報告最偏工程細節的一段。MacBook 麥克風陣列使用的自製 beamformer 是用 Rust 寫的。作者承認 Rust 的科學計算生態不如 C++ 成熟，而 beamforming 需要在填滿音訊樣本的 buffer 上做即時 FFT 與非常吃重的矩陣運算。成熟的科學計算函式庫帶有手工最佳化的程式碼，常用綁定目標 ISA 的 intrinsics；他們原本沒有這樣做，靠的是編譯器盡可能自動向量化，來達到效能目標。

這個安排在團隊拿掉以 FFT 為基礎的 analytic transform、改用基於 IIR（infinite impulse response）濾波器的實作時垮掉了。新實作理論上應該更快，但編譯器沒能把它自動向量化。Linkmauve 出手補上了 arm64 與 amd64 的 SIMD 最佳化程式碼，再加上 Frédéric Bour 的其他效能最佳化，文章說結果是 Triforce 快了將近兩倍，而且使用的 CPU 時間更少。

發行版這邊，Fedora Linux 45 在 11 月 3 日釋出，Fedora Asahi Remix 同一天出貨，作者說這是團隊第一次做到新版 Fedora Asahi Remix 與上游同日釋出。如果你手上有 M3 機器，依文章說法，現在安裝不需要 EXPERT 旗標；要用 Thunderbolt 的人則要記得，它目前只涵蓋 USB3、XDomain 與 Thunderbolt Networking。

報告最後一節談授權，是文章裡最不技術、也最有立場的部分。作者先講了一段歷史：WINE 最初也是以 MIT 授權釋出，那個年代的科技公司把寬鬆授權的專案視為可以隨意取用的資源，市面上出現了許多被商業化販售的 WINE 專有分支。WINE 團隊愈來愈擔心，這些分支雖然完全有權存在，卻可能造成整個生態嚴重碎片化，最後讓 WINE 本身難以為繼。2002 年，WINE 改為 LGPL 授權，目的是防止更多專有分支出現，並鼓勵直接向上游貢獻。作者在這一節的結尾引用了那句老話：不從歷史學到教訓的人，注定重蹈覆轍。

團隊自己的處境相似。作者說 Asahi Linux 一直盡可能以寬鬆的 MIT 授權釋出程式碼，好讓 BSD 與其他自由軟體作業系統的朋友參與；現在他們認為這不再可行。理由是團隊得知有多起利用寬鬆授權劫持其成果的嘗試，目的是取代專案並積極商業化 Apple Silicon 上的 Linux。在部分極端情況下，開發中的功能程式碼被直接從個人 fork 抄走、不標示來源就發布，或是在 LLM 協助下草率改寫以掩蓋出處。作者把成因歸咎於前沿 AI 實驗室對高品質訓練資料的貪婪，以及對自由軟體社群的敵意；這是作者的歸因，文章沒有指名具體對象。團隊因此決定開始把所有 repository 轉為 GNU General Public License 第 2 版或更新版本，今後所有 Asahi Linux 程式碼只會採用強 copyleft 授權。作者的措辭是開始轉換的過程（begin the process），文章沒有說所有 repository 已經完成轉換。同一節的開頭，團隊也重申開發一向公開進行：財務公開、開發分支公開，進度報告定期而坦率。

對讀者的實際判斷

如果你有 M3 機器，文章的結論最直接：installer 不再需要 EXPERT 旗標，DCP 的啟用帶來睡眠與瀏海周圍區域的可用性，但 GPU 仍是缺口。作者明說 M3 在其他方面「mostly at feature parity」，GPU 的逆向則才剛畫出第一個三角形，離整合進 Mesa 還有一段距離。依這些描述推斷，M3 現階段還不能指望有可用的 GPU 加速；這是從文章敘述推出的結論，文章本身沒有給使用建議。

如果你打算在 Apple Silicon 上用 Thunderbolt dock，目前的答案是等。已出貨的範圍只有 USB3、XDomain 與 Thunderbolt Networking，dock 常用的 PCIe 與 DisplayPort tunnelling 都還沒有，團隊沒有給時程，也已經表明不會再輕易承諾年份，這一點從他們對 2024 年那句承諾的態度可以看出來。

如果你想在 Asahi Linux 上玩 x86 遊戲，P3S 的展示很吸引人，但它不在出貨的核心裡。依文章的說法，團隊不想在 Google 的意圖明朗之前讓使用者依賴它，所以目前實際可用的仍是 muvm 路線，付出的是約 20% 的效能與 VM 帶來的限制。這個結論是推斷：文章沒有逐字說「現在仍用 muvm」，但它把 P3S 描述為尚未出貨，並把 muvm 描述為目前提供 4 KiB 頁面的做法。

如果你打算向 Asahi 的專案貢獻程式碼，授權的轉換值得先看清楚。團隊已經開始把 repository 轉向 GPL v2 或更新版本，今後的新程式碼只用強 copyleft 授權；原本抱著寬鬆授權預期的 BSD 方面的參與者，需要重新評估。這同樣是推斷，文章只講了團隊的決定與理由，沒有談對個別貢獻者的影響。

Take-away：這份報告留下的後續事實很具體。M3 的 m1n1 與核心更新預計在幾天內釋出；Thunderbolt 的 PCIe 與 DisplayPort tunnelling 還沒有；M3 的 GPU 只到畫出三角形，整合進 Mesa 仍需大量工程；P3S 讓遊戲脫離 muvm，卻要等 Google 回覆之後才決定是否出貨。每一項都是 Apple 的某個設計選擇，加上團隊願意或不願意替它付多少。
