GitHub 上最忙的 repository，一秒鐘最多只收到幾十次寫入，而且多半是短時間的突發。內部測試裡，新的儲存架構撐住了 5,000 個 agent 同時對單一 repo 推送，每秒 7,200 次 push，讀取延遲仍然持續偏低。

這篇文章出自 GitHub 工程部落格，作者是 Karthik Raman 與 Brian Celenza，2026 年 11 月 5 日發表。它回顧了系列前面談原則與過渡橋接的兩篇，自己的任務是把新資料平面攤開：請求怎麼走、reference 怎麼寫、pack 怎麼壓。本文只講這一篇，前兩篇的內容不重述。

從每秒幾十次寫入，到多出兩個數量級

GitHub 把規模分成兩條軸。水平軸是跨許多 repository 能服務多少開發者與 agent，租戶分區、流量隔離與公平性、依負載路由這些多年驗證過的做法會沿用到新架構。垂直軸是單一 repository 上能容納多少人與 agent，作者預期 agent 寫更多程式碼之後，個別 repository 會更大更忙，所以多數需求來自這一軸。

現況是最忙的 repository 一秒最多幾十次寫入，通常是短暫的突發。作者預期，當更多工作交給全天候平行運作的 agent，突發會在一年內變成持續的速率。每次 push 又會帶出更多讀取：CI 要跑，部署系統要拉新的 commit，別的 agent 抓下來當脈絡，讀取的放大量隨寫入一起長。文章舉了一個頂端 repository 為例，從 3 月到 5 月每日請求量成長約 4 倍，之後仍在指數成長。

團隊沒有按下一個增量規劃，而是把目標設成至少多兩個數量級。落到單一 repository，需求有六條：每秒接受數千次寫入；支援多個 writer 節點；把 commit 延遲壓到最低，因為 agent 要等 push 完成才進下一步；每個 reference 的變更有序記錄，並能快速跨 reference 線性化；沒有變更時讀取要便宜，這是讀寫比之下的常態；各元件能獨立擴充。另外，整套系統還得提升整體可靠度，並能全球擴展。要多個 writer，原因有二：索引收進來的 pack 與檢查物件連通性是寫入裡最吃 CPU 的部分，成本隨寫入大小成長，單一節點很快被運算綁死；工作分散之後，容錯更好，節點故障的恢復也更短。

支點是上一篇留下的觀察。Git 物件不可變，名字就是內容，兩個 writer 能同時存放而不必先取得共識。一次 push 真正需要共識的只有 reference 更新，而它比起整包資料小得多。照這個切法，過去緊緊綁在一起的三件事，儲存資料、服務請求、維護 repository，就能各自獨立擴充。對開發者而言，push、fetch、branch 的方式不變，保護機制也在。

文章給的時間節點不多，排開來是這樣。

兩次卡在 blob 上的嘗試，與 Rubicon 的成形

2026 年 5 月，緊接在初期 Azure 遷移之後，團隊開始設計能滿足上述需求的方案，試了好幾條路。每一條都把 pack 資料放在 Azure Blob Storage，有幾條也把 reference 狀態放在那裡。定案的設計，作者說是在吞吐量最大化的同時，守住這種平台要求的正確性、持久性、可用性與延遲保證，代號 Rubicon，取自產業在 agentic 開發上跨過、回不了頭的那個點。

從上往下看，不變的部分不少。Git client、API 與 web UI 的請求仍先到 Spokes，它照舊做路由與負載平衡、提供內部 API，也還是放置與平衡服務，水平擴充要的分區、隔離與租戶公平性都在它手上。全新的是它底下的資料平面。

Spokes 把請求交給分配給該 repository 的一小群 virtual replica。這是同一個機群裡可隨時丟棄的運算資源，可服務讀、寫，或兩者，本地磁碟只是可隨時重建的快取。Spokes 會盡量把同一個 repository 的流量送回同樣的 replica，保持快取熱、延遲低，但正確性不依賴請求落在哪一台。一台消失，其餘的繼續服務，替補的隨流量填快取；repository 變忙，就多加 replica。

背景另有一群 compaction node，直接對 Blob Storage 與 Ref-CAS 工作，合併 pack、清掉不可達的物件，這份工作不會跑在 virtual replica 上，replica 的 CPU 與記憶體幾乎都留給請求。持久狀態只落在兩處：Git 物件，也就是 pack 與輔助的讀取加速資料，放 Azure Blob Storage；reference 與組成 repository 的 pack 清單（pack manifest）放一個獨立的複製日誌服務，叫 Ref-CAS，全名 Reference Compare-and-Swap。下圖把五個角色並排，點開看各自管什麼、刻意不碰什麼。

走一遍就清楚了。寫入時，virtual replica 先索引收到的 pack 並上傳到 Blob Storage，再向 Ref-CAS 提交一筆交易，在 manifest 列出這個 pack 並更新 reference；之後 compaction node 會把它和別的 pack 合併，讓讀取維持快。讀取時，virtual replica 向 Ref-CAS 確認自己手上的 reference 版本，把需要的 pack 從 Blob Storage 拉進快取，從快取回應。

Ref-CAS：只有 reference 更新需要排隊

這一段對應系列開頭的第一個原則，把協調降到最少。文章的第二個原則是儲存與運算脫鉤，對應後面的 compaction 一節。兩個原則各用一個元件講完。

Blob Storage 耐久、有複製、容量夠、每位元組便宜，流量分散在許多 key 上時聚合吞吐量極高，所以新架構裡幾乎所有持久的東西都放那裡：各種 pack 與索引、multi-pack index 與 reachability bitmap 這類讀取加速資料、compaction 與垃圾回收的續跑紀錄和 lease、常被重複 fetch 的快取回應，以及 reference 狀態的 checkpoint（但不是服務請求時的權威狀態）。它們多半寫一次到獨立的 key 就不再改，正合物件儲存。

reference 剛好相反。忙碌 repository 的 reference 只是一小塊狀態，卻有許多寫入同時搶著改。物件儲存的條件式寫入白送一個 compare-and-swap，資料也已耐久複製，所以這條路直覺，也在某個規模以前行得通。原型卻讓他們面對一組兩難，文章用兩個嘗試說明。

第一個做法是替所有 reference 建一份 write-ahead log，用單一 blob 當索引，每次更新都是對該 blob 的條件式寫入。它正確，讀取也便宜：virtual replica 問 blob 有沒有變，沒變就結束。問題在寫入。同一個 blob 同一時間只能有一個條件式寫入在進行，即使把寫入期間到達的 push 全併進下一次，repository 的上限也只是每次往返一次寫入。實測的吞吐量落在每秒幾百次的中間水準。

第二個做法把 reference 分到幾個 segment blob，每個 reference 雜湊到其中一個。不同 segment 的寫入不再互等，上限提高了。代價轉到讀取：要判斷有沒有變動就得檢查每個 segment，速度取決於最慢的那個。作者的說法是拿寫入延遲換了讀取延遲，而讀取比寫入多出好幾個數量級。

下面的玩具模型讓這個取捨可以親手拉。它不是 GitHub 的量測，只用 N 個固定的分支名稱算雜湊，看分到 k 個 segment 之後最長的寫入佇列有多深、一次讀取要查幾個 blob，並把 Ref-CAS 的規則放在旁邊對照。模型沒有算批次，只展示方向。

把 k 拉到 1 就是第一個做法：寫入全排在同一個 blob 後面，讀取只查一個。k 拉大，最長的佇列縮短，讀取要查的 blob 卻跟著變多。合理的解讀是，這個此消彼長來自兩個目標綁在同一種元件上，於是他們另外做了第三樣東西：專門放 reference 的複製日誌服務，也就是上一篇結尾說還留在堆疊某處的那個小型共識群組。

Ref-CAS 的每筆 reference 更新是一次由 quorum 提交的 compare-and-swap。交易只鎖它碰到的 reference，檢查每一個是否仍是 writer 預期的值，等日誌的多數 replica 記下後才可見。agent 大多推自己的 branch，更新多半不互相競爭，可以平行複製；兩個 push 改同一個 reference 時，只有一個會附加到日誌。上面的模型裡，勾選同一個 branch 就是這個情境。

每次提交得到一個 log sequence number（LSN），repository 的版本就是最新提交的 LSN。讀取從版本檢查開始：virtual replica 送出自己持有的版本，若仍是最新，回覆完全不帶 reference，沒變動的 repository 只花一次比較；若落後，就拿回目前的 reference 與版本，加上 pack 資料的指標，以及其他需要知道的事，例如上一輪垃圾回收的時間。日誌上還能加額外的標註，文章說這些標註用來幫讀取判斷某次請求該下載什麼。

每次 push 都會帶出更多讀取，這讓「沒變更時讀取便宜」這條需求有分量。合理的推測是，CI、部署系統與其他 agent 大多是在問「有新東西嗎」，所以版本相同時只回一次比較的設計，省下的是最常見的那一類請求；這個推測文章沒有用資料支持。

Ref-CAS 與舊架構裡的共識群組不同：它從不存、也不驗證物件資料，只存指標。virtual replica 先把 push 的 pack 上傳到 Blob Storage，才提交 reference 交易，所以 reference 只會指向已經持久的物件。合理的推測是，上傳了 pack 卻沒提交成功的 push，會留下沒有 reference 指向的物件，文章列的垃圾回收對象是已刪 branch 與 force-push，沒有提到這種情況。文章說，單算 reference 狀態，這樣的設計可以做到每秒數萬次操作。這和前面的 7,200 次 push 不是同一個量：看起來前者是 Ref-CAS 單獨的量級，後者是內部測試的整體結果，文章沒有給兩者的換算。把 7,200 除以 5,000，平均每個 agent 每秒約 1.4 次，這是我自己的算術，文章沒說 5,000 個 agent 是否同時全速推送。

放在一起看：單一 blob 的原型落在每秒幾百次，內部測試的整體結果是每秒 7,200 次 push。兩者量的對象不同，一個是 reference 寫入的原型上限，一個是整套系統在內部測試下的 push 速率，不能當成同一把尺。合理的解讀是，瓶頸從「同一個 blob 一次只收一筆」換成了「只在同一個 reference 上排隊」。

把 compaction 搬出 replica，讓 pack 數量壓平

每次 push 都在 Blob Storage 多一個 pack。Git 能從許多 pack 服務一個 repository，但每多一個，查找就貴一點，所以 pack 數量不能無限長。舊架構裡 compaction 跑在服務流量的同一批 replica 上，每個 replica 都得跑；新架構把它完全移到背景的獨立節點，直接對持久儲存工作，再用 Ref-CAS 通知 virtual replica 狀態的變化。

compaction node 各自透過 lease 認領 repository 資料的一個子集，所以 compaction 能水平擴充。下圖是單一節點處理一個 shard 的八步。

順序值得多看兩眼。lease 先拿，保證同一個 shard 同時只有一個節點在壓。open segment 是等待壓縮的資料暫存區，封口條件看 pack 數量、大小或年齡，封口後不再收新 pack，下一個 segment 就能開始收 pack，壓縮期間輸入不斷。發佈前先驗證新舊 pack 的物件完全一致，才改 manifest；先用一筆交易加入新 pack，再用第二筆移除輸入，刪除留給之後的清理。我的解讀是這個兩段式讓 manifest 在任一時刻都列得出全部物件，文章沒有明說，只是順序支持這個讀法。

擴充靠 shard：每個 pack 的雜湊對應一個 shard，加 shard 與節點就加 compaction 吞吐量。壓過但仍未達大小上限的 pack，依自己的雜湊回到某個 shard 再合併，pack 一層層長大直到上限。結果是 push 上升時 pack 數量大致持平，文章以一張圖呈現，本文沒有引用圖上的數值。

Compaction 合併 pack，但物件一個不丟。移除沒有任何東西引用的物件，像已刪 branch 與 force-push 留下的，是垃圾回收的工作。新架構裡它的做法與 compaction 很像，吃運算的部分交給專用 worker，另有一些安全移除資料的特殊行為，作者說值得另文討論。團隊表示寫入上升時能穩定展示持平的延遲曲線，也還有計畫中的最佳化，要讓這兩個流程本身更快。

收斂點，與文章沒回答的事

收斂回兩個原則。讀寫靠加 virtual replica 擴充，Ref-CAS 對每個 reference 獨立排序而非整個 repository，維護靠加 compaction node 擴充。作者的目標是從個人小專案到最忙的 monorepo 都跑同一套架構、不為忙碌者特殊處理，理由是 repository 不會一直小，小專案可能一夜之間迎來一群 agent，不該為此遷移；單一架構也讓每項改進同時到達所有 repository。

如果把這篇當設計參考，我讀到三件可以帶走的事，都是我的解讀，不是文章的結論。第一，先問系統裡哪一小塊狀態真的需要共識；這裡答案是 reference，其餘的不可變資料可以並行寫。第二，物件儲存的條件式寫入能當 compare-and-swap 用，但把一個 key 當序列化點，上限就是每次往返一次寫入，拆成多個 key 又會把成本轉嫁給讀取。第三，把維護工作搬出服務節點，才能讓服務節點真的可以丟棄，快取壞了重建即可。

文章把接下來的工作分成三塊。第一塊是架構本身，列了六項：只讀需要的部分，也就是從 Blob Storage 取單一物件，不取整個 pack；依類型整理 pack，把 commit、tree、blob 各放各的，讓許多請求碰到的資料變少；partial replica，不必把每個 pack 放在本地磁碟就能服務請求；materialized view，把預備好的封存檔、預設分支近乎即時的淺層副本、與每個 commit 並存的 agent session 脈絡先備好；global replica，把 replica 放在任何區域、貼近使用它的工作負載，讀取維持在與最新寫入有界的過期範圍內；以及 scale to zero，機群隨真正活躍的 repository 伸縮。

第二塊是讓 agent 的每次操作更便宜：更少的位元組、更少的往返、更少等待變更的時間。文章列了三項緊接著要做的事：不用 clone 就能工作，因為許多 agent 任務只需要幾個檔案和足夠的脈絡，可以直接從伺服器讀；atomic commit API，多檔變更一次提交，整筆成功，或在衝突時乾淨地拒絕；以及 event stream，讓 agent 與周邊系統訂閱變更、即時反應。

第三塊在 Git 本身。作者提到 GitHub 長期參與 Git 專案，接下來的方向有四個：輕量 clone，partial clone、shallow clone、sparse checkout 都能讓 agent 少抓東西，但各有缺口，也不一定搭得好，他們想補每一塊並讓它們合得起來；移除隱藏的擴充成本，Git 仍有些程式路徑的變慢速度遠快於 repository 的成長，近期版本修了幾個，預期還會找到更多；更快的歷史走訪，用 commit-graph 這類 metadata 回答 merge-base 與可達性問題，不必走過每個 commit；以及避開常見陷阱，Git 可以攔下更多常見錯誤，在造成損害前警告。

把文章的六條需求和已描述的設計對照，會看出哪些有交代、哪些沒有。這張表是我的對照，不是文章自己的結構。

灰底那列最明顯：commit 延遲是 agent 每一步都在等的東西，文章只描述了方向，沒給數字。另外，5,000 個 agent、每秒 7,200 次 push 是內部測試，在我讀到的原文裡沒有看到 repo 大小、push 內容大小或衝突比例的說明。Ref-CAS 本身的 replica 數量、部署範圍，以及 quorum 失效時的行為，也是我在原文裡沒有看到的。可用性上，新架構目前是 limited private preview，更廣的推出在明年初。

The design order：這篇的做法是先認出系統裡真正需要共識的最小狀態，也就是 reference，再讓其餘一切變成可複製、可丟棄的東西；明年初 broader rollout 時，值得看公開的數字會不會補上 commit 延遲和同 branch 衝突的情境。
