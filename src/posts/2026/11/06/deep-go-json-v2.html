Go 1.27 讓 encoding/json/v2 轉正：同一個 struct，v1 把 nil slice 寫成 null，v2 寫成 []。官方遷移指南開頭先講的，卻是你不必遷移。

Go json v2 對上 v1：預設行為與遷移

Go 團隊的部落格開頭寫道，標準庫對 JSON 的支援「since well before Go 1.0」就已存在。同一篇文章宣布，新的 encoding/json/v2（下文簡稱 v2）與負責語法層的 encoding/json/jsontext 在 Go 1.27 進入「stable and generally available」狀態，舊的 encoding/json（下文簡稱 v1）繼續留著。兩個套件並存，你的專案就多了一個選擇題：要不要換，什麼時候換，換的時候哪些輸出會變。

這篇只比來源裡寫得出依據的事，分四條軸。第一條是輸入收得多嚴，第二條是輸出長什麼樣，第三條是 API 與擴充點，第四條是效能與相容層。最後一節把官方指南的三條遷移路線，對應到你手上服務的風險容忍度。部落格與指南都沒有提供的數字，這篇不會補。

表裡能看出一個方向。重複名稱、無效 UTF-8、大小寫、struct 結構錯誤這四列，v2 的預設都從「容忍」改成「拒絕」。nil 與 omitempty 兩列，改的是輸出的形狀。Duration 一列是新增的報錯。下面逐軸展開。

輸入收得多嚴：UTF-8、重複名稱、大小寫與 struct 檢查

先從最容易被忽略的一項開始。部落格寫道，v1「currently accepts invalid UTF-8, whereas the latest Internet Standard (RFC 8259) requires valid UTF-8」。遷移指南把 v1 的實際動作講得更具體：字串裡無效 UTF-8 的位元組會被靜默換成 Unicode 替換字元。v2 的做法是直接報錯。

兩者差在「資料有沒有被默默改過」。v1 不報錯，也就不會有人知道輸入和解出來的字串已經不是同一串位元組。我的推論是，如果這個欄位之後被拿去比對、簽章或當 key 使用，替換字元就是一顆沒人看得見的地雷。這是推論，來源沒有講到下游後果，講到的只有「v1 靜默替換、v2 報錯」這個事實。

重複名稱是同一個故事。部落格說 v1 接受含有重複成員名稱的物件，並主張預設行為「should err on the side of safety and reject duplicate names」。指南的對照句也很直接：v1 允許，v2 報錯。來源沒有展開重複名稱怎麼被利用，這裡不替它補情境。能確定的是，今天通過 v1 的某份第三方 payload，換成 v2 後可能直接變成錯誤。

大小寫比對是三者之中語氣最重的。部落格描述 v1 解碼時，JSON 成員名稱以不分大小寫的方式對應到 struct 欄位，並評為「a surprising default, a potential security vulnerability, and a performance limitation」。v2 的套件文件則寫明採用嚴格的、區分大小寫的比對。舉個直接的推論：欄位 tag 寫成小寫 name，v1 也會收下大寫開頭或全大寫的成員名稱，v2 不會。套件文件另外提到，沒有對應到任何欄位的成員預設會被忽略。這是推論：遷移後這類欄位不會報錯，而是安靜地少了值，比報錯更難發現。

第四項針對的是你自己的型別。指南說 v1 對有結構錯誤的 Go struct 型別（例如 tag 寫壞）從不在執行期報錯，v2 則會對「invalid as they relate to JSON serialization」的型別報執行期錯誤。指南舉了一個具體例子：把 string tag 套在不合法的型別（例如 struct）上，v1 直接忽略，v2 報錯。指南對這個例子的建議也值得抄下來：雖然 ReportErrorsWithLegacySemantics 能壓掉這個錯，更合理的做法是拿掉那個 tag，因為它本來就沒有作用。

這四件事串起來看，v2 的主張寫在套件文件裡：v2 API 一般而言選擇比 v1 更安全的預設。代價則是遷移指南的原話：v2 選擇更嚴格、互通性更好的預設值，「But they are not backwards compatible」，有些應用可能依賴 v1 的行為。換句話說，嚴格是 v2 的賣點，也是你升級那天會跳出來的錯誤清單。輸入收得嚴的服務，如果上游資料不乾淨，最先反映在 4xx 比例上。

輸出長什麼樣：nil、omitempty 與 time.Duration

輸出側最醒目的改變是 nil。v1 把 nil slice 與 nil map 寫成 JSON 的 null。部落格寫到，多數 Go 使用者偏好預設把它們輸出成空陣列或空物件，v2 照這個方向改了。指南用 Pet 的例子演示：Remi 的 Nicknames 欄位從 null 變成 []。

這個例子被指南放進「為什麼遷移最難的是行為而不是 API」的論述裡。指南的原話是，遷移困難的部分不在 API 差異，而在行為變動。輸出從 null 變成 [] 的時候，指南提醒下游消費者可能有人依賴 null，這個改動可能讓它們壞掉。我讀到的來源只說到這裡。哪些消費者依賴 null、依賴到什麼程度，要靠你自己的服務去查。

omitempty 的變動和 nil 的變動會互相作用。部落格說 v2 重新定義了 omitempty：欄位若會被編成「empty」JSON 值就省略，所謂 empty 值是 null、空字串、[] 與 {}。套件文件進一步說明，omitzero 與 omitempty 的差別在於前者以 Go 型別系統定義，後者以 JSON 型別系統定義。

把兩條規則接起來，可以推出一個遷移時會碰到的現象。這是我的推論，不是來源明寫的：nil slice 在 v2 編成 []，而 [] 屬於 empty 值，所以帶 omitempty 的 nil slice 欄位會被省略。反過來，若你用 FormatNilSliceAsNull(true) 把 nil 改回 null，null 同樣屬於 empty 值，欄位也會被省略。這個推論只靠部落格列出的四種 empty 值成立，細節請以套件文件為準。

time.Duration 是這條軸上唯一「從能用變成預設報錯」的型別。部落格說 v2 在嘗試序列化 time.Duration 時報錯，理由是它「currently has no default representation」。我讀到的頁面沒有交代 v1 對 Duration 的輸出長什麼樣，也沒有指出哪一個選項還原它。指南只保證所有分歧都有對應的 Options，所以你的 struct 如果有 Duration 欄位，要翻 DefaultOptionsV1 的文件確認，這裡不替它猜。

把這條軸收成一個判斷：輸出側的改動多半不會讓你的服務報錯，而是讓輸出的 JSON 悄悄變形。輸入側會大聲失敗，輸出側會安靜地換形狀。對有 JSON 契約測試的團隊，這一側容易抓到；對沒有的團隊，這一側的風險比較高。

API 與擴充點：選項、串流與自訂 marshaler

部落格對 v1 的 API 抱怨有四項。其一，Encoder 與 Decoder 可以設選項，Marshal 與 Unmarshal 函式不行。其二，實作了 Marshaler 與 Unmarshaler 的型別拿不到選項，「there is no way to plumb options down the call stack」。其三，定義在 pointer receiver 上的 MarshalJSON 因為實作細節而被不一致地呼叫。其四，常見的 json.NewDecoder(r).Decode(v) 寫法，不會拒絕輸入尾端的多餘資料。

第四項值得多看一眼。部落格的原話是 Users often write 這行程式，而它「fails to reject trailing junk at the end of the input」。這是在說，API 的預設用法本身就有漏洞，並不是使用者寫錯。v2 的處理方式在我讀到的頁面上沒有逐項說明，所以這篇不替 UnmarshalRead 做任何關於尾端資料的保證。

v2 的答案是把選項變成一等公民。部落格給的範例是 json.Marshal(..., json.DefaultOptionsV2(), jsontext.AllowDuplicateNames(true))，選項直接跟在參數後面；同時提供 MarshalWrite 與 UnmarshalRead 直接作用在 io.Writer 與 io.Reader 上，以及 MarshalEncode 與 UnmarshalDecode 直接作用在 jsontext 的 Encoder 與 Decoder 上。

自訂 marshaler 的差別最能說明設計取向。部落格列出 v1 的成本：MarshalJSON 迫使實作配置回傳的 []byte；UnmarshalJSON 要求拿到完整的 JSON 值，所以 encoding/json 必須先把整個值 parse 一遍才知道它在哪裡結束，然後 UnmarshalJSON 自己再 parse 一次。v2 新增 MarshalJSONTo 與 UnmarshalJSONFrom，直接作用在 Encoder 與 Decoder 上。下圖把兩條路徑並排。

這張圖要小心讀。v2 那兩列沒有寫「零配置」或「只 parse 一次」，因為部落格在我讀到的段落裡只說這兩個方法「operate on an Encoder or Decoder」，沒有量化。圖能證明的只有一件事：v1 的介面形狀逼著實作多做兩步，v2 的介面形狀不再逼。

相容性是這條軸的另一半。已經寫好的 MarshalJSON 方法不必改，部落格對這個疑慮的回答是「No problem, v2 supports MarshalJSON methods」。指南另外提到，v2 的 Marshalers 機制可以覆寫特定型別的 marshal 行為，包含你控制不了的第三方型別。這對遷移很重要：第三方型別在 v1 底下你只能包一層，在 v2 底下可以從呼叫端換掉。

語法層則獨立成 jsontext。部落格形容它只在語法層級處理 JSON，因此不依賴 Go 的 reflection。你若只想做 token 串流、不需要綁 struct，可以直接用這一層。對多數業務服務，你會碰的還是 v2 本身。

效能與相容層：v1 其實建在 v2 上

效能的說法很克制。部落格寫 Marshal 的效能「roughly at parity」，也就是大致持平；Unmarshal 則顯著比 v1 快，benchmark 顯示最多可達 10 倍的提升。文中還說，Go 1.28 預期有進一步的改善。部落格附了 benchmark 專案連結（go-json-experiment/jsonbench），想驗證的人可以自己跑。

「up to 10x」是上限，不是平均。部落格沒有說這個倍數來自哪種 payload、哪種型別，所以不要拿它估你的服務。能讀出來的只有方向：換 v2 不會讓 marshal 變慢，若你的瓶頸在解碼，才有機會看到明顯收益。以 marshal 為主的服務，效能不是遷移的理由，嚴格的預設與 API 才是。

相容層的設計是整個計畫能走得下去的關鍵。部落格說新套件的設計讓 v1 在底層是以 v2 實作的，因此兩個套件可以互通。這件事帶來一個直接好處：「Implementing v1 in terms of v2 options has the additional benefit of allowing gradual migration of callsites」。下圖畫出這個分層。

這個分層對決策有兩個含意。第一，v1 不會憑空消失。指南的說法是 encoding/json 套件「will never go away」，所以停在 v1 不會有哪天被拔掉的期限。第二，為什麼不直接修 v1：部落格認為這些問題是現有 API 的內生後果，幾乎不可能修，因為新增功能相對容易，改變既有功能很難。v2 因此是另開一個版本，不是對 v1 動手術。

這件事也不是倉促決定。部落格交代 v2 花了大約六年才走到穩定：2020 年底，在無法修復現有套件問題的壓力下開始原型，2023 年底有 GopherCon 演講與討論，2025 年初提出正式提案，最後在 Go 1.25 以實驗功能釋出，供所有 Go 使用者大規模試用。從這個時程可以讀出一點：預設行為的每一處改動，都是被公開討論過幾輪的結果，不是臨時起意。

相容層的實際操作介面是 Options。下面這個 widget 讓你自己疊選項：先挑 v1 或 v2 的預設組合，再對三個行為各自覆寫。指南的規則是後面的選項覆寫前面的，所以你可以從 DefaultOptionsV1 出發，一項一項切到 v2 行為。

把基底切到 DefaultOptionsV2()、覆寫全不設，三個探針都落在 v2 這一側：輸出 []、重複名稱報錯、大小寫不符的成員被忽略。切回 DefaultOptionsV1()，三項全部翻轉。真正有用的是中間狀態：基底 v1，只把 FormatNilSliceAsNull 設成 false，輸出就變成「除了 nil slice 以外都像 v1」，這正好是指南範例描述的組合。

怎麼選：三條路線與留在 v1

指南的態度很明確：不必遷移，v1 不會消失。所以第一個選項是不動。你的服務如果輸入受控、輸出契約已經凍結，v1 沒有逼你換的壓力，這一句是我的推論。新寫的程式碼也可以直接評估 v2，因為不必背遷移債；同樣是推論，指南沒有給新專案的建議。

決定要換之後，指南依「應用程式類型與風險容忍度」給三條路線。下面的卡片把三條並排，每張卡片的步驟與代價都來自指南原文。

三條路線的差別，在於你什麼時候知道出了差異。一次全換是升級之後靠測試與線上告警知道；逐項選項是每啟用一項時知道；jsonsplit 是在還沒真正切換之前就知道，因為它會把輸入送進兩邊、回傳 v1 的結果、同時回報差異，指南說這樣正式服務可以回報差異而不改變行為。jsonsplit 甚至會自動判斷是哪些選項造成差異。

jsonsplit 的代價要算進預算。指南明講，同時用 v1 和 v2 做 marshal 來偵測差異，會讓 marshal 成本大約加倍，緩解辦法是只檢查隨機抽樣的一部分呼叫。另一個提醒值得抄下來：輸出有差異，不代表下游的行為真的壞了，只代表有壞的機會。所以第三步「encode differences」之後，切到 v2 時還應該回頭重看這些位置，決定能不能接受新的行為。

我的判斷是這樣排優先順序。先看你吃不吃第三方 payload：吃的話，輸入側的嚴格化（UTF-8、重複名稱、大小寫）會最先出事，jsonsplit 或逐項路線比較穩。再看你的輸出有沒有下游依賴 null 與欄位省略，有的話，nil 與 omitempty 的互動要寫進測試。最後看 struct 型別上有沒有 string tag 之類的歷史包袱，v2 會在執行期把它們全部掀出來，最好先把相關型別各跑一次序列化測試。這個排序是我的推論，不是指南給的。

還有一件事先放進行事曆：Go 1.28。部落格預告那一版會有進一步的效能改善，細節沒說。若你的服務是解碼為主，可以先用 DefaultOptionsV1 完成遷移，把「逐項切到 v2 預設」留到有新的 benchmark 之後。遷移本身和享受嚴格預設，是可以分兩個時間點做的事。

How to choose：不動 v1 沒有任何壓力；要換，風險容忍度高就一次全換，低就先套 DefaultOptionsV1 再逐項啟用，線上服務不能先變行為就走 jsonsplit，並預留約兩倍的 marshal 成本。
