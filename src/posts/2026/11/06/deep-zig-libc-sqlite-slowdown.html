同一份 SQLite、同一批 JSON，在 Mac 上寫入幾乎無感，搬到 Linux 卻要等上數分鐘。程式碼沒換，資料沒換，連 SQLite 的原始碼都是同一份，兩邊的耗時卻差了一大截。

Zig 重寫 libc，掃描慢 12000 倍

四萬筆 JSON 記錄寫進 SQLite，在 Mac 上是一件感覺不到的事。同一個流程放到 Linux 上，Dennis Forbes 的西洋棋分析服務卻卡住了：依他的描述，插入大約 40,000 筆資料要花上數分鐘的 CPU 時間，而這個步驟本來預期只要毫秒等級。程式碼是同一份，SQLite 是同一份，資料也是同一批，唯一不同的是平台。

這篇文章照調查的順序走：先是症狀，接著是兩個合理但站不住的懷疑，最後落在一個誰都沒想到要看的地方。先交代一件事：原文是一則短篇的 microblog，主要貼出症狀、根因與繞路做法，沒有逐條記錄作者排除了哪些假設。下面兩個「假設」章節，是我依原文給的線索重建的推理，凡是推測都會明講。

四萬筆 JSON，Mac 上無感，Linux 上數分鐘

先把能確定的事實擺齊。作者在 Linux 目標上用 zig cc 編譯 SQLite，透過 cargo-zigbuild 取得跨平台編譯的能力。他在文中說，這個問題出現在 Linux，在他的 Mac 上從未見過。這條建置路徑是整件事的起點。

耗時記在 CPU 時間上，這一點本身就是線索。若這個描述準確，程式是在算，而不是在等磁碟或網路，嫌疑因此偏向某段會燒 CPU 的程式碼。這是依作者描述做的推論，原文沒有附上 profiler 的輸出。

有三件事要先記下來，後面每個假設都要拿來對照。第一，慢的地方是把大批 JSON 交給 SQLite 的那一步。第二，只有 Linux 這一側慢。第三，作者最早的處理方式是在自己的程式裡預先把 JSON 的空白清掉，清完會變快。這個小技巧先放著，到假設二再拿來當篩子。

作者選 zig cc 有他的理由，原文交代得很清楚：從 Mac 上的一個建置與部署腳本，他就能打包所有要支援的平台，不需要容器，也不需要額外的建置機器。這省下的是長期的維運成本，每多一台建置機、每多一個映像檔，都是要照顧的東西。這是一個合理的省事選擇，代價藏在一個看不見的角落。代價有多大，後面的算式會說明；它能被發現，是因為資料夠大，而且作者剛好兩個平台都跑過。

這裡還有一層容易被忽略的前提。用 zig cc 跨平台編譯，等於把 libc 這一層交給工具鏈代勞，而 libc 通常是沒人會去讀的依賴：你的專案裡沒有它的原始碼，測試也不會直接碰它。一個函式庫換了實作，介面不變、結果不變，唯一可能改變的是速度。這大概也是這類退化很少被列為第一嫌疑的原因：多數人腦中的清單上，沒有「字串函式本身變慢」這一項。

假設一：SQLite 的寫入路徑或資料量有問題

多數工程師看到「資料庫寫入很慢」，第一個反應是查儲存層。四萬筆資料、一次寫入，聽起來像是交易沒包好、索引太多，或是每筆都落盤的老問題。作者大概也從這一側下手，原文沒有記錄他實際先查了什麼。

這類嫌疑有一個共通點：它們的成本都跟寫入的筆數與位元組數掛鉤，交易、索引、落盤的次數，都是資料越多越貴，而且在哪個平台上都一樣貴。所以如果真是儲存層，預期會看到的是兩個平台一起慢，或者兩個平台一起隨資料量變慢。原文描述的現象正好相反，是同一批資料在一側正常、另一側異常。依這個推理，儲存層在第一輪就可以降為次要嫌疑。

如果要用最小的成本檢驗這個假設，做法是把同一批資料在兩個平台上各跑一次，並在 Linux 上換一個完全不同的建置來源再跑一次。三組數字就能說明問題是跟著平台走、跟著資料走，還是跟著建置走。這是我設計的檢驗方式，原文沒有描述作者的實際步驟，但作者最後把 Linux 建置搬進容器，做的正是第三組對照。

但這個假設有一個硬傷：原文的對照是 Linux 慢、Mac 不慢。如果是 SQLite 寫入路徑本身的演算法問題，同一份流程在兩個平台上應該一起變慢。能讓一個問題只在一個平台出現的原因，要嘛是平台不同，要嘛是兩邊跑的其實不是同一份程式碼。

資料量也站不住腳。原文提到的測量對象是一份 1.2MB 的檔案，是實際送進 SQLite 的 JSON。以記憶體頻寬的量級粗估，現代機器把 1.2MB 從頭掃一遍只是毫秒量級的事，這是我的估算，不是原文的數字。若耗時是分鐘，代表同一批位元組被反覆掃了很多很多遍，而不是資料「太大」。

假設二：Linux 這一側的執行環境有差異

把範圍縮到 Linux 之後，下一批嫌疑犯很自然：檔案系統、系統呼叫的成本、記憶體配置器、核心的排程。這些都是「同一份程式在兩個作業系統上表現不同」的常見原因。原文沒有說作者查過哪幾項。

不過原文有一句話透露了作者後來的判斷方向。他寫到，不知道這個問題還會在哪裡咬人，所以把 Linux 的建置整個搬進 Linux 容器。這個動作指向工具鏈：在容器裡，Linux 的程式碼就不必再經過 zig cc 跨平台編譯。他的嫌疑最後落在「SQLite 是怎麼被編出來的」。

空白提供了最後一道篩子。預先把 JSON 的空白清掉就會變快，代表耗時會隨資料的形狀改變，同樣的內容，空白越少越快。儲存層的成本取決於要寫多少資料，執行環境的成本取決於系統呼叫與記憶體，兩者都不太會因為少了幾個空白字元而大幅下降。能被空白左右的，是把 JSON 切成片段的那段程式，也就是 tokenizer 和它呼叫的字串函式。以上是用排除法推出來的，原文沒有寫成這樣：嫌疑到這裡縮小成「切詞時呼叫的字串函式」，而且出問題的是呼叫次數。這個方向在下一節得到原始碼的印證。

真相：每呼叫一次，就把剩下的整條字串重新量一遍

根因在 Zig 對 libc 的重寫。原文指出，Zig 以純 Zig 重寫的 strspn、strcspn、strpbrk 與 strstr，第一步都是先量整條字串的長度。作者還連到把 musl 版本換成純 Zig 版本的那個 commit，並把他測到的 1.2MB 的 tokenize 與原本的版本相比，約慢 12,000 倍。

看 Zig 原始碼，這個寫法很具體。strspn 的第一行是 std.mem.span，把傳進來的指標轉成一個帶長度的切片，第二行才在切片上用 findNone 做真正的搜尋，找不到時回傳切片的長度。std.mem.span 對以 0 結尾的指標做什麼，這裡是我的理解：它得走到結尾的 0 才知道長度，行為等同 C 的 strlen。Joel Spolsky 在那篇經典文章裡把原因講得很白，C 字串以 0 結尾，所以要知道長度就得把整條走完。

這個寫法在單次呼叫上沒有任何錯誤。結果正確，只是多做了工。問題在 tokenizer 的使用方式：它每切一個 token，就拿著指向「剩下部分」的指標再呼叫一次這些函式，而剩下的部分是一條很長的字串。原文的說法是，tokenizer 在一條大字串上反覆呼叫它們，每一次都先量整條的長度，成本因此隨規模二次方成長。

可以用最簡單的算式看出差別。假設字串長 N 位元組，tokenizer 要呼叫 k 次，每次前進約 L 位元組。不先量長度的掃描，每次只碰前進的那一小段，總量約是 N。先量全長的版本，第 i 次呼叫要走過當時剩下的 N 減去已消化的部分，總量約是 k 乘以 N 的一半。k 大約是 N 除以 L，所以兩者的比值大約是 N 除以 2L，隨檔案大小線性放大，總成本就是二次方。這是我推導的模型，原文的 12,000 倍是實測值，兩者不能直接對起來，因為原文沒有給 token 的平均長度和呼叫次數。

下面的動畫用 48 格的字串、12 個 token 把兩條路並排。上面一條掃到分隔符就停，下面一條是 Zig 版 strspn 的做法：每一個 token 先把剩餘的整條尾巴亮一遍，才開始真正的搜尋。數字是這個玩具模型的格數，不是實測。

跑完以後，B 條的累計是 357 格，A 條是 48 格。差距只有七倍多，是因為這個玩具字串只有 48 格；字串變成原文那份 1.2MB，N 變大四個數量級以上，差距就跟著放大。每一次呼叫看起來都不貴，貴的是它們加在一起。

拿動畫裡的玩具數字走一遍。第 1 次呼叫時，只掃到分隔符的做法碰 4 格，先量全長的做法要先走過整條 48 格，再加上搜尋的 4 格，共 52 格。到了第 12 次呼叫，字串只剩 3 格，兩種做法的差距才縮到 6 格對 3 格。越靠前的呼叫越貴，因為那時候剩下的尾巴最長。把 12 次加總，就是 357 對 48。依這個模型，字串加長一倍而 token 長度不變，只掃一小段的做法約增加一倍，先量全長的做法約增加到四倍，差距因此越拉越開。

12,000 倍這個數字也要讀準它量的是什麼。原文的說法是，對一份 1.2MB、實際送進 SQLite 的 JSON 做 tokenize，在這種模式下約慢 12,000 倍，措辭是「約」。它量的是切詞這一段，不是整個寫入流程的端到端耗時，也不是任何一個 SQLite 版本或任何一種 JSON 的通則。換一份空白更少的資料，倍數就會不同。拿它當作這份資料上、這一段程式碼的量級，比拿它當通用規律準確。

這也說明了為什麼功能測試抓不到它。strspn 的每一次呼叫都回傳正確答案，單元測試用幾十個位元組的輸入驗證，耗時是微秒，沒有任何訊號。只有輸入長到 tokenizer 得呼叫非常多次、每次的尾巴又都很長時，成本才浮上來。換句話說，這是一個只在規模上才看得見的 bug，而且越是大型的 JSON 越容易觸發，與資料庫本身無關。

這就是 Joel Spolsky 在 2001 年那篇文章裡講的 Shlemiel the Painter。Shlemiel 在路中央畫虛線，每天進度都比前一天少，老闆問原因，他說：Every day I get farther and farther away from the paint can! 每天離油漆罐都更遠，這是他的解釋。Joel 用它講 strcat：因為 strcat 的第一步要把目的字串從頭掃過，重複附加的成本就越來越高。他還拿 Pascal 對照，Pascal 字串把長度存在前面，知道長度只要一個組合語言指令，而不是一整個迴圈。

還有一點值得拆開看：原文點名的不是單一函式，而是 strspn、strcspn、strpbrk 與 strstr 四個，其中 strspn 的重寫他直接連到原始碼。四個函式都屬於「在一條字串裡找某種位元組或子字串」這一類，tokenizer 恰好是它們最典型的使用者：切一個 token，就問一次「下一個分隔符在哪裡」。四個函式都從 std.mem.span 開始，我猜是為了讓寫法一致，原文沒有解釋重寫者的動機。結果是同一個成本結構被複製了四次，tokenizer 不論呼叫哪一個都會踩到。

放在這個案例裡，對應關係很清楚。Zig 版的 strspn 就是沒有把長度記下來的 C 字串，每次問長度都得重走一遍。這個陷阱老了二十多年，換了一個工具鏈、換了一種語言，還是原樣出現。作者的結論也是這個意思：這些老問題會一再出現，我們都得保持警覺。

繞過去的兩種做法，以及還沒解決的部分

作者的處理有兩步。第一步是在自己的程式裡預先清掉 JSON 的空白：tokenizer 切出的片段變少，strspn 一類函式被呼叫的次數 k 跟著下降，算式裡的二次方項隨之縮小。原文只說這樣做降低了成本，k 下降是我依機制做的解讀。第二步是把 Linux 建置搬進 Linux 容器，他的理由是不知道這個問題還會在哪裡咬人。兩步都繞過了根因，沒有修掉它。清空白只救得了他自己的程式碼，SQLite 內部的其他呼叫端不會因此改變，資料再大一點，二次方的結構還在；容器換掉了函式的來源，卻不會告訴你工具鏈裡還有沒有別的差異。我在讀到的原文裡沒有看到上游已修正的消息。

容器的代價也寫在原文裡。作者原本的設定是在 Mac 上用一個建置與部署腳本打包所有平台，不需要容器或額外的建置機器，搬進容器等於放棄這份便利。這筆帳怎麼算，取決於你的服務有沒有處理大型字串的路徑。他的決定背後有一層邏輯：一個沒被發現的 libc 差異就能讓一段程式慢上約四個數量級，在找到全部差異之前，讓正式環境跑與開發環境相同的 libc，比省一台建置機划算。如果你的專案也用 cargo-zigbuild 或 zig cc 編譯會處理字串的 C 函式庫，上線前去查一下 Zig 的 issue 追蹤現況。

檢查方式不複雜。把同一批資料在原生環境和跨編譯產物上各跑一遍，耗時差異大到不像雜訊，就值得往下挖；接著用 profiler 看熱點落在哪個函式，作者在腳註裡寫了一句：Profilers are awesome。這個案子若一開始就看熱點圖，熱點大概會直接指向 strspn 一類的函式，不必繞兩個假設的圈子。自己寫 parser 或 tokenizer 的人還可以多帶走一個檢查項目：看迴圈裡有沒有對剩餘字串呼叫需要長度的函式。把長度在迴圈外量一次，之後傳長度或結尾指標，是最便宜的預防。這項建議從機制推得，原文給的是症狀、成因與兩個繞路。

Take-away：下次遇到只在某個平台慢、而且慢在 CPU 上的問題，先比對兩邊的編譯路徑和 libc 來源，再用 profiler 看熱點，最後才去調資料庫。
