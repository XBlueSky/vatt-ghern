Cloudflare 的 Zone Builder 現在每秒約收到 700 筆 DNS 紀錄變更，是 2022 年的近三倍，有些 zone 已超過 2,000 萬筆紀錄。他們讓建置延遲中位數減半、記憶體少掉 85%，做法是在動手之前先問一句：這次變更最少需要重建什麼？

Cloudflare 把 DNS 資料寫進 Quicksilver 之前，要先由 Zone Builder 決定「這次要建多少」。2022 年的前一篇文章把單筆紀錄的建置平均加快了 150 倍，在一百萬筆紀錄的測試 zone 上更快了 4,250 倍，結尾留下的下一步，就是對 zone 設定做同樣的事。這篇文章交代的就是那一步：他們做了一個 targeted build planner，從事件推出一個能證明安全的最小 build。下面照結構拆開看，先看完整重建為什麼撐不住，再看規劃器怎麼分類、怎麼在執行前修正計畫、怎麼處理同名 zone 與排程，最後才是驗證方式和數字。

「整個 zone 重建」為什麼走不下去

一筆變更從發生到抵達 Quicksilver，文章給的路徑很短。客戶透過 DNS Records API 或 dashboard 改紀錄，或是另一個 Cloudflare 服務改 zone 設定；變更存進資料庫，資料庫變更或其他系統產生一個 Kafka 事件；DNS Kafka Aggregator 把幾個 Kafka topic 的事件合併後送給 Zone Builder；Zone Builder 讀出需要的 zone 資料，轉成權威 DNS 伺服器看得懂的 key，與 Quicksilver 比對，只寫有變的部分，再由 Quicksilver 把變更散佈到整個網路。規劃器接手的是最後這一段，下圖示出它要回答的三個問題落在哪裡。

問題出在 Zone Builder 那一格。文章描述完整重建時說，它仍然要讀出、編碼並比對每一筆紀錄，而且整個過程把整個 zone 放在記憶體裡。成本因此跟著 zone 的大小走，而 zone 還在長：有些已超過 2,000 萬筆紀錄，Cloudflare 預期會繼續長到數億筆。流量這一邊也在長，2022 年 Zone Builder 每秒約收到 250 筆 DNS 紀錄變更，現在約 700 筆，近三倍。合理的推測是，zone 變大與變更變多兩件事同時發生，完整重建的負擔就從兩頭一起往上推。

2022 年的單筆紀錄 build 已經把紀錄變更的路徑切細了，設定變更卻沒跟上。難處在於設定可以伸到別的紀錄上。文章的例子是 Universal SSL：啟用或停用它會更新 metadata，也可能改動 zone apex（像 example.com 這種裸網域）上的 CAA 紀錄。一個看起來只是開關的設定，實際碰到的是共用的 metadata 和 apex 上的紀錄，沒辦法直接當成「改了某一筆」處理。

規劃器因此必須為每個事件回答三個問題：哪些 DNS 名稱可能變？共用的 metadata 或已發布的 zone 清單可能變嗎？Quicksilver 裡有哪些舊 state 必須移除？文章對這個設計的描述是，規劃器選出「能證明安全的最小 build」。重點在「證明」兩個字：答不出來的時候，不是猜一個小範圍，而是回到完整重建。

五種 build：從事件推出最小範圍

規劃器要有東西可判斷，第一個改動在事件的生產端。事件現在帶著變更過的 zone 欄位與設定，可以的話還附上變更前後的值。反過來，資訊不夠就不猜：只有 timestamp 更新的事件，在能辨認呼叫者與用途之前，仍然觸發完整重建；缺少細節、未知事件、或任何可能影響 zone 內任何紀錄的變更，同一條規則。保守的預設放在入口，後面的分類才敢放膽。

Quicksilver 的資料形狀決定了 build 能切到多細。每個 zone 的 record key 是分開存的，一個 record key 裝的是某個 zone 底下某一個名稱的 DNS 答案；另外有一個比較小的共用 metadata key，告訴權威 DNS 伺服器要怎麼使用那個 zone。有了這兩種 key，build 的類型就是「要碰哪幾種 key、碰多少」的組合。

文章用 24 小時的 build 統計列出五種類型：只動 resources 的占 86.81%，完整 zone 占 7.04%，resources 加 metadata 占 2.54%，apex 加 metadata 占 2.30%，purge 占 1.30%。前面提到的 Universal SSL 同時動 apex 和 metadata，合理的推測是歸在 apex 加 metadata 這一類。purge 對應的情況之一，是快照顯示 zone 不該再發布到這個 network。把前四種加起來，有 92.95% 的 build 沒有重建完整 zone。下面的模擬依這張表的比例抽樣事件，讓你直接看到比例的樣子。

把五種類型對回 key 的結構，會看得更清楚。只動 resources 的 build，碰的是被事件點名的那幾個名稱底下的 record key；兩種含 metadata 的 build，多碰了那個較小的共用 metadata key，其中一種還會動到 apex 上的紀錄；purge 的目標是這個 zone 不再發布；完整 zone 則是整個 zone 的所有 key。這個對應是我依文章對兩種 key 的描述整理的，文章本身是以統計表列出類型，沒有逐項畫出對照。但它解釋了為什麼分類能省下記憶體：大多數 build 只需要讀它點名的名稱，不必把整個 zone 讀進來。

看模擬時有兩個數字值得盯。切到「規劃器之前」，兩種含 metadata 的 build 併回 full，full 的占比會收斂到 11.88%；切回「規劃器之後」，收斂到 7.04%。文章說，這兩種 metadata build 以前是完整重建，連大 zone 也一樣，合計占 4.84% 的 build；加上本來就是完整重建的 7.04%，全部是 11.88%，所以完整重建少了約四成。要留意這是 build 的件數比例，不是耗時比例。被拿掉的完整重建有多少落在大 zone 身上，文章沒有給數字，所以「少四成」不能直接換算成省下四成的工時。

targeted build 只重建它點名的名稱，舊的東西怎麼辦？沿用 2022 年的做法：Zone Builder 掃描 Quicksilver 裡每個被重建名稱底下現有的 key，把新 build 沒有寫出的 key 刪掉。合理的推測是，少了這一步，一筆已經從 zone 刪除的紀錄就不會再被新 build 產出，它的舊 key 會一直留在 Quicksilver 裡，權威 DNS 伺服器仍然答得出一個已經不存在的紀錄。

規劃器有一個刻意設計的例外。紀錄數超過某個固定門檻的 zone，Zone Builder 永遠不會升級成完整重建，改為重建 apex、metadata，以及佇列裡事件點名的每個名稱。理由寫得很直接：這類 zone 的完整重建跑不完，而且重試的時候會擋住同一個 Kafka partition 上其他所有變更。代價是少了完整重建這道兜底，文章也承認同名衝突的風險：zone hold 阻止同一個名稱被加到另一個帳號，降低這個風險，剩下的少數情況可以手動重建個別名稱。這是在「兜底」和「不阻塞整條 partition」之間選了後者，而且把選擇寫在明處。

事件是過去式：執行前再讀一次

文章對時間差的處理是整個設計裡我認為最值得學的一段。事件描述的是過去發生的事；build 在排隊的時候可能還要等，這段時間更多事件進來，資料庫也在變，所以規劃會發生兩次。第一次依事件規劃，第二次在執行之前，Zone Builder 讀一份新鮮的發布快照：目前的 zone 設定、這個 Zone Builder 是否該把這個 zone 發布到自己的 network，以及哪些同名 zone ID 屬於 metadata key。

快照能改寫計畫的方式有四種。zone 現在有了需要完整 zone 工作的功能，targeted build 就升級成 full build；zone 不該再發布到這個 network，build 就變成 purge；觸發的 zone 已經不在 metadata key 裡，build 就被略過；metadata build 則可以從目前的候選集合重建共用 key。合理的解讀是，事件裡的資訊只負責決定從哪裡開始看，最後以執行當下的資料庫狀態為準，所以排隊再久，寫入依據的仍是執行當下的狀態。

快照的三項內容，恰好對上前面的三個問題。zone 的目前設定，決定哪些名稱與功能會被碰到；是否該發布到這個 network，決定這次是寫入還是 purge；同名 zone 的名單，決定共用的 metadata key 該長什麼樣子。這個對應是我的整理，文章沒有這樣逐一連起來，但它說明了為什麼快照只讀這三樣：規劃器要修正的，正是事件發生後最容易過期的那幾個事實。

讀資料庫就會碰到 replication lag。文章的兩道防線是：DNS Kafka Aggregator 把事件延遲一段時間，長到能涵蓋正常的 lag；最後的資料庫檢查則在讀到的副本仍然落後時拒絕這次讀取。有了第二道，第一道的緩衝才敢縮短：文章說，一旦資料庫開始拒絕落後副本的讀取，那段緩衝就能安全地縮小。

還有一個和發布判斷有關的細節：每個 Zone Builder deployment 只寫一個 network，同一個 zone 可以在某些 network 啟用、在另一些不啟用。合理的推測是，這就是「該不該發布」必須在執行前、由每個 deployment 各自判斷的原因，因為同一個事件對不同 network 可能是 targeted build，也可能是 purge。

支撐這一切的是一條很短的規則。文章寫的是：targeted build 寫出的每個 key，都必須和完整重建會寫出的逐位元組相同。這條規則把「安全」從形容詞變成可以測的性質；規劃器只要沒把握，就選回完整重建，前面提到的 timestamp-only 更新和未知事件都是這樣處理的。

同名 zone：共用的 metadata key

同一個公開網域在 Cloudflare 內部可能對應好幾個 zone。文章的例子是 example.com 有 Zone 101、202、303、404 四個內部 zone。Quicksilver 為這個網域存一個所有同名 zone 共用的 metadata key，這個 key 目前列出 101、202、303，Zone 404 不在清單裡。在這個結構下，一個 zone 的 record key 只屬於自己，metadata key 卻是大家共用的。

共用讓兩件事變得需要小心。第一件是順序：Zone Builder 先寫觸發的 zone 的 records，再寫指向這些 records 的 metadata。合理的推測是，這樣能避免 metadata 已經列出某個 zone、而它的 records 還沒到 Quicksilver，讓查詢落在一個空的答案上；文章只給了順序，沒有明說理由。第二件是名單本身會變：前面的快照包含同名 zone 的名單，觸發的 zone 若已被移出 metadata key，這個 build 就被略過，也不會去動共用的 key。

排程器與 Kafka offset：合併只會增加工作

事件在 build 開始前可能連續到達，同一個 zone 的多個事件由排程器合併。文章的規則很簡單，一句話說完：合併只會增加工作。任何一個事件需要完整 zone，合併後的 build 就是 full build；purge 蓋過所有重建，因為它想要的結果就是這個 zone 不再發布。我的解讀是，這個單向往大處走的性質，讓合併不可能把某個事件要求的工作吞掉，順序也就不影響結果。

zone 建完之後，下一次 build 要等一個 per-zone 的重建間隔，這個間隔依 Cloudflare 的方案而不同；等待期間到達的變更，併入下一次 build。合理的推測是，這讓同一個 zone 連續很多次的變更折疊成一次，排程的單位是 zone，而不是事件。同名 zone 也沿用這個思路：灰度推出時，文章用 zone 名稱而不是 zone ID 做雜湊，這樣所有同名的 zone 都落在同一個排程器上。

前面談大 zone 例外時提到，一個跑不完的完整重建會在重試期間擋住同一個 Kafka partition 上的其他變更。把這一點和 offset 的規則放在一起看：committed position 要等更早的訊息都完成才前進，所以一個卡住的 build 不只是自己慢，也會讓它後面所有訊息的提交停在原地。這是我從兩段描述合併出的推論，文章沒有把兩者連起來講，但它解釋了為什麼規劃器寧可為大 zone 放棄完整重建的兜底。

Kafka 的 offset 用 soft commit。一個 build 可以亂序完成，並在記憶體裡標成完成；但 Kafka 的 committed position 要等所有更早的訊息也完成才前進。照這個機制推算，服務重新啟動後會從已提交的位置重新讀取，已完成但尚未提交的 build 會被重做，換來的是不會漏掉任何一筆變更；這個取捨是我從機制推出來的，文章在這段沒有展開。

結果在 Kafka 消費曲線上看得最清楚。舊制下，消費速率在每秒約 300 到 1,550 筆訊息之間擺盪，而產生速率只在約 600 到 800 之間；現在消費緊貼著產生，同樣約 600 到 800。我的解讀是，擺盪的消費大概是積壓與追趕交替出現的形狀，貼著產生速率走才是穩定的消費。

怎麼證明「少建」沒有少寫

等價規則要有測試撐著。每個測試從同一個資料庫狀態出發，各跑一次完整重建和一次 targeted build，再把 targeted 計畫擁有的每個 Quicksilver key 逐位元組比對。這個測試對應的正是前面那條規則，不是抽樣，而是逐 key 比。

上線前還有一層和正式資料同步運行的鏡像。Mirror Zone Builder 消費正式環境的 Kafka 串流、讀正式環境的資料庫狀態，但寫進另一個不服務客戶流量的 Quicksilver 環境；比對器對 20% 的 zone 抽樣，檢查缺少的 key、多出的 key 與數值不同的 key。文章附的 DNS Mirror Dashboard 畫面顯示，在 234,313 個配對成功的 zone 上，差異率是 0.31%；差異大部分是時間差，等兩條 pipeline 都追上就消失。這個數字是一個時間點的畫面，所以真正要看的是差異率低、而且沒有出現新類型的差異。

結果在文章的數字裡分成三組。記憶體：平均用量從 49 GiB 降到 7 GiB，少了 86%；尖峰從 79 GiB 降到 12 GiB，少了 85%。延遲：建置完成延遲的中位數從約 7.7 秒降到約 3.3 秒，減半；最大的 p99 尖峰從 14.6 分鐘降到 1.21 分鐘，約 12 倍。剩下的完整重建平均 0.35 秒。

讀延遲數字時有一個文章自己標出的陷阱。舊的 histogram bucket 讓百分位估得偏高，p99 讀起來接近 30 秒，p90 超過 7 秒；換成原生 histogram 後，p90 約 5.5 秒、p99 約 12 秒。兩套數字量的是同一條曲線的不同解析度，把它們混著比，會得出錯的改善幅度。上圖的 14.6 分鐘到 1.21 分鐘指的是尖峰，是另一個量。

整篇文章的數字有三種性質，讀的時候要分開。92.95%、7.04%、11.88% 這幾個是 build 的件數比例，說的是哪一種 build 出現得多頻繁，不是各自花了多少時間。49 到 7 GiB、79 到 12 GiB 是記憶體用量，反映的是不再把整個 zone 放進記憶體。7.7 到 3.3 秒與 14.6 到 1.21 分鐘是延遲，一個是中位數，一個是最大的尖峰，代表的情境完全不同。把三類數字混在一起算，例如拿 40% 去乘延遲，得到的是文章沒有主張過的結論。

最後要記的是，完整重建並沒有消失。2022 年的計畫是完全消除完整重建，現在的結論是那既不實際也沒有用。文章給的理由是，變更可能影響 zone 內任何地方的紀錄時，完整重建仍然必要；意義不明的事件，也不能給它少於需要的工作。合理的推測是，第一次發布一個 zone、每筆紀錄都得寫的情況，同樣屬於這一類。如果你自己在做類似的 pipeline，這套設計能拿走的是它的順序：先讓事件帶出夠多資訊，再把「不確定」定義成回到完整重建，用逐 key 比對把等價變成可測，最後才談省了多少。

What this enables：完整 zone 的成本現在只留給確實需要它的事件，也就是 7.04% 的 build；其餘事件由規劃器選出能證明安全的最小範圍，執行前再以資料庫的最新狀態修正，讓 Zone Builder 的記憶體和延遲不再被最大的 zone 拖著走。
