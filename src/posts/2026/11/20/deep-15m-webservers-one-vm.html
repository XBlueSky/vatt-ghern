10GB 的 RAM 平均分給 1500 萬台伺服器，每台只剩約 667 bytes，而核心替一個 socket 配置的記憶體就約 3300 bytes。

單機撐起 1500 萬台 web server

這個實驗的目標，原文用一句話交代：「The goal is to run 15 million web servers on one VM with 10GB of RAM and 1 CPU core.」kapteko.com 的作者沒有把它當成產品，而是當成一道約束題，每個環節都得回答同一個問題：這個環節的單價是多少，乘上 1500 萬之後放不放得進去。本文照作者實際走過的路線拆開，port、行程、核心 socket 三面牆依序出現，最後一步是把網路堆疊搬出核心。

先交代這篇文章的結構。原文是一路排除障礙的寫法，沒有把幾個互相競爭的假說放在同一組條件下做對照實驗，所以下面的「假說」其實是作者逐一撞上的牆，本文的調查結構因此偏向「瓶頸排除」，不是「假說對照」。另外，我讀到的文字內容沒有列出各個網路堆疊的 RPS 數字，結果似乎放在圖表裡，這篇不會替它補數字，能引用的只有文字裡寫明的記憶體單價與耗盡點。

每台只分到約 667 bytes，題目本身就是矛盾

先把題目換算成每台的預算。10GB 除以 1500 萬，約 667 bytes（我的算術，GB 以 10 的 9 次方計，改用 GiB 約為 715 bytes，結論不變）。這個數字小到什麼程度？後面三節的數字排在一起就看得出來：一個行程 1.5MB，一個核心 socket 約 3300 bytes，只有使用者空間堆疊的閒置連線 620 bytes 落在預算線以內。

原文從最簡單的版本開始。web server 只需要幾個 syscall，依序是 listen、accept、recv、send、close，作者說這樣寫出的簡單版本「It gives us around 65k RPS.」這是一台 server 的基準，不是 1500 萬台合計的成績。

這個基準數字可以順手換算 CPU 這一側的預算。若把 65k RPS 當成單核的粗略上限（原文沒有這樣說，這是我的推測），平均到 1500 萬台，每台每秒只分到約 0.004 個請求，大約每 230 秒才輪到一次。合理的推測是，這個實驗預設絕大多數伺服器處於閒置，CPU 不是主要瓶頸，記憶體與位址才是；原文後續的每一步也都在處理記憶體與位址，不是請求吞吐。

假說一：port 不夠，改用整段 IPv6 子網

第一面牆是 port。作者的程式使用 port=0，由核心從 ip_local_port_range 挑一個可用的 port，原文的說法是「the kernel picks an available port from」這個範圍。查這個設定，輸出是 net.ipv4.ip_local_port_range = 32768 接上限 60999 的預設範圍，也就是 28,232 個 port（60999 減 32768 再加 1，我的算術）。

放寬範圍有用嗎？作者的答案是有限。改成 1-65535 之後，原文自己說「still a bit short of 15 million」。TCP 與 UDP 可以共用同一個 port 號，所以數量再乘二，文中寫成 128k（精確值是 131,070），距離 1500 萬仍差一百多倍。

接著作者列出一個算式「15M/32k=450」，並把它寫成替伺服器接上 450 張新網卡（原文是「new network cards to the server」）。合理的推測是這句帶著玩笑，不是認真的方案，但它把問題講得很準：port 只是每個位址底下的欄位，要湊出 1500 萬個 listener，就得有幾百個不同的位址，而不是更大的 port 範圍。

真正的解法叫 AnyIP。作者的說法是它「which lets us listen on a whole subnet」。做法是把整段 IPv6 子網的路由指到 loopback 介面：

sudo ip -6 route add local 2001:db8:1234:5678::/64 dev lo

路由指過去之後，目的位址落在這段子網內的封包，核心都當成本機位址處理，單一行程就能在大量位址上同時監聽。下面的計算器把「每個位址能用多少 port」換成「需要多少個位址」，三種預設都是原文出現過的範圍。

預設範圍要約 532 個位址，放寬到 1-65535 要約 229 個，再加上 UDP 要約 115 個（皆為我的算術）。三種情況都只是兩三位數，而原文說的是一整段子網，位址總數遠大於這個需求，原文沒有給總數，我不引用。port 這面牆在算術上就被拆掉了：它從容量問題變成一條路由設定。

不過這一步只解決了名字。1500 萬個 listener 有了可以綁定的位址，每一個仍然要有地方存放它的狀態。作者原本的寫法是在腳本裡用 seq 1 15_000_000 跑迴圈，逐個啟動 server，下一面牆就在這裡。

後面的核心 socket 量測還會讓這一步的限制更清楚：原文說單價與 socket 的狀態無關，連「listening」也照收。也就是說，AnyIP 讓 1500 萬個 listener 能各自擁有位址，但每一個監聽中的 socket 在核心裡仍要付同樣的錢。port 問題被拆掉，並不代表每台的成本下降了，它只是把「放不放得下」的問題往記憶體那一側推。

選 IPv6 不是隨意的。原文提到同樣的做法也能用在 IPv4，但「acquiring a subnet with 15M addresses would cost around $250 million」，作者接著說要依自己的環境調整指令。我的算術是 2.5 億美元除以 1500 萬個位址，平均每個位址約 16.7 美元。位址空間因此是這個實驗另一條看不見的預算線：IPv6 的 /64 子網只是一行路由設定，不用花錢，IPv4 要湊同樣的位址數則是以億計的採購。記憶體的算術決定了能不能塞進 10GB，位址的算術決定了這個題目能在誰的網路上重現。

假說二：一台 server 一個行程，記憶體先被行程吃光

作者量了單一 server 行程，結果是「Hm, one server consumes 1.5MB of RAM」。乘上 1500 萬是 22.5TB，約為 10GB 的 2250 倍；反過來算，10GB 只夠約 6667 個這樣的行程（皆為我的算術，MB 以 10 的 6 次方計）。原文給的判斷更簡短：「running millions of processes creates too much overhead」。數字比「overhead」兩個字更能說明問題，因為這個差距不是調參數補得回來的，它超過三個數量級。

於是作者換掉結構：「The answer is to run them all in one process inside a custom runtime」。這個 runtime 讓每個 guest 各自有沙箱，原文的描述是「It gives us memory isolation and replaces all syscalls with calls to our host handler」。再配上排程，讓 CPU 在 guest 之間輪流切換，原文的說法是「make the CPU constantly switch between guests」。

這張圖的關鍵是 syscall 的去向。guest 不再呼叫核心，所有 listen、accept、recv、send、close 都落到 host handler 手上，等於 host handler 才是這 1500 萬台伺服器唯一看得到的「核心」。合理的推測是，網路堆疊就接在 host handler 後面，因為只有 syscall 被攔下之後，才有機會換掉核心的網路路徑；圖上的虛線就是這個推測。

這個設計能成立，有一個前提寫在原文裡：guest 只呼叫那五個 syscall。合理的推測是，host handler 因此只需要實作這五個，而不是整套 POSIX 介面；範圍小，自己寫沙箱與排程才划得來。反過來說，guest 一旦需要別的 syscall，host handler 就得多實作一個，原文文字沒有討論這件事。

代價也寫在結構裡。隔離原本由核心與 MMU 提供，現在換成作者自己的沙箱；排程原本由核心的排程器負責，現在是 runtime 自己切換。這是用工程複雜度換記憶體單價的交易。原文最後也有一句提醒，內容是做出概念驗證很容易，後面會回到這句話。

假說三：核心裡的 socket 本身就太肥

行程的問題解掉，還剩網路堆疊。原文的量測是：「syscall allocates around 3300 bytes, whether the socket is active, listening, or doing nothing」，主詞是建立 socket 的那個 syscall。這句話的重點在後半：不論 socket 在連線中、監聽中，還是什麼都沒做，單價都一樣。閒置的伺服器在這個計價方式下沒有折扣。

3300 bytes 乘 1500 萬是 49.5GB，約為 10GB 的五倍；10GB 除以 3300 則是約 303 萬台（皆為我的算術）。換句話說，光是 socket 的配置，就足以在不到一半的目標規模處把記憶體用完。

原文實測的耗盡點還要更早：「The kernel network stack uses up all the RAM at around 2.5M web servers, and RPS drops as we run more servers.」10GB 除以 250 萬是 4000 bytes，比 3300 多出約 700 bytes。合理的推測是這個差額來自 socket 以外的核心與系統記憶體用量，但原文沒有拆解，2.5M 本身也只是「around」的近似值，不宜過度解讀。

引文的後半「RPS drops as we run more servers」只有結論，沒有機制，文字內也沒有給降幅，我不替它補原因。能確定的是，單價 3300 bytes 是核心替每個 socket 付出的固定成本，在不改核心的前提下沒有旋鈕可以調（這是我的推測，原文沒有討論核心參數）。對大量閒置連線的服務來說，這代表記憶體會比 CPU 更早成為上限，而且閒置不會讓成本變低（我的推論，原文只量到耗盡點）。

拖動滑桿可以看到，要讓 1500 萬台剛好貼在 10GB 線上，每台必須壓到約 667 bytes。核心 socket 的線在約 300 萬台就穿過上限，斜率最陡；smoltcp 的兩條線落在另一側，閒置連線在 1500 萬台時約 9.3GB，活躍連線（約 1KB）則是 15GB（皆為我的算術）。這個差別決定了下一節的故事：單價降到預算以內，問題才有解。

解法：把 TCP/IP 搬出核心，smoltcp 走到 1600 萬台

smoltcp 在原文裡的定位是「a standalone, event-driven TCP/IP stack」，在使用者空間運行。作者的量測是：「620 bytes per idle server and around a kilobyte for an active one, we got to 16M of servers」。620 bytes 低於 667 bytes 的預算線，這是整個實驗裡唯一落在線內的單價。

16M 乘 620 bytes 約為 9.92GB，幾乎正好填滿 10GB；15M 乘 620 bytes 是 9.3GB，乘上 1KB 則是 15GB（皆為我的算術）。合理的推測是，能到 16M 的那一輪以閒置連線為主，活躍連線只佔其中一小部分，否則記憶體放不下；原文引文沒有說明有多少伺服器同時活躍，這一點不能再往下讀。

還有一筆餘裕要算清楚。620 bytes 比預算線少 47 bytes，乘上 1500 萬是約 0.7GB 的空間（我的算術），這 0.7GB 要容納 runtime 本身、作業系統，以及每個 guest 自己的狀態。換成比例，620 是 667 的約 93%，單價層面的安全邊際只有約 7%，所以任何每台多出幾十 bytes 的設計，都會直接讓 1500 萬台放不進去（我的算術）。原文引文沒有交代這些項目各佔多少，16M 乘 620 bytes 已經逼近 10GB，合理的推測是這個單價是各項合計後的平均，或者其他項目小到可以忽略；不論哪一種，16M 這個數字只能當作 smoltcp 單價的證據，不能當成整個系統的總帳。

這些項目裡，有一項原文明確給了數字：排程狀態。排程為什麼只要 16 bytes？原文的推理是：「If our scheduler had to suspend a guest at any syscall point in this loop, we’d need to save the following state」。接在後面的結構只有返回的指令位址，加上 server 與 client 兩個 file descriptor。guest 只會呼叫那五個 syscall，暫停點就只有那幾處，要保存的因此很少。我的算術是 8 加 4 加 4 剛好 16，前提是位址佔 8 bytes、descriptor 各佔 4 bytes，原文文字沒有標型別，這只是對得上的一種解讀。

再看這 16 bytes 放在預算裡的分量。原文寫「We only need 16 bytes per guest」，並列出「Scheduling state for 15M guests - 220MB」。我的算術是 16 乘 1500 萬為 240MB，比原文的 220MB 略高，原文沒有交代單位換算，差距不影響結論。真正的重點是比例：3300 除以 16 約為 206，也就是讓 1500 萬個 guest 暫停在任何一個 syscall 上，花的記憶體只有核心替它們各開一個 socket 的兩百分之一左右。連線狀態才是大宗，排程狀態不是。

活躍連線則是另一筆帳。原文的粗估是「1M active connections at 5kb each = 5GB」，也就是假設同時活躍的連線有 100 萬個，每個佔 5KB。這 5GB 已經是 10GB 的一半。原文文字沒有說明 5KB 是否已經包含閒置時的 620 bytes，所以我不把兩者加總。能確定的是，1500 萬這個規模靠的是絕大多數連線閒置：我的算術是活躍連線一旦到 200 萬個，單是這一項就吃掉 10GB。合理的推測是，這個實驗展示的是記憶體上限，而不是 1500 萬條連線同時收發資料的負載。

單價為什麼能從 3300 bytes 降到 620 bytes，約為五分之一？原文沒有逐項拆解 620 bytes，但交代了兩個相關的設計特徵：「smoltcp does not need heap allocation at all」，以及 smoltcp「is essentially a smart parser and can’t do I/O」。合理的推測是，完全不用堆積配置，代表每個連線的狀態大小可以事先固定，不必替每個 socket 另外向配置器要記憶體，這是單價能壓低的可能原因之一；原文沒有明說這個因果，我只是順著設計特徵推。「只是聰明的解析器」這句話還解釋了下一步：堆疊自己不碰網卡，收發封包必須由別人代勞，所以才需要接下來的 DPDK 與 AF_XDP。

堆疊搬出核心之後，封包要有另一條進出路。原文介紹兩條：DPDK 與 AF_XDP。DPDK「requires exclusive access to the network device because it uses a driver that operates at the hardware level」，作法是「works by running a busy loop that takes up an entire CPU core」。AF_XDP 則把網卡留給核心：「The kernel still owns the device and interrupts still happen as usual」，封包進來時，「the kernel runs a simple eBPF filter that decides whether to send it directly to the userspace buffer」。要連中斷也省掉，可以改用 busy polling，原文的說法是「you get a busy loop with no interrupts at the cost of a CPU core」。

三條路徑各自付出的代價看得很清楚。核心路徑付記憶體，每個 socket 約 3300 bytes；DPDK 與 AF_XDP 的 busy polling 付 CPU，一個 core 空轉。原文對這次 benchmark 的結論是「DPDK is clearly the beast in this benchmark」，AF_XDP 緊跟在後。我讀到的文字沒有附各自的 RPS，所以兩者差多少，這篇回答不了。

這裡有一個值得追問的地方。原文的 VM 只有 1 個 CPU core，而 DPDK 的 busy loop 照原文說法會吃掉一整個 core。這兩個事實放在一起有張力，我讀到的文字沒有說明實驗怎麼配置核心，所以不知道作者如何處理，這是閱讀原文時最值得到圖表與程式碼裡確認的一點。合理的推測是，若 busy loop 與 guest 排程共用同一個 core，輪詢就得和 guest 搶時間；原文只說「make the CPU constantly switch between guests」，沒有交代 busy loop 放在哪裡。

DPDK 與 AF_XDP 的取捨還有另一面。DPDK 獨佔網卡，核心就看不到那張卡，後果在原文裡很具體：用 SSH 遠端啟用的話，「you’ll lose SSH access too」，連管理連線也跟著斷。AF_XDP 讓核心繼續擁有裝置，只用 eBPF filter 決定哪些封包直送使用者空間，管理流量因此不受影響，這是我從「核心仍擁有裝置」推出來的，原文沒有直接這樣寫。作者對兩者的評語是：DPDK 仍然最快，但 AF_XDP「is very close (and simply easier to manage)」。合理的推測是，如果機器只有一張網卡，選 DPDK 就得另外準備管理通道；這個實驗是單核單 VM，原文沒有說明作者實際怎麼連進機器。

回到最初的算術：預算線在每台約 667 bytes，核心 socket 是 3300 bytes，使用者空間堆疊的閒置連線是 620 bytes。整個調查的順序現在可以一次看完：port 的牆用整段子網拆掉，行程的牆用單一行程的 runtime 拆掉，核心 socket 的牆用使用者空間堆疊拆掉，每一步拆掉的都是當時單價最高、遠超預算的那一項。

三面牆的出現順序也不是偶然。合理的推測是，單價高的環節會遮住單價低的環節：行程每台 1.5MB 的時候，連 socket 的 3300 bytes 都看不見，因為記憶體早在幾千台時就用完了；行程問題解掉，socket 才浮出來；socket 問題解掉，剩下的才是使用者空間堆疊自己的 620 bytes。每解掉一面牆，單價降一到三個數量級，下一個瓶頸才有機會被量到。這是調查型工作很常見的節奏，原文沒有這樣總結，這是我的讀法。

這個結果有明確的適用範圍。合理的推測是，同樣的算法也適用於任何「大量連線、大多數閒置」的服務，例如推播閘道或 IoT 的 broker，但原文只談 web server，沒有討論這些場景。原文結尾的提醒也不能略過：「Simply is a bit of a stretch - building a proof of concept is easy.」概念驗證做得出來，不代表一個通用的 runtime 做得出來，原文沒有宣稱後者。

如果你要把這個算法搬到自己的服務上，步驟本身很簡單：用機器的記憶體上限除以預期的同時連線數，得到每條連線的預算；再量一條閒置連線在你的堆疊裡實際佔多少，包含核心配置與應用自己的狀態。兩個數字相差一個數量級以上的時候，微調不會有幫助，要換的是結構。這是從原文的做法歸納出來的建議，不是原文的結論。

Take-away：下次遇到「單機撐 N 台」的規模問題，先拿資源上限除以 N 得到每台預算，再逐一量每個環節的單價，單價超過預算的環節就是下一面要拆的牆。
