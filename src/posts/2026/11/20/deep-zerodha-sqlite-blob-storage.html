三個 4 vCPU、8 GB 的節點，線上 p99 大約 2 ms，p50 落在 250 到 550 µs，而它們要服務的 blob 從 2 KB 的設定檔一路到 5 MB 的圖表版面。Zerodha 的做法不是找到一個更快的儲存引擎，而是把資料切進很多個 SQLite 檔，讓每個檔只有一個 writer。

Zerodha 為了替換 SSDB，自己寫了一個叫 Blobasaur 的 blob 伺服器：對外說 Redis 協定，底層每個分片就是一個 SQLite 檔。這篇照一個 key 進來之後經過的順序拆開它。先看一整排現成方案為什麼都被排除，再看資料怎麼被分到節點與分片、分片換到多少吞吐、壓縮和放寬 durability 各自換到什麼，最後看 async 寫入留下的一致性債，以及遷移與線上的數字。

SSDB 的天花板與一排被淘汰的方案

起點是維運風險。來源寫得很直接：SSDB 已經無人維護，是明顯的維運風險；它也不是分散式系統，只能跑在單一節點上。單機的後果落在 blob 大小上：較大的 payload 會讓延遲劣化，所以他們被迫把 blob 上限壓在 1 MB。新系統的要求卻是同時服務 2 KB 的設定 blob 和 5 MB 的圖表版面，而且延遲要維持在個位數毫秒。舊系統的 1 MB 上限和新需求的 5 MB 版面，從一開始就互相衝突。

來源列出的需求有六項：Redis 協定相容、跨各種 payload 大小的低延遲、內建壓縮、帶 TTL 的簡單 CRUD、多節點分區，以及可以接受放寬的 durability。最後一項值得先記住。它是需求清單的一部分，不是做完之後的讓步，後面幾乎每個取捨都從這裡長出來。

這六項需求和最後的設計幾乎一一對應，攤開來看可以看出 Blobasaur 的骨架。Redis 協定相容，所以 client 端用現成的 Redis 與 Redis Cluster client 就能連。跨大小的低延遲，靠分片與壓縮去撐。內建壓縮是寫入路徑上的一個步驟。帶 TTL 的 CRUD 落在資料列的 expires_at 欄位上，來源提到這個欄位的索引是 partial index。多節點分區則借用 Redis Cluster 的 slot 機制。合理的推測是，這個設計的取向是把每一項需求都交給既有而成熟的零件，而不是為 blob 另外發明新的演算法。這是我對整體設計風格的歸納，來源沒有這樣自我描述。

被排除的方案各自卡在不同的地方，下面的卡片逐項對應來源的說法。把它們放在一起看，淘汰的理由其實落在幾個不同的軸上：吞吐量（ScyllaDB）、效能與磁碟空間效率（PostgreSQL）、並非為 blob 設計（YugabyteDB、RocksDB）、維運複雜度（Ceph）、TTL 的粒度（SeaweedFS 與 S3、MinIO），以及要自己補原子寫入和寫入批次（直接寫檔案）。沒有哪一個方案是全面落後，每一個都是在某一項需求上過不了關。

留下來的是 SQLite。來源的說法是，SQLite 幾乎給了他們原始檔案系統缺的所有東西；對小 blob，它最多比直接做檔案 I/O 快 35%。但同一份來源也承認反方向的事實：檔案超過大約 100 KiB 之後，原始檔案開始贏過 SQLite，所以他們在寫入之前先壓縮 blob。壓縮之後，99% 的值遠低於 100 KiB。這兩句放在一起，邏輯就接上了：壓縮讓這批資料留在 SQLite 比較有利的區間裡。這是我對兩句話關係的解讀，來源沒有把它寫成一條因果鏈，但每個前提都在來源裡。

如果你正在替一批 blob 找儲存，這一節最能直接搬走的是判斷順序，而不是結論。Zerodha 先寫下六項需求，再用最難滿足的那一項去篩：單機與 1 MB 上限先排除了 SSDB，TTL 的粒度排除了物件儲存，維運複雜度排除了 Ceph。結論之所以是 SQLite，是因為它在這些軸上都沒有明顯的洞，而它的短處，也就是較大的檔案，可以用壓縮繞過去。這是我對選擇過程的歸納，來源沒有用這種方式描述自己的決策。

一個 key 的路徑：節點、分片、writer

先看跨機器的那一層。Blobasaur 照 Redis Cluster 的做法，用 CRC16 把 keyspace 切成 16384 個 hash slot。每個節點擁有設定檔裡指定的一段 slot 範圍，節點之間透過 gossip 互相發現。client 如果把 key 送到錯的節點，該節點會回一個 MOVED 轉址，指向真正的擁有者。遷移時應用程式端唯一需要改的程式碼，就是把單節點的 Redis client 換成 Redis Cluster client。限制也寫在來源裡：目前 slot 的指派是靜態寫在設定檔的。

進到節點之後，資料再被切一次。每個 key 透過 multi-probe consistent hashing 對應到一個分片，每個分片是磁碟上獨立的一個 SQLite 檔。每個分片有一個專屬的 writer task，由一條有上限的佇列餵資料。writer 不會一個 key 一個 key 地 commit，而是從佇列裡一次取出一批待寫的資料，放進同一個 transaction。讀取走另一條路：每個分片有一個唯讀 SQLite 連線池，讀請求直接進這個池，可以和 writer 並行。

client 端用的是 Redis Cluster client，也就是說 slot 到節點的對應由 client 持有，節點只有在對應不準時才用 MOVED 糾正。合理的推測是，正常情況下一個請求只走一跳，中間沒有額外的代理層；來源沒有量過轉址發生的頻率。靜態的 slot 指派在這裡可能還帶來一點好處：對應表寫在設定檔、不會自己變動，client 端的對應失準的機會應該不高。這同樣只是推測，來源只說明了指派是靜態的。

批次的設計值得多說一句。SQLite 每次 commit 都有固定成本，一個 transaction 裡放的寫入越多，這個成本被攤得越薄。來源的對照實驗把 batch_size 設成 50，writer 則是一次從佇列取出一批待寫的資料。合理的推測是，在同步寫入的設定下，client 等的是整批 commit 完成，所以批次越大，吞吐越有利，單筆延遲的尾巴也可能越長；來源沒有掃描 batch_size，這個取捨只能當作推測。

為什麼要切這麼細？來源在別處說得很清楚：SQLite 只有一把寫入鎖。後面談到過期清理的問題時，這把鎖會變成主角。合理的推測是，每個分片一個 writer、再把資料分到很多分片，目的就是把這一把鎖複製成很多把，讓寫入可以在不同的檔之間平行進行。讀取不需要等這把鎖，因為它們走唯讀連線。下一節的數字可以檢驗這個推測。

分片數可以改，但代價不小。來源說 resharding 目前是離線操作，用內建的 CLI 完成，例如 blobasaur shard migrate 4 5 --verify，執行前要先停掉伺服器。遷移工具只搬目標分片改變的 key，加上 --verify 時還會檢查 key 的位置並回報資料列數。靜態 slot 指派加上離線 resharding，意味著這套系統在擴縮上是偏手動的。對一個把 durability 放寬、負載型態相對固定的設定與偏好儲存，這個取捨說得通；若換成需要隨流量彈性伸縮的場景，這兩個限制就會變成問題。

分片換到多少吞吐，讀寫為什麼不對稱

來源做了一組對照：1 個分片對 16 個分片，三種工作負載。設定是 100,000 個 key、64 KiB 的 payload、batch_size = 50，而且全部使用同步寫入。純 HSET 從每秒 7,740 次提高到 25,324 次，p99 從 10.7 ms 降到 8.3 ms。來源自己的歸納是：16 個分片下寫入吞吐上升 3.3 倍，寫入延遲的中位數從 8.2 ms 降到 2.1 ms。

混合負載（一半 HSET、一半 HGET）從 14,227 次升到 29,538 次，約 2.1 倍，p99 從 10.5 ms 降到 8.5 ms。純 HGET 幾乎沒動：67,128 次對 70,884 次，只多了約 5.6%，p99 甚至從 2.1 ms 微升到 2.3 ms。三組數字畫成圖，寫入那兩組的差距和讀取那一組的平坦，一眼就看得出來。

讀取為什麼幾乎不受分片數影響？一個 SQLite 檔在只有 1 個分片時，讀取已經能跑到每秒 67,128 次，因為讀取走唯讀連線池，不必排進 writer 的佇列。分片真正解開的是寫入這一側的序列化。這和上一節的推測一致：寫入受限於每個檔的單一寫入鎖，分片把鎖變多，寫入吞吐就跟著上去；讀取本來就沒有被這把鎖卡住，所以加分片幾乎沒有差別。

把倍數拉開看，還有兩件事。第一，寫入的中位數延遲降到原來的約四分之一（8.2 ms 到 2.1 ms），p99 卻只降了約兩成（10.7 ms 到 8.3 ms），吞吐與中位數的改善比尾端延遲的改善大得多。合理的推測是，尾端仍被批次 commit 的等待和 64 KiB 的資料量決定，分片能分散的是排隊，分散不了每一批 commit 自己的耗時。第二，混合負載的倍數（約 2.1 倍）夾在純寫入的 3.3 倍和純讀取的約 1.06 倍之間，方向上符合「寫入受益、讀取原地不動」的解釋，但來源沒有拆出混合負載裡讀寫各自的延遲，這只是和數字相容的讀法。

這組數字要有保留地讀。它是單一組設定下的結果，使用同步寫入，不代表任何一個線上負載。分片數從 1 跳到 16，中間的點來源沒有給，所以「分片越多越好」並沒有被這張表證明，這張表只證明了 1 與 16 兩個端點之間，寫入有 3.3 倍的差距。

壓縮與放寬 durability

Blobasaur 在寫入 SQLite 之前可以做壓縮，支援 zstd、lz4、gzip 與 brotli，線上跑的是 zstd。來源用一個平均值說明效果：平均 63.6 KiB 的 payload 壓縮後是 5.5 KiB，儲存佔用從大約 16 個 page 降到大約 2 個，表中列出的壓縮比約為 11 倍。page 是 SQLite 寫入與讀取的單位，payload 縮小，等於每個 blob 需要碰的 page 少了一大截。

壓縮發生的位置也有講究。它在寫入 SQLite 之前，所以 SQLite 看到的是壓縮後的位元組，page 數、checkpoint 與 vacuum 面對的都是壓縮後的大小。這把前面那個 100 KiB 的分界變成可以操作的量：只要壓縮後的 value 夠小，檔案就留在 SQLite 比較有利的一側，而來源說 99% 的壓縮後 value 遠低於這個門檻。至於 5 MB 的圖表版面壓縮後會落在哪裡，來源沒有給單一案例，只給了平均值這類彙總數字，所以不能由此推出大 blob 的行為。

durability 的取捨在另一端。分片設成 synchronous = NORMAL，來源明說 SQLite 不會在每次 transaction commit 時 fsync。對照前面的需求清單，這正是「可以接受放寬 durability」的具體實作。合理的推測是，伺服器當機時，最近幾筆已經回覆 client 的 commit 可能還沒真的落到磁碟；來源在這一段沒有逐項列出能遺失什麼，這個後果是我從「不 fsync」推出來的。

更激進的是 async_write 模式。開啟之後，寫入一進到分片的記憶體佇列就回覆 client，早於 SQLite 批次 commit。client 看到的寫入延遲不再包含 commit 的時間，換來的視窗是：佇列裡已經回覆、尚未 commit 的資料，在程序崩潰時沒有任何磁碟上的副本。這個模式只在能接受遺失的資料上才說得通。合理的推測是，使用者的工作區偏好與圖表版面這類資料屬於這一類，不過來源在這一段沒有逐項說明哪些資料開了這個模式。

對想借用這個設計的人，這一節有一個具體的檢查點：資料遺失的視窗能不能接受。放寬 durability 的收益是寫入路徑上少了每次 commit 的 fsync，在 async_write 下甚至連 commit 都不用等；代價是崩潰時有一個大小說不準的視窗。來源的需求清單只寫了可以接受放寬的 durability。我的歸納是，這種設計適合遺失一筆可以由使用者重新設定的資料，不適合直接搬去放訂單或帳務這類不能少一筆的資料。

async 寫入的債：pending map、tombstone 與刪除

讓寫入先回覆，讀取就得看得見還沒 commit 的資料，不然 client 剛寫完就讀不到。Blobasaur 的解法是把進佇列的寫入同時放進一個記憶體裡的 pending map，讀取在查 SQLite 之前先查它。來源記下了一個邊角情況：一個 DEL 後面緊接著 GET，因為佇列裡的 DEL 還沒 commit，如果 pending map 裡找不到這個 key，讀取就會落到 SQLite，回傳舊值。修法是在 pending map 裡存明確的 tombstone，並且讓每一種讀取（GET、HGET、EXISTS、TTL）都先過它。

要是你也打算在資料庫前面放一條寫入佇列，來源列出的四個指令就是現成的檢查表：GET、HGET、EXISTS、TTL。只要有一個讀取指令繞過 pending map，就會在刪除或覆寫之後讀到過時的狀態。TTL 特別容易被漏掉，因為它讀的是過期資訊而不是值本身，但在佇列裡的 DEL 或重新 SET 尚未 commit 時，它同樣可能給出過時的答案。這是從來源的四個指令延伸出來的推論，來源只說明它們全都先經過 pending map。

下面的模擬器把這個狀態機攤開。選一種寫入模式，對一個 key 做 SET、DEL、GET，看佇列、pending map 和已 commit 的 SQLite 三個地方各自長什麼樣。把 tombstone 關掉，再依序按 SET、commit、DEL、GET，就會重現來源描述的那個 bug；按 crash 則看到佇列裡還沒 commit 的寫入一起消失。模擬器只實作了來源明講的行為，其餘細節（例如佇列滿了會怎樣）刻意沒有模擬。

這個 bug 的形狀值得留意：它不是邏輯寫錯，而是兩個各自正確的設計疊在一起。async 寫入讓回覆早於 commit，pending map 讓讀取看得見未 commit 的資料，但「刪除」在 map 裡本來就是一個沒有內容的狀態，沒有明確標記就和「從來沒寫過」無法區分。tombstone 的作用，就是讓「已刪除」成為 map 裡看得見的一個值。

另外兩個教訓都來自 SQLite 自己的行為。第一個是檔案不會縮小。來源說他們早期就發現，即使有上百萬個 key 過期或被刪除，磁碟用量還是只增不減，原因是 SQLite 預設把釋放的 page 放在內部的 freelist 留給未來的寫入，而不是還給作業系統。他們在每個分片啟用了 PRAGMA auto_vacuum = INCREMENTAL，另外加了 blobasaur shard vacuum 子命令，在設定的額度內回收 freelist 的 page，預設是 128 MB；每次增量 vacuum 之後會立刻執行 PRAGMA wal_checkpoint(TRUNCATE)。

第二個是過期清理和 writer 搶同一把鎖。線上的寫入 p99 平常在 5 ms 以下，卻偶爾衝到 30 到 50 ms。原因是一個很大的 DELETE 和分片的主 writer 爭奪 SQLite 的單一寫入鎖，讓一般 client 的批次停住。修法是把清理切成小塊，每一輪以 cleanup_chunk_size 為上限，預設 1,000 列，並讓清理走分片的 writer；來源說這樣分散實體刪除之後，延遲尖峰消失，正確性不受影響。這件事回頭印證了前面的推測：單一寫入鎖不是理論上的限制，它真的在線上以 30 到 50 ms 的尖峰出現過。

三個問題有一個共通點：它們都是 SQLite 的行為在這個用法下被放大。freelist、單一寫入鎖，加上自己加的記憶體佇列，三者都不是 PostgreSQL 或原始檔案系統會以同樣形式遇到的問題。合理的推測是，選 SQLite 換來了嵌入式引擎的簡單與速度，也同時繼承了它的運作細節，而這些細節得由 Blobasaur 自己去補。

遷移路線與線上數字

遷移分成三步。第一步是新的工作負載先走：Kite Terminal mode 上線時，它的 workspace 儲存直接指向 Blobasaur。第二步是既有的工作負載，例如圖表偏好：服務同時寫進 SSDB 與 Blobasaur，同時有背景任務搬歷史的 key；讀取先去 Blobasaur，遇到 cache miss 或錯誤才退回 SSDB。第三步是切換，應用程式端唯一的改動，就是從單節點的 Redis client 換成 Redis Cluster client。雙寫跑了一個月、沒有任何不一致之後，他們關掉了 SSDB。

這條路線的安全性來自兩個設計：讀取先打新系統、失敗再退回舊系統，所以任何一邊出問題都有後路；而因為 Blobasaur 說的是 Redis 協定，client 端的改動才小到只是換一個 client。協定相容這條需求，在遷移這一步才算真正兌現。

一個月的雙寫期也值得單獨看。雙寫的目的不是壓力測試，而是比對：兩個系統收到同樣的寫入，結果應該一致，「零不一致」才是可以關掉舊系統的證據。合理的推測是，一個月的長度是為了讓使用頻率不同的使用者都至少碰過一次這條路徑；來源只說跑了一個月、沒有不一致，沒有交代為什麼選這個長度。

線上的狀態，來源給的是這幾組數字：三個節點（每個 4 vCPU、8 GB RAM）組成的叢集，所有指令的 p99 在每個節點上都維持在約 2 ms，p50 在 250 到 550 µs 之間。拆開看指令，HSET 的 p99 約 2 ms，HGET 的 p99 約 1.4 ms，HDEL 的 p99 多半低於 1 ms。把這組數字和前面的分片對照表放在一起看會有落差，例如對照表裡純 HSET 的 p99 是 8.3 ms，但兩邊的條件不同（payload 大小、同步寫入、硬體都不一樣），不宜直接比較。

值得補上的是 1 MB 上限的對照。SSDB 時代因為延遲而被迫把 blob 壓在 1 MB；現在同一個叢集服務的範圍從 2 KB 到 5 MB，而線上 p99 在 2 ms 上下。這個比較有一個限制：來源沒有給出不同 blob 大小各自的線上延遲分布，所以「5 MB 的 blob 也是 2 ms」並沒有被證明，被證明的是整體的延遲分布和需求涵蓋的大小範圍。

把整篇濃縮成採用前的檢查表，大概是四個問題：資料遺失的視窗能不能接受？壓縮後的 value 大小是否多數落在 100 KiB 以下？TTL 需要精確到 key 嗎？能不能接受靜態的 slot 指派與離線的 resharding？前兩個問題決定 SQLite 適不適合這批資料，後兩個決定 Blobasaur 的運維模式適不適合你的團隊。這份清單是我的整理，不是來源的結論。

What this enables：三台 4 vCPU 的節點就能用 Redis 協定服務從 2 KB 到 5 MB 的 blob，代價是接受放寬的 durability、靜態的 slot 指派與離線的 resharding。
