2026 年 9 月 9 日，OpenJDK 收到一個 PR，描述的輸入是 64 個 A 接一個等號。十一月十八日，Cloudflare 文章裡 Java4Shell 的最簡觸發條件，也是 64 個 A 接一個等號，評分 9.2。

這件事有三份材料可讀：OpenJDK 倉庫裡的一個 PR、Cloudflare 的 WAF 規則說明，以及部落客 mccue 的一篇短文。三份各自只看到事件的一段，拼起來才有時間順序，也才看得出彼此對不上的地方。下面照時間走，材料沒寫的地方就標成沒寫，不補。

九月九日的 PR，十一月四日被關掉

時間線從 OpenJDK 的 PR #32781 開始。按 PR 頁面顯示，albertnetymk 在 2026 年 9 月 9 日開出這個 PR，標題裡有一句話：「AVX-512 Base64 decoder overwrites output buffer on short padded tail」。這句標題已經把問題講完了：AVX-512 版的 Base64 解碼器，遇到一段很短、帶補齊字元的尾巴，會把輸出緩衝區蓋寫過頭。

描述寫得很具體。按 PR 的說法，L_finalBit 負責處理 1 到 63 個剩餘位元組，輸出大小的算式是 output_size = (len/4)*3。合法的 Base64 輸入長度一定是 4 的倍數，所以這個算式在合法輸入上沒有問題，bug 只在無效輸入上出現。PR 舉的例子是 64 個 A 後面接一個等號，跑完主迴圈 L_process64Loop 之後剩 1 個位元組。建議的修法是長度小於 4 時，提早回到 Java 實作。

兩天後的 9 月 11 日，PR 頁面出現被 adoptium-support 的 issue 引用的紀錄。被連到的 issue 標題裡，有 JVM Crash 發生在 parallel GC 的 PSPromotionManager、發生在 JVM_ArrayCopy，以及發生在 compiler thread。頁面只留下引用的紀錄，沒有說這些崩潰的根因就是這個 PR 描述的問題。合理的推測是：堆積記憶體被蓋寫之後，崩潰會出現在任何之後碰到壞資料的地方，GC、陣列複製、編譯執行緒這三個互不相干的位置，正符合這種症狀。但這只是推測，PR 頁面沒有確認。

接著是一段空白。頁面顯示 11 月 4 日 albertnetymk 自己把 PR 關了，頁面上同時有 bot 的訊息，警告 PR 閒置超過八週會被自動關閉。從 9 月 9 日到 11 月 4 日是 56 天，這個數字是我按日期算的，頁面沒有寫。PR 沒有合併，我讀到的頁面也沒有說明關閉的原因。11 月 19 日，有人（hmilkovi）在底下問為什麼關掉；在我讀到的頁面摘錄裡，沒有看到回覆。

這裡要把材料的邊界講清楚。PR 頁面沒有出現 CVE 編號，我讀到的 Cloudflare 摘錄裡也沒有看到對這個 PR 的引用。把兩者接起來的，只有觸發條件長得一樣：下一節會看到，Cloudflare 寫的最簡觸發條件就是 64 個 A 接一個等號。所以「這個 PR 描述的就是後來的 Java4Shell」是我的推論，不是任何一份來源的陳述。若這個推論成立，PR 被關掉的 13 天之後，同一類輸入就拿到了 CVE 編號。

64 個 A 加一個等號，為什麼會寫過界

Cloudflare 把這個漏洞稱為 Java4Shell（CVE-2026-114938），披露者是安全研究公司 Calif。它對觸發方式的描述只有兩句：最簡單的觸發條件是 64 個 A 接一個等號；換成 OpenJDK 17，需要的是 128 個字元接一個等號。這跟 PR 描述的那串輸入一模一樣，至少在 64 這個長度上。

能不能被打到，還要看硬體與版本。Cloudflare 列出的條件是 OpenJDK 17.0.6 或更新（包含從 OpenJDK 衍生的發行版），以及支援 AVX-512 VBMI 的 x86-64 處理器；ARM64 不受影響。這和 PR 標題裡的「AVX-512」對得上：出問題的是 Base64 解碼的硬體加速那條路。PR 的修法是提早回到 Java，可見另有一條 Java 寫的路徑，那條不在問題裡。

為了看清楚為什麼偏偏是這種輸入，我照 PR 的描述做了一個小模型。它只用到 PR 自己寫的三件事：合法長度是 4 的倍數；64 個 A 加等號會在主迴圈之後剩 1 個位元組；剩下 1 到 63 個位元組的尾巴交給 L_finalBit。模型再加一個我自己的假設：主迴圈每次吃掉 64 個字元，所以尾段長度就是總長度除以 64 的餘數。這個假設不是 PR 的原文，是從「64 個 A 加等號剩 1 個位元組」這個例子反推的。

拖到 n=64 和 n=128，尾段都是 1 個位元組，正好是 Cloudflare 與 PR 各自點名的兩個長度。這個吻合不算證明，因為尾段為 1 的長度還有 n=192 等其他點，來源只提到兩個；它只說明模型沒有跟來源打架。n 小於 64 的區域我用灰底蓋住：來源沒有寫短輸入會不會進入 AVX-512 那條路，模型在那裡不下判斷。

PR 的算式還能再多讀出一層。合法的 Base64 每 4 個字元解出 3 個位元組，所以長度是 4 的倍數時，(len/4)*3 剛好等於實際的輸出大小，這是 PR 說「合法輸入沒問題」的原因。如果其中的除法是整數除法（PR 的寫法沒有說明，我按 C 與 Java 的慣例這樣讀），那麼 1 到 3 個位元組的尾段算出的輸出大小是 0，4 到 7 個位元組才開始是 3。合理的推測是：修法條件選在長度小於 4，正是因為這一段算式給出的數字與實際要寫的位元組數落差最明顯。這是我從算式倒推的，PR 摘錄沒有解釋為什麼選 4。

再往下拖到尾段 4 到 63 個位元組的位置，模型給的結論是材料沒寫。PR 說 L_finalBit 處理 1 到 63 個位元組，建議的修法條件卻是 length < 4。如果 length 指的就是尾段長度（這是我的解讀，我讀到的摘錄沒有定義），那麼修法擋下的只是最短的一段，其餘長度的無效尾段是否安全，得看實際的程式碼差異，而我讀到的頁面摘錄沒有附上差異內容。PR 沒有合併；Oracle 十一月釋出的修補版實際怎麼改，三份材料都沒有說。

從蓋寫到遠端執行，中間的步驟只有 Cloudflare 的一句轉述：Calif 把那個蓋寫變成堆積記憶體的洩漏，形式類似 Heartbleed，再往下做到遠端程式碼執行。Cloudflare 列出的示範對象，免登入的有 Keycloak、Atlassian Jira、Atlassian Confluence，需要登入的有 Apache Kafka、Apache Solr、Elasticsearch，完整名單以 Cloudflare 原文為準。這些全部是 Cloudflare 對 Calif 的轉述，我沒有讀到 Calif 的原始報告，所以等同單一來源。

這份名單有個規律：免登入的幾個，都是身分驗證或協作平台的前門。Cloudflare 為 JWT 與 WebAuthn 各寫了一條規則，表示 Base64 會出現在這類認證資料裡。合理的推測是，攻擊面落在請求一進來就要解碼的欄位，所以登入前就能打；Kafka、Solr、Elasticsearch 這批要先登入，則可能是因為解碼發生在驗證之後的資料路徑。後半句是我對「pre」與「post」兩個詞的讀法，來源沒有逐一說明每個產品的路徑。

十一月十七日：披露、修補、旗標，同一天到齊

時間在這裡密了起來。Cloudflare 寫的是 2026 年 11 月 17 日 Calif 公開披露；同一天 21:00 UTC，Oracle 在 11 月的 Critical Patch Update 釋出修補版。Cloudflare 的文章發表於 11 月 18 日（頁面結構化資料的日期）。mccue 的文章沒有標日期，網址裡寫的是 11-18-26，內文說「We're less than a day into dealing with」這件事，兩者對得上。評分方面，Cloudflare 寫它是 9.2 分，滿分 10，等級 Critical。

Cloudflare 對修復的說法沒有留餘地：修復是更新每一個 Java runtime，並重啟用到它的服務。它補了兩個容易漏掉的地方：很多應用會自帶 Java runtime，容器映像也內含固定版本的 JDK；而且每個更新過的服務都需要重啟。照這個說法推論，伺服器上的系統 JDK 更新了，不代表自帶 runtime 的那個應用也更新了。

無法立刻更新時，兩份材料都給了旗標。Cloudflare 列了兩個：-XX:-UseBASE64Intrinsics 關掉硬體加速的 Base64 編碼與解碼；-XX:UseAVX=2 關掉 AVX-512。mccue 只提第一個，建議把它加進 VM 旗標。兩者範圍不同：前者關掉整條 Base64 加速路徑，後者關掉的是更廣的 AVX-512 支援。哪一個代價比較小，兩份材料都沒有給數字；合理的推測是 UseAVX=2 會連帶影響其他用到 AVX-512 的程式碼，但這是推測。

Cloudflare 也交代了自己的狀況：多數 Java 工作負載沒有排程在有漏洞的機器上，它仍然開始推出一個 JVM 啟動選項，關掉加速的 Base64 常式，並表示到目前為止沒有跡象顯示 Java4Shell 在它的基礎設施上被利用。這是廠商對自家環境的說法，沒有第三方佐證。

這句話本身也透露了風險的分佈方式。漏洞要同時有特定版本與特定指令集才會出現，所以同一個機房裡，同樣的應用跑在不同世代的機器上，曝險可以不一樣。Cloudflare 的觀察是它的多數 Java 工作負載落在沒有漏洞的硬體上；即使如此，它仍然把關掉加速常式的選項推到所有 Java 工作負載。這是一個可以抄的順序：先不管自己是不是真的在範圍內，把便宜的緩解先鋪開，再處理更新。這個做法的前提是旗標的代價能接受，而代價有多大，來源沒有給數字。

下面的檢查器把 Cloudflare 列的條件逐項拆開，讓你自己組合。前四項來自 Cloudflare 的描述；第五項「應用會解碼外部傳入的 Base64」是我加的推斷條件：Cloudflare 的規則都在 HTTP 請求裡找畸形 Base64，Calif 的示範對象也都是網路服務，沒有外部輸入就沒有觸發的路徑。這個前提合理，但不是來源的原話。

試幾組之後會發現，五項裡任何一項不成立，就脫離描述的範圍；真正由你決定的只有兩項：旗標與更新。硬體和版本是機器既有的事實，輸入有沒有外部來源是應用的設計。最容易在現場出錯的是「已更新但沒重啟」那一格，系統上的檔案新了，跑著的程序還是舊的。

WAF 規則：擋得到的位置，和擋不到的位置

同一天，Cloudflare 在 Managed Ruleset 放出六條規則，付費方案可用。規則名稱把攔截的位置寫得很清楚：Header、Query Value、Body Value、Path Segment、Base64url JWT Component、WebAuthn Value，每一條後面都接著 CVE-2026-114938。六條預設都是 Log，也就是只記錄不阻擋；文章的說法是付費方案可以自己切到 Block。先看紀錄再決定要不要阻擋，是我對這個預設的讀法，文章沒有展開理由。

六個名稱裡有一個細節：JWT 那條寫的是 Base64url，其餘五條寫的是 Base64。名稱把兩種變體分開，表示規則針對不同位置的編碼各寫了一份，不是同一個樣式套在六個地方。JWT 與 WebAuthn 各自占一條，也說明這兩種認證資料在 Cloudflare 看來夠常見、夠容易成為入口，值得單獨處理。後面這句是我的讀法，文章沒有解釋為什麼要拆成六條。

規則之外，Cloudflare 自己列了三塊盲區：編碼或巢狀的資料、非 HTTP 協定、繞過 Cloudflare 的流量。這三塊在實務上都不遠。照 Cloudflare 的說法，繞過它的流量它看不到，服務之間的內部呼叫通常屬於這一類，這是我的補充。至於編碼或巢狀的資料，一層 Base64 外面再包一層編碼，規則看到的就不是畸形的 Base64；這是我對這個詞的舉例，文章沒有給具體案例。

Business 與 Enterprise 客戶另有一層 WAF attack score，Cloudflare 稱它是機器學習層；Enterprise 的運算式範例是 cf.waf.score.rce le 20。這是規則之外的另一道線，我沒有展開分數的算法。文章同時寫明：WAF 是額外一層，不取代補丁。

讀這一節要記得出處是 Cloudflare 自己的產品文章，內容是它的規則怎麼用。有意思的是，同一篇文章明白寫出 WAF 不是補丁的替代品，連自家規則都先劃出界線。這對讀者的用處很直接：把六條規則留在 Log，看一陣子紀錄，是在補丁完成之前多一份可見性，並不是已經修好。

Log 與 Block 之間的取捨，來源只給了方向，沒有給判準。規則比對的是畸形的 Base64，而六個位置裡，Header、Query Value、Body Value 都是任何應用都可能自己放進去編碼資料的地方；合理的推測是，真實流量裡一定有些請求長得像畸形 Base64 卻不是攻擊，切到 Block 之前先在 Log 看過，是為了找出這些誤傷。這個推測有道理，卻沒有數據支撐：文章沒有說誤報率，我也沒有看到任何客戶的實測。

mccue 的反方向論點：這反而是該用 Java 的理由

三份材料裡立場最不同的是 mccue 的文章。他在事發不到一天時動筆，先給旗標，然後提出一個乍看反直覺的主張：Java4Shell 沒有動搖他的結論，在意安全時 Java 仍是好選擇。他的理由有三條。

第一條是原生程式碼被關在籠子裡。他的原話是「Normal Java programs are memory safe.」，接著說如果某個函式庫想呼叫原生程式碼，你會先拿到警告，之後是硬錯誤，除非使用者針對那個函式庫明確加上 --enable-native-access=the.specific.library。他的意思是，你可以列出自己的專案究竟讓哪些函式庫碰了原生程式碼，曝險面是看得見的。

第二條是對照。他寫 C# 允許任何相依套件寫內嵌組合語言（「which lets any dependency write assembly inline」），並用另一句話描述其他生態：「everything speaks C and lets any one of your dependencies bring along native code.」在我讀到的摘錄裡，這句話對應的是 Python、JavaScript、Go 這一組。他也順手說 Kotlin、Clojure、JRuby 等 JVM 語言享有大部分同樣的好處。

這三條合在一起，是一個關於「曝險面誰來控制」的論證，不是關於「Java 沒有洞」的論證。他把原生程式碼當成記憶體安全的主要破口，把相依套件當成破口進來的管道，再說 Java 在管道口裝了閘門。這個論證有自己的邏輯：如果多數記憶體損壞漏洞確實從原生程式碼進來，管住原生程式碼就管住了多數風險。「多數漏洞從哪進來」這個前提，他的文章沒有給統計，三份材料也沒有。

現在回到九月的那個 PR。出問題的路徑不是 Java 程式碼：PR 的修法是「early-return to Java」，Cloudflare 的緩解旗標關掉的是「hardware-accelerated」的 Base64 實作。換句話說，漏洞在 JVM 自己的硬體加速實作裡，不在某個相依套件帶進來的原生函式庫。mccue 的第一條論點管的是後者，--enable-native-access 針對的是函式庫，管不到 JVM 內建的加速路徑。合理的推測是，他的論點在「相依套件帶來的原生程式碼」這個範圍裡成立，而 Java4Shell 落在範圍之外。他的文章也沒有宣稱 Java 自己不會有記憶體損壞，說的只是一般的 Java 程式是記憶體安全的。

這個張力不需要裁判。兩邊回答的是不同的問題：mccue 問的是我的相依套件能帶進多少原生程式碼，Java4Shell 問的是我跑的 runtime 自己有沒有洞。對第一個問題，Java 的答案確實比較好控制；對第二個，答案是更新與重啟，跟用什麼語言沒有直接關係，任何語言的 runtime 都可能出現這種洞。最後這句是推論，不是三份材料的結論。

順著這個張力再看 Calif 的示範名單：Keycloak、Jira、Confluence、Kafka、Solr、Elasticsearch。這些產品我認得是 Java 應用，這是我的背景知識，Cloudflare 的摘錄沒有逐一標明。如果認得沒錯，那麼這份名單等於在說，漏洞影響的是跑在 JVM 上的主流服務，而它們的相依套件有沒有碰原生程式碼，在這個漏洞面前不是重點。對 mccue 的論點來說，這不是反證，只是提醒範圍：他論證的是依賴關係的曝險，漏洞發生在依賴關係的外面。

還有一個誰也沒回答的問題。如果 PR #32781 描述的就是 Java4Shell，那麼從 9 月提出到 11 月關閉的這 56 天，發生了什麼？PR 頁面只留下兩件事：9 月 11 日被 JVM crash issue 引用，11 月 19 日有人問為什麼關掉。這個問題無法從三份材料推出答案，只能等 OpenJDK 那邊補上說明。

把目前讀到的東西分成已知與未知，大概是這個樣子。已知的是：CVE 編號與 9.2 的評分、披露與修補同在 11 月 17 日、觸發條件與硬體前提、兩個旗標、六條 Log 規則與三塊盲區、PR 的日期與內容。未知的有五件：PR 與 CVE 是不是同一件事、Oracle 修補版的實際改法、PR 被關掉的原因、旗標的效能代價，以及除了 Cloudflare 對自家基礎設施的說法之外，有沒有真實世界的利用。
