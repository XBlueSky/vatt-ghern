GitHub 在 2026 年 10 月 28 日宣布 workflow lockfile 正式可用：YAML 繼續寫好讀的 tag，實際執行的 commit 另外記在 actions.lock。gslin 的評語很節制，他寫道「先前建議的防禦是鎖 hash 版本」，而 lockfile 帶來的是「主要是管理上會比較好讀」。

三種寫法放在同一份 workflow 裡，差別只在 uses: 後面那段字串：只寫 tag，寫完整的 commit SHA，或是寫 tag 再讓 workflow lockfile 記住它對應的 commit。三者擋下的事情不同，日常維護的負擔不同，審查升版 PR 時看到的畫面也不同。10 月 28 日的 GitHub changelog 標題是「GitHub Actions workflow lockfiles are generally available」，等於在原本的兩個選項旁邊放上第三個。

本文的機制說明以 GitHub 官方的兩份資料為準，一份是上述 changelog，一份是 docs 裡 enforce workflow lockfiles 那一頁。Hugo van Kemenade（以下稱 hugovk）的文章提供實際導入的步驟和 CI 設定，Gea-Suan Lin（以下稱 gslin）的短評提供判斷。這些來源都沒有給效能數字，也沒有給攻擊統計，所以下面只比較機制，不會出現假裝精確的百分比。

先把整張圖攤開。下表把三種做法放在同一組準則底下，格子裡標了出處；來源沒有談到的地方，我寫「來源未提」，不替它補答案。標了「推斷」的格子是我根據機制做的合理推測，不是來源的原話。

表裡的「來源未提」有幾格值得先說清楚。Dependabot 能不能替只寫 tag 或釘 SHA 的 workflow 升版，這幾份來源都沒有談，本文不判斷。composite action 內部怎麼被鎖，docs 那一頁沒有寫，後面的章節會回到這裡。

防護範圍：上游搬動 tag 的那一天

hugovk 開場先交代背景：Actions 是從 Git 取得的，所以一向的建議是把每個 action 釘到完整的 commit SHA，而不是 tag。理由是 tag 可以被搬到惡意程式碼，他舉的例子是 tj-actions/changed-files 那次攻擊。這一軸比的就是同一件事：上游搬動 tag 之後，你的 CI 跑的是哪一個 commit。

只寫 tag 的情況最單純。你可能審查過 v1 當時指向的 commit，但 workflow 裡沒有任何欄位記得你審查的是哪一個。tag 被搬走，下一次 workflow 啟動時取到的就是新的 commit，審查結果與實際執行的程式碼之間的連結就斷了。

釘完整 SHA 把連結縫上了。SHA 寫在 YAML 裡，指定的是一個確切的 commit，上游怎麼搬 tag 都不影響這一行。hugovk 記錄的先前建議就是釘完整 SHA，缺點要到後面兩軸才出現。

lockfile 走第三條路。YAML 裡留著 tag，tag 對應的 commit SHA 記在 .github/workflows/actions.lock。依 GitHub changelog 的描述，這個設計讓你保留好讀的 tag 與 branch 參照，同時讓 GitHub 執行你鎖定的那個確切 commit。

下面的圖把上游的動作變成開關。預設狀態是「上游把 tag 搬到另一個 commit」已打開，你可以直接看到哪一列的 CI 跑到了沒審查過的 commit。第二個開關對應 lockfile 自己的維護問題，圖下面的段落再談。

兩個開關各揭露一件事。打開第一個開關，只寫 tag 的那一列從 A 變成 B，另外兩列不動，也就是說 SHA pin 與 lockfile 在這個情境下結果相同。所以只問「tag 被搬了會怎樣」，lockfile 並沒有贏過 SHA pin。gslin 也沒有這樣主張，他先寫「先前建議的防禦是鎖 hash 版本」，接著把 lockfile 的好處歸在「主要是管理上會比較好讀」，重點放在管理面。

第二個開關是 lockfile 帶進來的新失敗模式。hugovk 寫到，任何新的 workflow 檔或變更過的 action，都要重新執行 gh actions-lock，CI 會標出這件事。docs 的描述一致：gh actions-lock --verify 在 lockfile 過期時以錯誤結束，可以當作 pull request 的 required check。合理的推測是，SHA pin 的失敗多半是人寫錯或忘了換，lockfile 則多出一種「YAML 與 lockfile 不同步」，不過這種狀況有指令能機器檢查。

維護成本：升版那天誰去動 hash

只寫 tag 的維護成本最低，升版就是改一個版號，但它什麼都沒固定，這個低成本也就談不上優點。SHA pin 的成本結構相反。合理的推測是 SHA pin 難讀也難維護：一串 hash 換成另一串，光看字面看不出新舊差在哪個版本。這是本文的觀察，hugovk 並沒有列出 SHA pin 的缺點。

lockfile 的成本分成一次性的導入與持續性的同步。導入只有三步，都寫在 hugovk 的文章裡：用 gh extension install github/gh-actions-lock 裝擴充套件，在 repo 裡執行 gh actions-lock，再 commit 被改動的 workflow 與新產生的 lockfile。執行時它會把原本的 SHA pin 改寫成 actions/checkout@v7.0.1 這種可讀的 tag，同時建立 .github/workflows/actions.lock。

持續性的同步交給升版工具。hugovk 指出 Renovate 與 Dependabot 都支援 lockfile，定期的相依更新會連 lockfile 一起更新。GitHub changelog 對 Dependabot 的描述更具體：已導入 lockfile 的 workflow 有 action 版本更新時，Dependabot 會在同一個 PR 裡重新產生對應的 lockfile 項目，不需要額外設定。

這裡有一條容易漏看的邊界，寫在 docs 裡：Dependabot 不會把還沒有 lockfile 項目的 workflow 納入，docs 的原句是「Dependabot will not onboard a workflow that has no lockfile entries yet」。它維持已有的覆蓋範圍，不擴大覆蓋範圍。所以第一次導入一定是人工作業，而且要逐個 workflow 確認它真的進了 lockfile。

docs 在談強制力時有一句前提：「Enforcement only works if lockfiles stay up to date.」換句話說，lockfile 擋得住的是「記錄下來的 commit」，記錄本身過期，就沒有東西可以擋。這也是為什麼前面提到的 --verify job 不是選配。同一頁還有另一句更直接的話：「A lockfile is only a security control if someone reads the diff.」升版 PR 自動化之後，diff 會源源不絕地出現，合理的推測是真正的成本落在審查者的注意力，而不是工具的設定。機器人負責把 PR 開好，commit 的對應有沒有被人看過，要靠 CODEOWNERS 與核准規則把人拉進來。

changelog 也提到可以逐步導入：團隊一次導入一個 workflow，已導入的 workflow 每個 dependency 都必須在 lockfile 裡，執行時 GitHub Actions 跑的就是記錄下來的 commit。如果一個 repo 有幾十個 workflow，這允許你分批處理。批次的順序是本文的建議，不是來源的：先處理權限最大、影響最廣的 workflow，例如會發佈套件或碰得到 secret 的那幾個。

同步機制自己也要維護。hugovk 把 GitHub 範例裡的 verify-lockfile.yml 改成現有 lint workflow 裡獨立的 lockfile job，跑在輕量的 ubuntu-slim runner 上，擴充套件釘在 v0.4.1，執行 gh actions-lock --verify，因為是獨立 job，所以和其他檢查平行跑。他也承認這個固定下來的擴充版本得手動更新，或之後自動化，他把這件事留待日後。合理的推測是，導入 lockfile 之後，你的 CI 多了一個要追版本的相依項：gh-actions-lock 擴充本身。

還有一個維護問題和工具無關。升版機器人只負責把新版本送到你面前，不負責判斷它能不能信。hugovk 建議搭配 dependency cooldowns，並連到 yossarian 談這件事的文章；來源裡沒有給細節，我只轉述建議。從 cooldown 這個名稱推斷，做法大概是讓新發布的版本先放一段時間再採用，這是推斷，細節請看他連結的原文。

可讀性與審查：升版 PR 的 diff 裡有什麼

可讀性是 gslin 認定 lockfile 的主要價值，他的原話是「主要是管理上會比較好讀」。具體的差別在 YAML：hugovk 的範例裡，gh actions-lock 把 hash 改回 tag，workflow 檔又看得到 actions/checkout@v7.0.1，commit 的對應關係則搬到另一個檔案。

lockfile 的內容，來源只描述到這個程度：每個 tag 對應的 commit SHA，加上 owner_id 與 repo_id；hugovk 提醒它是機器產生的，不該手改。owner_id 與 repo_id 的用途，來源沒有解釋，我不猜。

下面的圖把三種寫法並排：commit hash 住在哪個檔案，升版的 PR 會改到哪裡。lockfile 那一欄只列出來源提到的欄位，檔案格式是示意，不是 actions.lock 的實際內容。

審查面的差別在於哪個檔案會出現 hash 的變動。docs 有一句話把 commit SHA 的審查價值講得很直接：「A changed commit SHA, specifically, tells you the code your workflows run has changed.」對 SHA pin，這個訊號出現在 workflow 檔；對 lockfile，出現在 actions.lock。合理的推測是，lockfile 路線下 YAML 只剩版號變動，版號動了 commit 沒動、或 commit 動了版號沒動，這兩種狀況要看 lockfile 才分得出來，審查者得同時看兩個檔案。

docs 的建議是把 lockfile 加進 CODEOWNERS，並透過 ruleset 或 branch protection 要求 code owner 核准。這是 lockfile 路線多出來的審查控制：把「誰能改 commit 的對應」交給指定的審查者。至於 SHA pin 路線能不能用同樣的做法，來源沒有談，不過 CODEOWNERS 本身不綁 lockfile，合理的推測是可以對 workflow 目錄做同樣的設定。

linter 的相容性是另一個容易踩到的地方。hugovk 把 zizmor（GitHub Actions 的安全 linter）稱為「strongly recommended」，並指出 v1.32.0 之前的版本會建議 hash pinning，v1.32.0 是第一個支援 lockfile 的版本。他用 prek 跑 zizmor，在 .pre-commit-config.yaml 加上 zizmor-pre-commit hook，rev 設為 v1.32.0。合理的推測是，若你導入了 lockfile 卻沒升級 zizmor，舊版仍會依它的規則要求你改回 hash pin，兩個工具會互相拉扯。

沒涵蓋的部分：lockfile 不判斷依賴安全

GitHub 自己把界線寫在 changelog 裡：「Lockfiles help protect against unexpected dependency changes, but they don't determine whether a dependency is safe.」緊接著的建議是「Review dependencies before locking them.」lockfile 防的是之後的意外變動，不回答現在的內容可不可信。

這句話推得出一個時序問題。合理的推測是，如果你執行 gh actions-lock 的那一刻 tag 已經指向惡意 commit，lockfile 會忠實地把它鎖起來。這個限制對 SHA pin 同樣成立，所以表格最後幾列我把它標成推斷。實務上它把「鎖」排在「審查」之後，順序不能顛倒。

第二個邊界是涵蓋範圍。changelog 提到 lockfile 涵蓋 action 與它們的 transitive dependencies，docs 這一頁則沒有展開 composite action 的細節。兩處來源對傳遞相依只有這一句話，所以我不替你描述它在 composite action 內部具體怎麼鎖。要依賴這一點的話，先去 gh-actions-lock repo 的文件確認，或在測試 repo 跑一次 --verify 看結果。

第三個邊界是 reusable workflow。docs 明說，呼叫端 repo 的 lockfile 不涵蓋位於其他 repo 的被呼叫 workflow；如果被呼叫的 workflow 沒有在它自己的 repo 裡導入 lockfile，在政策啟用的情況下，呼叫端的執行會被擋下。換句話說，你自己 repo 的 lockfile 乾淨，並不保證整條呼叫鏈都被鎖住。

第四個邊界是強制力。沒有政策時，lockfile 只是團隊約定。Require lockfile policy 讓 enterprise、organization 與 repository 的管理員可以強制導入：被政策鎖定的 workflow 如果沒有導入 repo 的 lockfile，執行會被擋，連沒有 uses: 相依的 workflow 也一樣。Active 模式下，即使同一個 repo 的其他 workflow 已導入，沒導入的那個照擋。Evaluate 模式只在 GitHub Enterprise Cloud 提供，可以先用 Policy insights 看結果再切到 Active。docs 還說這個政策與 SHA 釘選政策是分開的，兩者可以同時啟用。

政策的檢查點也值得說清楚。docs 寫的是「The policy blocks a workflow run that has no valid lockfile.」被擋的是執行，不是推送或合併。合理的推測是，沒導入的 workflow 檔仍然可以合併進主分支，要到觸發的那一刻才失敗，這也解釋了 docs 為什麼反覆建議先開 Evaluate 模式、先看 Policy insights：先拿到會被擋的清單，比讓排程 workflow 在某天半夜失敗好。docs 的警告也是同一個方向，「Do not enable this policy in Active mode until you're confident you have systems in place」，意思是沒有準備好驗證與補救的機制之前，不要直接切到 Active。

第五個是方案與權限。changelog 列出的適用方案是 GitHub Enterprise Cloud、含資料落地的 Enterprise Cloud、Team 與 Free；我讀到的清單沒有列 GitHub Enterprise Server，如果你的 CI 跑在自架版本上，這點要自己向 GitHub 確認。權限方面，docs 說有 repository write access 就能建立 lockfile，不需要管理員權限。

把五個邊界和 SHA pin 對照，會發現大部分「不涵蓋」是重疊的：兩者都不判斷內容安全。lockfile 多出來的邊界，包括 reusable workflow、方案限制與同步問題，是它換回可讀性要付的代價；SHA pin 沒有這些，代價是 hash 難讀（本文推斷）。

下週能做的決定

先講本文的判斷，它和來源的結論是分開的：多數團隊現在的預設應該是 lockfile。理由有兩個，一是它保留了 SHA pin 在 tag 被搬時的保護（互動圖的前兩列已經示範），二是把可讀性拿了回來，加上 Dependabot 與 Renovate 都支援。這個判斷的前提，是你願意接受兩項新的維護：CI 裡的 --verify job，以及 gh-actions-lock 擴充的版本。

不是每個人都該立刻動。已經把完整 SHA 釘好、也有人在維護的 repo，在 tag 被搬的情境下保護範圍和 lockfile 相同。gslin 把 lockfile 的好處歸在管理面，這類 repo 的遷移理由就是可讀性，沒有急迫性，等下一次大規模升版再動即可。

如果你是 organization 或 enterprise 的管理員，要看的是強制力：用 Require lockfile policy 擋掉沒導入的 workflow。docs 提醒，啟用前要確認每個目標 workflow 都已導入，可以在每個 repo 跑 gh actions-lock --verify，或用 Policy insights。在 Enterprise Cloud 上，先開 Evaluate 模式觀察，再切到 Active，比直接上 Active 少一次全面擋下 CI 的風險。

docs 對管理員的導入順序講得很具體。第一句是「Run a pilot before enforcing this policy in all repositories.」第二句是「Scope the policy to specific repositories that have onboarded to lockfiles.」也就是先挑已經導入的 repo 當試點，政策範圍只畫在這些 repo 上，確認沒有誤擋之後再擴大。如果你的 workflow 會呼叫其他 repo 的 reusable workflow，docs 另有一句提醒：「If your workflows call reusable workflows from other repositories, confirm those source repositories are also onboarded.」這和前面談過的 reusable workflow 邊界是同一件事，只是從限制變成檢查清單上的一項。把它排進試點，是本文的建議：名單裡不只列自己的 repo，也要列被呼叫的來源 repo。

下面的選擇器把這些條件變成三個問題。預設答案是最常見的起點：現在只寫 tag、已經有自動升版機器人、不是管理員。換掉任何一個答案，建議就會跟著改。

不管選哪一條，順序都一樣：先審查，再鎖，再加 CI 驗證，最後才放給升版機器人。下面的清單把第一個星期可以逐項勾掉的動作排好，每一步的指令都來自 hugovk 的文章或 docs。

兩件事在來源裡還沒有答案。hugovk 把擴充版本的自動更新留待日後處理，傳遞相依怎麼被鎖，docs 也沒有細講。導入之後的第一個月，建議回頭檢查這兩點：擴充版本有沒有人在追，以及你用到的 composite action 是否真的出現在 lockfile 裡。

The call：多數團隊該把 workflow 導入 lockfile，並在 CI 加上 gh actions-lock --verify；已經釘好完整 SHA 的 repo 不急著遷移；不管走哪一條，lockfile 與 SHA pin 都只負責鎖住，不負責判斷安全，所以先審查，再鎖。
