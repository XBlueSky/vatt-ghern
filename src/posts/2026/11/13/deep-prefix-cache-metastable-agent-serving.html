burst 在第 20 分鐘就結束了，之後的到達率回到伺服器本來應付得來的水準，命中率卻停在 0.1 上下，再也沒有回來。同一批 session、同一台 vLLM，沒被注入 burst 的對照組全程健康。

burst 過去了，快取沒有回來

這篇論文是 Wen Huang 與 Jack Liu 的〈Bursts That Outlast Themselves〉，2026 年 11 月 10 日上 arXiv（2611.13412），稿件標示為 preprint。它描述的現象：用 prefix caching 服務 coding agent 這類長對話 session 時，一小段額外流量會把 vLLM 推進一個劣化狀態，流量退了，狀態還在。我們要拆的問題是「為什麼 burst 的效果比 burst 本身活得久」。

同一批 session，burst 之後只有一邊沒有回來

論文用成對實驗把「歷史」這個變數單獨抽出來。一對 run 共用同一條基底到達流：每個基底 session 在同一時刻到達，身分與形狀完全相同。burst 那一組多收一條獨立的額外流，從第 15 分鐘開始、持續 5 分鐘，速率是 1.5λ，總到達率因此變成 2.5 倍。第 20 分鐘之後，兩組的 offered load 一模一樣。每個 run 跑 90 分鐘，基底 λ 是 0.035 sessions/s，約為 cache-warm 容量的 70%。

主要設定是 Qwen3-8B 跑在單張 AMD MI300X 上的 vLLM 0.20，開啟 automatic prefix caching，KV pool 固定為 400K token。session 是合成的：共 25 輪，context 從 6K 長到 37K token，輪與輪之間的思考時間平均 5 秒。token 內容是隨機的，所以唯一的重用就是同一個 session 內，以及全體 session 共用的 system prompt。

burst 期間命中率下滑，這在預期之內。出人意料的是 burst 結束之後：命中率沒有回升，停在約 0.1，每秒完成的 turn 數掉到約 0.4，backlog 一路長到 run 結束時超過 100 個 session。沒有 burst 的孿生 run 則在整整 90 分鐘裡維持 0.94 到 0.95 的命中率，系統裡大約 10 個 session。下圖是論文 Table 2 的十二對 run，每一列是同一個 seed。

統計結果寫在論文正文：十二對之中，9 對只有 burst 那組持續退化，只有對照組退化的是 0 對，2 對兩邊都退化，1 對兩邊都沒事。論文用雙尾 sign test 檢定不一致的對子，p = 0.00391。

進得去、出不來，這個不對稱是整件事的核心。要解釋它，先得排除最順手的答案。

假說一：這只是過載，等流量退了就會消化完

burst 是額外負載，額外負載造成佇列，佇列會在負載回落之後被消化掉。這是排隊理論的標準劇本。如果這個解釋成立，劣化的 run 只是還在排隊，給它夠長的時間就會回到健康。

論文做了兩個對照來檢驗，都指向這個解釋站不住。

第一個對照回頭看孿生組。十二對裡的對照組在同樣的基底負載下有十組沒有退化；更早的一次掃描中，λ=0.04 沒有 burst 的 10 個 run 全部健康了 30 分鐘。基底負載本身並沒有超過容量，劣化不是負載水準造成的。

第二個對照關掉 prefix caching。引擎在約 80% 的無快取容量下運轉，注入相同絕對量的 burst，也就是 5 分鐘內約 16 個額外 session。backlog 升到 17 到 43 個 session，然後下降：最後 30 分鐘裡，每個 run 的 backlog 都在縮小（或者本來就回到 burst 前的水準）。四個 run 裡兩個回到孿生組的水準，另外兩個還在以無快取引擎的慢速消化。論文把這個結果總結成一句話：沒有快取，就沒有第二個狀態可以掉進去，只有要追的進度。

這個對照是整個論證的支點。過載的特徵是負載一退就恢復，亞穩態的特徵是負載退了，系統留在另一個穩定點上。關掉快取之後，同樣的 burst 只造成過載；開著快取，同樣的 burst 造成亞穩態。差別只來自快取。

所以「只是過載」這個假說被否定了。額外負載的殘餘已經排除，剩下的是系統自己的某個狀態。那麼，會不會是 burst 太大，把引擎裡的什麼東西打壞了？

假說二：burst 太大，打壞了某個東西

如果存在一個臨界大小，超過就壞、沒超過就沒事，那這個現象就是一個簡單的門檻問題：把容量留夠，別讓 burst 超過門檻即可。論文的資料不支持這麼乾淨的畫面。

再者，觸發源不一定是流量。論文試了一種 prefix cache flush 並搶佔執行中的請求，這正是 replica 重新啟動或權重更新時發生的事。在 λ=0.04 且沒有任何額外負載的情況下，5 個 run 裡有 1 個持續退化，崩掉的那個 run 恰好是快取重建期間到達的 session 最多的一個。論文在討論裡把這幾種情形歸在一起：由一次 burst、一次重新啟動、一串運氣不好的到達這類罕見組合決定伺服器何時崩潰，平均負載反而不是主角。

這些線索合起來，指向同一個圖像：門檻會隨 session 狀態、觸發類型、引擎和池大小移動，但門檻兩側各有一個能自我維持的狀態。這就是論文引用 Bronson 等人所用的亞穩態（metastable failure）定義：觸發源把系統推進一個劣化狀態，一個持續性的效應讓它在觸發源消失後仍留在那裡。下一個問題因此變得具體：這個「持續性的效應」是什麼？

真正的原因：在場的 session 就是 working set，而它和快取共用同一個池

答案要從 agent session 的結構講起。聊天流量是開迴路的：使用者什麼時候來，和伺服器快不快無關。agent session 是閉迴路的：模型發出 tool call，工具跑完，輸出附加到對話，整段長出來的 context 再送回模型，一個 turn 要等上一個 turn 被服務完才能發出。論文用 Little's law 寫成 N = λ·T·(Z+R)：系統內同時存在的 session 數，等於 session 到達率、每個 session 的 turn 數，與思考時間加回應時間的乘積。R 是伺服器的回應時間，所以伺服器變慢，在場的 session 就變多。

第二個事實是命中與未命中的成本差。命中時，只需要對新增的約一千個 token 做 prefill；未命中時，要重算 10 到 40K token 的整段 context。論文在 MI300X 上量到，Qwen3-8B 對 20 到 36K token 序列的 cold prefill 約為每秒 10 到 13K token。一個 context 21.6K 的中段 turn，未命中約花 2 秒的 prefill，命中約 0.15 秒。

第三個事實是池的共用。論文歸納出三個性質，合起來把迴路閉上，下面這張圖把它畫成一個環。

第一個性質：積壓就是 working set。閉迴路裡，系統內的活躍 session 數 N 由 λ·T·(Z+R) 決定，R 變大就直接讓必須同時留在池裡的 prefix 變多。第二個性質：未命中的懲罰隨 session 年齡成長，因為未命中要重算整段 context，而 context 每一輪都在變長，所以退化區裡的 session 越老，每次 miss 越貴。第三個性質：執行中的請求與閒置 session 的快取 prefix 共用同一個池，跑的請求越多，留給閒置 prefix 的空間越少。

把這三點套回成對實驗的數字，劣化狀態長什麼樣子就看得清楚了。在持續退化的 8B run 裡，最後 10 分鐘的已完成 turn 有 99.6% 到 100% 的 prompt 不到一半被快取，token 加權命中率 0.10 到 0.12，其實就是那段共用的 system prompt。引擎不是停擺，而是在做工：16 到 32 個請求同時在跑，KV 使用率 83% 到 100%，搶佔很少見（90 分鐘的 run 裡 23 到 37 次）。論文因此下結論，流失的 throughput 來自重算，不是搶佔造成的 thrashing。每秒 0.35 到 0.46 個 turn 的 throughput，正好等於同一個引擎關掉 prefix caching 時在相近負載下的 0.33 到 0.43。劣化狀態，就是一個仍然付著快取成本的無快取引擎。

這裡有一處論文自己標明的邊界：每個 session 的 prefix 在下一輪之前被它的同伴逐出，這一點是推斷，不是量測，因為引擎不輸出每個 block 的逐出事件。所有的證據是間接的：命中率崩落、重算 token 上升、需求越過池。論文把這個現象類比為 Denning 在 1968 年描述的 working-set thrashing：活躍程式的工作集超過記憶體時，系統就陷入 thrashing。

到這裡，進得去的原因有了：在場 session 一旦超過池的容量，LRU 就在每個 session 的下一輪前把它的 prefix 逐出。出不來的原因則來自一個可以計算的排空條件。如果每個 turn 都 miss，服務完一個 session 要花 S 個 engine 秒，劣化狀態只有在 λ 小於 1/S 時才排得空。論文在關掉快取的 run 上獨立量出 cold turn 的成本，推得 1/S 約為 0.013 sessions/s，遠低於觀察到崩潰時的負載。論文強調這只是必要條件，不是邊界預測。

先自己動手摸一下這個迴圈。下面的模擬器是一個玩具模型，只保留論文機制裡最必要的幾件事：閉迴路的 session、單一 FIFO 引擎、LRU 的 prefix 池，以及未命中要重算整段 context，但不重現論文的數字。

崩落之後，試試只擋新 session 與 budgeter 兩種策略，比較需求條回到中線以下的速度。依模型的設計，需求條越過中線（需求等於池）之後，命中率線會快速掉下去，burst 結束以後也不容易自己爬回來。

實測的排空邊界也在論文裡。他們先讓伺服器崩潰，再把到達率降下來，觀察估計的剩餘 cold work 在一小時內往哪個方向走。λ=0.006 時，剩餘 cold work 每小時約減少 900 engine 秒（一個 seed）；λ=0.010 時大致持平（三個 seed，每小時從減少 67 到增加 132）；λ=0.014 時增加（兩個 seed，每小時增加 604 與 663）；λ=0.018 時繼續增加，一個 seed 的在場 session 數在觀察的那一小時內從 53 長到 100。所以損益平衡落在 0.010 到 0.014 之間，把模型估的 0.013 夾在中間。

把這張圖和前面的成對實驗放在一起讀，就能看出「出不來」有多徹底。成對實驗與恢復實驗的基底 λ 是 0.035 與 0.04，都遠高於 0.010 到 0.014 這個損益平衡區間。一旦進入全 miss 的狀態，伺服器做完工作的速度遠遠趕不上到達的速度，所以這個狀態不會自己排空。論文也直接報告：觀察期間（2 小時，兩個未跑完的 run 為 80 分鐘）沒有任何一個 run 的快取自己重建起來。

怎麼出來：停放 session，而不是擋新流量

崩潰的伺服器有兩個問題：太多 session 同時想要快取，以及每個 session 的每一輪都 miss。擋新流量只處理第一個問題的增量。系統裡已經有的 session 還在對一個放不下它們的池不斷輪轉，每個都要把剩下的輪數（全部是 miss）做完，在場人口才會掉到 N* 以下，論文估計這要花幾十分鐘。

更快的路是讓 gateway 在 turn 邊界也停放一部分已入場的 session。被停放的 session 不再發出 turn，它的 prefix 就被允許逐出，剩下的 session 於是重新開始命中，throughput 恢復，佇列排空。論文把所有控制器都實作在 gateway，不改引擎，用同一個執行器，只有設定上限的方式不同。每個 session 的每一輪發出前，gateway 決定它是否可以繼續；不能繼續就在這個 turn 邊界停放，排進 FIFO 佇列；重新入場時優先處理被停放的 session，再處理新 session，一個 session 重新入場通常要付一次 miss。

比較的五種做法如下。budgeter 以所有已入場 session 的常駐 KV 需求（context 加輸出預算）為準，需求超過池的 0.95 就停放，降到 0.75 以下才重新入場。session cap 加停放，是固定的 session 數上限，超過就停放，數字來自健康負載下的實測。自適應 cap 的上限由池容量除以每 session 需求的 EWMA 決定。延遲 AIMD 加停放，用中位延遲驅動並發度，是論文稱為簡化版的 CONCUR 風格控制。最後是只擋新 session 的 admission-only cap，已入場的 session 從不停放。

結果相當一邊倒。限定在 7 個每組都崩潰、起點相近的 seed 上：budgeter 在 5 分鐘內全部恢復，session cap 在 6 分鐘內全部恢復，延遲 AIMD 恢復了 7 個裡的 5 個（14 到 25 分鐘之後），只擋新 session 的 cap 恢復 1 個，不控制的一個也沒有。budgeter 與 session cap 各自對 admission-only 的比較是 7/7 對 1/7（雙尾 exact paired p=0.031）。放寬到全部 8 個崩潰的 run，admission-only 恢復了 2 個，而且是在 21 到 23 分鐘之後，另外 4 個到 run 結束命中率都低於 0.1。摘要裡 1 of 7 的數字指的就是這一組。

兩個「停放」的做法勝過一個「只擋」的做法，是因為只有停放能直接縮小在場人口。論文在 Related Work 裡把這件事連回 Denning：working set 超過記憶體就 thrashing，解法是 load control，把一些程式停掉直到其餘的放得進去。

代價也要講清楚。停放會讓一些 session 變慢，換取整體 throughput：在崩潰的 8B run 上，控制開始後 20 分鐘內到達的 session，從到達到完成的中位數，budgeter 是 11.6 分鐘（p90 為 16.9），session cap 是 12.3 分鐘（p90 為 15.6），而從來沒崩潰的未控制伺服器是 3.8 分鐘。而且控制只是還給你引擎的效率，不替你變出容量。在 λ=0.025 的 32B 實驗裡，即使 budgeter 與自適應 cap 讓命中率在每個崩潰的 run 都回到 0.92 到 0.97 或 0.86 到 0.93，佇列最後還是沒有排空，因為這個 trace 的長期到達速度略高於 cache-warm 引擎的完成速度：每分鐘 1.5 到 1.6 個到達對 0.7 到 1.3 個完成。論文的結論是，排空 backlog 需要額外容量或減載。

放到你自己的 serving stack 上

論文自己列了威脅有效性的幾條，先看這些，才知道哪些結論可以帶回去。合成 session 用的是隨機 token；trace 重放只保留長度與時間，不保留內容，也不執行 agent。實驗只用一種 GPU、一個 replica，且是有限的時間範圍，沒有路由、autoscaling、client retry 或正式環境的證據。論文也指出，正式環境的 context 更長（TraceLab 上每次呼叫的中位數超過 100K），對固定大小的池來說會降低 N*，並提高 miss 的代價；我在論文裡沒有看到他們量測這個效應，這一點只能當作我的讀法。

在這些限制之內，論文對維運的討論有三點可以直接使用。第一，這個狀態很容易被誤診：GPU 使用率維持高檔，延遲告警響起，而等待或節流新流量很少把快取帶回來。第二，直接識別它的是兩個量：agent 流量的 prefix 命中率，以及系統內 session 數相對於 KV 池能容納的數量。第三，replica 重新啟動與權重更新本身就是觸發源：快取重建的期間要逐步放量，而不是一次把流量全部放進來。

下面幾點是從論文推出來的，不是論文的結論，所以只能當作推測。合理的推測是，如果你的 gateway 已經知道每個 session 的 context 長度，那麼在 turn 邊界用常駐 KV 需求做停放，所需的資訊你大概已經有了，成本主要在實作 FIFO 佇列與重新入場的規則。合理的推測也包括：把命中率與「在場需求除以池」這兩條曲線放上儀表板，比再多一條 GPU 使用率更能提早看見這個迴圈開始轉。

最後是一個該對自己的環境做的檢查。論文的做法本身就是一個便宜的測試模板：用同一條到達流重放兩次，其中一次額外注入一段 burst，再看 burst 結束很久以後，命中率與 backlog 是否回到孿生組的水準。合理的推測是，如果沒回來，你的 stack 上就有這個亞穩態，該補的是 load control，只加容量不夠。

Take-away：下次看到「流量退了、延遲沒退」，先查命中率與在場 session 相對 KV 池的需求比值，確認是亞穩態再動手，處置要作用在已入場的 session 上，只擋新流量救不回來。
