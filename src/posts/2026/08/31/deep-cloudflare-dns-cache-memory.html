把 Rust 裡最理所當然的一個型別選擇拿掉——Vec 的 capacity 欄位——沒有改動任何一行查詢邏輯，每個欄位卻少了 8 bytes，一筆 DNS 快取記錄合計少了 64 bytes。五個這樣的決定疊在一起，Cloudflare 從 1.1.1.1 背後的快取拿回了大約 100TB 記憶體。

Cloudflare 的 1.1.1.1 背後坐鎮的 DNS 快取平台叫 Big Pineapple，同時撐著超過 2500 億筆快取記錄，還要餵 Gateway DNS、DNS Firewall、AS112 等好幾個服務。在這個量級下，每筆記錄多浪費一個 byte，全機隊就多耗 250GB——這句話決定了整篇文章的優化尺度：不是重寫演算法，是把一筆記錄的記憶體佈局，一個欄位一個欄位地摳出來。五項改動沒有一項碰查詢邏輯本身，全部發生在同一個地方：一筆快取記錄在記憶體裡實際長什麼樣子。

五項改動疊在一起，把單筆記錄從 953 bytes 壓到 420 bytes，減少 56%；連帶著記憶體分配量從 1.1 KB 掉到 461 bytes。基準測試裡，insert 吞吐量從每秒 625,000 筆提升到 893,000 筆，查詢延遲從 828 ns 降到 670 ns。這四個數字都是五項改動合併之後的基準測試結果——實際拆開看，每一項改動各自的份量並不平均，有的貢獻在 bytes 上直接看得到，有的要等到查詢延遲的分布圖才看得出差別。下面照著這五項改動的順序，一項一項拆開看它們各自換掉了什麼。

五項改動大致分兩種性質：前兩項是「真的沒用到，直接拿掉」——capacity 欄位、還有拆成三份的 list header，都是死重量；後三項則是拿別的東西去換空間——owner 欄位換來的是讀取時多一步反推，enum boxing 換來的是記憶體局部性打折，wire format 換來的是失去隨機索引。分兩種性質看，比較容易判斷哪些手法可以直接搬到別的系統上用。

把記憶體精算到位元組層級，某種程度上也是 Rust 這個語言本身鼓勵的做法——型別的記憶體佈局是語言規範的一部分，Vec 三個欄位、Box 兩個欄位、enum 撐到最大 variant，這些都不是隨編譯器心情決定的細節，而是寫在型別系統裡、工程師可以直接讀出來推算的規則。換一種語言，這種看著型別定義就能算出省了幾個 bytes 的精算方式，不見得能這麼順手。

capacity 欄位的浪費

DNS 回應裡的每一筆記錄，都要存好幾段長度不固定的資料——網域名稱、record data 的 bytes、TXT 記錄的字串內容。Rust 裡處理這類資料最直覺的型別是 Vec<T> 跟 String，兩者的記憶體佈局都一樣：一個指向堆上資料的指標、目前長度、還有預留成長空間的容量。Big Pineapple 一筆快取記錄裡，剛好有 8 個這樣的 Vec 或 String 欄位。

快取一旦寫入就不會再改——插入之後只有讀，沒有任何一次追加或截斷。capacity 欄位存在的唯一理由是支援日後的成長，一個唯讀的結構完全用不到它。換成 Box<[T]> 跟 Box<str>——固定大小、建立後不能再變長的切片型別，天生就不需要保留成長空間，記憶體佈局只剩指標跟長度兩個欄位。每個欄位省下 8 bytes，8 個欄位合計每筆省 64 bytes；乘上 2500 億筆記錄，換算超過 15TB。

capacity 欄位平常的用途是攤銷成長成本——往 Vec 裡塞新元素時，如果容量不夠，整塊資料會被搬到更大的記憶體區塊，多留一點容量就能少搬幾次。這個機制對「會持續寫入」的資料結構很划算，但快取條目一旦組好就定型，插入之後只剩讀，這個機制從頭到尾都用不到，留著它純粹是白付一筆固定成本。這一步改動的性質也值得記住：純粹是型別替換，Rust 的型別系統保證了正確性，查詢路徑、序列化邏輯、快取淘汰策略，沒有一行需要跟著改。後面幾項優化就沒有這麼乾脆——為了多省一點 bytes，幾乎都得拿別的東西去換。

String 在記憶體佈局上跟 Vec<u8> 幾乎一樣，只是多了「內容保證是合法 UTF-8」這個型別層級的約束，所以這裡的省法對 String 欄位一樣直接適用，不需要另外處理。

三個 list 合併成一個

一筆 DNS 回應裡通常分三段——answer、authority、additional，各自可能有零到多筆記錄。Big Pineapple 原本的作法很直覺：三個獨立的 list，各自存自己的指標跟長度。在 64 位元機器上，一個指標是 8 bytes，長度也是 8 bytes，三個 list header 合計要背 48 bytes，但道理上真正需要獨立存在的容器只有一個。

換個角度看，這三段記錄其實可以放進同一塊連續記憶體，只要知道 authority 從哪裡開始、additional 從哪裡開始就夠了。改法是留一個 list 存所有記錄，另外用兩個 offset 標記第二段跟第三段的起點。offset 不需要是完整的指標——一筆回應裡的記錄數量不會超過 65536，一個 u16（2 bytes）綽綽有餘。原本要拆掉的兩個 list header，各自要付 8-byte pointer 加 8-byte length，換成兩個 2-byte offset 之後，省下 28 bytes。

這個改動對讀取路徑的影響不大：查某一段記錄時，先照 offset 找到起點，讀到下一個 offset（或是陣列結尾）就是這一段的邊界；跟原本「直接讀三個獨立 list」比，多了一次加法運算，換來的是省掉兩份 list header。文章沒有直接把這 28 bytes 換算成機隊等級的數字，但用同一個 2500 億筆去估，量級大約是 7TB 出頭，跟第一項的 15TB 相差不遠。三個 section 合成一個 list 這個決定，某種意義上是在提醒工程師：資料結構的邊界不必跟著業務邏輯的分類走，只要讀取的時候找得到，物理上放在哪裡是另一回事。

owner 欄位可以不用存

Record 的定義裡有一個 owner 欄位，記著這筆記錄屬於哪個網域：

pub struct Record {
    owner: Option<Box<Name>>,
    class: Class,
    ttl: Ttl,
    rtype: Rtype,
    data: RecordData,
}

多數情況下，owner 跟一開始查詢的網域是同一個——查 example.com 的 A 記錄，回來的記錄 owner 也是 example.com，重複存一次是浪費。Cloudflare 把 owner 改成 Option<Box<Name>>：owner 是 None 時，組回應的時候直接拿快取 key（也就是查詢的網域）回填；owner 是 Some 時，才真的存了一份完整的名稱。什麼時候一定要存？CNAME 背後藏著的記錄——查 www.example.com 拿到一筆 CNAME 指到 cdn.example.net，後面那筆 A 記錄的 owner 是 cdn.example.net，不是原本查詢的 www.example.com，這時候 owner 就不能省。

owner 這個欄位有意思的地方在於，它的存在與否本身就是資訊——不是每筆記錄都需要一份自己的名稱，大多數時候，查詢用的 key 本身已經帶著答案。這種「能推導就不存」的想法，其實貫穿了好幾項優化：offset 是從查表就找得到，推導出段落邊界；owner 是從查詢 key 就等於答案，推導出網域名稱，兩者的邏輯是同一套。組回應的時候，owner 是 None 代表拿查詢的 key 直接當作這筆記錄的網域，這個反推只需要一次字串複製，不需要額外查表——複雜度沒有增加，只是把「存起來」的時間點換成「用的時候現算」。

反過來想，這個決定也劃出了一條清楚的界線：只要一筆記錄的 owner 跟快取 key 對不上，就必須老老實實存一份完整名稱，沒有妥協空間。可以合理推測：CNAME chain 越長，這種「owner 跟 key 不同」的記錄比例就越高——對只查單一網域、沒有轉址的服務，這一項優化幾乎是純賺；對背後掛了好幾層 CNAME 的服務，能省下來的比例會打折扣。

enum variant 的 padding 稅

record data 本身也是一個型別——不同 record type 的資料長得完全不一樣，Rust 裡最自然的表示法是一個 enum，每個 variant 對應一種 record type：A 記錄存 4 bytes 的 IPv4 位址，AAAA 記錄存 16 bytes 的 IPv6 位址，其他 record type 各自帶著長度不一的資料。enum 的記憶體佈局有個限制：整個 enum 的大小要撐得住最大的 variant，因為同一塊記憶體要能裝下任何一種可能的值。A 跟 AAAA 這兩種記錄佔了超過 80% 的流量，卻要背著跟最大 variant 一樣寬的空間——多數記錄因此要浪費超過 120 bytes 的 padding。

解法是把比較大的 variant 搬到堆上（boxing）——enum 本身只留一個 8-byte 的指標，真正的資料另外配置。對 A 跟 AAAA 這兩種佔多數流量的記錄，這一項改動省下 120 bytes。代價也很直接：沒 boxing 之前，一筆記錄裡的所有 enum 值擠在同一塊連續配置裡；boxing 之後，每個 boxed variant 各自散落在堆上不同的位置。上百萬筆快取記錄同時存在時，這些 boxed 資料在記憶體裡到處都是，查詢時撞上 cache miss 的機率跟著上升。單看任何一個代價都不到致命，但把 padding 跟這種記憶體局部性一起解決，才換到可量測的改善。

對寫程式的人來說，boxing 換來的實際差別是一次額外的指標解參照——讀一筆 A 記錄，本來欄位就在 struct 裡，boxing 之後要先跟著指標找到 heap 上的那一小塊 4 bytes，才能拿到真正的值。這個代價在單次查詢裡幾乎量不出來，但快取每秒要應付的查詢量本來就大，這種多一次跳轉的成本，會隨著查詢頻率一起放大。

拿捏這個取捨的關鍵，其實是流量的分布——如果 A、AAAA 只佔一小部分流量，boxing 換來的收益有限；正因為這兩種記錄佔了超過 80%，boxing 才划算：省下來的 padding 乘上的是絕大多數記錄，局部性變差的代價卻只發生在原本就要付出的那一次記憶體存取上。

record data 直接存 wire format

前四項優化都還停留在「怎麼把 parse 過的資料存得更省」；第五項換了一個更激進的角度：乾脆不要 parse。record data 不再是一串 enum variant，而是直接存 DNS wire format 的原始 bytes——一個 Box<[u8]>，裡面按順序塞著每一筆記錄，每筆前面加一個 2-byte 的長度前綴標出邊界。

好處有兩層。第一，enum 的 per-variant overhead——tag、對齊、padding——整個消失，因為根本沒有 enum 這個結構要維護。第二，資料變成連續排列的 bytes，對 CPU cache 更友善——大多數 record type 可以直接從 buffer 複製出去，不用再一個欄位一個欄位序列化。這一項改動單獨拿出來量，在基準測試裡把查詢延遲壓低 5%、插入吞吐拉高 13%。代價是失去隨機索引能力——要拿到 buffer 裡的第 N 筆記錄，沒有捷徑，得從頭照著長度前綴一筆一筆跳過去，直到跳到目標位置為止。

這一步跟前四項的差別在於位置——前面四項都還是先 parse 出型別化的資料，再想辦法把型別存得緊一點；這一步乾脆把 parse 這個動作往後挪，挪到真正要用到某筆記錄的那一刻，快取本身只負責存 bytes。少了一層型別，也就少了一層轉換成本，代價是查詢端要多做一點照長度前綴掃過去的工作。這個 2-byte 長度前綴的角色，跟 offset 那一項用的邏輯很像——不是省一個指標，而是用「讀的時候順著算」取代「存的時候先分好」，兩項改動骨子裡是同一種取捨，只是換了套用的位置。

循序掃描聽起來像是退步，但可以合理推測，快取查詢原本就不是「隨機挑一筆」——通常是拿到一筆 DNS 回應之後，把裡面所有 answer、authority、additional 記錄一次性讀出來組回應，本來就是整段整段地處理，不是單獨挑某一筆出來看。若真是如此，失去隨機索引能力，換掉的剛好是這個結構裡原本就用不到的能力。

五項改動從 2026 年 5 月 18 日開始上線，7 月 6 日全部推完。上線後，生產環境量到的降幅方向一致，但幅度比基準測試小——按 Cloudflare 的說明，resident memory 除了快取本身，還涵蓋了行程裡其他所有資料：

p99 是相對少數用量特別大的 instance，p90 涵蓋了更大多數的機器；兩個數字幾乎同幅度下降（-43% 與 -42%），說明這批優化不是只在最極端的情況才有感，而是對大多數機器都普遍有效。機隊層級加總，五項改動共省下大約 100TB 記憶體，等於不用再添 130 台 Gen 13 伺服器的記憶體容量。

五項改動對 insert 的影響看起來比對 lookup 更大——插入時要把整筆記錄組裝進記憶體，牽涉到的欄位比單純讀取一筆記錄要多，吞吐的改善幅度或許因此比延遲更明顯，但文章本身沒有進一步拆解兩者的關係，這裡只能點出這個現象，不下結論。

換一個角度盤點這五項改動，會看到另一條線索：每一項省下來的 bytes，幾乎都對應著讓出一個能力。Box<[T]> 讓出的是隨插隨長的彈性；offset 讓出的是三個 section 各自獨立定位的直覺；owner 省略讓出的是欄位永遠有值這個簡單假設；enum boxing 讓出的是記憶體局部性；wire format 讓出的則是隨機索引能力，只能照順序掃過去。這條線索比單純數 bytes 更值得記住——省記憶體從來不是免費的，問題只是這次省下來的，剛好都是快取這個場景真正用不到的能力。

多數團隊面對記憶體吃緊，第一反應是加機器；這篇文章示範的是另一條路——先把資料結構榨乾，再談要不要加硬體。兩條路不衝突，但榨乾資料結構這件事，往往比想像中更值得先做一次，因為省下來的比例是乘上全機隊的，回收得比單一台機器換算的直覺快很多。

這五個問題不是 DNS 快取獨有的——任何長駐記憶體、條目數量夠大的資料結構，都可以照著問一輪：欄位真的需要成長能力嗎？平行的容器能不能合併、用 offset 取代指標？有沒有欄位其實可以在讀取時反推出來？enum variant 的大小差異夠不夠大，值得 boxing 嗎？資料真的需要提前 parse 好，還是存原始格式、用的時候再 parse 就夠？合理的推測是，下一輪要再擠出下一個 100TB，大概不會再有這麼多可以直接拿掉的欄位，多半得從資料結構本身的選擇，而不是型別的包裝方式，重新想一次。

回頭看最開頭那個例子——拿掉 capacity 欄位——之所以適合放在開場，是因為它最乾脆：一行型別宣告換掉，沒有任何後續效應。後面四項都要多想一層「這樣做要付出什麼」，這也是為什麼整篇文章讀下來，會覺得省記憶體這件事，越到後面選擇越少、代價越清楚。

換回來的容量：一個快取系統能撐多少條目，過去多半靠加機器解決；把單筆記錄的記憶體佈局重新設計一輪之後，同一批硬體能撐住的條目數量直接往上跳了一截——機隊層級省下的 100TB，換算下來等於不用再添 130 台 Gen 13 伺服器的記憶體。
