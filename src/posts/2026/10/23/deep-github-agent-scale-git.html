一筆寫入要等五個 replica 裡最慢的那個回應，而其中有的已經在 Azure，最忙的 repository 又偏偏卡在一趟 25ms 的往返上。這時該縮短的是往返，還是需要往返的寫入有多少筆？

GitHub 工程部落格在 2026 年 10 月 21 日發表「The bridge to agent-scale Git infrastructure」，作者是 Eleanor White 與 Victoria Dye。文章講的是 GitHub 怎麼在服務不中斷的前提下改寫 Git 儲存層：資料先搬，架構後換。搬的部分已經接近完成，文章說他們把 99.99999% 的 repository 複製了一份到 Azure；沒搬完的是平台上最忙的那批，被一件事擋住，就是一趟 25ms 的往返。換的部分有兩步，一是把 quorum 的範圍從整個 repository 縮到單一 reference，二是讓 object storage 以 virtual replica 的身分加入，讀取因此可以脫離寫入各自擴充。下面先看起點的寫入路徑為什麼慢，再依序看鎖、寫入端的 virtual replica、讀取端的 virtual replica 各拆掉哪一段等待，最後把三個零件接回同一條路上。

五份副本、一把涵蓋整個 repository 的鎖

先看起點。文章說，大多數 repository 有五個 replica，用來在持久性、可用性與擴充之間取平衡：「Most repositories have five replicas to balance durability, availability, and scale.」每個 replica 都持有 repository 的完整副本（「replicas that each hold a full copy of the repository」）。遷移的做法是把其中一部分副本放到 Azure。第一份副本在 2025 年 8 月落在 Azure 的 Central US 區域；文章寫現在大多數 repository 的五個 replica 裡有兩個在 Azure，Azure 服務約一半的 Git 流量。

為什麼資料要先搬？文章的取捨寫得很直接：要把工作排好順序，「move the data first, then evolve the architecture once it arrived」。我讀到的理由偏向風險與容量，也就是在成長持續、容量吃緊的時候，儲存和代管不適合同時換。搬遷期間的流量規則只有一句：「During the migration, traffic follows the data.」每多一個 replica 搬到 Azure，能由 Azure 服務的流量比例就跟著上升。

搬完的結果，文章用一句話形容：99.99999% 的 Git repository「began living in two places at once」，同時存在兩個地方。合理的推測是，這就是後面所有架構改動的前提。quorum 的成員分在兩個區域，寫入才會碰到跨區的往返，鎖與 quorum 的設計也才從單機房內的取捨，變成要把跨區延遲算進去的取捨。

這個搬法有一個好處：每一份副本都是完整副本，所以一個 replica 搬到 Azure，就多一個能就近服務流量的地方，不必等整個 repository 重新設計。流量跟著資料走，意味著遷移的進度可以用流量比例來讀：兩個 replica 在 Azure，約一半的 Git 流量由 Azure 服務。相對地，沒搬完的部分之所以顯眼，是因為它們不是隨機的零頭，而是平台上最忙的那批 repository，剩下 0.00001% 的數量很少，承載的壓力卻不小。文章把它們留在後面處理，等於承認這一步不能只靠複製資料：複製已經做完的部分，剩下的得靠改變寫入的做法。

搬完之後架構才開始動，起點的寫入路徑有兩個性質。第一個是 quorum 的行為：文章說 Spokes 的 quorum 只需要多數就能 commit 一筆寫入，卻會等每個健康的 replica 回應。五個 replica 的多數是三個。第二個是鎖的範圍：每筆寫入持有整個 repository 的鎖，直到它 commit（「each write holds a repository-wide lock until it commits」）。兩個性質疊在一起，文章的結論是「the slowest healthy replica sets the latency of every write」，最慢的那個健康 replica 決定每一筆寫入的延遲。

把這兩個性質分開看，各有各的成本。只等多數的話，一筆寫入的延遲原本可以由第三快的 replica 決定；多等的那一步讓所有健康的 replica 都跟上，代價落在尾端。鎖的範圍是另一回事，它決定的不是單筆寫入要等多久，而是有多少筆不相干的寫入得跟著等。前者拉長單筆延遲，後者把單筆延遲放大成整個 repository 的吞吐上限。理解後面兩步改動各自針對什麼，這個拆法很有用：縮小 quorum 範圍針對鎖，把 object storage 拉進 quorum 則改動寫入確認的條件。

這也說明 25ms 為什麼是問題。文章把還沒完成遷移的 repository 描述成平台上最忙的那批，它們被一件事擋住，就是一趟 25ms 的往返。把前面兩個事實接起來：寫入要等最慢的健康 replica，鎖又涵蓋整個 repository，最忙的 repository 寫入最密，若每筆寫入都要付一趟跨區往返，合理的推測是它們最先撐不住。這也是為什麼文章接下來不去縮短那 25ms，而是動寫入路徑本身：往返的長度是機房之間的事，需要等往返的寫入有多少筆，才是儲存系統自己能改的事。

把 quorum 的範圍縮到單一 reference

文章的對策是改變 quorum 管轄的單位：「we’re changing the scope of the quorum from the whole repository to individual references.」過去 quorum 與鎖的單位都是 repository，現在縮到 reference。依據是 Git 本身的性質，文章寫的是「Git’s consistency requirements apply to each reference individually.」Git 對一致性的要求本來就是逐 reference 的，branch 這類 reference 各自有自己的歷史與移動規則，一個 reference 往前推進，不需要另一個 reference 同意。把鎖放大到整個 repository，等於多收了一份 Git 並沒有要求的保護。

上面的小工具把這個差別拆成最小版本。七筆寫入落在四個 reference 上：一把 repository 鎖下，它們排成七格；改成每個 reference 一條線，main 上的三筆仍然要依序，其他三條線各自跑完，總長度只剩三格。這個例子裡我刻意讓每筆耗時相同，也沒有放進網路與儲存，目的只是讓你看到「誰不需要等誰」。同一個 reference 上的寫入仍然排隊，這個限制在新架構裡沒有消失，只是不再外溢到不相干的 reference。

小工具裡七格對三格約是 2.3 倍，這個比值只是例題的幾何，和文章的 3 到 4 倍沒有對應關係。前者取決於我挑了幾筆寫入、落在哪幾個 reference，後者來自文章的測試流量。兩個數字放在一起只能說明同一件事：寫入越分散在不同 reference 上，縮小鎖範圍的收益越大。

文章給的量測是：在內部測試、貼近實際流量的條件下，寫入不同 reference 的情況，吞吐量一致高出 3 到 4 倍，延遲也更低。證據強度只有這一層：來源是 GitHub 自己的工程部落格，測試條件沒有更多細節，我沒有讀到獨立重現，也沒有讀到失敗情境的描述，所以這個倍數適合當成機制有效的訊號，不適合直接拿去和別的系統比較。倍數的前提是寫入落在不同 reference；照這個機制推算，流量若集中在同一個 reference，例如全部推同一條 main，好處會小很多。

還有一個必須講清楚的邊界：縮小 quorum 的範圍，並沒有改變 quorum 本身。文章後面承認「the quorum remains the bounding factor for increasing further」，要再往上推，quorum 仍然是上限。範圍縮小解開的是不相干寫入互等的那一層浪費，每個 reference 內部的共識成本還在。這也是下一步要把 object storage 拉進來的原因。

回頭看小工具的兩種排法，有一個容易讀錯的地方。文章說變的是 quorum 的範圍，從整個 repository 到單一 reference；文章沒有說 replica 的數量變了，我讀到的版本也沒有說它不變。所以比較保守的讀法是：誰需要等誰的邊界從 repository 移到 reference，至於五個 replica 怎麼分工，這一步沒有給新資訊。

把 object storage 放進 quorum：virtual write replica

文章的第二步從 quorum 的成員下手：「The first step is making object storage a member of the quorum, but a special one that we call a virtual replica.」成員很特別，因為它不是一台持有完整副本的機器。代表它的運算資源，文章稱為「our first fully ephemeral node」，是他們第一個完全暫態的節點。它的角色是橋接：「It serves as a bridge to object storage, streaming incoming writes and serving no reads.」只把進來的寫入串流到 object storage，不提供任何讀取。

成為 quorum 成員有一個直接後果，文章寫得明確：「Because it’s a member of the quorum, a write isn’t acknowledged until it’s durable in object storage.」寫入要等到在 object storage 裡持久化，才會被確認。這裡的設計意圖，我的解讀是讓持久性由 object storage 背書，而不是靠哪一台暫態節點記住資料；暫態節點可以隨時被換掉，只要 object storage 裡已經有那筆寫入。

代價也在這一步出現：每筆寫入的確認多了一個條件，必須等 object storage 持久化。文章的緩解方法是合併。這個節點會把不同 reference 上的交易合成一組儲存 I/O，原文是「coalesces transactions on disjoint references into a single set of network I/Os to object storage」，結果是「a busy repository pays for one round trip across many concurrent writes instead of one per write」。忙碌的 repository 面對許多並行寫入，只付一趟往返，而不是一筆一趟。和前一節對起來看，這就是縮小 quorum 範圍之後才有的機會：不同 reference 的寫入互不排隊，才有大量彼此獨立的交易可以一起送出。

合併和縮小範圍是咬在一起的兩個動作。如果鎖還涵蓋整個 repository，同一時刻只有一筆寫入在飛，沒有「許多並行寫入」可以合；範圍縮到 reference 之後，不同 reference 的寫入同時進行，virtual write replica 才有一批彼此獨立的交易可以一起送出。反過來看，確認條件變嚴本來會讓每筆寫入更慢，合併把這筆額外的往返成本攤給同一批裡的所有寫入，寫入越忙，每筆分到的成本越少。上面的小工具只數往返次數，一筆時兩邊沒有差別，筆數越多差距越大，忙碌的 repository 正是文章點名受益的對象。

不進 quorum 的讀取：virtual read replica

寫入路徑處理完，另一半是讀取。文章對現況的描述是：「Today, reads and writes hit the same replicas, so they compete for the same resources and can’t be scaled independently.」讀和寫打在同一批 replica 上，搶同樣的資源，無法各自擴充。這個耦合的代價取決於讀寫比例，文章給的數字是「Most repositories are heavily read-skewed, with somewhere between 100 and 1,000 reads for every write.」大多數 repository 每一次寫入對應 100 到 1,000 次讀取。

解法是第二種虛擬節點。文章寫的是新的 read replica 會「warms its cache from Azure Blob Storage and starts taking read traffic without joining the quorum」：從 Azure Blob Storage 把快取暖起來，就開始接讀取流量，不加入 quorum。它的資料來源是「using object storage as the source of truth and reconciling its local state against it in the background」，以 object storage 為準，在背景把本地狀態對帳。結果是文章說的「we can begin to decouple read traffic from the write quorum, and independently scale the compute needed for each」，讀取流量與寫入 quorum 可以開始脫鉤，各自擴充需要的運算。

「各自擴充運算」這句話的實際意思，可以從起點對照出來。今天讀寫共用同一批 replica，想多撐一些讀取，就得多養能參與寫入的 replica；而起點的 quorum 會等每個健康的 replica，每多一個 replica，寫入就多一個要等的對象。合理的推測是這正是兩者耦合的代價。read replica 不進 quorum，多開一個不會替寫入路徑增加任何等待的對象，讀取量增加時，擴充的是讀取這一側的運算，寫入的 quorum 維持原樣。

文章對這個設計的限制講得很誠實。背景對帳「makes them a good fit for some read workloads but not all of them」，適合一部分讀取負載，不是全部。機制上的含義可以直接推出來：read replica 的本地狀態是在背景向 object storage 對帳，不屬於 quorum，因此合理的推測是它看到的狀態可能落後 quorum 一小段時間；這也是文章只說它適合一部分讀取負載的原因所在。

三種節點各自站在哪裡，用一張圖並排會比文字清楚。一般 replica 持有完整副本，在 quorum 內，讀寫都做；virtual write replica 在 quorum 內，只收寫入，不提供讀取；virtual read replica 在 quorum 外，只提供讀取。注意兩個虛擬節點的分工是互補的：一個把寫入的持久性接到 object storage，一個把讀取的資料來源接到 object storage，object storage 因此同時是寫入端的持久層，也是讀取端的真實來源。

讀寫比的數字值得多看一眼。每筆寫入對應 100 次讀取，讀取約占請求數的 99.0%；對應 1,000 次，約占 99.9%。在這樣的分佈下，讀取若和寫入共用同一批 replica，寫入那一小條就得和近乎全部的讀取搶資源，文章說的「compete for the same resources」因此有了具體的量級。請求數不等於資源成本，但它說明了為什麼讀取脫鉤會被放進這次改動，而不是留作日後的附帶優化。

三個零件接成一條路

把一筆寫入從頭走一遍，三個零件的位置就清楚了。寫入進來，先看它碰哪個 reference：範圍縮到 reference 之後，它只和同一個 reference 上的寫入互相序列化，不再被其他 reference 的寫入擋住（「Git’s consistency requirements apply to each reference individually」）。接著它進 quorum，quorum 的成員裡有一個 virtual write replica，這個暫態節點把寫入串流到 object storage；寫入要在 object storage 裡持久化，才會被確認。最後一步發生在這個節點內部：同一時刻落在不同 reference 上的交易，被合併成一組對 object storage 的 I/O，忙碌的 repository 因此「pays for one round trip across many concurrent writes instead of one per write」。三步各自處理寫入路徑上的一段等待：第一步移除不相干寫入的互等，第二步把持久性接到一個不依賴特定機器的地方，第三步把這個新增的往返攤薄。

讀取那條路和寫入共用同一個終點。virtual read replica 不進 quorum，從 Azure Blob Storage 把快取暖起來，就開始接讀取流量，並在背景拿 object storage 對帳。object storage 因此站在兩端：寫入端靠它持久化，讀取端以它為準。合理的推測是順序也因此固定下來，先有寫入端把資料可靠地放進 object storage，讀取端才有可以信任的來源去暖快取與對帳；讀取脫鉤的設計，建立在寫入端那一步已經完成的前提上。讀寫比落在每筆寫入對應 100 到 1,000 次讀取之間，意思是 quorum 只需要面對那一小部分請求，其餘的由可以隨需擴充的 read replica 吸收，兩邊各自長大，不再互相搶同一批資源。

這條路鋪在遷移完成的資料上。99.99999% 的 repository 已經同時存在兩個地方，大多數 repository 的五個 replica 裡有兩個在 Azure，Azure 服務約一半的 Git 流量；遷移期間流量跟著資料走，每搬一份副本，能由 Azure 服務的比例就多一分。沒搬完的是最忙的那批，它們停在 25ms 的往返前面，也正是最需要上面三個零件的 repository：寫入密、讀取更密、鎖範圍一大就互相擋。文章標題裡的 bridge，我的解讀是指這座橋，一端是已經就位的資料，另一端是尚未完工的新架構。

橋的另一端還沒蓋完，文章自己也這樣說。quorum 仍是進一步提升的上限（「the quorum remains the bounding factor for increasing further」），下一個限制是寫入吞吐，還有幾個題目沒有答案，包括持久的 reference 狀態放在哪裡，以及 compaction 與垃圾回收如何擴充。文章預告系列的最後一篇會在 GitHub Universe 登場，帶讀者看終態的全貌，包括它對寫入吞吐的影響，以及剩下的那個共識群組。這篇可以確認的是前半段的機制：範圍怎麼縮、object storage 怎麼進 quorum、讀取怎麼離開 quorum；後半段留給那一篇。

The shape of it：鎖縮到 reference、持久性交給 object storage、讀取移出 quorum，三件事各拆掉寫入路徑上的一段等待，留下來的那一段是 quorum 自己。
