R2 的 range 大小設成 64 MiB，一個橫跨邊界的小請求，卻可能讓兩個資料中心之間多搬 128 MiB。Cloudflare 的解法不是找出更好的數字，而是把這個數字從客戶手上拿掉。

Cloudflare 的快取原本替每個 zone 設一個固定的 range 大小，回源抓多大一塊由客戶自己調。這次發表的 Origin Range Requests 把旋鈕換成 Pingora 本來就有的東西：快取在磁碟上就是把每個檔案切成固定大小的 chunk 來存，現在回源的 range 也直接對齊這些 chunk 的邊界。這個改動帶來三件事。客戶不再需要猜一個 range 大小；同一個 chunk 正在下載時，後到的請求可以掛上去，不必另外回源；組合出來的回應則在送出前檢查，確認每一段都來自同一份檔案。文章報告的結果是 R2 的 p99 time to first byte 大約砍掉一半，tiered cache 流量下降約 6%。

固定 range 大小的兩難

先看舊做法的形狀。快取收到 range request，要決定向源站抓多大一塊。舊系統的答案是每個 zone 一個固定的 range 大小，由客戶調。文章舉的極端例子是 R2，它設定的 range 大小是 64 MiB，而一個小請求碰到邊界時，原文的說法是 「could cost us 128 MiB of transfer between data centers」。128 正好是 64 的兩倍，這個數字的來歷值得拆開看。

把檔案想成一排 64 MiB 的格子。快取每次回源都以整格為單位。一個讀取如果落在單一格子裡，抓一格，64 MiB。同一個讀取如果剛好跨過兩格的交界，就得抓兩格，128 MiB，而客戶真正要的位元組可能只是交界兩側各幾個 KiB。下面的互動小工具把這個算術攤開：拖動讀取位置，看舊式的 64 MiB range 碰到幾格。讀取長度固定為 1 MiB，這是我為了演示選的數字，文章只給了 64 MiB 與 128 MiB 這一對。右側 chunk 對齊那一排用的 chunk 大小也是示意值，文章沒有公布實際的 chunk 大小，你可以自己拉動滑桿，看 chunk 大小如何改變回源量的上限。

把滑桿拉到 64 MiB 邊界以外，舊式那一排只會亮一格，這時抓 64 MiB；拉回邊界，亮兩格，抓 128 MiB。這個浪費只在邊界附近出現，卻很難靠調參消除。格子調小，邊界變多、單次浪費變小，但同一個大檔案要拆成更多次回源；格子調大則相反。合理的推測是，客戶得依自己的流量形狀選一個折衷值，而且 zone 底下的流量一變，最佳值就跟著變，這正是這次改動想拿掉的調校負擔。

第二個限制出在舊的 nginx 快取，文章寫的是 「Our nginx-based cache also couldn't combine range caching with concurrent streaming」。換成讀者的情境：一個大檔案正在被某個請求拉進快取，第二個請求要同一段位元組，舊系統兩件事只能挑一件，不能一邊做 range 快取，一邊讓並行的請求共享正在進行的串流。於是後到的請求要嘛等，要嘛自己再回源一次。原文沒有說舊系統在這種情況下具體選了哪一條路，我只能說這兩個選項都不便宜。

以 chunk 為單位的回源

新做法的出發點很樸素：Pingora 本來就把每個快取檔案以固定大小的 chunk 存在磁碟上，原文的措辭是 「it stores every cached file on disk in fixed-size chunks」。既然快取內部已經用 chunk 當單位，回源也用同一個單位，就不需要另設一套 range 大小。原文的說法是回源的 range 「aligned to the cache's fixed-sized-chunk boundaries」。

流程可以這樣讀。客戶端送來一個 range request，快取先看自己磁碟上已經有哪些 chunk，把能直接回的部分標出來；缺的部分向源站要，而且要的是對齊 chunk 邊界的範圍；最後把兩邊湊成一份回應，只送出客戶端真正要的位元組。原文也提到，一份回應可以同時混合三種來源：已經在磁碟上的前段、正在進行中的下載、剛抓回來的後段。合理的推測是，這代表回應不必等整個 chunk 到齊才開始送，這點對 time to first byte 很重要，下一節會看到它怎麼和 attach 機制配合。

為什麼對齊 chunk 邊界值得做？合理的推測是這樣：回源片段的邊界和快取儲存的邊界一致，抓回來的每一段都能原封不動落成一個或多個完整的 chunk，不會有「抓了一半的 chunk」需要特別處理，不同請求要的片段也比較容易落在同樣的邊界上被共用。這是我對設計動機的推斷，原文只陳述了對齊這件事本身。

回到舊例子。在 chunk 方案下，同樣橫跨某條邊界的小讀取，碰到哪些 chunk 就抓哪些 chunk，量級由 chunk 大小決定，而不是由某個 zone 設定決定。上面的小工具已經讓你試過：把 chunk 拉到 1 MiB，回源上限就剩 1 到 2 MiB；拉到 64 MiB，就回到舊式的水準。文章沒有公布真正的 chunk 大小，所以我沒辦法替你算出實際省下多少，只能說這個量級被限制在一個可預期的範圍內。

同一份下載，多個請求

固定 chunk 解決了「抓多大」，沒有解決「誰去抓」。大檔案的熱門區段常常同時被好幾個客戶端要，如果每個請求各自回源，源站與資料中心之間的流量就會隨請求數成長。新機制的處理方式，原文寫成：後到的請求發現已有下載涵蓋它要的位元組，「the second request can attach to that download instead of starting another origin fetch」。

我在這一節自己做了一個模擬，用來看 attach 的效果。畫面上方是一個切成 12 個 chunk 的檔案，隨機的請求不斷到達，每個請求要連續的 1 到 3 個 chunk。一個 chunk 被第一次要到時，開始回源，要 3 秒才下載完；下載期間若有別的請求也要它，開著「共用進行中的下載」時，它們只是掛上去，回源次數不增加；關掉之後，每個撞上正在下載的 chunk 的請求都會再發一次回源，chunk 下方的「回源 ×n」就會往上跳。回源 3 秒與請求的到達節奏都是我設的示意值，真正的下載時間取決於 chunk 大小與網路，原文沒有給。模擬唯一想表達的是 attach 的邏輯：回源次數追著 chunk 數走，而不是追著請求數走。

模擬跑一陣子之後，所有 chunk 都會變成綠色，之後每個請求都是命中。切換模式會清空快取並歸零，你可以先在「關」的狀態看一輪，再在「開」的狀態看一輪，比較每個 chunk 下方的回源次數。「關」的狀態下，第一個 3 秒窗口內回源次數明顯超過 chunk 數；「開」的狀態下，每個 chunk 最多回源一次。這是由模型本身的邏輯決定的，不是量測結果。

回到原文。attach 還有一個容易被忽略的前提：掛上去的請求要的位元組，必須被那個進行中的下載涵蓋。原文的條件寫成 「If an existing download covers another request's bytes」，涵蓋才掛得上去。涵蓋不到的部分，合理的推測是仍然要自己回源，原文沒有逐項展開這一點。所以一個請求的回應，可以是磁碟上的前段、掛上別人的中段、自己新抓的後段三者的拼接，原文的說法是 「One request can use a cached prefix, an in-flight download, and a newly fetched suffix」。

拼起來的回應，憑什麼是同一份檔案

把幾段不同來源的位元組拼成一份回應，最大的風險是它們根本不是同一個版本。磁碟上的 chunk 是上午抓的，進行中的下載是另一個請求啟動的，新抓的片段又是現在向源站要的；如果源站的檔案在這中間被換掉，拼出來的東西會是一份不存在的檔案。原文的對策是在組合時檢查兩件事：總大小是否穩定，以及 entity tag 在各次子請求之間是否一致，原文寫成 「that the total asset size is stable, and that the entity tag remains consistent across subrequests」。

下面的圖把一份 range 回應拆成三段來源，再標出這兩項檢查作用在哪裡。chunk 的數量與位置是示意，原文沒有給這樣的例子。

這兩項檢查的意義，可以從失敗的方向反推。總大小如果變了，代表源站的檔案已經不是原來那份；entity tag 不一致，代表至少有一次子請求拿到的是另一個 representation。兩者任一出現，拼出來的回應就不能保證是連貫的檔案。原文沒有寫檢查失敗時的處理細節，我不替它補。

還有兩個退回路徑，原文有明確交代。第一個是 If-Range：它讓客戶端表達「只在 representation 仍符合我手上的 validator 時，才給我這段 range」，原文的說法是 「lets a client request a range only if the representation still matches a known validator」。不符時，原文寫的是 「If it does not match, Cloudflare returns the full representation instead of combining bytes from different versions」，回完整的 representation，不會把不同版本的位元組湊在一起。第二個是轉換過的回應：原文寫 「Cloudflare also avoids composing ranges for a representation it is about to decompress」，即將被解壓縮的內容不走 range 組合，原文說 Cloudflare 改為回傳轉換後的完整回應，而不是宣告一個它無法正確履行的 range。這很合理，因為解壓縮之後的位元組位置，和磁碟上以及源站那邊的位元組位置已經對不上了；這是我對原因的推測，原文只給了行為。

小請求的代價，以及怎麼開啟

chunk 對齊不是免費的。原文自己承認的代價是：小於一個 chunk 的請求，仍然可能得把整個 chunk 抓回來，原文的措辭是 「such a request can still require fetching the whole chunk containing it」。換句話說，舊系統那個「小讀取放大成整個 range」的問題沒有消失，只是放大的單位從客戶調的 range 變成固定的 chunk。你如果有大量只讀幾個 KiB 的存取模式，要先弄清楚 chunk 的實際大小，這個數字原文沒有公布，需要你向 Cloudflare 確認或自己量。

這個代價和舊方案的差別在於可預期。舊方案的浪費取決於客戶選的 range 大小與讀取是否碰到邊界；新方案的放大上限就是一個 chunk，不會因為某個 zone 設了很大的 range 而爆開。文章的整體論點是這筆交易划算，後面的數字是它的證據。

文章報告的生產結果有兩個。R2 的 p99 time to first byte 在 cache hit 與 cache miss 兩種情況下都大約降了一半，原文是 「p99 time to first byte dropped by roughly half on both cache hits and misses」。另一個是 tiered cache 的流量：原文寫 「tiered cache traffic for R2 and similar workloads dropped about 6% week over week」，並補了一句 「petabytes less data moving between our data centers every day」。這裡有兩點要保持克制。一是 「roughly half」 與 「about 6%」 都是原文自己的概略說法，不要當成精確值引用。二是 6% 是 week over week 的比較，原文給的是這個週與前一週的差，我沒有辦法替你拆出其中有多少歸功於 chunk 對齊，有多少來自其他同期的改動。

要開啟，原文的步驟是建立一條 Cache Rule，匹配你的大檔案流量，把 Origin Range Requests 設成 On。可以在 dashboard 的 Caching 底下的 Cache Rules 設定，也可以用 API。API 的設定欄位如下。

origin_range_requests: { "mode": "on" }

用 Cache Rule 開啟而不是整個 zone 一起開，有個實務上的好處：你可以先只匹配一類流量，例如大型的安裝包或磁碟映像，觀察效果，再決定要不要擴大。這是我依規則機制做的使用建議，不是原文的步驟。判斷效果時，最直接的兩個指標就是原文自己報的那兩個：p99 time to first byte，以及資料中心之間的回源流量。

表裡「行為」欄中，If-Range 與解壓縮兩列的退回方式是原文明說的；「代價或限制」欄有幾格是我依機制補的理由，已經盡量標明。對讀者來說，最實用的判讀是：你的流量裡如果有很高比例的請求帶 If-Range，或內容在邊緣被即時解壓縮，這個功能對你的幫助會打折。這是從原文的退回條件推出的結論，不是原文直接下的判斷。

What this enables：大檔案的 range 讀取不再需要為每個 zone 調一個折衷的 range 大小，熱門區段的並行請求共用同一份回源，回源量的上限由 chunk 大小決定；文章報告 R2 的 p99 time to first byte 大約減半，tiered cache 流量下降約 6%。
