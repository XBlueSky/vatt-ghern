請求拿到成功的 HTTP 狀態碼，prompt_tokens 對得上長 prompt，回覆也讀得通順。唯一的問題是，這段通順的文字是在別人留下的資料上生成的。

KV 池太小，155 筆回應讀到別人的資料

這是 Cloudflare 在 Workers AI 上遇到的事故。GLM-5.3 在 2026 年 8 月 27 日上線，部署時宣告的 context window 是 1,048,576 tokens，但 prefill GPU 上的 KV cache pool 只放得下 681,280 tokens。兩個數字差了約 367,000 tokens，而 Cloudflare 的事後報告說得很直接：「We were aware of this mismatch before launch.」這篇文章不重述公告，而是照一位工程師查這類問題的順序，把每個假設拆開來看：哪些假設在事後證據前站不住，哪一個才是真正的原因，以及 Cloudflare 與 SGLang 社群各自補了什麼。

先交代範圍。報告的結論是 155 筆回應受影響，全部對應長度超過 681,280 tokens 的 prompt。Cloudflare 說沒有發現蓄意利用的證據，已辨識出的請求在時間與數量上也與一般長 context 使用相符。它也確認 Workers AI 上沒有其他模型受影響。下面的內容全部取自這份報告，凡是我自己的推論，都會標明是推測。

HTTP 狀態正常、回覆連貫，內容卻不是這個請求的

這類問題難查，是因為它沒有任何明顯的失敗訊號。報告列出的事實是：預先上線測試時，團隊只驗證了 HTTP 回應碼和長 context 下的引擎效能，看到的是成功的狀態碼。出事之後回頭檢查，prompt_tokens 與長 prompt 吻合，回覆也連貫。三個最直覺的健康指標全部是綠的，錯的是回覆文字取材自哪裡。

時間線也很短。報告寫的受影響區間是 8 月 27 日到 9 月 9 日之間。9 月 8 日，一位研究員透過 Cloudflare 的 HackerOne 計畫通報；Cloudflare 的 Product Security 用兩個獨立帳號在 25 分鐘內重現了洩漏；GLM 5.3 隨後被設為 private，請求回傳 HTTP 400，9 月 9 日恢復對外提供。從通報到下線再到恢復，一共不到兩天。

報告把上線前的判斷寫得很誠實。Cloudflare 說，團隊事先知道 pool 與 context 的大小不一致，但在上線前測試中看到的是成功的 HTTP 狀態碼，於是沒有把它視為阻擋上線的問題。這個判斷在當時有它的邏輯：既然送出超長 prompt 得到的是成功的回應，不一致看起來就只是設定上的瑕疵，不是功能上的缺陷。事後才知道，成功的回應正是缺陷本身的外觀。

這張圖要放在心裡的是兩個長度。受影響區間有將近兩週，但這兩週裡大部分長度的請求都正常，出問題的只有超過 681,280 tokens 的那一小群。這個門檻不是什麼神祕的閾值，它就是 prefill 端 KV pool 的容量。換句話說，問題的邊界早就畫在部署設定裡，只是沒有人把它和 context window 放在同一張表上對照。

假設一：引擎會拒絕放不下的 prompt

工程師看到「prompt 超過 pool 容量」，第一個問題通常是：引擎對放不下的輸入會怎麼處理？合理的預期是回錯誤。Cloudflare 自己的檢討正是這個預期：「We expected the engine to return an error for any prompt it could not process」，它也承認團隊假設引擎能優雅處理這個差距。上線前的測試因此只看 HTTP 狀態碼與長 context 效能，沒有去驗證回覆內容的來源。

這個假設要靠證據才能推翻，而證據來自 SGLang 的行為。報告描述的是：放不下 pool 的 prompt 在內部被標記成 rejected，並被換成一個 one-token placeholder。引擎確實「拒絕」了請求，但拒絕只是一個記在請求物件上的標記，並沒有讓請求離開流程。報告說，換成 placeholder 的目的，是讓請求能順著正常的 batch 機制排出去。

這裡有一個值得工程師細想的取捨。把被拒絕的請求留在 batch 裡排空，可以讓排程邏輯保持單純，不必為「中途被拒絕」另外開一條路徑；代價是被拒絕的請求仍然是一個完整參與後續階段的請求，後面每一站都必須記得它其實是被拒絕的。換句話說，拒絕這個狀態必須被每一個下游元件正確讀取，只要有一站漏看，替身就會被當成真的請求處理。

所以假設一的結論要拆成兩半。引擎有偵測到問題，這一半成立；偵測之後請求會被擋下，這一半不成立。合理的推測是，這個設計的初衷是避免被拒絕的請求卡在 batch 裡讓其他請求受影響，所以才用最小的替身讓它繼續走。這在單機模式下也許行得通，到了 prefill 與 decode 分離的部署，替身後面還有一段傳輸，事情就不同了。

假設二：傳輸完成就代表 KV cache 已被覆寫

第二個要檢查的地方是 prefill 與 decode 之間的交接。在 disaggregated 模式下，prefill 節點算出 KV cache，再傳給 decode 節點。decode 節點判斷自己能不能開始生成，依據的是一則訊息。報告說得很清楚：decode 節點收到「transfer complete」訊息，並假設 prefill 已經把 KV cache 覆寫好。

這是整個事故裡最脆弱的一個假設，因為訊息只描述傳輸動作結束，並沒有證明那些頁面裡裝的是這個請求的資料。如果 prefill 端根本沒有為這個請求算出完整的 KV，傳輸再完整，也只是把原本就在那些頁面上的內容原封不動交過去。報告舉的例子是 pages P1 到 P7：它們仍然留著先前請求的內容，那些是其他使用者的 prompt 和部分生成結果。decode 於是在這些過時的頁面上做 attention，生成了回應。

為什麼舊頁面還讀得到？報告沒有再往硬體層展開，所以這裡只能推測：頁面被釋放回 pool 時，內容通常不會被清零，下一個使用者拿到的就是上一個使用者留下的位元組。這個推測與報告中「頁面仍保留先前請求留下的東西」這句話一致，但報告並沒有逐字這樣說，讀的時候請把它當作推論。

假設三：只有這個部署出問題

第三個檢查是縮小範圍。如果問題是引擎對所有長 prompt 的共通缺陷，那 Workers AI 上其他分離式部署也該中招；如果問題與 pool 容量有關，用更大的 pool 重做同樣的請求就該恢復正常。報告給了兩條證據：用較大 pool 的 canary prefill 節點確認不受影響；Workers AI 上其他所有分離式部署，KV pool 都比各自的 context length 大。Cloudflare 因此確認沒有其他模型受影響。

這兩條證據把嫌疑縮到一個交集上：只有 pool 小於 context window 的部署，才會讓一個合法長度的 prompt 放不進 pool。換個說法，GLM 5.3 的設定讓「合法請求」和「放得進 pool 的請求」成了兩個不同的集合，而差集裡的請求全都落入那條不該走的路徑。

驗證修補時用的方法，也說明了這類洩漏該怎麼測。報告說兩項修改都對照了研究員的重現腳本和 Cloudflare 自己的 canary-marker 測試：在請求裡放入可辨識的標記，再看這個標記有沒有出現在別的請求的回覆裡。這種測試問的是「資料屬於誰」，與 HTTP 狀態碼、延遲、吞吐量都無關。上線前的測試只看到後面那一類指標，所以對這個缺陷完全沒有偵測能力。

報告裡還有一條操作層面的佐證，值得運維的人記下來：SGLang 啟動時會在日誌裡印出選定的 KV pool 大小，也把它暴露成 metric。換句話說，檢查這個數字不需要任何額外工具，只需要有人去看。

真正的原因：被拒絕的請求仍然活著，而 pool 又比 context 小

把前面三條線接起來，因果鏈是這樣的。部署讓一個合法的長 prompt 超過 pool，引擎把它標成 rejected 並換成 placeholder。問題在於準入佇列怎麼判斷這個請求還活不活著：報告說，prefill 與 decode 兩端的準入佇列檢查請求是否 finished，而被拒絕的請求把拒絕原因存在 to_finish，不在 finished_reason，所以 finished() 仍然回傳 False。報告用一句話總結：「A rejected request reported itself as live.」

請求因此照常通過準入，進入 KV 傳輸，decode 收到完成訊息，在還裝著別人資料的頁面上生成。到外面看，一切都正常：狀態碼成功，prompt_tokens 吻合，回覆連貫。下面這張圖可以逐站點開，看同一個請求在每一站「舊行為」與「修補後」各是什麼樣子。

第二站和第三站是這條鏈上互相咬合的兩環。pool 小於 context window，保證了會有合法請求被判定放不下；準入端把被拒絕的請求當成存活，保證了這些請求不會被攔下。兩個缺口單獨存在時都不會洩漏資料：pool 夠大，就沒有請求會被拒絕；準入端判斷正確，被拒絕的請求就到不了 decode。Cloudflare 的分析同樣把兩者並列為根因，一個是設定不匹配，一個是 SGLang 的缺陷。

下面的滑桿讓你自己掃一遍輸入長度。把 prompt 長度從 0 拉到 context window 的上限，並在兩種 pool 大小之間切換，看看哪一段長度落進危險區。這個互動只依據報告給的三個數字：681,280、1,048,576 與約 2.04 million。

切到修補後的 pool 之後，整條滑桿都落在安全側，這就是報告那句話的意思：符合 context window 的 prompt，現在一定放得進 pool。反過來看，事故時的 pool 把安全區切在 681,280，從那裡到 1,048,576 之間約 367,000 tokens 的長度，都是引擎「合法接受、實際放不下」的灰色地帶。

修補：把 pool 加大，再讓被拒絕的請求早點退場

Cloudflare 的修補分成兩層，各自處理一個缺口。第一層是容量：prefill KV pool 現在約 2.04 million tokens，約為 1,048,576 tokens context length 的兩倍。這一層直接消除前提，符合 context window 的 prompt 不再會被判定放不下。

第二層是行為：SGLang 的補丁讓帶著待處理拒絕的請求，在 disaggregation 準入佇列被退場，並附上原本的錯誤。也就是說，被拒絕的請求不再被當成存活，不會抵達 KV 傳輸。報告提到上游已有對應的 PR，包括 #36988 與 #38935；Cloudflare 也驗證了兩項修改，對象是研究員提供的重現腳本和它自己的 canary-marker 測試。

兩層修補互為備援，但它們的性質不同。加大 pool 是設定層的修正，依賴的是「context window 與 pool 的關係永遠被維持」，只要下一次部署又調動其中一個數字，保護就會悄悄消失；準入端的修補是程式碼層的修正，不管 pool 多大、請求為什麼被拒絕，被拒絕的請求都會在入口退場。報告說修補後符合 context window 的 prompt 一定放得進 pool，這是容量層給的保證，它並不取代準入端對其他拒絕原因的處理。這是我對兩層分工的解讀，報告本身沒有這樣分類。

在這兩層之外，Cloudflare 還補了幾項加固。報告列出的有：延遲釋放擴大到 prefill 的來源頁面，並涵蓋每一種失敗類型，不只是 abort；部署了有上限的 Mooncake 傳輸批次；修改負載平衡器，讓客戶端斷線不再於傳輸中途中止請求；並在每一次分離式部署的變更檢查裡，加入「KV pool 大小與 context length 的對照」這一項。最後一項最便宜，也最直接對應這次事故的根源。

報告也坦白交代了一條沒走完的路。Cloudflare 與 SGLang 維護者在研究頁面層級的完整性標記：每個實體 KV 頁面帶一個在頁面重新配置時會改變的標記，讀取時就能發現請求在讀一個不屬於它的頁面。報告說原型在測試中，吞吐量與尾端延遲的代價低於 1%。但它在 GLM 5.2 上的測試是 8 月中旬做的，不久後因為可靠性問題被停用，而且原型綁定特定的 attention 後端與模型架構。這條路的價值在於它是備援：即使前面的檢查全部失效，錯誤的讀取也有機會被抓到。

有一句話值得單獨抄下來。報告談到某項檢查時說：「it is the backstop for the day your check in step one is wrong.」意思是，第一步的對照檢查總有一天會失靈，後面的每一層都是為那一天準備的。這次事故的教訓不在「pool 比 context 小」這個錯誤本身，因為任何一個人都可能設錯；教訓在於這個錯誤被預先發現，卻沒有被當成上線阻擋條件，而下游又沒有任何一層會把它擋下。

把這次事故放回一般的 LLM 服務架構，可以抽出三個問題，每個都能在自己的部署裡直接回答。第一，你的 KV pool 大小和宣告的 context length 是不是同一張表上的兩個數字？第二，當請求放不下時，引擎的行為是明確回錯誤，還是用某種替身繼續走？報告的經驗是不能預設引擎會替你擋下，也不該指望 proxy 來強制上限。第三，如果前兩項都失靈，有沒有一層機制能發現「這個請求在讀不屬於它的頁面」？頁面層級的完整性標記就是在回答這一題，只是目前還在與上游維護者共同開發，不是現成的選項。

Take-away：下次看到「回覆正常、狀態碼正常」，先去檢查回覆的資料來源，再去對照 KV pool 與 context length 兩個數字，因為健康指標看的是請求有沒有完成，看不出完成的內容屬於誰。
