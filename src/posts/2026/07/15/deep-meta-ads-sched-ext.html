2026 年初，Meta 廣告艦隊裡有一批主機遲遲升不了 kernel——不是流程卡住，是升到 6.9 之後 p99 延遲反而變差，團隊只好把這批主機硬留在舊版 6.4 上。半年後，同一批機器全數換成 6.9 加上自製的 sched_ext 排程器，p99 降了 28%，還順手省下 3.28 MW 的電。

Meta 廣告換上 sched_ext：p99 延遲砍 28%

這是一個排程器逼你重新分艦隊的故事——Linux 6.9 把 CFS 換成 EEVDF 之後，Meta 的廣告服務先付了一次延遲退步的代價，接著用 sched_ext 把排程邏輯搬進使用者空間，讓「哪個 thread 該優先」這件事第一次由懂廣告工作負載的人決定，而不是由通用排程器用猜的。

這段記述來自 Meta 官方工程部落格 2026 年 7 月 13 日發布的文章，作者是 Blaise Sanouillet、Sunyi Shao、Jeff Song、Gosh Arzumanyan、Shawn Wu、Tejun Heo、Praveen Sampath、GP Musumeci 等八人——下面每一句放在「」裡的英文，都是這篇文章裡的原話，不是轉述或翻譯後再回填的版本。

艦隊分裂：一次 kernel 升級退回來的延遲

廣告服務原本跑在 kernel 6.4 上，用的是 Linux 傳統的 CFS（Completely Fair Scheduler）。Meta 工程團隊把整個艦隊往上升級到 6.9 時，撞上了取代 CFS 的新排程器：Earliest Eligible Virtual Deadline First，EEVDF。升級後，廣告服務的延遲出現退步——用原文的話說，這次退步「reduced the number of ads ranked in response」，不是抽象的效能數字，是直接咬到業務的產能。

退步沒辦法忍，也沒辦法馬上解決，團隊做了折衷：把一部分廣告主機硬留在舊的 6.4，繼續用 CFS，其餘的才往前升級。代價寫得很白：「a subset of ads hosts were forced to remain on the older v6.4 kernel, creating technical debt and operational fragmentation」——兩個 kernel 版本同時上線跑，維運要為兩套假設同時負責，alert 門檻、容量規劃全部要分兩份想。

這種分裂對維運來說不只是帳面上的小事：同一套 monitoring 得為兩種 kernel 行為分別設一次 alert 門檻，同一份容量規劃得分別估算兩種排程假設下的伺服器吞吐量，任何跨版本才會冒出來的 bug，第一步都得先確認是「6.4 特有」還是「6.9 特有」。原文沒有把這些維運細節逐條列出，這裡是根據「operational fragmentation」這個詞推斷出的合理延伸，不是已核實的數字。

問題不在 EEVDF 寫得不好，而在通用排程器的設計目標。CFS 到 EEVDF 換的是「怎麼公平分時間片」的演算法，但公平的對象一直是「所有 thread」，不是「使用者正在等的那個 thread」。原文的說法是，這類通用排程器「balance threads across CPUs with no understanding of the workload」——它不知道、也沒有機制去知道，一批 thread 裡哪個是使用者在等的 ads retrieval 請求、哪個是可以晚一點跑的背景工作。EEVDF 換了公平的演算法，但這個「不知道」的性質沒變，廣告服務用得到的公平，剛好不是它需要的那種。

這個問題不是 Meta 廣告服務獨有的，是所有把「延遲敏感的前景請求」跟「不急的背景工作」混在同一批機器上跑的系統都會碰到的張力。通用排程器要維護的是「對 kernel 上所有可能的工作負載都合理」這個目標，這個目標對整個 Linux 生態很有價值——但代價是它沒辦法為單一一種工作負載去做特化。EEVDF 想解決的是 CFS 在某些場景下的公平性瑕疵，這個目標跟「讓廣告服務的 p99 不要退步」根本不是同一個問題，兩者在設計時就沒有必然要對齊。

兩個 pool、一份 BPF policy——sched_ext 把排程搬進使用者空間

能繞開這個「不知道」的辦法，不是再等一個更好的通用排程器，而是換一種排程器的做法。sched_ext 是「an open-source, BPF-based scheduler framework」，正式進 Linux 主線是 v6.12——它讓開發者把排程策略寫成 BPF 程式，而不是把邏輯焊死在 kernel 裡、等下一次 release 才能改。

這裡有一個版本落差：Meta 這次首發用的是 6.9 kernel，而 sched_ext 官方進主線要到 6.12——推斷這代表 Meta 在正式合流之前就已經把這套框架 backport 進自己的 kernel tree，先解決眼前的延遲退步，不等上游進度。這一段原文沒有明說，這裡只提供合理推測，不當作已核實的事實。

Meta 自己寫的 policy 做的事很單純：把 CPU 軟性切成兩個 pool。原文寫得很清楚：「The policy soft-partitions CPUs into two pools, one for threads on the latency-critical request path and one for less latency-sensitive work」——一個 pool 專門留給使用者在等的 request-path thread，另一個 pool 留給背景工作。這個切法能成立，靠的是「the domain-specific knowledge encoded inside the policy」——這份 policy 事先就知道「廣告服務裡誰是誰」，這正是 CFS、EEVDF 從一開始就不具備的東西。policy 執行的優先順序寫得很直白：「Work that improves the p99 request latency is scheduled first, and everything else takes a back seat.」延遲敏感的工作永遠排第一，其餘一律讓路，沒有模糊地帶。

「soft-partition」這個字選得有意思——不是拿 cgroup 或 cpuset 把 CPU 硬鎖死分兩半，而是讓 policy 自己決定每一刻兩個 pool 各自該拿多少顆 CPU。原文說得直接：「The size of each pool is adjusted dynamically using load-based heuristics.」背景工作暫時沒什麼要跑的時候，延遲敏感 pool 可以借到更多算力；使用者流量衝高的時候，policy 也能把 CPU 從背景工作那邊收回來。這種即時借用的判斷，只有事先懂這個工作負載的 policy 敢做——通用排程器不知道「借了會不會出事」，所以乾脆不借。

切成兩個 pool 還有一個原文特別點出的附帶效果：「This approach tends to keep related work on the same CPUs over time, improving last-level cache (L3) locality and reducing costly DRAM access.」把同一類工作留在同一批 CPU 上，代表 L3 cache 裡留著的資料，多半是同一批 thread 之後還會再用到的，少了很多要跑去 DRAM 拿資料的次數。至於首發那筆省電，原文把來源交代得很清楚：3.28 MW「is derived from the 1.1% weighted-ads-ranked increase and 1.6% CPU-utilization reduction」，也就是從業務指標上升與 CPU 使用率下降推算出來的。cache locality 的改善跟這筆省電是不是同一個機制的兩面，原文並沒有直接畫上等號——合理的推測是兩者方向一致，但這一步是推斷，不是原文的斷言。

這種 domain-specific knowledge 不是天上掉下來的：得有人先弄清楚「這個服務裡，哪些 thread、哪些呼叫模式屬於延遲敏感的請求路徑」，再把這份知識寫進 policy 裡；流量形狀一變、加了新的呼叫路徑，這份知識也得跟著更新。sched_ext 換來的是「這件事現在可以做」，不是「這件事現在不用做」——框架把門檻從「改 kernel 原始碼」降到「寫一份 BPF 程式」，但寫對這份 policy 所需要的工作負載理解，還是得靠人一點一點補上，這正是它跟通用排程器最本質的差異，也是它的維護成本所在。

對廣告排序這條 pipeline 來說，「使用者在等」這件事很具體：一次廣告請求進來，要在一個很短的時間窗內完成模型推論、候選排序、回傳結果，這段路徑上的每一個 thread 都被同一個延遲目標追著跑；至於模型重訓、log 處理、離線特徵計算這類背景工作，晚個幾秒甚至更久完成也不影響使用者體驗。把這兩種性質完全不同的 thread 丟給同一個「對所有 thread 一視同仁」的排程器，背景工作偶爾搶到 CPU、把延遲敏感的 thread 卡住一拍，就是延遲曲線裡那些拖長的尾巴。兩個 pool 的存在，說到底就是把這個「誰該讓誰」的判斷，從排程器的黑箱裡搬出來，寫成一條可以被檢視、被改的規則。

原文只列出 wake-up、enqueue、dispatch、idle transition 這四個 callback 的名稱，沒有逐一說明每個 callback 具體判斷什麼；以 BPF 排程框架的一般運作模式來推斷（這段是根據 sched_ext 這類框架常見設計做的解釋，不是原文逐字內容）：thread 從睡眠中醒來時（wake-up）是第一個決定要不要優先塞進延遲敏感 pool 的時間點；進入待跑佇列時（enqueue）確認目前該在哪個 pool 排隊；真正被 CPU 挑中執行的那一刻（dispatch）是 policy 最後一次確認分配是否還成立的機會；CPU 沒事做進入 idle 時，policy 可以趁著這個空檔把背景工作往上推一點。四個掛勾合起來，讓 policy 在 thread 生命週期的每一個轉折點都有機會重新評估分配，而不是只在 thread 一誕生時決定一次就不再更動。

policy 本身跑在使用者空間，靠這四個 callback 跟 kernel 交握，不是靠修改 kernel 內建的排程演算法。這句話看起來只是實作細節，但後面的迭代速度全靠它——一份改動不需要重新編譯 kernel、不需要重開機、也不需要走完整的 kernel release 流程，改完、驗證過，就能上線。

首發：一次從舊機隊跳到 6.9 + sched_ext

首發選的不是漸進式：團隊直接把數量最大的一批廣告伺服器，從 6.4 加 CFS 一次升到 6.9 加上這套自製 sched_ext policy，跳過了「先升 kernel、再想排程」這種中間狀態。先挑規模最大的那批機器動手，通常也代表受 EEVDF 拖累最深、對業務數字影響最大的就是這批——把資源優先投在這裡，等於把整個遷移案的投資報酬率拉到最高；原文沒有明確講這個排序背後的邏輯，這裡是根據「最大量的廣告伺服器」這個描述做的合理推測，不是已核實的決策依據。這個「一次跳」的選擇本身也在還債：分裂艦隊維持的時間越長，兩套假設分岔得越遠，之後要收斂回同一個 kernel 版本的成本就越高——首發把最大量的伺服器一次帶過去，等於把「分裂」這個狀態的存續時間壓到最短，而不是讓它變成常態的維運負擔。

數字寫在文章裡：ads retrieval 階段的 service p99 延遲降了 28%；整個機隊的耗電省下 3.28 MW；weighted-ads-ranked 這個業務指標往上走了 1.1%。延遲、電費、業務排序品質，三個維度同時往同一個方向移動，這在單一次基礎設施變更裡並不常見。

這組結果打破了一個常見的直覺——延遲優化通常伴隨代價，壓 p99 常常要靠拉高 headroom、多擺機器、犧牲 CPU 使用率來換；但這次三個數字全部同向移動：p99 降、耗電降、業務指標還往上。原文附註裡還提到一個支持這個方向的數字：「1.6% CPU-utilization reduction」——機隊整體的 CPU 使用率降了 1.6 個百分點，跟前面 cache locality 機制解釋的「少了 DRAM 等待」方向一致，替 3.28 MW 這個省電數字補上一個可以對照的技術指標。與其說是「多花資源換延遲」的取捨，不如說是把同一批資源用得更有效率的結果。

這組數字也不是上線當天就量出來的。原文寫的是「Measured by backtest after the rollout reached global scale and stabilized (~3 weeks)」——團隊等機隊全部上線、流量分佈穩定了大約三週之後，才用 backtest 量測這組結果。這個等待是必要的：排程這種東西，剛上線時 cache 狀態、CPU 使用習慣都還在重新摸索，太早量測容易把「暖機」的雜訊當成真正的效果，量出來的數字沒有代表性。

從「kernel 升級的絆腳石」到「持續優化平台」

首發之後的兩次後續更新，都沒有再碰 kernel 版本——改的只是 policy 本身這份 BPF 程式。原文講得直接：「Each follow-on iteration above shipped in days rather than months because the scheduler policy lives in user space as a BPF program.」同一套邏輯，換一個載體，交付週期從跟著 kernel release 的節奏，變成跟著 policy 修改的節奏。

原文把這兩次後續更新算作一組來報數字：「Two follow-on scheduler-policy updates, delivered as purely user-space changes, extended the win」——60% 的 p99 額外降幅跟 18% 的 timeout error 下降，是兩次更新加總後的結果，原文沒有拆開各自的貢獻。這種節奏的差別，感受最深的通常是負責 tuning 的工程師：以前想微調一個排程參數，得先確認要不要等下一輪 kernel 升級、要不要重開機、會不會跟其他排隊等上車的變更卡在一起；現在只是改一份 BPF 程式、跑內部驗證、逐步 rollout。對排程這種「效果要在真實流量下才看得準」的系統來說，把實驗週期從月縮到天，理論上等於把工程師敢嘗試的假設數量放大了不只一輪。

對正在評估要不要自己寫一份 sched_ext policy 的團隊來說，這篇文章給的其實是一個具體的參照，不是「值不值得」的抽象討論，而是「多久能看到效果」的實際對照：從 6.4 加 CFS 卡住不能升級，到 6.9 加 sched_ext 做到 p99 −28%，中間是一次完整的 kernel 升級週期；後續兩次再砍 60%，只花了「幾天」。這個時間對照本身，就是這整段故事裡最值得帶走的數字。

文章給這整件事的定調是：「That cadence is what turned sched_ext from a 'kernel upgrade unblocker' to a continuous-optimization platform for ads serving.」sched_ext 一開始只是拿來解決 EEVDF 退步、讓卡住的機隊能重新升級，後來變成一個不需要等上游 release 就能持續調整的平台。這個轉變比任何一次的百分比都重要——它把排程優化從一次性的 migration 專案，變成一個可以反覆迭代的日常動作。

這裡值得拆開兩層來看：一層是「用 sched_ext 解決艦隊分裂」，這是任何跑在 Linux 上、又剛好在某次 kernel 升級撞上排程退步的團隊都能複製的做法——把排程邏輯搬進使用者空間、繞開等上游修的節奏，這件事本身跟廣告服務沒有必然關係。另一層是「兩個 pool、domain-specific knowledge」這份具體的 policy 內容，這是 Meta 針對「大量前景請求 + 大量背景批次工作混跑在同一批機器」這種特定流量形狀寫的，換成別的工作負載——比如純粹的線上交易系統、或者沒有明顯前景背景之分的批次運算叢集——這份 policy 的兩池切法不一定適用，甚至可能整個判斷邏輯都要重寫。框架可以借，policy 裡的 domain knowledge 借不走。

把時間拉長來看，這篇文章記的其實是基礎設施工作性質的一次轉向：從「排程優化是升級 kernel 時附帶要處理的麻煩」，變成「排程優化是一個可以獨立於 kernel release 排程、隨時可以再動一次的旋鈕」。對維運廣告服務這種規模的團隊來說，能單獨迭代的旋鈕越多，被上游時程綁住的環節就越少——這個好處不會在下一次的百分比數字裡出現，但決定了下一次類似的退步發生時，團隊手上有沒有工具可以直接動手，而不是只能等、只能分裂艦隊。

如果只能記住一件事，大概會是這個：sched_ext 解決的不是「CFS 跟 EEVDF 哪個排程演算法比較好」這種爭論，而是「排程邏輯應該活在哪裡」這個更底層的問題。把它從 kernel 裡搬進使用者空間之後，改動排程行為不再是一次要跟著 release 節奏走的昂貴 kernel 工程，而是一次跟改設定檔差不多重量級的軟體迭代——這才是首發的 28% 跟後續的 60% 之間，那個真正值得留下的差別。

後續要看的：這套 policy 是 Meta 內部針對 ads serving 這一種工作負載寫的，換一個服務、換一種流量形狀，兩個 pool 怎麼切、四個 callback 裡怎麼判斷，都得重新寫一份——sched_ext 給的是框架跟交付節奏，不是現成答案。
