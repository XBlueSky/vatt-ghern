柏林時間週二傍晚，DENIC 把新的 KSK 推進 .de 區的權威伺服器，幾分鐘後全世界開了 DNSSEC 驗證的解析器幾乎同時對 .de 開始回 SERVFAIL——德國最大的 TLD 在規範要求下被自己的簽章關進門外，前後三小時。

2026 年 5 月 5 日 19:30 UTC， DENIC 對 .de 區進行一次例行的 KSK rollover， 發出去的 RRSIG 卻無法被任何符合 DNSSEC 規範的解析器驗證。 從那一刻起， 故事的所有後續發展都被一條硬規則決定： bogus 就是 bogus，驗證器 MUST 回 SERVFAIL。 三小時後， 是 stale-serve 與 negative trust anchor 兩條臨時延長線把網際網路撐到 Cloudflare 22:17 UTC 的修補與全球 resolver 同步把 NTA 推上線—— 德國的 web 才慢慢回到 NOERROR。

這篇文章嘗試把這三個小時拆得仔細一點。 事故的物理過程其實不長： DENIC 在某一刻推送了一批無效簽章； 幾秒後驗證器開始拒絕； 之後是各方 resolver 操作者陸續上 NTA， 直到 DENIC 修正。 但每一段都疊在另一層機制之上—— DNSSEC 的信任鏈、 stale-serve 的 cache 衰退曲線、 NTA 的安全／可用取捨、 DNS-OARC 這種事實上的協調管道。 所有這些機制都不是為了「救一次 TLD 級故障」而設計的， 但 5 月 5 日這天， 它們確實救了。

DNSSEC 與其他常見故障最大的不同， 是它的「正確失敗」是 by design。 當簽章算不過時， 規範要求驗證器主動拒絕—— 這不是 bug， 是密碼學保證的核心： 若降級為「無法驗證但仍回答」， DNSSEC 整套設計就失去意義。 這個性質意味著一次 TLD 級的操作失誤， 會被規範本身放大成「整個子樹立即下線」。 這次事件的所有後續討論—— NTA 為什麼必要、 stale-serve 為什麼是剛需、 DNS-OARC 為什麼有存在價值—— 都繞著「規範強制下線」這個前提打轉。

19:30 UTC——DENIC 一次 KSK rollover 發出無法驗證的 RRSIG

背景是 DNSSEC 的兩把鑰匙： ZSK（Zone Signing Key）日常簽 zone 內所有 RRset， KSK（Key Signing Key）簽的是 DNSKEY RRset， 並透過父區 root 發布的 DS record 與信任鏈接續起來。 輪換 KSK 是 DNSSEC 操作裡最敏感的一步—— 你要先把新 KSK 的 hash 放進父區的 DS， 再切換 zone 內 DNSKEY 的角色， 整套過程必須讓 cache 中的舊紀錄與權威伺服器上的新紀錄之間始終有一條可被驗證的鏈。 DENIC 在 19:30 UTC 推送的那一批 RRSIG 沒能滿足這個條件。

更精確地說： DENIC 在這個時點把新的 KSK 設為「active signing」角色， 並用新 KSK 重簽 .de 的 DNSKEY RRset。 事後分析指向， 這個重簽過程裡至少有一批被發布到 public secondary 的 RRSIG， 當你拿 .de DNSKEY 裡對應的那把公鑰去驗證時， 怎麼算都不對。 簽章是「non-validatable」—— 這是 DENIC 自己對外的措辭， 沒有更細的技術歸因。 對驗證器來說， 這就是 bogus； 對 zone operator 來說， 這意味著生產鏈裡某一步沒有做端到端驗證， 把一份壞掉的簽章順著發布管道送到了全網。

為什麼這條 pipeline 沒有自我攔截？ 這是這次事件最值得 zone operator 反覆檢視的問題。 DNSSEC 的簽章流程本質上是離線完成的—— 在 HSM 或同等保護下， operator 用 KSK 簽 DNSKEY， 用 ZSK 簽 zone 內所有 RRset， 產出新的 zone file。 這個新 zone file 還沒有被任何 validator 看過， 它的「驗證對不對」只能透過事後 query 才會知道。 一個成熟的發布管道應該在「離開簽章機」與「進入 public secondary」之間， 插一個內部 validator 角色去做端到端 query， 對自家的權威伺服器發 query 並嘗試以 root trust anchor 驗證回應。 這層 self-validation 通過， 才放行給 public secondary。 這次事件存在本身就指出： DENIC 的 pipeline 在這一層要麼缺失、 要麼被某種特殊 path 繞過。

Cache 行為讓這層失誤被快速放大。 DNSSEC 的所有 RRset 都有 TTL， .de 的 DNSKEY RRset 典型 TTL 是 86400 秒（24 小時）， DS RRset 在 root 的 TTL 是 7200 秒。 當 DENIC 推送新 KSK 與新 RRSIG 時， 全球 resolver 並不是「同步立刻」看到新內容—— 有些 resolver 還握著舊 DNSKEY 的 fresh cache， 驗證仍然能過； 有些已經 expire 並去拉新的， 新的就壞了。 所以事件初期幾分鐘內， 全球各 resolver 看到的狀態並不一致： 這個 cache 還沒過期的看「一切正常」， 那個剛 refresh 過的看「全 SERVFAIL」。 對監控系統來說， 這意味著事故的「真正起點」會被誤讀為一個慢慢爬升的曲線， 而不是一個垂直跳起的台階。

下方這條時間軸把整個事件的關鍵節點放進可拖曳的 scrubber—— 把游標推到任意時間點， 可以看到那一刻全球驗證器看到的狀態描述。 這比起靜態 timeline 圖的好處是， 事件之間的時間距離不再被視覺壓縮： 你能直覺感受到「19:30 出事」到「22:17 Cloudflare 修補」之間其實是慢吞吞地過了 2 小時 47 分， 每一分鐘都有 cache 紀錄陸續落出 stale window、 SERVFAIL 比例慢慢爬升。 把它推到 20:30 那一格， 你會看到「resolver 操作者陸續上 NTA」—— 這是一個關鍵節點， 在它之前唯一在止血的是 stale-serve， 在它之後才有「主動繞過 DNSSEC」這條延長線開始發揮作用。

Cloudflare 在事後說得直接： 「any validating DNS resolver receiving these signatures was required by the DNSSEC specification to reject them」。 也就是說， 從 19:30 UTC 起， BIND、Unbound、Knot Resolver、PowerDNS Recursor、systemd-resolved、 所有 1.1.1.1 / 8.8.8.8 / 9.9.9.9 等公開 resolver—— 只要打開了 DNSSEC 驗證—— 都被規範本身強迫對 .de 的任何回應回 SERVFAIL。 沒有「降級」這個選項； DNSSEC 的安全模型就是建立在「驗證失敗等於不回應」之上的。

這個設計來自一個根本選擇： DNSSEC 解的是「資料在路上被改」這個威脅， 而不是「資料原本就壞」這個威脅。 當簽章算不過時， validator 沒有辦法區分「DENIC 操作失誤」與「中間人攻擊把簽章換掉了」—— 兩種情況看起來完全一樣。 保守的選擇必然是「兩者皆視為攻擊」， 把資料封鎖。 這個保守性是 DNSSEC 的價值所在， 也正是這次事件「沒有後門可走」的原因。 NTA 之所以是 operator decision 而不是 validator 自動行為， 正是因為這個降級決策必須由人來負責—— 自動降級會把整個密碼學保證腐蝕掉。

診斷訊號很乾淨。 打開 EDE (Extended DNS Errors, RFC 8914) 的 resolver 會在回應裡附帶結構化錯誤碼， 攻擊面分析直接讀 EDE: 6 (DNSSEC Bogus) 並把具體 RRset 標出來： 

;; status: SERVFAIL, id: 12345
;; EDE: 6 (DNSSEC Bogus): (RRSIG with malformed signature
;;     found for example.de/nsec3 (keytag=33834))

keytag=33834 指向 DENIC 在 rollover 中正在切換的那把 KSK； nsec3 則是 .de 用來做 authenticated denial of existence 的記錄類型—— 換句話說， 連「這個名字不存在」這種否定回應， 因為它的 NSEC3 鏈也被同一把 key 簽， 一樣會 bogus。 整個 zone 都被自己的簽章鎖了起來。

對訂閱了 Cloudflare 解析報告的客戶來說， 這個訊號出現的速度其實是「秒級」： 對 .de 的 query 仍然能進來， 但 1.1.1.1 在 cache miss 的時候必須回 upstream 去拿， 拿回來的 RRSIG 算不過， 於是合成出 SERVFAIL。 從 19:30:00 到 19:30:30， Cloudflare 自家的 dashboard 上對 .de 的 SERVFAIL 計數線就已經垂直拉起來—— 拉起來的瞬間， 事故已經是事故， 後續只剩「多大、多久、怎麼緩解」三題。

EDE 6 與單純的 SERVFAIL 在客戶端訊號處理上差異巨大。 沒有 EDE 的 resolver 只能對應用程式吐 SERVFAIL—— 一個語意極度模糊的錯誤碼， 可能是網路斷、 可能是權威死、 可能是 query 太大被 truncate、 可能是 DNSSEC 失敗， 應用程式無法分辨。 所以多數 HTTP client 與 OS resolver 看到 SERVFAIL 的 fallback 是「等一下再 retry」或「換 resolver 再試」—— 對 DNSSEC 失敗來說， 這兩個 fallback 都沒用： re-query 還是會撞到同樣的簽章、 換 resolver 多半會撞到同樣啟用 DNSSEC 的 resolver。 EDE 6 出現的時候， 客戶端原則上應該停止重試、 並把訊息傳達給使用者， 而不是無謂消耗網路。

為什麼一個 TLD 的簽章錯誤會把整個 .de 變成 SERVFAIL

DNSSEC 的信任鏈是嚴格的父對子： root zone 的 DNSKEY 由社群以 ceremony 形式管理； root 的 DS 指向 .de 的 DNSKEY； .de 的 DNSKEY 簽 .de 區內所有 RRset， 包括給每一個 example.de 的 DS。 驗證 www.example.de 的 A record 時， validator 從 root 一路往下檢查： 每一步的 DS hash 必須對得上下一層的 DNSKEY， 每一層的 RRSIG 都必須能用那把 DNSKEY 驗過。

這個設計的隱含假設是「每一層的操作者都比下一層更可信」。 Root 的 KSK 由 IANA 與 RSSAC 透過實體 ceremony 管理， 每年只動兩次、 每次有公開錄影、 十多位 trusted community representative 與會。 .de 的 KSK 由 DENIC 管理， 操作頻率高很多， 但仍然在 HSM 內、 流程有 dual control。 example.de 自己若簽 DNSSEC， 可能就是 ZSK 在自動化 pipeline 裡跑—— 操作頻率可能很高， 但範圍只影響自己一個 zone。 這種「越上層、操作越保守、影響範圍越大」的金字塔， 在這次事件裡正好相反過來： DENIC 這層中等保守的操作出了失誤， 把下面所有層級都拖下水。

下面這張圖把信任鏈的五個主要角色拆開—— 點任意元件可以看到它在這次事件裡承擔了什麼責任、 知道什麼、 不知道什麼。 這比起一張只標箭頭的 architecture 圖能多攜帶一層資訊： 你能讀到每個位置「故障時誰應該動、 誰被綁住、 誰其實沒做錯事」。 特別注意「不知道什麼」這欄—— DNS 的故障常常正是因為某一層假設下一層「知道」自己根本不知道的事情。

關鍵設計在於： 任何一層斷掉， 下面所有層級都失效。 Validator 看到 .de 的 DNSKEY RRset 無法用 root 的 DS hash 對應的那把鑰匙驗過—— 或者 .de 內某個 RRSIG 完全 malformed—— 它就會把整棵子樹標成 bogus。 請注意四個 DNSSEC 狀態的差別：

  • secure：鏈完整、所有 RRSIG 驗證通過、資料可信。
  • insecure：父區沒有發布 DS，子 zone 明確選擇不簽——這是合法狀態，validator 直接放行。
  • bogus：父區發布了 DS（宣告子 zone 應該簽），但 RRSIG 驗證失敗。這時規範要求 validator 必須回 SERVFAIL，不得回答 query 結果。
  • indeterminate：較罕見，validator 無法判斷父區是否啟用 DNSSEC（例如查不到 trust anchor）。

DENIC 那批簽章把整個 .de 推到了 bogus 狀態。 example.de 本身有沒有簽 DNSSEC 都不重要—— 它的 DS（如果有）放在 .de 區裡， 連帶被無效 RRSIG 拖下水； 它的 NS 紀錄也是 .de 區的 referral 一部分， 同樣 bogus。 對 validator 來說， .de 整個 zone 失去了密碼學意義， 只能對任何來自這個樹的查詢回 SERVFAIL。

對最終使用者就是： 德國的銀行、 鐵路、 電商、 新聞—— 只要域名以 .de 結尾， 瀏覽器都連不上。 對 .de 這種規模—— 以全球 TLD 排名「one of the largest」算—— 意味著「millions of domains unreachable」。 Cloudflare 的事後報告沒有給出精確的影響百分比， 但他們自家的 1.1.1.1 query log 顯示對 .de 的 SERVFAIL 在 19:30 之後立即跳起， 並隨著各層 cache 逐步過期持續攀升三小時。

這裡有一個值得單獨指出的細節： .de 的 NSEC3 鏈也壞了。 NSEC3 是用來簽「這個名字不存在」這種否定回應的—— 把所有名字 hash 過後排序、 簽相鄰兩個 hash 之間「沒有別的東西」。 它的簽章由同一把 ZSK 產生。 所以這次事件不只是「正面查詢拿不到答案」， 連「明知道不存在的名字」也拿不到「確認不存在」的回應。 對應用層的影響是， 瀏覽器的 NXDOMAIN fallback、 DNS-based ad-blocker 的負面 list 查詢、 email 的 SPF/DKIM/DMARC lookup—— 全部一視同仁 SERVFAIL。

這個 NSEC3 細節對 email 系統影響特別大。 SPF 與 DMARC 的 lookup 在許多實作裡會把「DNS 查不到」當成 fail-open（允許這封信通過）， 但若 query 回 SERVFAIL， spam filter 可能會把它解讀為 transient error 而 defer—— 使得在事件期間， 所有 .de 寄出去的合法郵件都進入 retry queue。 使用者體驗是「我寄出去的信沒人收到」， 收件方體驗是「.de 的伺服器今晚怪怪的」。 這條鏈條讓 DNS 故障跟 email 故障的時序往後拖了好幾小時—— 在 DNS 恢復之後， email retry queue 還要花更久把堆積消化掉。

KSK rollover 的五步操作——以及這次卡在哪一步

把鏡頭拉回故障的起點： DENIC 到底做了什麼操作， 才會推出一批 bogus 的 RRSIG？ 標準的 KSK rollover 流程（RFC 6781 第 4.1.2 節， Double-KSK 方案）是個五步舞， 每一步都有明確的 cache 過渡期。 下面的 scroll-driven 圖示把這五步拆開—— 把這篇文章往下捲， 每捲一段你會看到右側的 trust-chain 狀態變一次， 紅色高亮指出這次事件可能卡在哪一步。

Step 4 是這次事件的最大嫌疑點。 從 EDE 訊息裡的 keytag=33834 與 NSEC3 失敗共同指向「DENIC 用新 KSK 角色重簽 DNSKEY、 ZSK 又重簽整個 zone 時， 至少一批 RRSIG 算錯了」。 這種錯誤通常不會來自演算法本身—— SHA-256 + RSA 之類的標準組合都很穩—— 而是更可能來自簽章生成 pipeline 的某個邊界條件： 簽到一半換 key、 把舊 key 的 timestamp 帶到新 RRSIG、 或是 zone serial / record ordering 在某種狀況下與簽章時的快照不一致。 DENIC 還沒公布細節。

一個值得猜測的失敗模式是 inception/expiration timestamp 不對。 RRSIG 帶兩個時間戳： inception（這個簽章從什麼時候開始有效）與 expiration（什麼時候失效）。 Validator 如果在「現在」之外的時間驗證這個簽章， 一律 bogus。 KSK rollover 過程中， 若簽章生成腳本錯誤地把新 KSK 的 inception 設成未來時間（例如時區處理錯誤、 或從一個 stage 環境拷貝了 timestamp）， validator 就會在「現在」驗證時拒絕。 這個失敗模式的特性是「在 inception 還沒到之前一直 bogus、 到了 inception 之後突然全 PASS」—— 這正好與 DENIC 在 22:30 UTC「修正簽章」的描述吻合（也許他們做的就是重簽一份正確 inception 的 RRSIG）。 當然這只是猜測， 具體細節要等 DENIC 自己出 postmortem。

真正的工程教訓不在「這次具體錯哪裡」， 而在「為什麼壞掉的 RRSIG 能順著發布管道走到 public secondary 而沒被攔住」。 DNSSEC 簽章流程的閉環應該是： sign → push to internal validator → run real query against own RRSIG → if PASS, push to public。 這個 self-validation 步驟是把「簽生產失誤」與「全網中斷」隔開的最後一條防線。 這次事件的存在本身就說明這條防線在 DENIC 的 pipeline 裡可能沒拉到那個層級， 或者拉了但被某種特殊 path 繞過。

Pre-publish validation 的設計細節值得展開。 它不是「跑一個 BIND 並對自家簽章 RRSIG 做一次驗證」這麼簡單—— 那只能抓 syntactic error。 真正有效的驗證必須： (a) 用 root 真實 trust anchor 從上而下完整跑一次解析， (b) 在內部模擬 fresh resolver（沒有 cache、沒有任何 trust shortcut）， (c) 對 zone 內代表性的 RRset 全部都驗一遍—— DNSKEY、各 DS、各 NS、NSEC3 鏈、wildcard、否定回應。 這樣才能 catch 像「NSEC3 鏈計算 bug」「特定字元組合的 hash 邊界」這種非典型失敗。 對 TLD 級別的 zone operator， 這層 validation 應該是強制 pre-deploy gate， failed deploy 不應該能被人為 override 推出去。

stale-serve 與 NTA——兩條延長線怎麼撐到 22:17

嚴格按照規範， 19:30 UTC 之後德國網際網路就應該完全停擺三小時。 實際上沒有—— 這是因為兩個「在規範邊緣」的工程實踐救了場： 1.1.1.1 用 serve-stale 撐住已被快取的紀錄， 而全球 resolver 操作者用 NTA 從第一個小時內就開始繞過 DNSSEC 對 .de 的檢查。 下面這張表把這兩個機制與相關的「規範後援」放在一起： 什麼時候自動啟動、 什麼時候需要人為決策、 安全代價、 覆蓋面是什麼。

Serve-stale (RFC 8767) 是 2020 年標準化的一個 recursive resolver 行為： 當權威伺服器無法回應， 或回答持續失敗， resolver 可以繼續服務 cache 裡已過期的紀錄， 避免使用者直接看到 timeout。 1.1.1.1 預設啟用了這個機制。 所以 19:30 UTC 之後， 那些「最近被查過一次」的 example.de、 www.spiegel.de、 db.de—— 只要 cache 裡還有一份 fresh-or-stale-but-recent 的紀錄， 使用者仍然能解析。 Cloudflare 的圖顯示 NOERROR 比例「remained relatively stable」， 那條曲線就是 serve-stale 撐起來的。

Serve-stale 的設計細節有意思的地方在於它的「stale-answer-ttl」參數： 當 resolver 決定用 stale 紀錄回應時， 它會在回應上覆蓋一個很短的 TTL（典型 30 秒）， 避免下游再 cache 太久。 這個短 TTL 同時起到「主動探測」的作用： 每 30 秒下游會再來查， resolver 就有機會再試一次去 upstream 拿 fresh data—— 若 upstream 仍然壞， 繼續 stale； 若已修好， 立即恢復 fresh cache。 這個 self-probing 機制讓 serve-stale 從「失敗緩衝」變成「快速恢復偵測」。 對這次事件， 它意味著 DENIC 一旦修好簽章， 1.1.1.1 在最多 30 秒內就能切回正常解析—— 不需要任何主動的 operator action。

但 serve-stale 不是萬靈丹。 它有兩個天然限制： 第一， cache 沒有的紀錄它救不了—— 任何「使用者今天第一次查」的 .de 域名， 都會直接撞上 SERVFAIL。 第二， stale 也是有上限的（典型一天）， 而且大型 zone 的紀錄會逐步過期， 曲線會慢慢往下走。 所以隨著時間推移， 更多紀錄落出 stale window， SERVFAIL 的相對比例會持續攀升—— 這就是為什麼 Cloudflare 的描述是「climb over 3 hours」而不是「立即衝頂」。

從產品角度看更明顯： 高流量電商或銀行的首頁， cache 裡幾乎一直有最新的紀錄， 使用者完全感覺不到事故。 但是當使用者點到網站上某個少見的子網域—— 客服頁、 靜態資源 CDN 的某個 region 子網域、 APP 動態打的 SaaS 子網域—— 這些 cache 沒見過、 需要新查的名字， 就會在事故期間直接 SERVFAIL。 終端使用者體驗到的是「首頁進得去， 但點完帳號頁就一片白」這種怪現象。

另一條延長線是 NTA。 RFC 7646 定義的 negative trust anchor 是一種 operational override： resolver 操作者可以對特定 zone 暫時關閉 DNSSEC 驗證， 相當於告訴 validator「這個 zone 就當它 insecure 處理」。 NTA 一掛上去， .de 的 RRSIG 是否驗證通過就不再重要， resolver 直接把資料回給 client。 代價是顯而易見的： 在 NTA 生效期間， 攻擊者若能在 .de 上 spoof 紀錄， validator 不會發現—— 你用安全性換可用性。 

# Unbound 範例：對 .de 暫時掛 NTA
domain-insecure: "de."
# BIND 範例：
rndc nta -lifetime 6h de.
# Knot Resolver 範例：
trust_anchors.set_insecure({ 'de.' })

NTA 的設計很狡猾的一點是「lifetime」必有上限—— RFC 7646 建議 24 小時， 多數實作預設更短（6 小時）。 原因是： NTA 是緊急止血， 不該變成永久 workaround； 如果 zone 還沒修好， operator 必須主動續期， 這個動作本身強制 operator 回去看狀況。 BIND 的 rndc nta 命令還會在過期時自動寫 log， 讓 NTA 不會被忘記。

更隱微的設計考量是 NTA 的「衰退路徑」必須明確。 當 NTA 接近 expiration、 或被 operator 主動撤掉時， resolver 不能直接「砰一聲恢復 DNSSEC 驗證」—— 若 zone 還沒修好， 這會讓全部使用者重新撞到 SERVFAIL。 成熟的實作會在 NTA expire 前先做一次 quiet probe： 嘗試以正常 DNSSEC 驗證對 zone 做幾次內部 query， 若全 PASS 才真的把 NTA 撤掉。 這層 graceful exit 對使用者來說是無感的， 但對 oncall 來說可以避免「我撤掉 NTA 後系統又壞了」這種尷尬時刻。

事件中真正讓 NTA 有效的， 是 DNS-OARC 這個業界協調管道。 OARC 的 Mattermost 從 19:30 之後幾分鐘就有人開始 cross-check： 「我也看到 .de 變 bogus」、 「我這邊 keytag 33834 的 RRSIG 對不上 DNSKEY」、 「我準備上 NTA 了，誰跟」。 Cloudflare 在事後敘述裡寫得清楚： 「Resolver operators across the Internet independently applied Negative Trust Anchors within an hour, restoring resolution.」—— 一小時內， 全球主要 recursive resolver 操作者各自獨立決定上 NTA。 沒有單一指揮， 但事實上的協調發生在那個聊天室裡。

這種「事實上的協調」是 DNS 生態的隱性基礎建設。 OARC 的 mailing list、 Mattermost、 定期 workshop—— 它們不在任何 SLA 上， 沒有合約義務， 但對於跨組織的 DNS 事故來說， 是唯一能在分鐘級內把各家 resolver 操作者拉到同一個對話的地方。 對需要設計類似事故 IR 的工程團隊， 這條經驗值得抄： 「我們有沒有一個非正式的對話空間， 能讓友商在 30 分鐘內告訴我們他們看到的東西？」 如果沒有， 下次跨組織事故就只能靠 Twitter 看新聞。

對比之下， 其他類型的網際網路基礎建設並沒有這麼成熟的協調管道。 BGP 異常通常仰賴 NANOG mailing list 或 RIPE 的協調—— 速度慢得多。 TLS / CA 事故有 mozilla.dev.security.policy 這種討論串， 但時程是天級而不是分鐘級。 CDN 之間的協調更幾乎不存在。 DNS-OARC 的存在某種程度上是「DNS 社群早年就被自己嚇到過」的結果—— 經歷過 cache poisoning、 BGP hijack DNS、 多次 root server attack 之後， 這個社群長出了一種「先吹哨再處理」的反射， 而 OARC 成了那個哨子。

Cloudflare 自己的 1.1.1.1 是 22:17 UTC 才部署正式 override， 比一般操作者晚得多—— 這部份反映了大型公開 resolver 的決策審慎度（停 DNSSEC 是一個有政策意涵的動作）， 也反映了 stale-serve 已經把痛點壓得夠低， 讓 Cloudflare 有空間先確認 DENIC 的狀態再決定行動。 Cloudflare 的內部評估直白： 「There is no user of 1.1.1.1 resolving a .de name right now who would prefer a SERVFAIL over an unvalidated response」—— 換句話說， 當「正確但拿不到」比「拿到但不再有密碼學保證」更糟時， override 就應該動。 22:30 UTC 前後 DENIC 自己也修正了簽章； NTA 與 override 在驗證恢復後被陸續撤掉。

把這三個小時切片來看： 第一小時（19:30–20:30）是「stale-serve 撐、 各家 NTA 陸續上」， 多數使用者感覺不到事； 第二小時（20:30–21:30）是「cache 持續衰退、 未上 NTA 的 resolver 開始痛」； 第三小時（21:30–22:30）是「DENIC 與 Cloudflare 各自完成最後修補」。 這個時序裡有一個經常被忽略的設計觀察： 當系統有充足的「軟」緩衝（cache、 stale、 replication）， 故障的可見性不會在第一秒爆發—— 它會像血壓上升一樣慢慢來， 給工程團隊一個按部就班處理的窗口。 沒有 serve-stale， 這次事件會在 19:30 就成為頭條新聞； 有 serve-stale， 它在第二小時前都還是 DNS-OARC 群裡的內部話題。

這個「軟緩衝給時間」的觀察可以類推到其他基礎建設層。 CDN 的 origin shielding 在 origin 出事時撐幾分鐘到幾小時、 HTTP 的 stale-while-revalidate 在後端慢時撐使用者體驗、 Kafka 的 in-flight buffer 在 consumer lag 時撐 producer—— 每一層都遵循同樣的設計哲學： 把「快速失敗」轉換成「慢速衰退」， 換取人類處理時間。 DNSSEC 的 stale-serve 與 NTA 只是這條哲學在 DNS 層的具體實現。 對任何新建系統的設計者， 這條哲學值得反覆檢視： 我們的系統在依賴失效時， 給 oncall 多少緩衝時間？ 這個問題的答案決定了事故的嚴重度。

事後檢討——EDE 的可觀測性、rollover 的可逆性、NTA 的剛需化

DENIC 的官方說法很短： 「The outage is linked to a routine, scheduled key rollover. During this process, non-validatable signatures were generated and distributed.」 並宣布暫停所有後續 KSK rollover 直到根因分析完成。 對社群來說， 這意味著 .de 在可預見的未來會繼續使用同一把 KSK—— 這延長了 key 的暴露時間， 但避免了在根因未明前再踩一次。 從威脅模型角度看， 這個取捨偏可用性： KSK 暴露時間延長是「理論風險」， 再踩一次是「驗證過的具體傷害」。

Cloudflare 在事後文章裡點名自己一個小缺陷： 1.1.1.1 在這次事件中對部分查詢誤回 EDE 22 (No Reachable Authority)， 而非正確的 EDE 6 (DNSSEC Bogus)。 對下游使用者來說， 這兩個錯誤碼指向不同的處理路徑—— EDE 22 暗示「網路／權威伺服器問題」， EDE 6 才正確點名「密碼學失敗」。 誤碼會讓客戶端的 fallback 邏輯（例如「換一個 resolver 再試」）做出錯誤決策。 Cloudflare 自己的描述指出問題在「The verifier detects a bogus signature it creates the DNSSEC Bogus EDE code, but this is never inserted into the response」—— 驗證器內部分類對了， 但 EDE 6 沒被寫進回應包。 這是一個 propagation bug， 不是分類 bug。 Cloudflare 承諾改善 DNSSEC 失敗時 EDE 碼的傳播精確度—— 這是這次事件對 1.1.1.1 自身行為的主要改動。

Propagation bug 比分類 bug 更難發現， 這值得單獨講一句。 分類 bug 在單元測試裡很容易抓—— 給驗證器一個壞 RRSIG， 檢查它回的錯誤類型是不是 6。 但 propagation bug 跨越的是「驗證器內部」到「最終 DNS response」之間的整個 stack—— 必須在 integration test 裡才看得到， 而 integration test 又必須讓真實的 query 走完整條路徑。 當這條路徑跨越多個微服務、 多個語言、 多個團隊維護的元件時， propagation bug 就會慢慢累積。 Cloudflare 這次事件抓到的這個 bug， 可能就是 Big Pineapple 內部驗證模組與 response builder 之間， EDE 欄位在某條 path 上沒被傳遞—— 這種 bug 在正常 happy path 不會出現， 只有在「驗證失敗 + 特定 query 類型」這種 cross product 才會浮現。

對其他 zone 操作者， 可以學到的有幾項：

  • Rollover 的可逆性是一線議題：DENIC 把無效簽章「推出去」之後，要等 TTL 自然過期才能完全撤回。設計 rollover 流程時，「能不能快速撤回上一步」應該與「能不能往前推下一步」一樣被 drill。具體做法是讓上一輪的 RRSIG 保留在生產備援，緊急時 30 秒內能切回。
  • Pre-publish 驗證不可省：在簽章被推送到 public secondary 之前，內部 validator 應該對新生成的 RRSIG 做端到端驗證——這次事件的本質是「驗證步驟在發布鏈中遺漏了」。實作上是在 sign → publish 之間插一個 query loop：對自家權威伺服器做正常 query，validator 角色驗證 RRSIG，PASS 才繼續推。
  • EDE 是 DNS 可觀測性的剛需：如果中間商 / resolver 不傳遞 EDE 結構化錯誤碼，使用者只看到 SERVFAIL，根本判別不出是 DNSSEC 失敗、權威死掉、還是網路問題。RFC 8914 從可選的 nice-to-have 變成了「事故 IR 必備」。內部 monitoring 應該對 EDE 6 / 7 / 9 / 10 等 DNSSEC 相關碼設專屬告警。
  • NTA 是一把雙刃刀：它是事件當下唯一能在分鐘級內全球生效的緩解工具，但它也讓 DNSSEC 的安全承諾在那段時間內歸零。任何 resolver 操作者都應該預先把 NTA 的部署/撤除流程寫進 runbook，包含「最長保留時間」這個自我約束。不要讓 NTA 變成「我們忘了關」的長期狀態。
  • DNS-OARC 是 IR channel：對任何運行 recursive resolver 的組織來說，OARC 的 Mattermost 應該是 oncall 預設加入的群組。在事故發生時，你需要的不是「自己看 dashboard」，而是「跟其他 resolver 操作者交叉確認自己看到的不是局部現象」。

對 application 層的開發者， 這次事件也帶幾個提醒。 第一， DNS resolution failure 不是 transient error—— 遇到 SERVFAIL 不要無腦 retry， 要看 EDE 碼決定行為。 EDE 6 / 7 / 9 / 10 屬於 DNSSEC 相關， retry 沒用， 正確做法是切換 resolver（從 ISP DNS 切到 1.1.1.1 或 8.8.8.8）或讓使用者看到合適的錯誤訊息。 第二， 如果你的服務嚴重依賴某個 TLD 的可用性（例如你是 .de 上的 PaaS）， 你應該在 monitoring 裡有「我自家域名的 EDE 6 比例」這個指標。 第三， DNS 的故障有強烈的地理不均勻性—— 這次事件對德國使用者影響大、 對其他地區只有「正好查 .de」的人受到影響， 所以你的全球可用性 dashboard 必須能按 resolver 區分。

第四個提醒值得單獨強調： 服務依賴的「外部 DNS 名字」應該被當成一條看不見的關鍵相依。 多數 application 把 DNS query 隱藏在 HTTP client 或 SDK 的底層， 視為「總是能解的」基礎建設—— 這個假設在 5 月 5 日這天破產了。 成熟的系統設計應該對外部 DNS 名字有一份明確 inventory： 哪些 hostname 是 critical path、 哪些可以 graceful degrade、 哪些有 fallback。 在 critical path 上， 最好在 application layer 自己做一層 DNS cache， 並讓這層 cache 在 upstream resolver 全 SERVFAIL 時仍能服務舊紀錄—— 本質上就是把 stale-serve 從 OS resolver 拉到 application layer。

更大的脈絡是： DNSSEC 是一個「全有或全無」的系統。 它要求父子兩層的操作都精確一致， 否則整個子樹失效。 這次事件是個提醒， 但不是 DNSSEC 該被放棄的理由—— 同樣的 stale-serve、 NTA、 EDE、 DNS-OARC 協調機制， 正是為了讓「全有或全無」這個邏輯架構在現實工程裡仍能容忍人為失誤而設計的。 三小時不是好結果， 但三小時內全球 resolver 操作者能各自獨立地把流量恢復到接近正常， 本身就是 DNS 生態相對健康的證據。

從更長期的角度， 這次事件還會推動兩個方向的討論。 第一是 KSK rollover 的自動化標準化—— 目前各 TLD 的 rollover 流程仍然帶大量手工色彩， CDS / CDNSKEY（RFC 7344, 8078）這套「子區用 in-band 機制通知父區更新 DS」的協定已經存在多年， 但在大型 TLD 上仍然採用率不高。 如果 DENIC 之類的 zone 能把整個 rollover 流程做成可重複執行的 IaC pipeline， 端到端 self-validation 也容易自然成為其中一步。 第二是 EDE 的下游傳播—— 目前 stub resolver 與應用層對 EDE 的支援普遍不足， 瀏覽器更幾乎完全不顯示 EDE 細節給使用者看， 這層斷裂讓「DNSSEC 失敗」對終端使用者來說仍然是個謎。 改善這層需要的是漫長的瀏覽器與作業系統合作， 但 5 月 5 日這天， 這個需求變得比以前更具體了。

DNSSEC 部署本身仍在緩慢推進。 2026 年的全球 DNSSEC validation 率大約在 35% 上下（依不同來源）， 部署率（簽 DNSSEC 的 zone 比例）更低。 一次 TLD 級的事故對「應不應該打開 DNSSEC」的辯論一定會有影響—— 悲觀派會說「看吧、 DNSSEC 就是脆弱」， 樂觀派會說「這次事件三小時就過去了， 沒有 DNSSEC 我們連這層保護都沒有」。 我個人偏樂觀派： DNSSEC 解決的「在路上被改」這個威脅是真實存在的， 放棄這層保護的代價遠大於三小時的可用性。 但要說服悲觀派， 社群必須拿出更穩定的 rollover 流程、 更好的觀測性、 更明確的緩解 playbook—— 這次事件正好把這些議題都帶到桌面上了。

最後值得提一句的是這次事件對未來 KSK ceremony 的影響。 Root KSK 的 ceremony 每年只動兩次、 流程嚴密； 各 TLD 的 KSK 操作頻率與嚴謹度差異很大。 這次事件之後， DENIC 暫停後續 rollover 直到根因清楚—— 但根因清楚之後呢？ DNS 社群應該會討論是否需要對 TLD 級 KSK 操作建立更嚴格的同行審查或第三方驗證機制， 類似 CA / Browser Forum 對 CA 操作的審計要求。 這條路要走多久不好說， 但 5 月 5 日把它放回了議程上。

The lesson： DNSSEC bogus 是一條沒有妥協的規範線， TLD 級的簽章錯誤會把整棵子樹推下這條線； 真正能在現場救場的， 是把 stale-serve、 NTA、 EDE、 與 DNS-OARC 這類業界協調管道當成 IR 一級工具， 而不是 nice-to-have—— 這次 .de 三小時的代價， 是這套組合確實能撐住的證據， 也是它必須撐住的提醒。
