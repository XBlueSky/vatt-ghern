2023 年 11 月 Notion AI Q&A 上線那一刻，數百萬 workspace 同時排上了候補名單；負責後端向量搜尋的小組買進了一批 dedicated pod，storage 與 compute 綁在同一台機器，按「資料庫開機時間」計費。兩年之後，這些 pod 全部消失，取而代之的是 Turbopuffer 的 object-storage namespace、DynamoDB 裡的 xxHash64、以及一條跑在 Ray Serve 上的 embedding 服務——總成本砍掉九成、p50 query latency 從 100 ms 壓到 50 ms。

{{ title }}

這篇是 Notion 向量搜尋兩年的演進——四個階段，每一段都明確對應一條成本曲線或一個架構瓶頸，沒有 big-bang rewrite，也沒有單一銀彈。組件選擇本身並不稀奇（Spark、Kafka、Turbopuffer、Ray、DynamoDB 都是現成的），值得記下的是每一次切換背後的判斷：什麼條件下，「換掉這一塊」比「再優化原本那塊」便宜。

一個檢視框架先擺在前面：對任何資料密集型 service，總成本可以拆成三條曲線——「為 capacity 預留付的固定成本」、「為單位操作付的可變成本」、以及「為了把資料保持新鮮付的重複工作成本」。Notion 這兩年的四個動作剛好對應這三條曲線的不同位置：第一段砍預留固定成本；第二段砍單位操作成本；第三段砍重複工作成本；第四段把單位操作成本再砍一輪、並順手把另一塊預留固定成本（embedding GPU pod）整個拆掉。

這個三條曲線的框架有個容易被忽略的細節：三條曲線之間並不獨立。把 dedicated pod 換成 serverless，砍掉的不只是 over-provision 的固定成本，也順帶讓「dedicated SSD 的容量成本」這條結構性曲線變成「object storage 的容量成本」——後者一旦切到，下一段才有條件再砍重複工作（因為 hash diff 的儲存與查詢是建在 DynamoDB 上、跟 vector storage 解耦）。換言之，這四段的順序不是任意的，而是「前一段的結果是後一段的前提」——這也解釋了為什麼這套劇本不能跳關。

四個階段裡，第一段（serverless）與第四段（Ray）是相對「直接的工程置換」——換廠商方案、換 compute 模式，可以複製貼上其他公司的經驗。第二段（換引擎）跟第三段（hash diff）才是 Notion 真正需要自己想清楚的判斷：什麼時候該換底層引擎、什麼時候該在 application 層加 dedup、什麼時候兩件事都該做。這份判斷的價值遠超過具體技術選型，因為廠商方案會變、開源工具會更替，但「在這個 cost shape 下該換哪一層」這個判斷力是長期可複用的。

在開始走進每個階段之前，先把整段時間線視覺化擺出來。下面是一個 scroll-driven 的 walkthrough：左邊是時間順序的四個階段卡片，右邊的 sticky 圖會隨閱讀進度切換到對應階段的架構快照。每一格的重點不是「畫了哪些 box」，而是「這一段砍掉了什麼支出」——換言之，每個 stage 對應的不只是技術切換，更是一條被刪掉的計費邊界。

2023 年的 dedicated pod——storage 與 compute 為什麼綁在一起就撐不住

第一版架構在 2023 年 11 月 Notion AI Q&A 上線那天就跑起來了。設計圖很標準：兩條 ingestion path 同時餵向量資料庫——offline 那條由 Apache Spark 跑批次任務，對既有頁面做 chunking、呼叫 embedding API、bulk-load 到向量索引；online 那條由 Kafka consumer 處理頁面即時編輯，把變更打進索引，端到端延遲控制在 sub-minute。前端的 Q&A 查詢則走另一條短路徑：把查詢字串送進 embedding model、拿回 query vector、丟到向量資料庫做 ANN 搜尋。

這個 dual-path ingestion 不是空想——它是為了應對兩種完全不同的工作量：bootstrapping 一個新接入的 workspace 可能要處理數百萬頁，這只有 Spark 規模的並行批次能在合理時間裡完成；而既有用戶的日常編輯量是「小變動高頻次」，那條路徑必須走 streaming，否則「我剛改的東西為什麼搜不到」就會立刻變成支援 ticket。把這兩條路保持獨立，是 Notion 兩年中一直沒動過的根基——後面所有的演進都是在替換或優化「向量資料庫」與「embedding 計算層」，但 ingestion 的 dual-path shape 一直在。

這個架構穩定性還有一層意義：當底層引擎要換的時候，dual-path 提供了天然的雙寫平台。新引擎可以先掛在同一條 Kafka 後面收 online 寫入，Spark 也可以同時 bulk-load 到新舊兩邊；要驗證新引擎的時候只需要在 query path 上設 feature flag。後續所有的引擎切換——從 pod 到 serverless、從 serverless 到 Turbopuffer——能不停業務地搬完，這個 dual-path 結構是 silent enabler。

真正的痛點不在這兩條 path，而在「向量資料庫長什麼樣」。當時用的是 dedicated pod 模型——每個 pod 是一整台機器，storage 跟 compute 綁在一起。Notion 把 workspace ID 當分片 key、用 range partitioning 把不同 workspace 散到不同 pod 群，這個設計刻意模仿了既有 Postgres 的分片邏輯，讓營運心智模型一致——同一個 workspace 在 Postgres 跟向量資料庫上「應該找哪台機器」的回答是同構的，這對 oncall debugging 是很大的省心。

為了應付容量擴張，他們做了一個 generation-based 路由：當一組 index 接近容量上限時，不去重新 reshard 既有資料，而是 provision 一組新的 index、把新 workspace onboarding 導向新 generation；每個 generation 有自己的 ID，決定讀寫去哪。為什麼不 reshard？因為 reshard 在 pod 模型下意味著「把所有 vector 從一台機器複製到另一台機器」，這個過程要麼 pause 寫入要麼承擔 race condition，對「不能停 onboarding」的 product 是不可接受的——而且 reshard 本身的 IO 跟計算成本也很高。Generation-based 是一個典型「用時間換空間」的設計：付一點長期的路由表複雜度，換來短期的零停機擴容。

這個 generation 設計後來證明是 Notion 整段歷史裡最值得記下的營運模式——它最初是 pod 模型下的緊急 workaround，但「逐代 cutover、新流量導新代、舊代慢慢退役」的思維後來被沿用到 Turbopuffer 的搬遷上，甚至成為「資料層引擎更換」這類動作的 default playbook。把 cohort 這個維度埋進系統設計的早期，後面所有的大遷移都會更便宜——這不是事後諸葛，而是一個可以提前選擇的設計傾向。

看起來很 clean，問題出在計費模型。Pod 廠商按「資料庫開機時間」計費，不是按實際使用量——一旦預留出來，不管有沒有用滿，帳單就持續累積。Notion AI 上線即爆量，「上線一個月後 index 就接近容量」——這個節奏意味著如果要保留 headroom，就得長期 over-provision、付一個遠超實際使用的固定成本。更糟的是這種計費結構與業務曲線完全反向：白天高峰、夜間低谷，按開機時間付費沒辦法在低谷時把錢省回來。

同時，多個 generation 共存讓營運心智變得複雜：路由表要維護、跨 generation 的 reindex 要協調、debug 一個 workspace 的查詢得先查它屬於哪個 generation。Generation 數量隨著時間單調增長——每幾個月就會多一個 generation，永遠不會合併。對 oncall 來說，「這個查詢慢」變成「先看 workspace 在哪一代 → 看那一代的健康狀況 → 看那一代下分到哪台 pod → 看那台 pod 的狀態」，rabbit hole 很深。

跨 generation 的 oncall 還有個隱性成本：alert 配置必須複製給每一代，但是每一代的「合理門檻」會隨著 cohort 大小與年齡不同——新一代裡放的多是 onboarding 中的活躍 workspace，query QPS 普遍高；舊一代裡留下的多是低活躍 workspace，QPS 低但 storage 大。一個 alert 配置複製到不同 generation 上會大量誤報或漏報。最後的辦法常常是「為每個 generation 單獨調 threshold」，這把 alert 配置文件膨脹成單調增長的維護負擔。 

// 2023 年的查詢路徑——pod model 下的路由
def search(workspace_id, query_text):
    generation = lookup_generation(workspace_id)   // 哪一代
    pod_id     = range_shard(workspace_id, generation)  // 哪台 pod
    query_vec  = embed(query_text)                 // 走外部 API
    return pods[pod_id].ann_search(query_vec, top_k=20)

// generation 滿了：
//   不 reshard 既有資料，而是 provision 新的 index set、
//   把新 workspace 都導向 generation N+1。
//   代價：路由表越來越胖、跨 generation reindex 是噩夢。

2023 年底到 2024 年 4 月之間，這套架構靠著「持續加 pod、持續調 generation」勉強撐住了業務量擴張。具體數字很驚人：daily onboarding 容量提升 600 倍（從每天數百個 workspace 上升到單日數十萬量級），active workspace 數 15 倍、vector DB 容量 8 倍，4 月時把累積的百萬等級候補名單清空。這 600 倍很大一部分要歸功於 Airflow scheduling + Spark tuning——讓 onboarding 批次可以在離峰時段插隊、在尖峰時段讓位，把同樣的計算資源用得更精細。

但帳單也以類似節奏在增加——dedicated pod 的計費結構天生不站在「使用率波動大」的客戶這一邊。到 2024 年 4 月候補清空時，工程團隊有了第一次系統性回頭審視成本結構的空間：上線那波的「先撐住」階段過了，接下來的問題從「能不能跑」變成「跑得起多久」。這個轉折是組織裡很常見的——危機模式下沒人有功夫優化計費，等業務指標止跌、候補清空，cost 才會浮上來成為下一個季度的主旋律。

這裡有個值得記下的組織觀察：「能不能跑」與「跑得起多久」需要的是完全不同的工程心智。前者強調速度、容忍粗糙；後者強調量化、容忍迭代。團隊從前一種心智切到後一種心智並不自動發生，常常需要明確的「stop adding capacity, start measuring cost shape」決策——而這個決策在組織裡是不容易做的，因為「停下來算帳」聽起來像是在減速。Notion 這次能成功切過去，部分原因是候補清空提供了一個自然的休息窗口；如果業務繼續爆炸性成長，這個切換點會被一直延後。 

# Pod model 下的「能 scale 但不能省」
# 假設一個 workspace 平均使用率 30%，pod 在 50% headroom 下 provision
#  → 實際付費容量 = 1.5x 預期峰值 ≈ 5x 平均實際使用
#  → 每多 1 個 workspace，固定成本是平均使用的 ~5 倍
#  → 沒有空間用「夜間關機」省錢，因為 pod 是恆定 provisioned
storage:  bound to pod, paid by uptime
compute:  bound to pod, paid by uptime
scaling:  add pods → add fixed cost
shrink:   ~impossible (data lives on the pod)

2024 年 serverless 化：解耦 + 換 Turbopuffer，砍 60% 搜尋成本

2024 年 5 月做的第一個動作是同一家廠商內部的方案切換——從 dedicated pod 改成 serverless 模式。技術差別只有一個關鍵字：storage 與 compute 解耦，計費從「資料庫開機時間」變成「實際 query 與儲存用量」。對 Notion 這種「白天高峰、夜間低谷、跨時區但仍有明顯波形」的查詢流量，serverless 立刻把峰值的 over-provision 浪費省掉，整體成本相對 pod 模式降了 50%。容量限制也消失了——不需要再為「快滿了」provision 新 generation，理論上 generation 路由表可以開始凍結。

這個切換本身的工程量並不小（要驗證 query latency 沒有 regression、要設計 traffic 遷移節奏），但比起後面要做的 Turbopuffer 遷移仍算「同一家廠商內」的局部優化。Notion 的描述是「省下幾百萬美元」——對單一基礎設施項目來說已經是顯著金額，但仍不滿足成本目標。

但 50% 不夠。Serverless 之後年度跑率仍然是「以百萬美元為單位」，向量資料庫單一項目就佔了很大一塊預算。同時 Notion 工程團隊系統性地評估了當時市場上的其他向量搜尋引擎——這個評估的關鍵候選是 Turbopuffer，一個把整個 vector index 建在 object storage 之上的新進向量資料庫。

選 Turbopuffer 的判斷有三層：

  1. 成本結構——object storage 比 dedicated SSD 容量便宜一個數量級，對「冷資料佔比高、熱查詢集中」的工作量友善。Notion 的 workspace 分佈長尾很長：少數活躍 workspace 貢獻多數查詢，大量低活躍 workspace 的資料只是偶爾被讀。把這些長尾 namespace 放在 object storage 上，每 GB 月費可以從 dedicated SSD 的「以 cents 計」降到「以 fractions of cents 計」。
  2. 架構簡化——Turbopuffer 把每個 namespace 視為獨立 index，不需要 application 層維護分片表，workspace-ID 直接對應一個 namespace，原本的 range partitioning + generation 路由整套可以拆掉。對 application 程式碼來說，「我要查 workspace X」變成 turbopuffer.namespace(workspace_id).query(...)，路由邏輯從 application 完全消失。
  3. 批次寫入支援——對 Notion 這種「會做大批量 re-indexing」的工作量提供了相對便宜的 bulk modification API，讓「換 embedding model 重 embed 全站」這種動作的成本可控。

這三層判斷裡，第二層其實是最隱性也最大筆的回報——把 application 程式碼裡的「路由邏輯」整層刪掉，意味著未來新功能不需要再考慮「這個 query 要去哪一代 pod」。後續所有的 retrieval feature——比如新加一個 BM25 hybrid、新加一個 metadata filter——都不再需要先想清楚「我這個新功能怎麼跟 generation router 共存」。這是組織槓桿，不只是運維簡化。

對應的代價是「全公司的 retrieval 程式碼要改成 Turbopuffer client SDK」——這個一次性的程式碼遷移成本不便宜，但是相比「未來每個新 feature 都繞 generation router」的長期 tax 還是便宜很多。這個取捨在做底層引擎更換時是恆常出現的：短期一次性 migration cost vs 長期累積的 abstraction tax，多數情況前者勝。

2024 年 5 月到 2025 年 1 月，Notion 用約八個月把多達數十億筆 vector object 從 pod 模式搬到 Turbopuffer。搬遷策略沿用了原本就在用的 generation-based 思路——不去 reshard 既有 generation，而是把新 workspace cohort 導向「新一代」的 Turbopuffer namespace，逐代切換、逐代驗證；每搬完一代就可以把對應的 pod cluster 退役。這個策略最大的好處是避開了「為了搬遷而 pause onboarding」的風險——onboarding 流量在整個搬遷期間沒有中斷。

搬遷的安全網來自 Notion 早期就一直在做的雙寫實踐：在切換的中段，新舊兩個引擎同時收寫入、應用層的讀取路徑可以按 feature flag 切到任一邊；當對應 cohort 的「新引擎讀寫驗證」連續一段時間 zero diff，就把這 cohort 的讀路徑切過去、舊引擎進入唯讀狀態；唯讀一段時間沒有客訴或差異後，舊引擎這份 cohort 的資料才會真的被刪掉。這個模式對任何「資料層引擎更換」都適用——關鍵不是技術細節，而是把「驗證 → 切讀 → 退役」三段顯式化，每段都有可以 rollback 的視窗。

同時做了兩件附帶優化：（a）藉著 full re-indexing 的機會把 embedding model 換成更新版本，後者在召回率與語意理解上都更好；（b）把 Spark offline pipeline 的 throughput 重新調過，配合 Airflow 的 scheduling 讓白天/夜間的 onboarding 容量可以靈活伸縮。「順手換 model」這個動作在獨立做的時候是個 painful 的全站重 embed 工程，但既然遷移本身就要全資料量過一遍 Spark + embedding pipeline，這個成本被 amortize 掉了——好的遷移時機是「順便」做其他原本要單獨付成本的事。

完成後拿到的數字：搜尋引擎成本降 60%、AWS EMR compute 成本降 35%、p50 query latency 從 70-100 ms 降到 50-70 ms——這個 latency 改善的關鍵不只是引擎更快，也包括 application 端拿掉了 generation lookup 與分片路由那一層。EMR 那 35% 是個容易被忽略但很實在的省下：原本的分片路由邏輯讓 Spark 批次也需要按 generation 切批次，每代的 ingest job 都有獨立的啟動成本；切到 namespace 模型後，Spark 可以直接以 workspace 為單位 parallel，啟動成本均攤回去。

EMR −35% 這個數字背後還有一層連動效應：Spark 啟動成本變便宜之後，「跑一次 full re-indexing」這個操作的成本門檻也下降了。以前要全站重 embed 是一個必須提前幾週規劃的大動作，現在可以更頻繁地做——這直接讓「想換新 embedding model」這種實驗變得便宜。底層引擎更換的回報常常是這種「下游動作變便宜」的隱性收益，純粹看引擎本身的成本比較會錯過這部分。

Latency 那段也值得單獨拆：從 70-100 ms 降到 50-70 ms 看起來只是 20-30 ms 的改善，但這 20-30 ms 不是均勻分佈的——p50 改善大概一半來自引擎本身（object storage 上的 ANN 比 pod 上的 SSD ANN 在熱資料 cache hit 時其實沒明顯快，但 cold cache 時差距更小），另一半來自路由層的消失（application 不需要做 generation lookup → shard lookup → pod address resolution 這一連串 lookup）。對 tail latency 來說，後者的價值通常更大，因為 lookup 鏈越長、p99 越容易被任一環節的 slow path 拉長。

2025 年 Page State Project：xxHash64 把 re-embed 量砍 70%

2025 年 7 月做的第一件事是 Page State Project——這個專案處理一個原本一直被忽略的浪費：頁面只要被編輯，無論改動是「整段重寫」還是「一個字元變動」，原本的 ingestion pipeline 都會把整頁重新 chunk、重新 embed、重新上傳。對 Notion 這種高編輯頻率的產品，這個語意意味著大量的「重複工作」——同一個 paragraph 因為旁邊的 typo 修正而被反覆 re-embed。

這個浪費為什麼能存在這麼久？因為它在帳單上不會自己跳出來。Embedding API 的計費單位是 token，pipeline 每天送 N billion token 過去、月底拿到一張帳單——沒有任何維度告訴你「其中有多少 token 對應的內容其實沒變」。要看出這個浪費，需要主動拆「同一個 span 被 embed 過幾次」這個指標，而這個指標必須先建立 span ID 的概念、然後跨時間追蹤——這正好是 Page State Project 第一步要做的事。

這是一個很值得記下的觀察模式：對任何 usage-based 計費的服務，帳單只給你「總量」，不會告訴你「總量裡有多少是重複工作」。要回答後者，必須在 application 層先建立可以跨時間 dedupe 的識別碼。一旦這個識別碼存在，後續的 hash diff、Merkle tree、CDC（change data capture）等模式才能落地。沒有 span ID 之前，「不要重做沒變的工作」是不可能被執行的——因為你連「哪些工作是同一個工作」都還沒辦法說。

解法的概念很直接：對每個 span（chunked 之後的文字單位）算兩個 hash——一個 hash text 內容、一個 hash metadata（權限、作者、頁面屬性等）——把這對 hash 與 span ID 一起存進 DynamoDB，一個頁面一筆 record、record 內含這個頁面所有 span 的 hash struct。下次同一頁變更時，先把新版的所有 span 算一次 hash，跟 DynamoDB 裡的舊版逐 span 對： 

// Page State Project：用 xxHash64 判斷哪些 span 真的變了
def reindex_page(page_id, new_spans):
    old_state = dynamodb.get(page_id)              // span_id -> (text_hash, meta_hash)
    new_state = {}
    to_embed  = []
    to_patch  = []
    for span in new_spans:
        new_th = xxhash64(span.text)
        new_mh = xxhash64(span.metadata)
        new_state[span.id] = (new_th, new_mh)

        if span.id not in old_state:
            to_embed.append(span)                  // 新 span：完整 embed
        else:
            old_th, old_mh = old_state[span.id]
            if old_th != new_th:
                to_embed.append(span)              // 內容變了：re-embed
            elif old_mh != new_mh:
                to_patch.append(span)              // 只有 metadata 變：PATCH，不重 embed
            // 兩者都相同：什麼都不做

    dynamodb.put(page_id, new_state)
    if to_embed:  embed_and_upsert(to_embed)
    if to_patch:  turbopuffer.patch_metadata(to_patch)

這個邏輯把 ingestion 工作拆成三個 case：完全沒變的 span 不動；只有 metadata 變了的 span（例如權限調整、作者改名）走 PATCH 路徑、直接更新 Turbopuffer 裡的 metadata 而不重新呼叫 embedding API；真正內容變動的 span 才走完整 chunk → embed → upsert 流程。在 Notion 的實際編輯分佈下，這個拆分把 ingestion pipeline 的資料量砍了 70%——同時省 embedding API 費用與 Turbopuffer 寫入費用，這兩塊都是按用量計費。

特別值得注意的是 metadata-only 那條 PATCH 路徑：對「權限變動」這種操作，舊版 pipeline 會把整頁所有 span 全部 re-embed 一次——權限是頁面層級的屬性，所有 span 共享同一個 metadata，動一次牽動全頁。在企業 Notion 場景裡，「把某文件分享給新部門」這種操作很頻繁，每次都觸發整頁 re-embed 是純粹的浪費。把 text 跟 metadata 拆成兩個獨立 hash，就把這條昂貴路徑變成廉價的 PATCH。

為什麼選 xxHash64 而不是 SHA-256 或更短的 32-bit hash？Notion 寫的判斷是「ease of use、速度、低 collision 機率、storage footprint」之間的平衡。64-bit hash 對 Notion 規模的 span 數量來說 collision 機率仍然遠低於可觀察的門檻，比 SHA-256 算得快很多；比 32-bit hash 又安全得多。重點是這個 hash 不是用於 cryptographic 安全（攻擊者沒有理由刻意造 collision），純粹是「change detection」——這個前提下 xxHash64 就是甜蜜點。

具體量級對照：xxHash64 在 modern CPU 上吞吐約 5-10 GB/s（純 in-memory），SHA-256 大約 0.3-0.5 GB/s——差約 20 倍。對「對每個 span 算 hash」這種高頻、要在 pipeline critical path 上跑的操作，這個差距會直接體現在 pipeline overhead 上。Storage footprint 也重要：DynamoDB 每筆 record 越小、總成本越低；64-bit hash 是 8 bytes，SHA-256 是 32 bytes——4 倍 size 差，對「一個頁面一筆、每筆內含所有 span 的 hash」的儲存模型來說會直接放大 4 倍。

下面這張表把 xxHash64 跟常見替代品的取捨並排起來——點欄位 header 可以按該欄排序，看出「為什麼 xxHash64 是這個工作量的甜蜜點」。Cryptographic 安全與 change detection 是兩種完全不同的 requirement；把錯誤的工具放在錯誤的位置會用 10-20x 的 CPU 換來不需要的 collision 抗性。

這張表的關鍵欄位是「適用情境」——選 hash 不是看哪個「最強」，而是看哪個剛好對應你的 threat model。Content fingerprint for change detection 的 threat 是「兩個不同 span 偶然算出同一個 hash」，這個機率在 64-bit hash + 1e9 scale 上仍然遠低於 disk error rate；沒有理由再多付 SHA-256 那 20x 的 CPU 與 4x 的 storage。反過來，如果是簽名場景（攻擊者可以選擇 input），那 xxHash64 不夠，必須上 cryptographic hash——這個分界要清楚。

另一個常被搞錯的點：很多人把 xxHash64 與 SHA-256 看成「快但不安全 vs 慢但安全」的二元光譜，這個理解漏掉了重要的中間刻度。BLAKE3 在 modern CPU 上吞吐約 3.5 GB/s（用 AVX2 + multi-thread 可以更高），同時提供 cryptographic 安全等級——這在「需要密碼學保證但 SHA-256 太慢」的場景是值得考慮的。Notion 用不到這層安全，所以 xxHash64 是對的；但對其他「change detection 也要抗惡意輸入」的系統（例如 build cache 必須抗 supply chain attack），BLAKE3 才是真正的 sweet spot。Hash 選擇是個三維問題（速度、size、threat model），不是一維比較。

Ray Serve 收尾——拆掉 GPU pod 的雙重計算

同個月（2025 年 7 月）做的第二件事是 embedding 服務的整個搬家：從原本掛在外部 embedding API 與內部 GPU pod 上的兩條路徑，整個搬到 Ray / Anyscale 上跑。要解的痛點有三個：

  1. 「雙重計算」問題——舊架構下，Spark 做 preprocessing（chunking、normalization、metadata 抽取），完成後把結果丟給 embedding API，又被計算一次 token。同樣的 token stream 在不同層被算兩次，這是純粹的浪費。
  2. 外部 API 可靠性綁定——embedding API 的延遲、rate limit、故障時間，直接決定 ingestion pipeline 與 query path 的可用性，沒有降級路徑。Embedding model provider 一旦發 incident，Notion 的 ingestion 就會 backlog；reactor 沒有「先用本地 fallback model」的選項，因為架構上根本沒有本地 model。
  3. 難看的 pipelining——為了配合 rate limit，工程師得寫一堆 S3 batching 跟 retry 邏輯把資料分批送過去，這些 batch 是手寫的、不容易調整。每次想換 batch size、加 retry policy，都得改 Spark job 的 partitioning，跟 embedding pipeline 的物理特性綁太緊。

Ray 的賣點對應這三點：

  • Ray 把 preprocessing 與 inference 放在同一個 compute layer，GPU-bound 的 embedding inference 跟 CPU-bound 的 preprocessing 可以在同一台機器上 pipeline 起來，把 GPU 利用率推高同時消掉 double compute。Notion 引用的措辭是「pipelining GPU-bound inference with CPU-bound preprocessing on the same machines, keeping utilization high」——這句話的具體含義是：當 GPU 在算 batch N 的 embedding 時，同一台機器的 CPU 正在 chunk batch N+1、normalize batch N+2，三件事 overlap 進行，GPU 不會空等資料。
  • Embedding model 改成在 Ray 上跑開源模型，不再受外部 API gate。Notion 在文章裡強調的 model flexibility 包括「想試新 model 不需要等 provider 開放」、「可以用 fine-tune 過的內部模型」、「可以隨時 fallback 到 cheaper model」——這些自由度在綁外部 API 時都不存在。
  • Ray Serve 把模型包成持久 GPU-resident 的 deployment，配置用 YAML 描述 batching、replication、autoscaling，model serving 是普通 Python——對 query path 來說，embedding 從「外部 HTTP 呼叫」變成「同 cluster 內的 RPC」，把第三方 API 的網路 hop 從 critical path 上拿掉。一次外部 HTTP 來回在跨區情境通常是 20-50 ms 起跳；同 cluster RPC 通常 1-5 ms。對 query path 的 p50 50 ms 預算來說，這是值得砍的一塊。

下面這個架構圖把 2025.07 之後的最終 stack 攤開來——點選任一個元件可以看它的責任與「它不知道的東西」。每個元件的責任邊界都是有意識劃出來的：xxHash64 不知道 span 的語意（它只看 byte stream）、Turbopuffer 不知道 workspace 的 ACL（namespace 只是字串）、Ray Serve 不知道 vector 之後會被誰查（它只 embed 然後回傳）。這種「明確的不知道」是組件可以被獨立替換的前提。

Embedding 基礎設施成本拿到的數字是 90% 以上的下降，Notion 把這歸功於：拿掉外部 API 的 per-token 計費、用開源 model 取代付費 model、preprocessing 與 inference 共用機器把 GPU 利用率推上去、以及 query path 從「外部 HTTP」變成「同 cluster RPC」省下的固定成本。對 query path 的 latency 影響沒有單獨披露數字，但「拿掉一次外部網路 hop」在 p99 尾部通常會看到明顯改善。

另一個容易被忽略但很實在的好處是開發體驗：Anyscale 的整合 workspace 讓 engineer 可以用 Cursor、VSCode 這類熟悉工具直接在 cluster 上開發，不需要每個改動都自行 provision GPU 環境——這對「快速試新的 embedding model」這種需求是很重要的迭代成本下降。對 retrieval team 來說，「試 model」的頻率本來就應該高，每次都要等 30 分鐘 provision GPU 會直接壓低嘗試次數。

Ray 上的 query-time serving 還有個技術細節值得記下：embedding model 是 GPU-resident 的常駐 deployment，不是 cold-start 的 serverless function——這對「query path 必須 sub-second」是關鍵差異。Serverless inference 在 LLM 領域有 cold start 動輒幾秒的問題（要把 weights load 進 GPU 記憶體），對 query path 完全不能接受；Ray Serve 用 always-on replica 加 dynamic request batching 把這個問題避開——request 進來時 model 已經在 GPU 上，只需要把 input tensor copy 過去、forward pass、回傳。

Dynamic batching 在這裡是另一個關鍵細節：query path 是一筆一筆進來的，但 GPU 在 batch 大小 1 的時候利用率很差（forward pass 的 kernel launch overhead 占多數時間）。Ray Serve 的 dynamic batcher 會在 sub-millisecond 的時間窗口內把進來的請求聚成一個 batch（典型 8-32 個）再丟給 model，這個 trick 把 GPU 的有效吞吐量推高一個數量級，同時把每筆 query 的額外等待控制在 1-2 ms——對 50 ms 預算來說可以接受。沒有 dynamic batching 的 inference 服務在 sparse query load 下會非常浪費 GPU。

Dynamic batching 的窗口長度是個典型的 tail latency vs throughput tradeoff：窗口越長，batch 越大、GPU 利用率越高，但 p99 latency 會被「最不幸運的、剛好錯過上一個 batch」的 request 拉長。Ray Serve 預設的 batch wait time 通常是 1-2 ms，這對 50 ms 級別的 query path 還可以；但如果 query path 本身是 sub-10ms 的（例如 in-cluster cache lookup），這 1-2 ms 就會變成顯著比例。任何用 dynamic batching 的系統都需要為這個窗口設一個 explicit budget，不然 throughput 的好處會被 tail latency regression 吃掉。

Ray + Anyscale 這個組合還隱性解決了另一個 Notion 沒明說的問題：multi-tenancy 在 GPU 上的 isolation。同一台 GPU 機器上跑 embedding model A 跟 fine-tune 過的 model B，需要在記憶體上隔離 weights、在計算上 schedule batch；如果用裸 CUDA 自己寫，這層 scheduling 是手工的、容易出錯。Ray Serve 把這個層級包成 deployment 抽象，每個 model 是一個 deployment、底層自動做 GPU memory 與 batch scheduling 的分配。這對「retrieval team 想同時跑 3-5 個 model 做 A/B」是必要的基礎設施，否則每次 A/B 都要 provision 新的 GPU pod。

把四個階段串起來看到什麼

四個階段背後其實是同一條 thesis：不要在錯誤的計費邊界上付固定成本。第一段拆掉的是「按開機時間計費」的固定成本（換 serverless）；第二段拆掉的是「dedicated SSD 容量」的固定成本（換 object-storage based 引擎）；第三段拆掉的是「為了沒變的 span 重做工作」的隱性固定成本（hash diff）；第四段拆掉的是「外部 API 的 per-token + 雙重 compute」的固定成本（Ray 收編）。每一段都對應「停止為某種不必要的恆定支出付費」。

另一個觀察是 generation-based 策略貫穿整段歷史——它最初是 pod 模式下「避開重新分片」的應急設計，但同樣的「逐代 cutover、新流量導新代、舊代慢慢退役」模式被沿用到 Turbopuffer 的搬遷上。這是個值得記下的營運模式：當底層引擎要換但業務不能停，用 generation 思維讓搬遷變成「持續部署的一部分」，而不是「需要 maintenance window 的大事件」。把 cohort 維度加進系統設計的早期，後面所有的大遷移都會更便宜。

還有一個可以拿走的工程觀察：很多人把 embedding pipeline 當成「黑盒子」——丟資料進去、拿向量出來——但 Notion 把它拆成可量化的子問題（哪些 span 真的變了、哪些只是 metadata 變、preprocessing 與 inference 能不能合機器跑）之後，每個子問題都能砍 60-90% 的成本。這個拆解能力在 LLM-adjacent 系統裡會反覆有用——成本壓力在這類系統上特別大，誰能把工作拆到正確顆粒度誰省得多。

對工程同行有幾個可以直接拿去用的「決策觸發條件」：（1）一旦資料庫帳單裡「未使用容量」佔比超過 30%，就該檢查計費模型是不是按 uptime 而非用量——這通常是換 serverless 或 object-storage based 引擎的訊號。（2）一旦 application 程式碼裡「路由邏輯」開始長出多層 lookup（generation → shard → pod），就該重新評估底層引擎能不能用 namespace 抽象掉這層複雜度。（3）一旦 ingestion pipeline 的 cost 與「實際變動量」的比值大於 2x，就該引入 content-defined diff（hash、Merkle、CDC pattern）——重複工作的成本被計費系統隱藏得最深，需要主動量測才看得見。（4）一旦 embedding 或 inference 成本超過總基礎設施支出的 20%，就該認真評估「自己跑 vs API 呼叫」——這個門檻會隨開源模型品質持續下移。

這四個觸發條件之所以可以複用，是因為它們不依賴 Notion 的具體業務形態——任何「資料規模單調增、編輯頻率高、有 retrieval 需求」的系統都會撞到這四道牆。Slack、Linear、GitHub Copilot 的 codebase indexer、Glean、所有 enterprise search 產品都在類似的成本曲線上滑動，只是各自處於不同的階段。把 Notion 的時間線當成自己的 forward look——把自己現在的處境定位到「我在 stage N」，下一步應該是什麼會比較清楚。

最後一個值得注意的細節：Notion 的演進跨度恰好兩年（2023.11 → 2025.07），平均每階段 6-7 個月。這個節奏不是巧合——每段都需要時間把上一段穩定下來、量出真實的 cost shape、設計下一步、執行遷移。如果一年內想做完所有四段，大概率每段都做得不徹底；如果三年才做完，那業務早就被成本壓垮。「半年一個階段」這個節奏值得任何處在類似 hyper-growth + infra-rebuild 階段的團隊參考。

這個節奏感與 widget 設計裡常見的「scroll-driven explanation」很像：閱讀的人需要每一個 stage 都有時間吸收、看到它的具體形狀，才能在進入下一 stage 時做正確的對比。架構演進在組織內部也是這樣——團隊需要每個階段都跑一段時間，才能量出實際的 cost shape、build muscle memory、形成下一步的合理直覺。「快速 ship」在這類重構裡是反 productive 的，因為每段的真正 ROI 只有在它穩定運行幾個月之後才會浮現。

最後一個觀察留給「為什麼這套劇本不是 day-one 就該套用」：所有四階段的順序之所以對，是因為每段都依賴前段提供的可量測信號。Day-one 的時候 Notion 沒有「未使用容量佔比」這個指標、沒有「重複 embed 量」這個指標、甚至沒有 span ID 這個基礎概念——這些都是在 pod 階段把產品撐起來之後才有條件建立的。換言之，「先撐住、再量、再砍」不是延誤，而是必要的時序——day-one 就追求最終形態的架構，會把工程資源花在還沒被驗證的優化上，這比 over-provision 的成本更貴。

寫到這裡，把 Notion 兩年的故事壓回一句話：架構演進的真正生產力來自「把不對的計費邊界找出來、然後一段段拆掉」。技術選型（Turbopuffer、Ray、xxHash64、DynamoDB）只是執行這個動作的工具；判斷哪一條邊界該動、什麼時候動、用什麼順序動，才是這份兩年總結真正值得記下來的內容。

這個觀點對讀者下週的工作有具體含義：先別急著評估「我們要不要換 Pinecone / Qdrant / Weaviate」，先打開最近 3 個月的雲端帳單，把 vector DB 與 embedding 相關支出按「固定 provision、按用量、按 token」三類拆出來——拆完後通常會看到某一類支出明顯失衡（例如 80% 是固定 provision，但實際使用率只有 30%）。失衡的那一類就是該動的計費邊界，技術選型只是「能不能把這條邊界搬掉」的執行細節。Notion 之所以能把總成本壓下九成，是因為他們每次都先看清楚哪條邊界錯了再動手，而不是相反。

What changes：兩年下來，Notion 把「向量搜尋」從一個寫死在外部供應商與 GPU pod 上的固定支出，重組成一條 namespace-on-object-storage + hash-diff + 自家 Ray 集群的可伸縮 pipeline——對任何要從「demo 規模」走到「平台規模」的 retrieval 系統，這四個階段的順序（解耦計費 → 換引擎降結構性成本 → 砍重複工作 → 整合 compute layer）就是預設模板。
