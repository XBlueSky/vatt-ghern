把一台 vLLM 推論伺服器從空白機器拉到第一個 token 出來，預設大約要 2,000 秒——下載映像、解壓、import torch、把幾 GB 的權重灌進 GPU、編譯 CUDA graph。Modal 沒有把這條路上的任何一步「加速」，而是把它切成四段，每段都套一層快照，最後只剩 ~50 秒。拆掉任一層，那一層原本的 fixed overhead 就會回來。

{{ title }}

Modal 把「serverless GPU」這個曾經被認為跟物理現實衝突的 promise 拆成四個獨立的工程問題：cloud GPU 的 instance 從哪裡來、container 映像怎麼快速可讀、CPU 端的 Python process 狀態怎麼回放、GPU 端的 device memory（含模型權重、CUDA graph、KV cache）怎麼回放。四層各自解決自己那段的 fixed overhead，組合起來把 AI 推論的 replica scale-up 從 kiloseconds 拉進 tens of seconds。Q1 2026 production 數字：CPU snapshot 還原 35M 次、CPU+GPU snapshot 還原 15M 次。

這個 stack 的整體框架被 Modal 稱為「GPU Allocation Utilization」——付費的 GPU-second 裡有多少真正在跑使用者程式碼。產業 baseline 在 70% 上下，許多單租戶 deployment 落在 10–20%。問題不是 GPU 不夠強，而是供給節奏跟需求節奏不對齊。

Marc Brooker 在引用語裡的講法是：「The cost of a system scales with its (short-term) peak traffic, but for most applications the value the system generates scales with the (long-term) average traffic.」serverless 在 CPU 世界已經把這個 gap 吃掉了——AWS Lambda、Cloudflare Workers 都是把冷啟動壓到毫秒級換來的；GPU 世界的瓶頸是冷啟動時間長到無法讓 idle pool 隨需求收縮。當 cold start 是 30 分鐘時，你只能 over-provision；當它降到 50 秒，你才開始有「按請求收縮」的營運選項。Modal 的四層就是逐一拆掉造成冷啟動的 fixed overhead。

底下四個小節各自處理一層，順序對應 request 在路上撞到的順序：先有 instance（LP），才有 image（FUSE），才有 process（C/R），才有 device state（CUDA-checkpoint）。每層的 caveat 不一樣，組合起來的營運成本也不一樣——但拆解的方式是工程上最乾淨的——讓每層的 failure mode 各自獨立可診斷，而不是一個 monolithic 「啟動好慢」黑盒。

另一個值得先說的觀察：這四層只有最後兩層真的算「快照」——前兩層 LP 跟 FUSE 解的是「把工作搬離 hot path」而不是「把工作做快」。LP 在請求進來之前就完成了 instance provisioning，FUSE 把 image 解壓推遲到「用到才做」；C/R 跟 CUDA-checkpoint 才是真正的 snapshot/restore。這個分類有意義，因為它告訴讀者哪些層在概念上是 amortization、哪些層在概念上是 memoization——兩種不同的工程武器。

LP：cloud buffer 的線性規劃

第一層在使用者請求送到之前就要動。AWS、GCP、Azure 上的 GPU instance 從 API 呼叫到 ready，通常要 tens of minutes——這段時間如果落在使用者的 hot path 上，後面三層做什麼都沒用。GPU 缺貨期更糟：H100、L40S 在尖峰時段甚至直接回 capacity error，必須換 zone 重試。Modal 的解法是維持一個 idle GPU buffer，並把 buffer 的尺寸用線性規劃求解。

Optimization 的 objective 與 constraint 很簡單：在「至少要提供 requested + buffer 個 GPU」的前提下，最小化 total cost。輸入是三個量——cloud provider 即時報價（scrape 來）、使用者的 task 到達速率、以及目前實際看到的 supply 狀況。每個 instance 通常裝 8 顆 GPU，是 packing 的單位（你想要 5 顆 H100 在某個 zone，最小單位仍是一整台 8x instance）。Modal 把這個 LP 餵給 Google 開源的 GLOP solver，週期性地重新求解，調整每個 zone / instance type 要 pre-warm 多少 instance。

GLOP 是 Google 為 OR-Tools 寫的開源 LP solver，內部以 revised simplex 為主、針對「需要在 tight loop 裡反覆求解」的場景做了優化——這跟 Modal 的場景剛好對齊：價格變了要重解、task arrival rate 變了要重解、新的 GPU 型號上市要重解。形式化上是個經典的整數線性規劃，但因為 instance 數量上界明確、變數規模相對小，整數約束放鬆成連續、求完再 round 的近似解通常已經夠用。

minimize  Σ (price[z][t] × instances[z][t])
subject to
  Σ gpus_per_instance × instances[z][t]
      ≥ requested[z][t] + buffer[z][t]    // 供給下界
  buffer[z][t] ≥ predicted_arrivals[z][t] × headroom
  instances[z][t] ≥ 0,  integer            // instance 不能切半

// solver：Google GLOP（GNU LP-style，simplex 為主）
// 輸入：scraped prices, observed arrivals, current supply
// 輸出：each (zone, instance_type) 的目標 idle count

把這層拿掉，使用者第一個 request 撞上的就是 cloud provider 的 instance 配發延遲——這個延遲在 GPU 缺貨期甚至會直接失敗。LP buffer 是「serverless GPU」這個 promise 能夠開始談的前提：剩下三層都假設「需要的時候，有 instance 在 idle pool 裡可挑」。

有兩個 LP 層特別微妙的工程決策值得提。第一，buffer 不是固定大小——它要對「下一個窗口的需求預測」做反應，預測過低會撞到配發延遲，預測過高則直接燒錢。Modal 的做法是把 prediction 也納入 LP 的 input 量，讓 cost minimization 自動權衡 over-provision 與 under-provision 的代價。第二，buffer 是按 zone × instance type 分別維持的——同樣是 H100，us-east-1a 與 us-west-2c 的 idle pool 完全分開，因為 cross-zone 傳輸成本與延遲讓它們在實務上是不同的資源池。

從營運上看，這層是 Modal 跟雲廠商之間 cost arbitrage 的所在。GPU spot price 在不同 zone、不同 instance type 之間差距可以到 2–3 倍；LP solver 可以把 demand 自動 route 到當下最便宜的 supply 池。對使用者來說 API 仍是 gpu="H100"，後面到底用了哪個 zone、哪個 generation 的 H100、是 on-demand 還是 reserved，都是 platform 的決策。這個抽象層級的維護成本不低，但它把「serverless GPU」的 unit economics 從「使用者付一個固定 price」轉成「使用者付一個合約價、platform 在背後做價格優化」。

LP solver 重新求解的週期也是一個值得提的工程選擇。求解頻率太低會跟不上 demand 變化、買到太貴的 GPU；頻率太高會讓 placement 抖動（剛開的 instance 又被關掉）。Modal 沒公開具體頻率，但從「scraped prices」這個說法推測應該在分鐘到十分鐘量級——對應 cloud provider 公告 price 變化的頻率。LP 本身求解很快（GLOP 對這個規模的問題基本是亞秒級），瓶頸是 input 資料新鮮度與 placement 抖動的平衡。

有一個跟 LP 同框的概念叫「scaling-to-zero」——意思是 idle 時 buffer 可以縮到零，完全不留 instance。這在 CPU FaaS（Lambda 等）是預設行為，在 GPU 上目前還做不到，因為冷啟動即便壓到 50 s 仍比典型 web request 慢一個量級。Modal 的 LP 預設是「永遠保留某個非零 buffer」，這個 buffer 大小由 demand prediction 決定。真正的「serverless GPU scale-to-zero」需要冷啟動再降一個量級——這也是後面提到的 driver-level 改進的長期 motivation。

另一個值得提的營運維度：LP solver 的 objective function 還可以加入「碳排放」這類非價格 cost——某些 region 的電力來源更乾淨、單位 GPU-second 的碳足跡更低。如果使用者願意付溢價選 green region，LP 可以把這個偏好直接編進 objective。Modal 目前的公開資訊沒涵蓋這層，但 GLOP 的 framework 完全支援這類擴充——LP 的可塑性是它能持續吸納新約束的關鍵。

FUSE：content-addressed cache 的懶載入

有 instance 之後，第二段 overhead 是 container image。一個典型的 PyTorch + CUDA + 推論框架的 image 動輒 5–10 GB——預設的 Docker pull + extract 路徑在 gzip 單執行緒解壓的瓶頸下大約 100 MB/s，光是把 layer 拉下來解開就要一分鐘以上。注意 gzip 解壓是 CPU-bound 而非 IO-bound：image registry 把每個 layer 包成 gzip stream，client 端必須單執行緒解到磁碟才能 union mount。多核 CPU 沒幫助、SSD 寫入頻寬也吃不滿，整段就在「一個核心解壓」這個瓶頸下排隊。

Modal 不走 Docker 路徑，他們用 libfuse 自己寫了一個 ImageFS——把 container rootfs 以 content-addressed 的形式存進一個多層 cache，container 啟動時只需要拉 metadata，檔案內容 lazy 拉。Content-addressed 的意思是 storage key 就是 content hash——同一個 base layer（例如 pytorch/pytorch:2.5-cuda12）在不同 image 之間共用儲存與快取，新 image 只需要儲存它真正新增的 block。

關鍵的觀察來自 USENIX FAST '16 的 Slacker 論文——「The majority of the files will not be read」。一個 image 裡 90% 以上的檔案在容器整個生命週期裡不會被任何 process 開啟。Eager 拉所有 layer 等於把 90% 的頻寬花在沒人要的 byte 上。Lazy 把這個成本完全推遲——container 啟動只需要把 metadata（檔案表、permission、symlink 結構）拉下來，這份東西很小，~100 ms 就能 ready，container 就可以 boot，剩下的 block 等 application 真正 read 的時候再從 cache 抓。

FUSE 的選擇背後也有一個 trade-off：所有 read 都會穿過 user-space 的 FUSE daemon，比 kernel-mode 檔案系統慢。但這個延遲開銷對 image 這種「冷啟動時讀一陣子、之後幾乎不再讀」的 workload 是完全 acceptable 的——而且 user-space 實作的好處是 cache 後端的拓樸可以變得很自由：可以 page cache、可以本機 SSD、可以同 AZ 的 cache server、可以區域 CDN、可以全球 blob storage。

有個小但關鍵的調整：Linux 的 FUSE 預設 read_ahead_kb 是 128，對 container image 這種「會連續讀大塊」的 workload 太保守。Modal 把它調到 32 * 1024（32 MiB），讓 kernel 一次預取的大小跟 cache 後端的 round-trip 成本對齊。在 1 ms round-trip 的 AZ cache server 上，預取 32 MiB 等於把 throughput 推近 10 GiB/s 上限；如果留在 128 KB，每個 block 都得吃一次 round-trip，throughput 會跌一個數量級。

# Linux FUSE 預設值（保守，為一般 desktop FS 設計）
$ cat /sys/class/bdi/0:30/read_ahead_kb
128

# Modal 為 ImageFS 調整後
$ echo 32768 > /sys/class/bdi/0:30/read_ahead_kb

# 對應的 mount 端設定（libfuse 啟動參數）
imagefs --max-readahead=$((32 * 1024 * 1024)) \
        --backend=multi-tier-cas \
        /var/lib/modal/container-rootfs

整體節省下來，FUSE 這層大約挪掉一分鐘的 image 拉取與解壓——這還不算它讓後面 C/R 的 snapshot 檔案（也是大量區塊讀寫）也跑得更快的次級效益。另一個值得提的細節：因為 storage 是 content-addressed，一個常見的 base image 像 pytorch/pytorch:2.5-cuda12 在第一次被 pull 之後，AZ cache server 與 page cache 都會留下它的 block——後面任何使用同 base 的 user image 的 cold start，這些 block 都直接命中近端 cache，幾乎沒有額外 wire 流量。

這也帶出一個系統設計的 second-order 效應：當 image 是 content-addressed，「相似 image」這件事在儲存層就會自動 dedup——使用者修一行 application code 觸發一次 build，產出的 image 跟前一版可能只差一個 layer 裡的少數 block。預設 Docker 路徑下這個 image 還是要重新 push、重新 cache；ImageFS 把它退化成「幾個 block 的差異」。對 CI / CD 高頻 deploy 的場景，這個 dedup 力直接折算成 image registry 出口流量帳單的省錢。

FUSE 設計裡有個值得拿出來看的 layering trick：cache 命中率不是均勻分布的——少數熱門 image（PyTorch、CUDA runtime、HuggingFace transformer）佔了絕大多數的 read 流量。Modal 的多層 cache 用 hit rate 的 power-law 來設計容量：page cache 容量最小但 hit rate 最高（同 process 內的重複 read 都打到這），SSD 大一點但 hit rate 略低，AZ cache 更大、再次低，最後是 blob storage 作為 source of truth。這個拓樸不是憑感覺畫的，是反映了 image read 流量本身的長尾分布。

把 cache miss path 攤開看：當 application 在 container 內部 open("/usr/lib/python3.11/site-packages/torch/lib/libtorch.so")，FUSE daemon 接到 read，先查 page cache（命中就是奈秒級），miss 再查 SSD（百微秒級），miss 再查 AZ cache（毫秒級），miss 再查 regional CDN，最後 fallback 到 blob storage（200 ms）。每一層的命中或 miss 都會帶動 admission（讓 block 留下來給下次用）與 eviction（容量滿了趕走舊 block），這套 cache hierarchy 的整體 hit rate 在 Modal 自己的 workload 上應該是接近 99%——這是「~100 ms 就能 boot」這個數字能成立的前提。

還有一個 subtle 的設計選擇：FUSE 的 metadata 跟 block 是分開儲存的。Metadata（檔案表、permission、symlink、xattr）必須在 container 啟動前 fully resolve——所以 metadata 是 eager pull、block 才是 lazy。這個分割讓 ~100 ms 的 metadata phase 不會被任何 block latency 干擾，是個簡單但 critical 的工程決策。

C/R：gVisor 把 CPU process snapshot 成檔案

映像準備好之後，下一段是 process 自己的啟動。對 Python 推論框架而言，這段被「import torch、import vllm、初始化 logger、建立 tokenizer」這類成本主導，從 python -c "import torch" 到 prompt 就緒，通常吃掉 10–15 秒；vLLM、SGLang 這種更厚的 server 更久。Python 的 import system 在這裡尤其差勁——一個 import torch 觸發數千個 .py 與 .so 的 stat / open / read、執行頂層 module 初始化程式碼、建立全域物件，這段是純 single-threaded、IO-bound 與 CPU-bound 都有。

Modal 的做法是 checkpoint/restore——讓使用者把「import + global init」做完之後 snapshot 整個 process，後面所有 replica 都從這份 snapshot 還原，跳過 import。概念上等於把「冷的 Python interpreter + 已 import 的所有 module + 已建立的 global 物件」凍結成一份 image，需要時 thaw 出來繼續跑。這個想法在 Python 社群叫 process forking + module pre-import，Modal 把它做到 production grade。

有趣的選擇是底層用 gVisor 的 runsc runtime，不是 Linux 原生的 CRIU。CRIU（Checkpoint/Restore In Userspace）試圖 snapshot 真實 Linux kernel 的所有狀態——open fd、socket、namespace、cgroup、TCP buffer、shared memory、futex——複雜到許多 corner case 會失敗。任何使用了 io_uring、eBPF map、特定 capability 的 process 都有可能無法被 CRIU 乾淨還原。

gVisor 把 Linux ABI 的一個子集用 user-space 的 sentry 重新實作了一遍——snapshot 的對象變成 sentry 自己掌握的那份「假 kernel state」，量小、邊界清楚、可序列化。換句話說，gVisor 用「縮減 host-kernel 接觸面」換到「snapshot/restore 的 mechanical simplicity」。代價是 syscall 跑得比裸 Linux 慢（每個 syscall 都得經 sentry 翻譯），但對推論這種「import 一次、跑很多次、syscall 多半是 read/write/poll」的 workload，這個 trade 划算。

使用者面的 API 是 decorator 形式：

import modal

app = modal.App()

@app.cls(enable_memory_snapshot=True)   # checkpoint global scope
class InferenceService:
    @modal.enter(snap=True)              # snapshot 在這個 method return 之後拍
    def load_model(self):
        import torch, vllm
        self.engine = vllm.LLMEngine.from_engine_args(...)

    @modal.enter(snap=False)             # 還原後才執行，不入 snapshot
    def per_replica_init(self):
        self.replica_id = os.environ["MODAL_REPLICA_ID"]

    @modal.method()
    def run(self, messages):
        return self.engine.generate(messages)

@modal.enter(snap=True) 標記的 method 跑完，gVisor 對整個 process 拍一張 snapshot——zipped archive，主檔是 pages.img，從幾十 MB 到幾 GB 不等，視 import 進來多少東西而定。後續 replica 直接從這份 image 還原，跳過所有的 import 與 global init。snap=False 那段標的是「跟 replica 綁定的東西」——例如 replica id、per-replica logging context、根據 env var 動的 feature flag——這些不該被 snapshot，因為它們在每個 replica 都不一樣。

snapshot 寫出的格式很直接：pages.img 是 process 的 raw page data（heap、stack、mmap regions 的逐 byte dump），外加一份 manifest 描述 register 狀態、open fd、namespace 結構等。restore 流程是反向：分配對應大小的虛擬位址空間、把 pages.img map 進去、回填 register、重新註冊 fd——sentry 的 user-space 設計讓這幾步都不需要 host kernel 的特殊配合。

snapshot 在儲存層走的也是 ImageFS 的 content-addressed 路徑——同一個 service 不同 deploy 之間的 snapshot 大量共用 page。例如修一行 application code 重新部署，weights 對應的那幾 GB page 完全沒變，只有少數 page 是新的，新 snapshot 的儲存成本 marginal 接近零。這也解釋了為什麼 700k 份 distinct GPU snapshot 在 storage 上 still tractable——它們不是 700k × 幾 GB 的全量，而是高度重疊的 content-addressed slice。

實測數字非常直接。單純 import torch 從 ~15 s 掉到 ~2 s（約 7x）——這個 2 s 主要是把 pages.img reload 進 process 的時間，跟 import 邏輯本身已經無關。整 server boot（包含 framework + model 初始化但不含 weight 灌進 GPU）的 benchmark 對照如下：

有個 production 上一定會踩到的 caveat：snapshot 對 host CPU 的 micro-architecture 敏感。如果 snapshot 是在支援 pclmulqdq（carry-less multiplication，用於 CRC32 與 GHASH 等加密原語）指令的機器拍的，restore 到不支援這個指令的 AWS instance type（例如某些 g6 family）就會 SIGILL——原因是 Python interpreter 或某個 native module 在 import 時做了一次 CPU feature detection、把指令地址直接 inline 到了某個 code path 裡，restore 後跑到那段 code 才炸。

實務上 Modal 對每個 service 維持多份 snapshot——對應 deployment 會 land 的 CPU family——而不是只存一份。Scheduler 在 placement 時就要選對：snapshot tag 與 instance CPU family 對得上才會被排上去。這個多 snapshot 策略也部分解釋了為什麼 distinct snapshot 數量達到 1M 級——它包含了 service 數量 × CPU family 變體。

Q1 2026 數字：CPU-only snapshot 還原 35M 次、累計 5M+ 小時的 execution time、約 1M 份 distinct snapshot。從另一個角度看，這意味著平均每份 snapshot 還原 ~35 次、每次 restore 後撐了 ~9 分鐘的 execution——這個分布跟 inference workload「scale-up 一陣子、用完就回收」的節奏吻合。

CUDA-checkpoint：device memory（含模型權重與 CUDA graph）

CPU snapshot 把 Python interpreter、import 過的 module、PyTorch 的 tensor metadata 都還原了——但 GPU device memory 的內容（模型權重、KV cache、CUDA graph、torch.compile 產出的 PTX）仍是空的。如果第四層停在這裡，每個 replica 還是得花 30–60 秒把 GB 級權重重新塞進 GPU、把 CUDA graph 重新捕獲一次。CUDA graph 捕獲尤其貴：vLLM、SGLang 都會在 boot 時針對多個 batch size、context length 預先 capture 一輪 graph，這段 CPU-GPU round-trip 動輒上百次。CUDA-checkpoint 把 device 端也納入快照範圍。

這層的核心是 NVIDIA driver 本身提供的功能：driver 把 device memory dump 到 host memory，Modal 的 host-side 系統把它寫進 ImageFS，restore 時反向操作——把 host 端的快照 reload 回 device，並重建 CUDA context。被快照的東西包含模型權重（GB 到 TB 級）、CUDA graph、torch.compile 產出、KV cache。整段 device init 的加速是 4–10x，把典型推論伺服器的「整 server boot」從 300+ s 拉到 ~50 s。

關鍵的設計選擇是讓 driver 處理 device 端、Modal 處理 host 端——這個分工讓 CUDA-checkpoint 不需要碰任何 NVIDIA 的 proprietary 內部結構，driver 是 black box，Modal 只跟 documented API 互動。restore 時的順序是：先把 CPU snapshot 還原（Python interpreter、tensor handle、CUDA context 的 host-side 結構）、再把 device memory dump 從 host 拉回 GPU、最後把 CUDA context 跟 device 重新綁定。這個三段 dance 的任何一段出錯都會讓 application crash，但只要照順序做就是 deterministic 的。

實測：vLLM 上跑 1 GiB 的 Qwen 3 0.6B（bf16），median boot 從 96 s 降到 14 s——這個數字之所以漂亮，是因為 model 不大但啟動成本很高。對 audio、structured extraction、vision-language 這類「模型在 tens of GB 以下，但對啟動延遲敏感」的場景，CUDA-checkpoint 的價值最被放大。如果模型大到 70B 級需要 tensor parallel，這層的 win 反而會被「把 70 GB device memory 從 host reload 回 GPU」的時間吃掉。

// 啟用 CUDA-checkpoint：在 cls decorator 上加 snapshot scope
@app.cls(
    enable_memory_snapshot=True,
    enable_gpu_snapshot=True,    // 連 device memory 一起拍
    gpu="L40S",
)
class VisionLanguageService:
    @modal.enter(snap=True)
    def load(self):
        import vllm
        self.engine = vllm.LLMEngine(model="Qwen/Qwen3-0.6B")
        self.engine.warmup()      // 觸發 CUDA graph capture, 一起進 snapshot

    @modal.method()
    def caption(self, image): ...

// production 注意：
//   - 拍 snapshot 之前要把 weights 從 vLLM weight loader 暫時 offload
//     回 host，driver 才能乾淨地序列化
//   - 還原後要主動 recreate KV cache（eager），不能等 lazy 觸發

限制相當具體：第一，只支援單 GPU——多 GPU 程式如果用了 NCCL（NVIDIA Collective Communications Library，tensor parallel 與 data parallel 的底層通訊），snapshot 暫停的瞬間集合通訊會 deadlock，目前沒有乾淨的解。原因是 NCCL 的 all-reduce 等 collective 是同步原語，多個 GPU 必須同時參與；snapshot 把其中一顆 GPU 凍結，其他幾顆會在 collective 上 hang。要解這個問題，要嘛 NCCL 自己提供 quiesce 點、要嘛 NVIDIA driver 把所有參與 GPU 同步凍結，目前兩條路都還沒打通。

第二，對 application 有微調要求。vLLM 在拍 snapshot 之前要把 weight 從 weight loader 暫存回 host（不然 weight loader 內部的 device handle 還活著，restore 後變成 dangling reference）；SGLang 也類似；KV cache 必須在 restore 後主動重建——若 application 依賴 lazy path 在第一個 request 時才建立 KV cache，那麼 cold path 上的延遲又跑回來了。這些調整 Modal 通常會跟上游 maintainer 一起 land 進框架本身，但 application 端仍需要遵循 snapshot-friendly 的 coding pattern。

第三，只適合模型在 tens of GB 以下的服務——超大模型把 device memory 從 host 拉回 GPU 的時間自己就變成新瓶頸。對 70B+ tensor-parallel 模型，目前還是要走「正常 model loading 但搭配 LP buffer」的混合路徑——LP 至少讓 instance ready，model load 還是要等。

Q1 2026 數字：CPU+GPU snapshot 還原 15M 次、累計 2M+ 小時 execution、約 700k 份 distinct snapshot。比 CPU-only 少約 2.3 倍——因為 GPU snapshot 還有更多 production 上的工程約束（單 GPU、device memory size 上限），覆蓋範圍自然比純 CPU snapshot 窄。

另一個工程細節：restore 時 device memory 從 host pull 回 GPU 走的是 PCIe，理論頻寬大約 32 GB/s（PCIe Gen4 x16）、實務上能跑到 25 GB/s 就不錯。對 1 GiB 模型這段是 ~40 ms，可以忽略；對 70 GB 模型就是 ~3 s——這個延遲還沒含 CUDA context 重建。所以 GPU snapshot 的最佳區間就是「模型大小遠小於 PCIe 頻寬乘以可容忍的 cold start」這個物理約束之內。

實務上 NVIDIA 的 driver-level checkpoint 還有一個微妙的設計選擇值得提：device memory 是「整塊 dump」還是「按頁面 dump」？前者實作簡單但會把不必要的 page 也寫進去（例如 buffer 裡的零、暫存區），後者複雜但 snapshot 更小。Modal 的 blog 沒明說 NVIDIA 選了哪個方向，但從 700k 份 distinct snapshot 仍能 tractable 來看，至少 driver 沒做出完全不可壓縮的 dump——配上 ImageFS 的 content-addressed dedup，重疊區段不會重複佔空間。

對推論框架本身的影響也值得一說：vLLM 跟 SGLang 都在 2025 下半年到 2026 上半年陸續加入「snapshot-friendly」的 API。例如 vLLM 提供 explicit weight offload hook、SGLang 暴露 cache pre-warm 與 KV cache eager rebuild 介面。這些 API 不只 Modal 受惠——任何想做 CUDA-checkpoint 的 platform 都可以用。也就是說 NVIDIA driver 開放 device checkpoint 之後，inference framework 跟 serverless platform 之間的 contract 正在重新定型——這條 contract 過去是隱性的、現在變顯性。

下面是 vLLM application 端跟 CUDA-checkpoint 的最小整合範例，凸顯 snapshot-friendly 寫法跟 naive 寫法的差別：

import vllm, modal, torch

app = modal.App()

@app.cls(
    enable_memory_snapshot=True,
    enable_gpu_snapshot=True,
    gpu="L40S",
)
class Inference:
    @modal.enter(snap=True)
    def setup(self):
        # 1. 建立 engine，weights 在這裡 load 到 GPU
        self.engine = vllm.LLMEngine.from_engine_args(
            vllm.EngineArgs(model="Qwen/Qwen3-0.6B", dtype="bfloat16")
        )

        # 2. trigger CUDA graph capture，會被 snapshot 一起拍下
        self.engine.warmup(batch_sizes=[1, 2, 4, 8], max_seq_len=2048)

        # 3. snapshot 前把 weights offload 回 host pinned memory
        #    避免 driver checkpoint 時碰到 vLLM weight loader 內部 device handle
        self.engine.offload_weights_to_host()

    @modal.enter(snap=False)
    def per_replica(self):
        # 4. restore 後第一件事：weights 從 host pull 回 GPU
        self.engine.reload_weights_to_device()

        # 5. KV cache 主動重建（不能 lazy）——避免第一個 request 撞到 cold path
        self.engine.rebuild_kv_cache(eager=True)

    @modal.method()
    def generate(self, prompt: str):
        return self.engine.generate(prompt).text

注意這四個 hook 的順序：setup 階段完成所有「冷成本」（load weights、capture CUDA graph），結尾把 weights offload 回 host；snapshot 拍照；restore 後 per_replica 把 weights pull 回 GPU、重建 KV cache。Naive 寫法（直接 setup 裡 load 完就 serve）在 snapshot path 上會踩 driver 處理 dangling device handle 的 race condition——這個 explicit 的 offload / reload 模式是 NVIDIA driver 跟 inference framework 共同協商出來的 contract。

Reducto：把 6x 折成可營運的容量曲線

Reducto 做的是文件處理——把 vision-language model 用在 PDF / 表單 / 票據解析。流量分布極端：peak-to-average 比例非常高，平日很閒、突然某個客戶把幾十萬份文件全推上來。在沒有 GPU snapshot 的時候，他們的冷啟動 ~70 s——這個延遲意味著要嘛 over-provision idle GPU（成本高）、要嘛使用者等 70 s 看到第一頁結果（體驗差）。

啟用 CUDA-checkpoint 後，冷啟動降到 ~12 s（約 6x）。對 Reducto 這個 use case 意義非常具體：他們現在可以把 idle pool 拉到接近 0、由突發流量觸發 scale-up，使用者等的不是 70 s 而是 12 s——這對 batch document processing 是 acceptable latency。整體 kilo-GPU 級的 workload 在 GPU Allocation Utilization 上從低於 30% 拉到 70% 以上。

這個案例展示了四層 stack 不是逐層「再快一點」而已——它把「serverless」這個詞對 GPU workload 從口號變成可營運的合約。沒有 LP buffer，6x 還不夠；沒有 FUSE，每次 scale-up 還要等 image 拉；沒有 CPU C/R，CUDA-checkpoint 還原後 Python interpreter 還要重新啟動。組合起來才把 cold start 拉到「跟使用者請求進來的尾延遲是同一個量級」這個臨界點。

另一個值得指出的二階效應：當 cold start 從分鐘級降到秒級，autoscaler 的 control loop 也可以變短。原本 autoscaler 必須以 5 分鐘為窗口做決策（因為再短了 scaling action 都還沒生效），現在可以縮到 30 秒——也就是說系統不只是「scale-up 快了」，整個 capacity planning 的時間粒度都跟著變細。

Reducto 的 70 s → 12 s 改變也讓 user-perceived latency 模型重新建立。原本 70 s 的場景下，使用者體驗是「上傳完之後可以去喝咖啡再回來」；12 s 則是「在介面 spinner 跑完之前結果就出來了」。這兩者觸發完全不同的產品設計——前者必須做 email notification、async webhook，後者可以做 synchronous request/response。Modal 把這層 infrastructure 改善 propagate 到 application UX 的層次。

同樣的計算也可以套到 batch / queue 系統：一個 job queue 如果每個 job 都吃 70 s 啟動成本，10K 個 job 的端到端 latency 會被冷啟動主導；12 s 的話，autoscaling 可以快到 worker 拉起來就消化 queue，end-to-end 接近「純 inference 時間」。Reducto 把 idle pool 從「必須維持的固定成本」降到「按需 burst」，這個轉變對任何 spiky workload 都有借鑒意義。

四層 compose 的代價與邊界

每一層都有它特定的失敗 mode，這些 mode 在組合裡會互相牽動：

LP 層失準     ——> 突發流量撞到 cloud provider 配發延遲, tens of minutes
FUSE 層退化   ——> 大檔案的第一次 read 撞到 blob storage 200ms 延遲
C/R 層相容性 ——> pclmulqdq 等 CPU 指令差異, 需要 per-CPU-family snapshot
CUDA-ckpt    ——> 多 GPU + NCCL 不行, 模型過大會反成瓶頸

// 共通的 operational cost：
//   每個 service 對應一族 snapshot 而非一份
//   ImageFS 必須處理 PB 級 content-addressed 物件
//   GLOP 求解必須跟得上市場價格波動的速度

這個 stack 不會自動讓所有 inference workload 都享受 40x。多 GPU 的大模型（70B+、需要 tensor parallel）目前完全跳不上 CUDA-checkpoint 列車；NCCL 在 snapshot 點 deadlock 是個基本架構問題，需要 NVIDIA driver 或 NCCL 自己提供 quiesce 機制才能解。對小到中型模型、單 GPU 推論的場景，四層快照的曲線非常陡——但這也正好對齊 Modal 自己的客戶 profile。

另一個值得注意的觀察是 snapshot 的「分布」：1M 份 distinct CPU snapshot、700k 份 distinct CPU+GPU snapshot——這個數字暗示了 Modal 上 distinct service 的量級，也暗示 ImageFS 必須當成一個 PB 級的 content-addressed object store 在維運。snapshot 不是 cache 友善的 workload（每個 service 的 pages.img 幾乎不會被另一個 service 命中），但同一個 service 的不同 replica 之間命中率極高——這是 FUSE 多層 cache 設計的真實受惠者。

從 system-design 角度，這個 stack 也是一個關於「抽象層該畫在哪裡」的案例。傳統 IaaS 把抽象畫在「虛擬機器」上、PaaS 畫在「container」上、FaaS 把它畫在「function invocation」上——Modal 在 GPU workload 上把抽象畫在「decorator-marked 的 class method」上：使用者標記什麼東西該被 snapshot、剩下的由 platform 負責。這個抽象的代價是 application 必須接受某些 coding pattern（snap=True / snap=False 的拆分、weight offload、KV cache 主動重建），但換來的是 cold start 變成 platform 的責任而不是 application 的責任。

還有一個 longer-term 的觀察：四層 stack 跟 NVIDIA 在 driver 端的演進高度耦合。CUDA-checkpoint 本身是 NVIDIA 的功能，多 GPU 的 NCCL quiesce 也只能 NVIDIA 解；Modal 在 user-space 能做的優化已經接近極限。下一輪的提升大概率得來自 driver 或 NCCL 本身——譬如 NCCL 提供 explicit quiesce API、driver 允許 multi-GPU atomic checkpoint。這個觀察跟整個 AI infra 行業在 2026 年正在發生的趨勢一致：很多 user-space 的 cleverness 已經做到頭，下一輪的 unlock 在 driver、firmware、interconnect 上。

同樣的 user-space 邊界也適用於 AMD 跟其他 accelerator 廠商。Modal 的 stack 目前 GPU snapshot 只支援 NVIDIA，因為 AMD ROCm、Intel Gaudi 沒有對應的 device checkpoint 功能。這意味著「serverless GPU」的 multi-vendor 化還要等廠商的 driver-level 配合——這是個產業協調問題，不是工程問題。

把這四層的「invariants」整理出來，方便讀者把 stack 內化成自己的判斷工具：

// 拆掉任一層 invariant 都會破：
// 
// LP invariant      ：「使用者請求到達時，目標 zone 有 idle GPU」
// FUSE invariant    ：「container 啟動只需要 metadata, block 可以 lazy」
// C/R invariant     ：「import + global init 的成本只付一次」
// CUDA-ckpt invariant：「device memory + CUDA graph 可以 freeze/thaw」
// 
// 整 stack 的 invariant ：
// 
//   end-to-end cold start ≈ Σ (per-layer restore time)
//                       而不是 Σ (per-layer naive init time)

當這四個 invariant 同時成立，end-to-end cold start 就從 naive 的 ~2,000 秒（per-layer naive init 之和）退化成 ~50 秒（per-layer restore 之和）。一旦某個 invariant 破了（例如撞到 pclmulqdq 不相容、或多 GPU NCCL），那一層就 fallback 到 naive path、那段 overhead 立刻回來——這也呼應 opener 講的「拆掉任一層，那一層原本的 fixed overhead 就會回來」。

整理一下選型脈絡：runc 是 Docker / Kubernetes 預設的 OCI runtime，直接走 Linux kernel 的 namespace + cgroup——強隔離但 snapshot 困難（如前所述要靠 CRIU、而 CRIU 在 production-grade 推論 workload 上 corner case 太多）。runsc（gVisor）是 OCI-compatible 的替代 runtime，把 Linux ABI 在 user-space 的 sentry 裡重新實作；snapshot 容易，但 syscall 性能比 runc 慢一截。Modal 在這裡選 runsc 是「snapshot 友善 > syscall 性能」的明確 trade-off。

nvidia-container-toolkit 是把 GPU device 注入 container 的標準工具——但它本身不負責 device memory 的 checkpoint，那是另一回事。CUDA-checkpoint 是 NVIDIA driver 在 device 端開放的新功能，理論上跟 container runtime 正交：Modal 在 runsc 裡用、別人在 runc 裡也可以用——但 runc 沒有 host process snapshot，CUDA-checkpoint 單獨拿出來價值有限（device 還原了、但 Python interpreter 還在 boot）。這四層的 compose 力來自「device snapshot 跟 process snapshot 互相強化」。

containerd 與 stargz-snapshotter 是 CNCF 圈做 lazy image pull 的標準路線，思想類似 Modal 的 FUSE + CAS：metadata 先拉、block 按需。Modal 沒採用 stargz 而是自己寫，原因猜測是要把 cache 拓樸（page cache → SSD → AZ → CDN → blob）跟 snapshot 還原路徑深度整合——stargz 的設計目標是相容 OCI image format，這個相容性 Modal 不需要也不想付代價。

整體看下來，這四層各自選了「比預設更激進但更難維護」的路徑：LP 而不是固定 buffer、custom FUSE 而不是 stargz、gVisor 而不是 runc + CRIU、device checkpoint 而不是「每次都 reload weights」。每個選擇分開看都不算特別新，但組合到 production scale、跑出 Q1 2026 的 35M + 15M 次 restore，這個工程量是真實的。

不是所有 inference workload 都應該全開四層——每層的 application-side 成本都不一樣，照需求挑能讓 platform 跟 application 雙贏：

# 場景 A：小模型、低 QPS、要求最低 cold start
#         例：embedding service, classifier, 小型 vision
@app.cls(
    enable_memory_snapshot=True,    # 開 C/R
    enable_gpu_snapshot=True,       # 開 CUDA-checkpoint
    gpu="L40S",
)

# 場景 B：中型模型、單 GPU、高 QPS
#         例：Qwen 3, Llama 8B, vision-language
@app.cls(
    enable_memory_snapshot=True,
    enable_gpu_snapshot=True,
    gpu="H100",
    min_containers=2,               # LP buffer 永遠保 2 個 warm
)

# 場景 C：大模型、多 GPU、tensor parallel
#         例：Llama 70B+, DeepSeek
@app.cls(
    enable_memory_snapshot=True,    # CPU C/R 仍有用
    enable_gpu_snapshot=False,      # NCCL deadlock, 不開
    gpu="H100:8",
    min_containers=4,               # LP buffer 必要
)

場景 A 是 CUDA-checkpoint 最甜蜜的 use case——小模型、啟動成本主要在 framework boot 而非 weights load。場景 B 是 Modal 上的主流 workload，四層全開最大化收益。場景 C 暫時只能用前三層，等 NVIDIA 解 NCCL quiesce 問題後才能拿到 GPU snapshot 的紅利。

有一個容易被忽略的議題：snapshot 的「保鮮期」。Application code 變、framework 升級、CUDA driver 升級——任一條都會讓既有 snapshot 失效，platform 必須重新拍。Modal 的 build pipeline 把這個成本 amortize 到 deploy 時間：第一個 replica 是「冷拍 snapshot」、其餘 replica 都用快照。這意味著 deploy latency 變長（從 push 到第一個 replica ready 多了拍 snapshot 的時間），但 steady-state scale-up latency 降到 ~50 s——這個 trade 對推論 workload 來說明顯划算。

還有一個 snapshot lifecycle 的細節：因為 distinct snapshot 數量已經到 100 萬等級，GC（哪些 snapshot 可以刪）變成 non-trivial 的問題。每個 service 通常維持 N 個版本的 snapshot 給 rollback 用，舊版本要按 retention policy 過期；外加 per-CPU-family、per-driver-version 的變體，總量很容易爆炸。Modal 沒有公開這部分細節，但從規模反推，他們的 ImageFS object lifecycle 管理必然有獨立的一套——這也是「serverless platform 比 IaaS 多做的事」的另一個面向。

最後一個值得提的角度：四層 stack 對「failure mode 可觀測性」的影響。Cold start 從一個黑盒變成四段獨立的 phase——使用者看到的「scale-up 慢了」可以對應到「LP 沒命中、要新 provision」、「FUSE 在 blob storage fallback」、「C/R restore 失敗、回 fallback path 重啟 process」、「CUDA-checkpoint 在某個 instance 上 SIGILL」等具體 cause。這個分層讓 Modal 的 oncall 不再追「整體啟動慢」這個 vague signal，而是看 per-stage 的 latency breakdown。對 platform 維運而言，可觀測性的提升其實跟性能提升一樣重要——一個系統能跑快是因為它的瓶頸可以被定位、可以被治。

把這個 stack 放在更大的脈絡看，2024–2026 這幾年 AI inference 的 ops 重點從「模型怎麼跑得更快」轉向「整體 GPU fleet 怎麼跑得更滿」——前者由 framework（vLLM、SGLang、TensorRT-LLM）負責，後者由 serverless platform（Modal、Replicate、Together、Anyscale）負責。Modal 這篇 deep dive 是後者陣營的代表作之一，它把過去「GPU 用得很滿但啟動慢」的營運難題，用四個獨立的工程子問題加上廠商配合（NVIDIA driver checkpoint）解掉。下個階段的問題已經在路上：multi-GPU snapshot、跨 vendor 的統一 abstraction、scale-to-zero——這些都是更深層的工程戰場。

What this enables：把 GPU 冷啟動從 ~2,000 s 壓到 ~50 s 的關鍵不是任何單一層的優化，而是承認「provisioning、image、process、device」是四個獨立的延遲源——LP 移除 instance 配發、FUSE 移除 image 解壓、C/R 移除 Python init、CUDA-checkpoint 移除 device init——讓「serverless GPU」從一個物理上不可能的口號變成可以對單租戶 inference workload 簽 SLA 的營運合約，前提是模型在單 GPU 容量內、沒有 NCCL 集合通訊。
