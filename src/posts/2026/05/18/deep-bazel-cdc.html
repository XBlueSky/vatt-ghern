Bazel 的 remote cache 早就會 dedup——只要兩個 action 產出 byte-for-byte 相同的輸出，第二份不會佔新的儲存。問題出在「99% 相同的輸出」這種情況：改一行 source code，得到一個新的 link、新的 archive、新的 deploy bundle——digest 全部變了，cache 把它當成完整的新 blob。BuildBuddy 的解法是把 dedup 從檔案層拉到 sub-file chunk 層，演算法叫 content-defined chunking。

BuildBuddy 在 Bazel remote cache 啟用了 content-defined chunking（CDC）：上傳前把 ≥2 MiB 的檔案切成內容定義的 chunk、各自編 digest、各自存。之後同一個檔案的後續版本只上傳真正新出現的 chunk，沒變的 chunk 直接命中既有 digest。內部 benchmark 顯示上傳資料量減少 40%、整體 cache 流量節省 20–40%，兩週生產環境累積跳過 ~300 TiB。

boundary detection：rolling hash 怎麼找切點

CDC 的核心是「切點要由內容決定，不由位置決定」。傳統 fixed-size chunking 每 N 個 byte 切一刀，問題是檔案前段插入一個 byte，後面所有的切點都跟著位移——dedup 整段失效。CDC 改用 rolling hash 在小視窗（例如 64 或 96 byte）上滑動，當 hash 命中某個稀有 pattern 時切一刀。內容不變的區段，rolling hash 抽到相同的切點；新內容只影響到它所跨的 chunk，前後 chunk 保持原 digest。

BuildBuddy 用的是 FastCDC 風格的演算法：rolling hash 通過視窗時，命中「稀有 pattern」就切一刀。「稀有」由 hash mask 控制——例如 hash 結尾 19 bit 全 0 大約是 1/524288 的機率，平均每 ~512 KiB 觸發一次，這就是目標 chunk 大小。除了平均值，FastCDC 還在實作上加了 normalization（避免極小或極大 chunk），但概念骨架仍是 rolling hash + rare pattern。

chunk 大小目標：~512 KiB

Chunk 太小，每個 chunk 都有 metadata 開銷（hash、index entry、storage backend 的 key），總開銷被吃掉。Chunk 太大，dedup 粒度退回接近檔案層，CDC 的優勢稀釋。BuildBuddy 的目標是 ~512 KiB——「平均每 512 KiB 一次匹配」這個數字是經驗值，平衡了 metadata 開銷與 dedup 粒度。

有兩個額外的細節：第一，rolling hash 雖然平均切在 512 KiB，但實際 chunk size 服從幾何分布（很多小、極少超大）。FastCDC 的 normalization 透過在小於 min 與大於 max 時調整 hash mask 來縮緊分布。第二，CDC 對「靠近切點的小修改」是穩定的，但對「跨多個 chunk 的大重排」（例如 link order 重排）會退化——這時候大量 chunk 同時失效，CDC 的節省變小。

啟用條件：2 MiB 門檻

BuildBuddy 對小於 2 MiB 的檔案不啟用 CDC，直接整檔上傳。原因是小檔案的內容變動率高、又往往無法切出多個有意義的 chunk——CDC 的 metadata 開銷超過節省。Bazel 產出物的大頭通常是 link、archive、bundle、container layer，每個動輒幾十到幾百 MiB——這才是 CDC 真正發揮的對象。

2 MiB 門檻同時也是「相對成本」的閾值：小於這個尺寸時，網路傳輸與儲存的固定開銷比 chunk metadata 還小。把 CDC 留給大檔案，是個明確的 cost-benefit 切割。BuildBuddy 描述這個策略是「CDC 在 outputs that are large and byte-stable across revisions」最有效——關鍵詞是 byte-stable：source revision 之間 byte 級不漂移，例如不含 timestamp、不含 random ID、不含 build serial number。Bazel 預設 build 是 reproducible 的，這個前提剛好成立。

有一個值得注意的負面情境：CDC 對非 byte-stable 的輸出（例如帶 timestamp、未做 reproducible build 的 binary）幫助有限——切點仍會找到相同的 pattern，但實際 chunk 內容仍會變，dedup 退化。要真正吃到這 40%，得先把 build 的 determinism 做好。CDC 是放大器，不是修復器。

What this enables：把 dedup 從「整檔 digest 比對」拉到「sub-file rolling-hash chunk 比對」，讓 Bazel 在每次源碼小變動時，只為真正新出現的 byte 付儲存與網路成本——前提是 build 本身已經是 byte-reproducible 的。
