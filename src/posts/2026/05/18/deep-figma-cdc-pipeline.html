2023 年 Figma 的每日資料管道從凌晨開始跑：對每張資料表做一次完整 dump、複製到 Snowflake、覆寫舊版。一張資料表 1 億 row、改了 100 row，pipeline 還是搬了完整 1 億 row。某天工程師發現整個 daily sync 花了超過 6 小時，分析師早上 9 點打開 dashboard 仍是「前天」的數字——而 Figma 為這條每日複製鏈付了多個專屬 RDS replica、年費以百萬美元計。

這篇是一條資料管道從每日全表 dump 走到分鐘級 CDC 的三年路。技術選型是常見的——PostgreSQL WAL、Kafka、S3 snapshot、Snowflake——但 Figma 把每一步銜接的失敗模式都用一個額外設計補上。關鍵不在組件清單，在 snapshot 與 stream 之間怎麼對齊、incremental merge 怎麼冪等、以及離線怎麼證明資料是對的——這三件事決定了一條 CDC 管道能不能撐到三年後仍可信。

從 cron 到 6 小時

Figma 在 2020 年的資料同步是一個典型的初創公司形狀：production PostgreSQL 跑在 Amazon RDS、分析需求剛開始長出來、有人寫了一個 cron job 在午夜跑、把每張需要分析的表完整 dump 到 S3、再 load 進 Snowflake。當時的「每張表」是 6 張左右、每張幾百萬 row，整條 pipeline 半小時跑完。這套方案的好處是極簡——沒有 Kafka、沒有 schema registry、沒有 CDC 工具鏈，幾百行 Python 加一個 cron entry 就上線。

但這套設計從第一天就有一個結構性問題：dump 不在乎變動量。如果一張表昨天到今天只改了 100 row，pipeline 仍然會完整搬完整張表。當資料量小，這個浪費沒人在意；當資料量大，它就會把整個系統壓垮。

到了 2023 年，Figma 的業務量是另一個世界。要同步的表從 6 張長到上百張、最大的表破 1 億 row、每天的修改範圍仍然是「相對於總量很小的一部分」——但 cron dump 仍然執著於把整張表搬一次。最直接的後果：daily sync 從 30 分鐘膨脹到 6+ 小時，最大的幾張表「要花好幾天才能跑完一輪」。這意味著分析師早上 9 點打開 dashboard 時，看到的是「前天甚至大前天」的數字。

第二個後果更貴。對 production PostgreSQL 做 SELECT * 會把整張表掃過——這對線上服務是不可接受的壓力，所以 Figma 開了多個專屬 RDS read replica，把 export 的工作隔離到這些 replica 上。每個 replica 是一台完整的 PostgreSQL 機器，按 RDS 的計價跑 7×24，年費以「以百萬美元計」的尺度累積。ByteByteGo 的原文沒有給出具體 replica 數量，但形容「replica costs made that untenable」、「costing Figma millions of dollars a year」——這是個夠硬的訊號。

第三個後果是「不能再上新表」。當每張表的 dump 動輒花掉資料工程團隊的一整天 cron 視窗，工程師開始拒絕分析師提的新同步請求——「這張表太大、現在的 pipeline 不能再吃了」。資料倉的價值被基礎建設的擁塞反過來限制住，這在資料平台團隊裡是個典型的「技術債轉化為產品負面影響」的時刻。

2023 年中，Figma 內部對「要不要重做」這件事做了一個決定。結論明確：cron dump 的問題不是調 tuning 可以解決的，因為「搬全表」這個前提本身就錯。要解的是「只搬變更」，這就是 CDC（Change Data Capture）的形狀——讀 PostgreSQL 的 WAL（write-ahead log）、把每筆變更事件流出來、下游按 primary key 做增量 upsert。CDC 不是新技術，2010 年代後期已經是大型資料平台的事實默認；Figma 要做的不是發明新技術、是把這套架構在自己的環境裡跑通並做對。

把當時的選擇放在更廣的脈絡看：CDC 在 2023 年已經有成熟的開源實現（Debezium、自研 PostgreSQL connector、各大雲廠商的 native CDC service），也有成熟的下游 sink 模式（Snowflake、Databricks、BigQuery 都支援增量 merge）。Figma 沒有選擇任何一條「pure off-the-shelf」的路徑——ByteByteGo 的報導沒有明說具體的 connector 選型，只描述了概念上的元件，這通常意味著內部對既有工具做了相當程度的客製。對讀者的啟示：CDC 的「上手成本」並不在 connector 本身，而在 schema 變更怎麼處理、bootstrap 怎麼對齊、audit 怎麼跑——這幾件事每家公司都得自己做一次。

那個夏天的另一個觀察值得記下：當資料工程團隊向公司財務說明「我們要花一個季度做這個重構」時，他們手上的數字不是「延遲改善 X 倍」這種抽象的工程指標，而是「我們會關掉這些 RDS replica、年費省下 $M」這種帳面上立刻可見的支出削減。「成本驅動的工程投入」往往比「延遲驅動的工程投入」更容易過內部審批——因為前者直接對應到財報、後者只對應到「使用者體驗」這種柔軟的概念。對技術領導的啟示：在跟非工程的決策者談大型基礎建設重構時，先找出能對應到帳單削減的軸線。

CDC 切換與 bootstrap 怎麼對齊

2024 年的重建是分階段的，不是一次切換。第一階段：對所有需要同步的表啟用 PostgreSQL logical replication，這是 PostgreSQL 9.4 之後提供的功能、可以把 WAL 上的變更事件透過 publication / subscription 模型流出去。CDC 讀的是 WAL，不是線上查詢，所以對 primary 的負擔接近零——這個性質讓 Figma 可以把 CDC 直接掛在 primary 上、不再需要專屬 replica 跑 export。

第二階段：每張表配一個 Kafka topic，所有 CDC 事件按 primary key 分區寫入。Kafka 在這裡的角色是「order-preserving、持久化的 delta 緩衝」——它接收 WAL 流、保留可重放的歷史、給下游一個穩定的 offset 概念。為什麼一張表配一個 topic 而不是所有表共用一個 topic：因為 per-table topic 讓下游可以獨立消費、獨立調 commit 頻率、獨立暫停——一張表的 schema 變更不會卡住其他表的 sync。

第三階段：Snowflake 端寫 stored procedure，每隔 N 小時從 Kafka 上對應的 topic 拉取累積的 delta、對 production table 做 incremental merge。預設 N 是 3 小時，per-table 可調——billing 等對新鮮度敏感的表配 30 分鐘、ad-hoc 觸發走 CLI 工具。Merge 的形式是 Snowflake 的 MERGE statement，按 primary key 做 upsert：

MERGE INTO prod.table_X target
USING (
    SELECT * FROM stage.table_X_delta
    WHERE offset > last_committed_offset
) source
ON target.pk = source.pk
WHEN MATCHED AND source.op = 'DELETE' THEN DELETE
WHEN MATCHED AND source.op = 'UPDATE' THEN UPDATE SET ...
WHEN NOT MATCHED AND source.op = 'INSERT' THEN INSERT ...;
// 每個 cycle commit 後更新 last_committed_offset

這套 incremental merge 的關鍵性質是冪等：同一筆 delta event 被 apply 兩次、結果與 apply 一次一樣。這個性質之所以重要，是因為 CDC 管道最怕的不是「漏一筆」，而是「不知道有沒有漏」——冪等讓 retry 變成安全的工具，failure mode 從「資料正確性問題」降級為「重複工作問題」。

更具體一點：當一個 merge cycle 因為網路抖動、Snowflake warehouse 重啟、或 Kafka consumer offset 提交失敗而中斷時，下一次 cycle 會看到「上次處理到一半」的狀態——某些 delta event 已經 apply 進 prod table、但 last_committed_offset 還沒推進。如果 merge 不是冪等的，這時候要嘛漏資料（從更後面的 offset 繼續）、要嘛髒資料（同一筆事件 apply 兩次造成計數錯誤）。冪等讓「從上次的 last_committed_offset 重新開始」變成永遠安全的選擇——這把 CDC pipeline 的容錯模型從「複雜的兩階段提交」簡化為「從上一個 checkpoint 重做」。

WAL 本身的性質讓冪等變得自然：PostgreSQL 的 logical replication 輸出的事件帶 LSN（log sequence number）、嚴格遞增、且每筆事件都明確標示是 INSERT / UPDATE / DELETE 並包含完整的 primary key。下游可以用「MERGE 按 primary key」這個單一動作來吸收任何順序的事件——這跟「以時間戳為主」的傳統 ETL 不一樣，後者很容易因為時鐘漂移或處理順序問題產生奇怪的中間狀態。

Snowflake 端還有一個值得記下的設計：merge stored procedure 的執行頻率與 Snowflake warehouse 的 auto-suspend / auto-resume 配合得很巧。warehouse 在不需要時自動 suspend、merge cycle 觸發時自動 resume——這意味著「per-table 可調到分鐘級」在配置上很彈性，但在帳單上不會線性放大，因為短週期的 merge 不會讓 warehouse 長時間 idle。傳統 ETL 系統因為要長時間佔用計算資源，這套「sleep when idle」的彈性很難拿到——Snowflake 的 separated compute / storage 模型讓 CDC 管道能享受到這個性質。

第四階段也是最棘手的：bootstrap。前面三階段處理「穩態」——CDC 已經在跑、delta 在 Kafka 上、merge 在 Snowflake 上。但是當一張新表第一次接入 CDC 系統時呢？這張表已經有 5000 萬 row 存在於 PostgreSQL，CDC 流只能從「啟用之後」的變更開始——這 5000 萬 row 怎麼進 Snowflake？

Figma 的解法是 Amazon RDS 的 snapshot-to-S3 export 功能。流程是這樣的：

// 1. 先在 CDC stream 上記下 offset
O_start := current_offset(kafka_topic_X)

// 2. 立即觸發 RDS snapshot export 到 S3
trigger_snapshot_export(table_X, S3_bucket)
// snapshot 完成可能要幾十分鐘到幾小時
wait_until(snapshot_complete)

// 3. 把 S3 上的 snapshot 批次匯入 Snowflake
load_into_snowflake(S3_bucket, audit_table_X)

// 4. 從 O_start 開始 apply stream
apply_cdc_stream(kafka_topic_X, from_offset=O_start)
// stream 會 replay snapshot 期間的所有變更——重複 apply 被冪等吸收

這套順序的關鍵：先記 offset、再 snapshot。為什麼？因為 O_start 是 snapshot 開始之前的時間點，snapshot 完成時 RDS 提交的事務必然涵蓋了所有 offset ≤ O_start 的寫入（snapshot 是 transaction-consistent 的，內部使用 RDS 的 MVCC 快照機制）。stream 從 O_start 開始 replay，會覆蓋 snapshot 期間的任何寫入——包括 snapshot 開始到完成之間 RDS 上發生的所有變更。因為 merge 是冪等的，重複 apply 不會造成髒資料。

對比常見的「先做 snapshot、snapshot 完成後再記 offset」的順序：這種順序會在 snapshot 完成的瞬間與「開始記 offset」之間留一個 race window——snapshot 過程中 RDS 上發生的寫入可能既不在 snapshot 內、也不在 stream 內，於是就漏掉了。Figma 用「先 offset、後 snapshot」的順序把這個 race window 在設計階段消掉，不靠人類盯著時間戳對齊。

2024 到 2025 年之間，Figma 把這套 bootstrap 流程做成了 self-serve 工具——資料工程師只要在內部 CLI 跑一條命令、指定要接入的表名，背後的 controller 會自動觸發 snapshot、設定 Kafka topic、建 Snowflake stored procedure、啟動 merge cycle。原本「每張表 1-2 天的人工 bootstrap 工程」變成「跑一條命令、幾小時自動完成」——這對能搬的表規模有複利效應，因為新表接入的摩擦變低了。

把這條 self-serve 工具拆開來看，它其實是兩層的自動化。最底層（Tier 1）是「對單一表的 bootstrap 與 validate 執行」——這層處理 snapshot 觸發、S3 上傳、Snowflake import、stream apply、offset recording 等具體動作。上面一層（Tier 2）是「scheduling 與 dispatch」——一個 controller 持續掃描需要新接入的表、自動 dispatch Tier 1 的任務、追蹤狀態、在週期性 audit 時間到時批次觸發 re-bootstrap。這種「執行層」與「調度層」分離的設計讓兩層可以獨立演化——bootstrap 邏輯改變不影響 scheduling、scheduling 策略調整不需要動 bootstrap 代碼。

bootstrap 流程裡有一個容易被忽略的細節：RDS snapshot export 不是「對 production 拷貝一份」這麼簡單。RDS 的 snapshot 機制在 EBS 層做 copy-on-write、不對 production 造成任何 I/O 壓力——這就是為什麼 Figma 可以從專屬 read replica 解放出來。snapshot 完成後 export 到 S3，這個 export 動作會把 PostgreSQL 的 binary heap format 轉成 Parquet 或 ORC（具體格式 ByteByteGo 未明說），讓 Snowflake 可以直接讀。整條 bootstrap 路徑——RDS snapshot → S3 Parquet → Snowflake COPY INTO——沒有任何一步要動到 production PostgreSQL。

audit：cell-by-cell 與 zero-downtime re-bootstrap

到 2025 年底，Figma 的 CDC pipeline 已經在 production 跑了一年多——延遲從 30+ 小時降到 3 小時、最大表能跑下來、replica 帳單顯著下降。但團隊內部有一個揮之不去的擔憂：怎麼證明資料是對的？

CDC 管道有一個經典的、難以察覺的失敗模式：靜默偏離（silent drift）。某個 stored procedure 的 corner case、某次 schema 變更時的順序錯誤、某段時間 Kafka topic 的 retention 配置漂移——這些都可能導致少量 row 在 Snowflake 上的值與 PostgreSQL 不一致。整體 row count 看起來對，因為大部分 row 還是對的；只有那些靜默偏離的 row 在分析報表上產生詭異的數字，往往要好幾週後才有分析師察覺。

傳統 ETL 圈用 row count 抽樣比對來捕捉這類問題，但 row count 只能抓粗暴的失敗（一整批 row 漏掉、整個 partition 沒寫入）。對「100 萬 row 裡有 17 row 的某個 column 值錯了」這種情境，row count 完全失明。Figma 決定不靠抽樣——他們每週對所有同步的表做一次完整的 re-bootstrap：

// 每週對每張表跑一次
weekly_audit(table_X):
    // 走獨立的 snapshot 路徑——不重用 CDC pipeline
    snapshot := rds_export_snapshot(table_X) → S3
    audit.table_X := load_into_snowflake(snapshot)

    // cell-by-cell diff
    diff := SELECT * FROM prod.table_X p
            FULL OUTER JOIN audit.table_X a ON p.pk = a.pk
            WHERE p IS DISTINCT FROM a

    if diff.rows > 0:
        alert(diff.rows)
        log(diff)

這套 audit 在工程量上不便宜——每週做一次完整 snapshot 並 cell-by-cell diff，等於把 CDC 之前的「全表 dump」這件事重新跑一次，只是頻率從每天降到每週。但這是「資料正確性」的唯一硬保證：因為 audit 走的是完全獨立的路徑（snapshot → S3 → Snowflake），它與 CDC pipeline 共享的代碼面積接近零；CDC pipeline 的任何 bug 不會影響 audit 的結果——這種「獨立路徑驗證」是分散式系統裡證明正確性的標準手段。

2026 年初 audit 系統在 staging 環境抓到過一次嚴重的 silent drift——某個 schema 變更觸發了 stored procedure 的 corner case、導致一張關鍵表的部分 row 在 merge 過程中被錯誤地 update。ByteByteGo 的原文描述這次發現「would have triggered a site-wide outage lasting at least twenty minutes」——意思是如果這套 audit 不存在、這個 bug 順利進入 production，下游依賴這張表的服務會在 20+ 分鐘的時間內讀到錯誤資料、最終觸發 cascading failure。staging 的 audit 在發布前就攔下了它。

這次攔截值得拆開來思考它的反事實價值。如果 audit 不存在、bug 進入 production，會發生什麼？大概是這個次序：（1）某些下游 dashboard 出現詭異的數字、但因為偏離量小、團隊以為是上游業務變動；（2）依賴這張表做 routing 決策的某個內部服務開始用錯誤資料、產生一連串對使用者不可見但正在累積的副作用；（3）某個敏銳的工程師發現「這個數字不對勁」、開始調查、發現上游資料錯誤、但已經是 bug 進 production 的好幾天後；（4）回滾需要對 prod table 做 rebuild，整個過程的下游服務需要降級或停機。整套修復的工程成本以「人週」計、業務成本以「分析師信任度」計——後者比帳面數字更難恢復。audit 把這套 cascading 成本在發布前就消掉了，這是它最大的價值。

對「audit 是不是過度投入」的反駁：每週做一次完整 snapshot 並 cell-by-cell diff，工程成本是 RDS snapshot export 的雲端帳單 + Snowflake compute 的執行時間 + 自動化代碼的維護成本——這個總和遠小於「一次 silent drift 進 production 後的 cleanup 成本」。audit 的 ROI 在第一次攔截 silent drift 的瞬間就回本了。

audit 還有一個側面值得記下：re-bootstrap 過程本身被做成 zero-downtime 的。傳統的「重建表」流程是「drop + reload」——這意味著從 drop 到 reload 完成之間，下游讀到的是空表或半填的表。Figma 的做法是用「版本化 artifact + atomic view swap」：

// audit table 用版本後綴避免衝突
audit.table_X_v_20260518 := load_snapshot()

// diff 與 alert 都針對這個版本
run_diff(audit.table_X_v_20260518, prod.table_X)

// 完成後，atomic 切換 audit view
CREATE OR REPLACE VIEW audit.table_X AS
    SELECT * FROM audit.table_X_v_20260518;

// 舊版本保留 N 週，作為回滾或調查證據

這套版本化讓 audit 對下游分析任務透明——任何讀 audit schema 的下游 query 看到的永遠是一個一致的版本，view swap 是 atomic 的、不會出現「query 跑到一半 audit 表被 drop」的情境。

把 audit 的設計拆成幾個值得獨立分析的決策。第一個決策：「每週」這個頻率怎麼定的？週期太短，audit 的雲端成本（snapshot export + Snowflake compute）會線性增加；週期太長，silent drift 可能在被抓到之前就影響業務。Figma 選擇「每週」是一個經驗值——對 CDC pipeline 的成熟度與 schema 變更頻率而言、一週的偏離窗口可以接受。對更敏感的系統（金融、計費），這個週期可以拉到「每天」或「每小時」、但成本也會相應增加。

第二個決策：「全表 cell-by-cell」而非「抽樣比對」。抽樣比對的代表是「對每張表隨機抽 1% 的 row 做 hash 比對」——成本低 100×、但對非均勻分布的 drift 完全失明（如果 drift 集中在特定 partition、抽樣命中率可能是零）。Figma 沒有走這條捷徑、堅持完整 diff，理由是「我們無法事先知道 drift 會集中在哪裡」——這是個誠實的設計判斷。

第三個決策：用 PostgreSQL 的 snapshot 而非「重跑 CDC pipeline」做 audit 來源。如果 audit 用 CDC pipeline 的歷史 event 重建另一份 table，它與 production CDC pipeline 共享了 Kafka topic 與 merge logic——CDC 的 bug 會以相同的方式污染 audit。用 RDS snapshot 走完全獨立的路徑（snapshot → S3 → Snowflake COPY）只依賴 RDS 自己的事務一致性，這條路徑與 CDC pipeline 共享的代碼面積接近零。這是 audit 的「diversity」性質——它不只是「再做一次」、是「用一條截然不同的路徑做一次」。

第四個決策：alert 的細節。當 audit diff 發現偏差，系統不只是發一個 PagerDuty「資料不一致」的通知——它列出每一筆偏離 row 的 primary key、prod 的值、audit 的值、以及最近的 schema 變更歷史。這把 on-call 工程師的負擔從「我要從零開始查」降低到「我直接看 17 筆 row 各自的差異、推測哪一次 merge 出問題」。alert 的可操作性決定了它的實際價值——一個告警如果只說「有東西錯了」、沒有給出可立即動作的線索，往往會被忽略或延後處理。

三年的變動軌跡

下面這張資料表把每個階段的關鍵數字並列：原本的 cron 系統、CDC 過渡期、與 2026 年的穩定狀態。讀者可以橫向掃過、感受每一個指標的量級變化。

把上面這幾個維度合起來看：CDC 切換不是單一指標的改善、而是一條多維度的曲線整體位移。最值得記的是「延遲與成本同時下降」——傳統 ETL 圈的直覺是「想要更低延遲就要付更高成本」（更頻繁的 cron、更多 replica），但 CDC 把這條 trade-off 重塑了：因為 CDC 讀 WAL 的負擔接近零，更頻繁的 sync 不會線性增加成本。Figma 從「6 小時跑一次、付 $M」變成「分鐘級可調、近乎免費」——這是架構變更帶來的非線性收益。

除了維度層面的比較，把延遲本身的軌跡按時間畫出來、用 log scale 拉開三個世代的量級差，這條曲線最能說明「CDC 切換」是怎樣一個拐點。下面這張 chart 把「每張表的同步延遲」按年份排列——兩條線分別是「最常見表」與「最大表」、後者的曲線變化更戲劇。

這張 chart 用 log scale 是必要的——線性 Y 會讓 2023 年的 30 小時點完全淹掉 2026 年的 5 分鐘，視覺上的拐點就看不出來了。log 之後，兩個關鍵的特徵浮現：第一，2022 → 2023 年的曲線是「指數惡化」——資料量成長、cron 模型不調整、延遲呈現非線性膨脹；第二，2024 → 2025 年的兩條曲線開始「收斂」——因為 CDC 模型下延遲與表規模脫鉤、最大表不再是延遲瓶頸。

第三個值得注意的特徵：2026 年兩條線完全重疊在 5 分鐘左右——這不是測量誤差，而是「per-table 可調」的副作用。每張表的 sync 頻率由 owning team 在配置裡指定，跟表規模無關。這個性質本身就是 CDC 架構帶給 Figma 的最大組織槓桿——資料工程團隊不再是新鮮度的單點瓶頸、每個 owning team 可以根據自己的 SLA 自己決定。

把同一條故事的最終形狀畫成可互動的元件圖、讓讀者點選任一節點看它的職責邊界——這是用「空間」去印證上面用「時間」描繪的同一條敘事。下面這張是 2026 年穩態的 CDC 架構，五個主要元件、每個都可以點選展開它的不變式。讀完這張圖，讀者應該能回答「哪個元件擁有 offset 重疊的不變式？」、「哪個元件擁有 cell-by-cell 比對的責任？」這兩個問題——這也是這套設計的兩個關鍵保護點。

這張圖讓兩個容易被忽略的設計點凸顯出來。第一是 Kafka 在 bootstrap 流程中的角色——很多人寫 CDC 都以為 Kafka 只是「delta 流的緩衝」，但 Figma 把 Kafka 的 offset 拿來當 bootstrap 對齊的錨點。這個用法把「snapshot 與 stream 對齊」這個分散式系統的經典難題，從「時間戳對齊」轉成「offset 對齊」——offset 是嚴格遞增的整數，比時間戳容易推理。

第二是 audit 的獨立性。audit schema 與 CDC pipeline 共享的元件只有 PostgreSQL（資料來源）與 RDS snapshot 機制（搬資料的工具）——下游的 audit table、diff query、alerting 都是獨立的代碼路徑。這意味著 CDC pipeline 的任何 bug（merge stored procedure 的 corner case、Kafka consumer 的 offset 漂移、Snowflake 的版本不一致）不會也以同樣的方式影響 audit；audit 與 CDC 不會「相同地壞掉」。這是分散式系統裡證明正確性的標準形狀，名字叫「diverse redundancy」——用兩條足夠不同的路徑算同一個結果，比對它們。

從這條三年路能學到什麼

對任何維護資料管道的團隊，這條三年路有幾個直接可拿走的設計選擇。

第一，只要管道夠大，CDC 比定期 dump 划算的點來得很快。Figma 的觸發點是 RDS replica 帳單——每年 $M 級的支出讓「拆掉 cron dump」成為一個帳面上明顯划算的工程投入。對更小的團隊，這個觸發點可能是延遲（早上 dashboard 看到的是「前天」）、可能是不能再上新表的擁塞、可能是 dump 對 production 的壓力。無論哪個觸發點，CDC 模型的根本好處不是「更新更頻繁」、而是「成本與規模脫鉤」——CDC 讀 WAL 的負擔幾乎不隨表規模變化，這就改變了「sync 頻率與成本的 trade-off」。

第二，bootstrap 設計常被當成 one-off 工程，但它是 CDC 管道每次新表上線時都要重做的——把它做成 self-serve 的工具流程，不要每張表都人工對 offset。Figma 用「先 offset、後 snapshot」的順序把 race window 在設計階段消掉、再用 CLI 把整個 bootstrap 流程自助化。這對「能搬的表規模」是複利效應，因為新表接入的摩擦變低、團隊願意把更多表納入分析。原本因為「dump 太慢、replica 不夠用」而被擱置的表，現在可以以幾小時的成本接進來。

第三，資料正確性的審計不能靠 row count、要靠獨立路徑重做的 byte-level diff。傳統 ETL 圈在這一塊長期失守——大家都知道 row count 抽樣只能抓粗暴失敗，但「每週對所有表做一次完整 re-bootstrap」聽起來太貴、就沒人做。Figma 用 RDS snapshot 把這件事的成本降到「可接受但不便宜」、再用 atomic view swap 把它做成 zero-downtime——這套組合讓 audit 從「理論上應該做」變成「實際上每週在跑」。staging 環境攔下一次 20+ 分鐘級事故就證明了這個投入的價值。

第四個更廣的觀察：CDC + Kafka + Snowflake 增量合併，現在已經是大規模資料管線的事實上預設架構。Figma 的故事與 Stripe 的 Data Movement Platform、Notion 的 schema 遷移管道、Airbnb 的 Spinaltap、Netflix 的 DBLog 是同一條曲線上的不同站點——共同前提是「不要每天搬全部資料」，方法各家略有不同（Debezium、自研 connector、雲廠商的 native CDC）。值得追蹤的是 audit 這一段：因為「靜默偏離」是 CDC 的特有失敗模式、且 row count 抽樣對它失明，誰把這部分做得最便宜、最自動，誰的長期可信度最高。Figma 在這條路上走得比多數家深。

第五個觀察是組織的——資料平台團隊在 cron dump 時代是「新鮮度的單點瓶頸」，因為所有人的 sync 頻率都被 cron 視窗綁定。CDC 切換後，per-table 配置讓 owning team 可以根據自己的 SLA 自己決定——billing 30 分鐘、metrics 5 分鐘、long-tail 表 6 小時。這個「組織槓桿」往往比延遲數字更有意義：資料平台團隊不再每天接到「我的 dashboard 還是昨天的數字、能不能加速？」的請求，而是把 CDC pipeline 當作平台、讓 user 自己調參數。這跟雲端基礎建設 self-serve 化的曲線是同一條。

第六個觀察：bootstrap 對齊的「先 offset、後 snapshot」是一個普適的設計 pattern，不只用在 CDC 上。任何「啟動一個 stream 並 backfill 歷史資料」的場景——日誌聚合、事件溯源、materialized view 重建——都面對同一個 race window 問題。Figma 把它在 Kafka offset 上解掉的方式，是一個值得在自己團隊內部教學的範例。Stripe 的 DMP 用的是類似但更複雜的「dual-write + reconcile」、Airbnb 的 Spinaltap 用 binlog position——共同的形狀都是「先把 stream 起點記住、再 snapshot」。

第七個觀察是經濟學的——當資料平台的固定成本（replica、ETL 開發、運維）佔總成本的大頭時，「降低延遲」與「降低成本」這兩個目標其實是同向的。傳統直覺認為「想要更新更頻繁就要付更多錢」，但 CDC 切換證明這個 trade-off 可以被架構重塑：刪掉專屬 replica（成本下降）+ 接近實時的 delta sync（延遲下降）。這種「同時改善兩個本來 trade-off 的指標」的時刻，是工程上值得投入的訊號——它通常意味著之前的設計選擇本身就是錯的，而不是 tuning 的問題。

最後一個觀察：這條三年路也是「漸進式重構」的一個樣本。Figma 沒有一次性把 cron dump 廢掉、然後切到 CDC——他們用兩條 pipeline 並行了一段時間，新表先走 CDC、舊表逐張遷移、audit 系統先在 staging 跑了一陣才上 production。這種「並行 + 逐步遷移」的形狀在大型基礎建設變更裡是默認模式，因為它讓 rollback 變便宜——任何一張表發現問題、把它切回 cron dump 就可以，不需要整個系統回滾。對讀者的啟示是：當你準備啟動一個類似規模的重構時，先規劃好「兩條 pipeline 怎麼共存」、再規劃「怎麼逐張遷移」，比一次切換的計畫更務實。

Take-away：CDC 管道的設計不在組件清單（Kafka、Snowflake、S3 大家都有），而在三件事——bootstrap 與 stream 的 offset 怎麼重疊銜接、incremental merge 怎麼冪等、以及靜默偏離怎麼用獨立路徑 re-bootstrap 的 cell-by-cell diff 抓出來。這三件事決定了一條 CDC pipeline 在三年後仍然可信。
