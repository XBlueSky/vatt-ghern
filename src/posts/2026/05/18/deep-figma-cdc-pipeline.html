2023 年 Figma 的每日資料管道從凌晨開始跑：對每張資料表做一次完整 dump、複製到 Snowflake、覆寫舊版。一張資料表 1 億 row、改了 100 row，pipeline 還是搬了完整 1 億 row。某天工程師發現整個 daily sync 花了超過 6 小時，分析師早上 9 點打開 dashboard 仍是「前天」的數字——而 Figma 為這條每日複製鏈付了多個專屬 RDS replica、年費以百萬美元計。

這篇是一條資料管道從每日全表 dump 走到分鐘級 CDC 的三年路。技術選型是常見的（PostgreSQL WAL、Kafka、S3 snapshot、Snowflake），但 Figma 把每一步銜接的失敗模式都用一個額外設計補上——關鍵不在組件清單，在 snapshot 與 stream 之間怎麼對齊、以及離線怎麼證明資料是對的。

what happened

2023 年的 pipeline 是一個簡單的 cron job：每天午夜 fork 出一條 worker，對每張需要同步的 PostgreSQL 資料表執行 SELECT *、寫入 staging、再 swap 到 Snowflake 的 production table。架構簡單，缺點是「無視變動量」：100 row 改動觸發 1 億 row 的搬運。Figma 的業務量在 2023 年成長到每天的同步需要 6 小時以上，且因為 dump 對來源 PostgreSQL 造成壓力，必須跑在多個專屬 read replica 上——RDS 帳單以百萬美元為單位累積。

2024 年的改造是分階段的，不是一次切換。第一階段：對所有需要同步的表啟用 PostgreSQL logical replication，把 WAL 變更事件寫到 Kafka——每張表一個 topic，下游可以獨立消費。第二階段：在 Snowflake 端寫 stored procedure，每隔 N 小時把 Kafka 上的 delta 與既有 production table 做 incremental merge；N 預設 3，但 per-table 可以調到分鐘級。第三階段也是最棘手的：bootstrap。新資料表第一次接入時，必須先把目前完整內容搬到 Snowflake、然後從某個 CDC offset 開始 apply stream——這兩者必須在時間上「重疊」否則會漏資料。

Figma 的解法是 Amazon RDS 的 snapshot-to-S3 export 功能。流程是這樣：先在 Kafka 上記下「現在的最新 offset O_start」，立即觸發 RDS export snapshot 到 S3；snapshot 完成後（可能要幾十分鐘），把 S3 上的 snapshot 批次匯入 Snowflake，然後從 O_start 開始 apply Kafka 上累積的 delta。因為 O_start 是 snapshot 開始前的 offset，snapshot 內容必然涵蓋這個 offset 之前的所有變更——「重疊」確保了即使 snapshot 過程中有寫入，也會被 stream 重新 apply、不會漏。重複 apply 是冪等的（每筆 CDC 事件有 primary key），所以重疊不會造成髒資料。

2026 年的最後一塊是審計。CDC 管道有個經典失敗模式：某個 stored procedure bug 或 schema 不一致導致 delta 漏掉特定 row，整體 row count 仍然看起來對，但個別 cell 的值靜默偏離。Figma 不靠 row count 抽樣——他們每週對所有表做一次完整 re-bootstrap（獨立的一條 snapshot → 匯入到 audit schema），然後跑 cell-by-cell 比對。發現偏差時，系統會自動 alert 並列出具體偏離的 row。

why it matters

三個結果值得單獨記下：第一，延遲從 30+ 小時降到 3 小時，per-table 可調到分鐘級——對 dashboard、alerting、A/B 測試 readout 是完全不同的可用性等級。第二，能搬的 table 規模從原本上限放大 10 倍——之前因為 dump 時間太長而被列為「不適合同步」的大表，現在可以接進來。第三，因為不再需要專屬 RDS replica 跑 dump，每年節省以百萬美元計。

有兩個容易被忽略的設計值得記住。第一是 bootstrap 與 stream 的 offset 重疊：很多人寫 CDC 都會在「snapshot 起點」與「stream 起點」之間留個 race window，靠人類盯著時間戳對齊；Figma 用「先記 offset、再 snapshot」確保 snapshot 必然涵蓋 offset 之前的 state，把對齊問題在設計階段就消掉。第二是審計：每週 re-bootstrap 在工程量上不便宜（要再一次完整 snapshot 並 cell-by-cell diff），但這是「資料正確性」的唯一硬保證——靠 row count 比對只能抓掉粗暴的失敗。

so what

對任何維護資料管道的團隊，這條三年路有幾個直接可拿走的設計選擇：（1）只要管道夠大，CDC 比定期 dump 划算的點來得很快——RDS replica 帳單是個很硬的訊號。（2）bootstrap 設計常被當成 one-off 工程，但它是 CDC 管道每次新表上線時都要重做的——把它做成 self-serve 的工具流程，不要每張表都人工對 offset。（3）資料正確性的審計不能靠 row count，要靠獨立路徑重做的 byte-level diff。傳統 ETL 圈在這一塊長期失守，現代資料平台正在補課。

更廣的脈絡：CDC + Kafka + Snowflake 增量合併，現在已經是大規模資料管線的事實上預設架構。Figma 的故事與 Stripe 的 Data Movement Platform、Notion 的 schema 遷移管道、Airbnb 的 Spinaltap 是同一條曲線上的不同站點——共同前提是「不要每天搬全部資料」，方法各家略有不同。值得追蹤的是審計這一段：因為「靜默偏離」是 CDC 的特有失敗模式，誰把這部分做得最便宜、最自動，誰的長期可信度最高。

Take-away：CDC 管道的設計不在組件清單（Kafka、Snowflake、S3 大家都有），而在三件事——bootstrap 與 stream 的 offset 怎麼重疊銜接、incremental merge 怎麼冪等、以及靜默偏離怎麼用獨立的 re-bootstrap diff 抓出來。
