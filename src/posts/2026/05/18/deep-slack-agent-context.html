一個 agent 在跑安全調查，第一個小時叫了三十個工具、看了五份 log、發了兩個 SQL；第二個小時，它要 plan 下一步。問題是：它的 message buffer 已經塞滿了第一個小時的工具呼叫與回應，token 預算開始吃緊。把全部歷史交給下一輪、它讀不完；丟掉太多、它會忘掉重要證據。Slack 安全工程的回答是：根本不要把訊息歷史往下一輪傳。

這篇講 Slack 安全工程在 long-running agentic 任務上的上下文設計：訊息歷史不傳，三個結構化資源（Director's Journal、Critic's Review、Critic's Timeline）取而代之。對於正在做 agent 應用、想避開「context window 吃滿就崩」的工程師，這個三件式設計是一個值得抄的骨架。

start with a concrete case

想像 Slack 內部安全團隊收到一個 alert：某個服務帳號的 API 呼叫頻率在凌晨 03:17 突然飆高。要不要 page 人？這個判斷本身需要先回答十幾個小問題：這個帳號平常的 baseline 是多少？此刻發出的請求落在哪些路由？來源 IP 屬於哪個 region？最近這個帳號的 secret 是不是被 rotate 過？有沒有同一段時間其他帳號也出現異常？

每個小問題都對應一個工具呼叫——查 metrics、查 audit log、查 IP intelligence、查 secret store。一輪調查可能用上幾十到幾百個工具呼叫，跑幾個小時。把這幾百次 tool call 與 LLM response 全部塞進 message buffer，LLM 的 context window（即使是 200K token）會在中段就滿，而且越往後 LLM 越難在自己上千 token 的 chat history 裡找到關鍵證據。這就是 long-run agent 真正的痛點：不是模型不夠強，是工作記憶不夠用。

where today's tools fall short

主流的 agent 框架（LangChain、AutoGPT、ReAct）預設都是「message history 滾大」式設計：每一輪 reasoning step 都把先前所有 tool call 與 response 串接在 prompt 裡。短任務沒問題，長任務一定撞牆。常見的補救手段有三種，但每種都有缺陷：

第一種是 sliding window——只保留最近 N 輪。簡單但暴力，N 輪以前的關鍵發現直接消失。第二種是 summarization——讓 LLM 自己把舊歷史壓縮成摘要。問題是摘要的品質取決於 LLM 對「什麼重要」的判斷，且 hallucination 會在壓縮過程被放大：一個沒發生的事件被「summarize」進摘要後，下一輪 LLM 把它當事實處理。第三種是 RAG retrieval over chat history——把歷史 embedding 到 vector store，按需要 retrieve。延遲與 retrieval 漏召的問題會逐漸累積。

三種都共享一個前提：訊息歷史是主要的工作記憶。Slack 的選擇是把這個前提整個換掉。

the core idea

不在 agent 之間傳訊息歷史。每次 agent 被呼叫，只看三個明確結構化的共享資源：

Director's Journal 是 Director 的工作記憶：決策、觀察、發現、未解問題、假設、已採取的行動，每筆帶時間戳與優先序。Critic's Review 是 Critic 對每個 Expert finding 的逐項評分（0.0–1.0 可信度），標註是否被證據支持。Critic's Timeline 是只從「可信度足夠的 findings」中重建的時序敘事，並標出證據 / 時序 / 邏輯三類缺口。

三者的角色分工是這個設計的關鍵：Director 知道「下一步該做什麼」，但不直接看 raw tool output；Expert 直接接觸 tool，但不負責決策；Critic 看 Expert 的輸出但用較強的模型 + 較窄的指令做驗證。幻覺只能通過「跟其他證據一致」這道關卡才能進 timeline——「A hallucination can only survive this process if it is more coherent with the body of evidence」。

what it actually looks like

每一輪的呼叫流程概念上像這樣：

// 一輪迭代
loop:
  // Director 看 Journal + Timeline，決定下一個 sub-task
  task = director.plan(journal, timeline)
  if done(timeline): break

  // Expert 拿 task 與相關的 Journal 切片（不是整個 history）
  finding = expert.investigate(task, journal.slice(relevant_to: task))

  // Critic 評估 finding，寫入 Review
  review = critic.assess(finding, evidence: timeline)
  reviews.append(review)

  // 若 review 通過門檻，把它合進 Timeline
  if review.credibility >= 0.5:
    timeline = critic.consolidate(reviews, prior: timeline)

  // Director 把這一輪結論記進 Journal
  journal.append({ task, finding, review, ts: now })

幾個重點：第一，expert.investigate 的輸入是 task + Journal 的相關切片，不是「完整的 chat history」。Journal 的切片大小是可預測的（O(任務數)而非 O(token 數)）。第二，Critic 在 consolidate 時主動標出邏輯缺口，這些缺口會回饋給 Director，下一輪的 plan 會優先補洞。第三，Critic 用的是「比 Expert 更強的模型」（例如 Expert 用一般推理模型、Critic 用 reasoning 模型），這把驗證的品質與成本分離開——Expert 跑得快但會錯，Critic 跑得貴但少錯。

when you'd reach for it

這個三件式設計適合：（1）任務時長以小時計、需要幾百次 tool call 的調查 / planning agent；（2）容忍「驗證有延遲」的 use case——Critic 的評分必然落後 Expert 一步；（3）對幻覺 cost 敏感的應用（安全、合規、醫療、法務），值得多付一個 Critic 的成本換 hallucination 過濾。

不適合：（1）秒級回應的對話 agent——三角驗證的延遲吃不消；（2）任務本質就是「按順序執行幾個固定步驟」——message history 反而比結構化資源輕量；（3）小型 agent 系統，工程開銷比節省的 token 更貴。三件式的成本是「每個 finding 多一次 Critic LLM 呼叫」與「維護三份共享資源的 state machine」，要小心衡量。

還有一個間接好處值得記住：因為三份資源都是「結構化 + 帶時間戳」的，系統可以在事後 audit——回放 Director 在每一步看到的 Journal 切片，重現 Critic 為什麼把某條 finding 評為 misguided。傳統「滾大的 message history」式 agent 在出事時除錯極為困難；結構化 context 讓 agent 系統的 observability 終於與普通服務齊平。

Take-away：long-run agent 的工作記憶不該是訊息歷史——把它換成幾份角色化的結構資源（決策、評分、敘事），加上一個「比 Expert 更強的 Critic」做幻覺過濾，agent 系統就從「越跑越亂」變成「越跑越收斂」。
