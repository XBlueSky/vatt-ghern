在 us-east1-b 那個 12:13 PDT 的時刻，一份 Kubernetes 部署檔把 session 管理 pod 的副本數砍了一半，graceful draining 還沒跑完，17% 的 session 就被硬切斷——這道裂口最終要花掉 voice 團隊 3 小時 17 分鐘，並讓 15 台 voice syncer 的 Erlang mailbox 同時膨脹到接近一百萬則訊息才補得起來。

Discord 3/25 語音崩盤覆盤——一行誤設掀翻 voice control plane

這是一份標準的 Elixir 服務遷上 Kubernetes 的部署，按照變更紀錄上的描述「沒什麼新鮮事」——直到 12:13 PDT 那一刻，那份 manifest 把 us-east1-b 區的 sessions service pod 副本數壓到只剩一半，安全機制還沒來得及把記憶體裡的 GenServer 狀態交棒出去，pod 就先被排程器殺掉了。

Discord 的工程師 Bo Ingram 與 Stephen Birarda 在事後報告開頭引了一個很久沒聽到的比喻：「The sad trombone haunts our dreams. Womp, womp, womp...」這不是文采上的修飾。任何人經歷過一次連續切了三波 rollback 都失敗的當班，都會明白那種聲音在腦中揮之不去的感受——你看著儀表板上 mailbox 曲線從 0 萬一路漲到 100 萬，你的指令照理說該讓它下來，但它就是不動，或者跌一下又被新湧進來的流量打回去。這一篇就是把那 3 小時 17 分鐘裡，每一步發生了什麼、為什麼前三次救火沒用、第四次又為什麼救得起來、後續結構性的修補拼成什麼樣，按時間順序復現一次。

一份誤設的 manifest——故事從這裡長出來

整個事件的「起爆點」其實只有一行。

一份 Kubernetes deployment 的 replicas 從原本的數值改成大約一半——就這麼簡單。

這個變更發生在 Discord 正在把 Elixir 服務逐步搬上 Kubernetes 的過程中。當時的目標是讓 sessions service——也就是負責管理「每一個使用者裝置 ↔ 連線」對應關係的核心服務——能享受 horizontal pod autoscaler 與滾動更新的好處。

把 sessions service 搬上 Kubernetes 是合理的工程決定。每個服務都應該能夠 horizontal scale；每次部署都應該能夠 rolling update；每個節點都應該可以被 replace 而不影響整體服務。這是 Kubernetes 存在的全部意義。問題不在「為什麼搬」，而在「搬的過程中漏了什麼」。

問題不在「縮減副本」這個動作本身，而在於 graceful draining 沒跑完。

Elixir 的 sessions service 在每個 pod 裡跑著數以萬計的 GenServer process。每個 process 都拿著一個正在連線中的使用者裝置的 in-memory state。

把這些 process 從一台 node 平順地搬到另一台 node，必須等「狀態交棒」流程跑完——對 GenServer 而言，這意味著 hibernate、序列化、跨 node 重建。

Kubernetes 的預設 terminationGracePeriodSeconds 通常不夠這套儀式跑完。而那次部署偏偏沒有相應地調高、也沒有設定一個 admission webhook 去攔截不安全的縮容。

結果就是 sessions service 在那一瞬間被「ungracefully stopped」掉了一批 pod。

事後報告給出的數字是：「17% of sessions across Discord were ungracefully stopped」。

Discord 全球同時在線 session 數不會公開，但稍微估算就能體會，這代表了千萬量級的連線在毫無心理準備下被剪斷。對一個以即時通訊為主要使用情境的平台來說，這個比例不是小數。

更關鍵的是，這 17% 並不是均勻分散——它們全集中在 us-east1-b 同一個 zone 裡。

當這些 session 嘗試重連、轉到鄰近 zone 時，重連的流量就會形成一道朝著 us-east1-c 與 us-east1-d 灌過去的「reconnection storm」。後續所有故事，幾乎都長在這道風暴的不同岔路上。

這也是分散式系統故障常見的一個結構特徵：故障的「物理位置」與故障的「影響範圍」往往不一致。Bug 出在 us-east1-b 的一個 deployment 設定，但被它打垮的是 us-east1-c、us-east1-d，最後是全球的 voice syncer fleet。當你的系統有 cross-zone failover 機制——這幾乎是現代分散式系統的標配——任何一個 zone 的局部問題都有機會經由 failover 路徑變成全域問題。

從 sessions 切到 gateway——兩分鐘內第一波擴散

12:13 到 12:15 PDT 之間，Erlang/OTP 的 process linking 機制把這場意外從局部變成了全域。

Elixir 的設計哲學是「let it crash」加上 supervisor 樹。

當一個 GenServer 異常退出，它的 monitor 會發 {:DOWN, ref, :process, pid, reason} 訊息給所有訂閱者。

Discord 的 realtime 系統是高度互鏈的：每個 session 同時被 guild process（也就是「伺服器」）、presence tracker、gateway connection 訂閱。

事後報告用了一個動詞——「flurry of messages」——來形容那兩分鐘內整個系統內部的訊號雜訊。

這個比喻很精準。它不是穩定的高流量，是一陣短時間內爆發的雜訊。所有 17% 被殺掉的 session 同時放出 DOWN 訊息，每個 DOWN 訊息又會觸發訂閱者各自的清理邏輯——guild process 要把這個 user 從成員快取裡踢掉、presence tracker 要更新使用者狀態、gateway connection 要決定要不要保留或關閉對應的 websocket。每一條清理路徑都是合理的；但同時跑這麼多次，本身就是負載。

這道雜訊很快撞上了下一個瓶頸：gateway service。

Gateway 是負責收發 websocket 的代理，前面是公網的 wss 連線，後面是 Discord 內部各 realtime 服務。

原則上，當前端的 session 斷線時，websocket 也該斷。但實務上有大量 client 會立刻嘗試重連——Discord 的 client 端 SDK 預設就會在連線中斷後做指數退避的重連。

於是 gateway 在 us-east1-b 區的節點同時要處理「上一批連線正在拆」與「下一批連線正在建」兩股流量。

每個 host 上原本有 session start rate limit 來保護自己，但這個限制值在遷移過程中被「miscalibrated post-migration」——也就是說，新 host 的設定值並沒有按照新 pod 的 CPU/記憶體比例重新計算。

於是 gateway 在湧入的 reconnection 面前等於沒有保護。

Gateway memory capacity 圖顯示，us-east1-b 的節點記憶體佔用幾乎是垂直拉升到接近 100%。

當 OOM killer 開始介入，那些節點重啟，把流量甩到 us-east1-c 與 us-east1-d——失敗自此跨越了 zone。

這個傳染路徑要記住，因為它解釋了為什麼後面當 voice syncers 出狀況時，影響範圍是全球而不是局部：reconnection storm 已經在前 15 分鐘裡讓所有可用 zone 都進入「異常負載」狀態。

當某個下游服務在第 30 分鐘開始撐不住時，整個 stack 已經處在一個「沒有任何 zone 還有 head-room」的脆弱狀態。這意味著任何小規模的擾動，都會被放大成跨 zone 的災難。

cascade 的真正長尾——voice syncers 的 mailbox 是怎麼漲到一百萬的

從 12:13 一直到 15:30，整個事件最難解的部分都集中在一個名字平淡無奇的內部服務：voice syncers。

Discord 用了一個段落來解釋它的職責——「manages SFU endpoint placement across more than 25,000 external instances」。

換成白話：當你按下「加入語音頻道」，session 端不會直接跟 SFU（Selective Forwarding Unit，負責轉發音視訊封包的那層）談判。

而是先打到 voice syncers，由它根據負載與地理位置決定要把這通通話接到哪一台 SFU 上，再透過 HTTPS RPC 通知那台 SFU「來，把這個 user 收進來」。

15 台 syncer 實例要照顧 25,000+ 台 SFU。每秒鐘要處理的「endpoint select/create」請求，平時就已經不算少。

當 reconnection storm 來臨時，所有正在語音通話中的 session 都嘗試重建到 SFU 的關聯，syncers 收到的負載瞬間倍增。

瓶頸是怎麼被找出來的，是這次覆盤裡最有教育意義的部分。

voice syncers 內部用了一個叫做 Holster 的內部函式庫來池化 HTTP 連線。

Holster 底層用 Erlang 生態的 gun HTTP client。

而 gun 的 connection 生命周期是由兩層 supervisor process 管理的。每當 syncer 需要對 SFU 發起新的 HTTPS RPC，連線建立的請求都要經過這兩層 supervisor 之一。

Erlang 的 process 是 actor model：彼此之間靠 mailbox 通訊，process 主迴圈是一個 receive ... end 區塊。一般情況下這個機制非常便宜。

但這兩層 supervisor 使用的是 selective receive——亦即它們在 receive 區塊裡用 pattern match 挑選符合條件的訊息，不符合的就跳過保留在 mailbox 裡。

當 mailbox 短的時候這個動作幾乎免費。但 mailbox 一旦變長，每次 selective receive 都得從頭掃過所有未處理訊息，複雜度退化成 O(n)。

這是 BEAM 一個冷門但決定性的細節：selective receive 的性能特性會隨 mailbox 長度二次惡化——每個 spawn 變慢、處理速度變慢、mailbox 又因此變更長。它本身就是一個自我加速的退化模式。

事後 Discord 的工程師做了量化測試，給出了一個讓人印象深刻的數字：「we confirmed that this selective receive on a supervisor with a ~100k mailbox queue adds ~1ms to process spawn time」。

1 毫秒聽起來不多，但每個 SFU RPC 都會觸發一次新的 connection spawn——當 syncer 每秒鐘要 spawn 幾百到幾千次 connection 時，1 毫秒/次的 overhead 直接吃光所有 CPU。

更糟的是，這條 critical path 還跟 service discovery 黏在一起。

voice syncers 透過 etcd 註冊自己的健康狀態：每個實例定期 refresh 一個 TTL，告訴 consistent hash ring 上的其他 service「我還活著，把流量送過來」。

問題在於，這個 TTL refresh 的訊息也要經過同一組已經被連線請求塞爆的 supervisor mailbox。

當 mailbox 排到一百萬則訊息深時，TTL refresh 根本來不及處理，etcd 就把那個實例從 ring 上拔掉了。

這是事故設計上最殘酷的一個細節——control plane（service discovery）與 data plane（connection management）共享同一條 critical path，等於把「我還活著」的訊號跟「我正在處理流量」的訊號綁在一起。當後者卡住，前者也一起死。健康檢查機制本身變成了崩潰加速器。

結果是一個糟糕的正回饋迴圈：

  1. mailbox 變長 → process spawn 變慢 → endpoint create 失敗率上升
  2. endpoint create 失敗 → 上游服務重試 → mailbox 變更長
  3. TTL refresh 排不上 → etcd 把實例移出 ring
  4. 剩下的健康實例要承擔更多 failover 流量 → 它們的 mailbox 也開始堆
  5. 回到第 1 步

正回饋迴圈是分散式系統最危險的一種失效模式。不像線性退化會在某個負載點停下來，正回饋會自我加速——每跑一輪迴圈，下一輪的速度更快、影響範圍更大。對抗它唯一有效的方法不是「修復某個壞掉的部位」，而是「切斷迴圈中至少一條邊」。

儀表板上的「Endpoint Select/Create Success」指標在 12:14 PDT 跌到接近零。

15 台 syncer 裡，當下只有一台序號 2-8 的實例還活著——但它一台要扛全球三分之一的流量，根本撐不住。

同一時間，所有 15 台的 mailbox size 都顯示出穩定且持續成長的曲線。

注意一個重要的觀察：問題不是某幾台「壞掉」——是 15 台同時走向同一個失敗模式。當你的儀表板看到這種「同步退化」的形狀，幾乎可以斷定問題不在實例本身，而在它們共同依賴的某個系統屬性——這次是上游沒有節流。

三次失敗的 rollback——為什麼救火比起火還難

從 12:43 到 13:09 PDT，on-call 團隊嘗試了三波恢復動作。

每一波都短暫地讓人鬆口氣，再馬上把人打回深淵。

這段是這次覆盤裡最像戰爭故事的部分。

第一波（12:43 PDT）：重啟單一實例。

團隊先挑了一台問題最嚴重的 2-13 完整重啟，期望它從 cold start 開始重新接流量。

重啟確實成功——新 process 起來、mailbox 歸零、etcd 註冊回 ring 上。

但只持續了不到一分鐘。上游服務發現有一個健康節點回來，立刻把累積的 retry 全部灌過去，mailbox 在三十秒內又從 0 漲到數十萬。

這是 thundering herd 的縮小版示範。當一個服務從「健康但過載」變成「健康且能接流量」，所有等在門外的請求會在第一個 epoch 裡同時湧入——對單一被選中的實例而言，這個瞬間負載比平均負載高出至少一個數量級。

第二波（12:47 PDT）：殺掉特定的 supervisor。

團隊改變策略，不重啟整個實例，只 kill 並重啟 Holster.Pool 這個 DynamicSupervisor——理論上這應該清空 mailbox 但保留 etcd 註冊。

結果同樣的模式重現：mailbox 短暫歸零後又漲回來。

問題不在於「mailbox 清不掉」，而在於「清掉之後流量湧進來太快」。

這次嘗試其實透露了一個重要的診斷訊號——但當時沒有人有閒情逸致去注意它。如果 mailbox 清零之後依然立刻被填滿，那麼 root cause 不在於「mailbox 內容」也不在於「process 狀態」，而在於「上游流量速率」。要解決問題就必須往上游找。

第三波（13:05 PDT）：整個 cluster 同時重啟。

團隊賭一把，希望同時清空所有 15 台的 mailbox 能讓整體系統得到一個「同步的喘息窗口」。

重啟瞬間 mailbox 全部歸零，事後報告稱這個瞬間「briefly recovered」。

但下一秒，所有上游服務同時發現 voice syncers 全體健康，把累積了 50 分鐘的 retry queue 一次釋放出去。

這就是傳說中的 cold-start thundering herd——15 台新生兒同時被一群餓壞的爸媽撲倒。

事後檢討用了一句很乾淨的總結：「cold-start thundering herd was too much to handle」。

三次失敗的共通結構是：問題從來不是 voice syncers 自己的狀態，而是上游沒有節流。

Bo Ingram 與 Stephen Birarda 在覆盤裡點明了這條邏輯——「A sufficiently large traffic spike will find a bottleneck in your system」。

只要進來的流量沒有被限速，無論 voice syncers 重啟幾次、清 mailbox 幾次，都會被同樣的流量打回去。

對於任何處理過真實事故的人，這條邏輯都會很熟悉。事故當下你會很想去動最直接看得到問題的那個服務——它的儀表板紅了、它的 alert 在響——但很多時候，真正的解法在上游或下游某個離問題很遠的地方。經驗豐富的 on-call 會在「重啟看看」之前先問：「上游有沒有累積？下游有沒有節流？」

第四次嘗試——同時增加供給、減少需求

13:43 PDT 開始的這一波恢復動作不再是單一招式。

團隊把整個策略升級成兩條並行的修復路徑。

事後覆盤用了一句很 SRE 味的話來描述它：「your solutions either increase supply (adding additional services) or reduce demand (rate limiting inbound traffic)」。

這次他們同時做了兩件事。

路徑一：在上游服務加上 syncer spawn rate limit。

team 緊急更新了 call owner services（guilds、calls、streams 三個）的設定，引入新的 rate limit。

最關鍵的一條是針對 coordinator syncer 的限速。當一個 guild 有大量語音頻道時，coordinator syncer 會為每個頻道再 spawn 一個 child syncer。

這個「unbounded spawning of child syncers」是放大效應的源頭。把它鎖住，etcd 上看到的 syncer 創建速度立刻降一個數量級。

這個細節有教學價值：許多 amplification bug 都長這個形狀——「對每個 X 都 spawn 一個 Y」這種模式，當 X 變大時 Y 就以乘法速率成長。任何地方有這種 unbounded fan-out，都該預設加上 cap。

路徑二：水平擴容 SFU endpoint dispatcher。

透過 GCP Terraform 加 Salt 配置，team 手動補上了 15 台額外的 dispatcher 實例，把整體容量翻倍。

這不是優雅的擴容——是手動 provisioning，沒有經過正常的 release pipeline。

但在那個時間點，把 per-instance load 砍半就等於把 selective receive 的 mailbox queue 砍半，就等於把 process spawn time 從幾毫秒拉回亞毫秒。

事故狀態下「手動 provisioning」是合理的選擇。Release pipeline 平時的價值是避免 bad change 進入生產；但在事故狀態，你 absolutely sure 想做什麼、也願意承擔風險，跳過 pipeline 是合理的。重點是事後一定要回去問：「為什麼這個動作平時沒有作為一鍵化的 incident-response 工具？」

13:43 PDT 的重啟結果與前三次有質的不同：這一次失敗的部位不是 Holster.Pool，而是底層的 gun supervisor。

這代表新增的容量加上上游節流已經把瓶頸位置往下推了一層。

實例還能保持 etcd 註冊，意味著至少可以承擔部分 RPC 負載。

「失敗的部位換了」這個訊號在事故診斷裡非常重要——它告訴你「先前的瓶頸已經不是 critical bottleneck」，問題開始往下一層推。這意味著你的修補方向是對的，繼續往同一方向施力就會看到收斂。

14:03 PDT，實例 2-3 重啟後 mailbox 持續維持在低位，第一台「真正恢復」的實例出現。

14:15 重啟了五台，其中四台維持低 mailbox。

14:26 最後一台恢復——doubled cluster 全體健康。

從第一聲警報響到所有指標復原，總計 3 小時 17 分鐘。

結構性修補——把這條 critical path 永久拆掉

Discord 在事後報告裡列了四條軸線的後續修補。

這幾條都值得作為「自家系統還可能犯同樣錯」的檢查清單來讀。

部署層：Kubernetes admission webhook。

最直接的修補是在 Kubernetes 那一層加一個 validating admission webhook，專門用來檢查 Elixir workload 的縮容請求。

Webhook 會去問該 service「你現在有多少 GenServer process 還沒交棒？」——只有當 entity drain 真的跑完，admission 才會放行。

這個修補的價值不在於它救了多少場後續事故，而在於它把「graceful drain 必須跑完」這條原本只存在於工程師腦中的隱性契約，明文寫進了 control plane 的 enforcement 裡。

把隱性契約變成顯性 enforcement，是組織擴張時最重要的工程改良。一個 50 人的團隊可以靠口耳相傳維持「縮容前要 drain」這條規矩，但 500 人的團隊不行——當你不認識所有寫部署檔的人，唯一可靠的執行方式就是讓系統來做檢查。

架構層：PartitionSupervisor 取代 Holster.Pool 的單一 supervisor。

這是這次最關鍵的結構性修補。

原本 Holster.Pool 用一個 DynamicSupervisor 管所有 HTTP connection 的生命周期，所有 spawn/terminate 訊息都打到同一個 mailbox 裡。

換成 Elixir 1.14 之後內建的 PartitionSupervisor，等於把單一 supervisor 切成 N 個分區（通常 N 等於 scheduler 數），每個分區自己一個 mailbox。

selective receive 的 O(n) 退化也跟著被切成 N 份。

同時，原本由 gun 額外多一層 supervision 也被拿掉——HTTP connection 的生命周期直接由 Holster.Pool 管理，少一層 hop 就少一條 critical path。

這個修補哲學上的精彩之處在於：它不是「加大 mailbox」也不是「跳過 selective receive」，而是「把單一 contention point 切碎」。當你不能讓某個瓶頸消失，把它切成 N 份是退而求其次也最有效的方案。

流控層：上下游同時加 rate limit。

call owner services（guilds、calls、streams）統一更新成有合理的 syncer spawn rate limit。

voice syncers 內部也補上了 endpoint selection rate limit。

另外多了一套「optional load shedding tool」，在偵測到過載時可以選擇性地強制 syncer 重建——把先前手動操作的應急路徑變成可程式化呼叫的工具。

把 incident response 動作變成 first-class operator tool 是成熟的工程做法。事故當下你寫過的每一條「手動 fix」，事後都該問：「這個動作以後會不會再用到？如果會，能不能變成一條按鈕？」

可觀測性層：mailbox health 變成一等公民。

團隊新增了 HTTP connection pooling 的 mailbox health 監控、service discovery announcement 的儀表板、以及 voice-to-SFU RPC traffic 的細部 instrumentation。

報告裡還提到一條更廣的目標：「pursuing generic process mailbox monitoring across all Elixir services」——也就是把「任何 Elixir process 的 mailbox 長度都應該是被監控的指標」這個原則推到全公司。

對於跑 BEAM 的團隊，這條值得抄。

對於跑其他語言的團隊，等價的監控目標是：所有 message channel、所有 worker queue、所有 event loop 的 backlog 長度都該被監控。任何「訊息傳遞層的累積」都是 leading indicator，比 latency 或 error rate 提前一兩個訊號。

更長期的方向。

A/V 基礎設施會從手動管理的 GCP VM 慢慢搬上 Kubernetes，享受 horizontal scaling 的便利。

voice control plane 會被重新切成跨 region 架構，讓單一 region 的 connection spike 不再能拖垮全球。

這兩條都是「需要做但不會在下一個 sprint 就做完」的長期工程。能在覆盤裡明白寫出「這些事還沒做」是難得的誠實——很多公司的覆盤會把長期項目隱去，只列「已修補」的部分，給讀者一種「都已經解決」的假象。Discord 沒有這麼做。

給其他人讀的注解——mailbox、selective receive 與你自己的服務

覆盤裡有幾個結論值得被抽出來，因為它們對任何跑 actor model 或 message queue 的服務都成立。

第一條：O(n) selective receive 是 Erlang/OTP 一個冷門但會吃人的細節。

BEAM 的 receive 區塊預設行為——掃 mailbox 找匹配 pattern——在 mailbox 短的時候快得不像話，這讓很多開發者忘了它在 mailbox 長的時候會變慢。

如果你的 supervisor 或 GenServer 用了 pattern match 從 mailbox 裡挑特定訊息（例如 receive {:reply, ^ref, msg} -> ...），就要假設這條路徑在過載時會退化。

能避免就避免；不能避免就要監控 mailbox length。

BEAM 21+ 有一個編譯器最佳化叫做 receive ref hint，可以在某些情況下把 selective receive 的複雜度從 O(n) 降回 O(1)——但前提是編譯器能識別 pattern 是針對某個唯一的 reference。Holster.Pool 那次跌進的洞，正好是 hint 沒辦法應用的場景。

第二條：service discovery 跟 connection management 不應該共享同一條 mailbox。

Discord 的事故展示了一個非常具體的反例：當 health TTL refresh 跟 connection spawn 走同一個 supervisor，過載的 connection spawn 會把 health refresh 餓死。

然後 service discovery 把實例從 ring 上拔掉——加速崩潰。

這條原則寫進設計守則可以很簡單：control plane 與 data plane 必須是物理上分開的 process tree。

不只是 Elixir，這條原則對任何架構都成立。Kubernetes 的 readiness probe 該走獨立的 endpoint、獨立的 thread pool；資料庫的 health check 該走獨立的 connection；任何「我還活著」的訊號傳遞路徑都不該跟「我正在處理業務」的路徑搶資源。

第三條：graceful drain 不是 deployment manifest 的可選欄位。

對任何在 process 內部持有狀態的服務（Elixir GenServer、Go in-memory cache、Rust actor），terminationGracePeriodSeconds 必須跟 drain 流程的實際時長對齊。

並且應該有 admission control 來確保不被誤改。

一份 manifest 的 typo 不該能夠導致 17% session 失聯。

第四條：cold-start thundering herd 是恢復流程的隱形殺手。

Discord 的前三次嘗試告訴我們：當問題的源頭是「上游流量沒節流」，無論你重啟多少次，下一次重啟都會被同樣的流量打回去。

恢復計畫必須同時包含「停止流量灌入」與「恢復服務容量」兩條軸線——只做其中一條等於不做。

對抗 thundering herd 的常用工具包括：startup jitter（讓重啟時間隨機分散）、warm-up traffic（先讓實例承擔 1% 流量，再慢慢拉高）、circuit breaker（在實例還沒準備好時拒絕新流量）。Discord 的事故顯示，這些工具在 voice control plane 那一層是缺失的——後續修補裡應該都會補上。

第五條：「increase supply 或 reduce demand」是一條乾淨的 SRE 公理。

當系統撞到容量瓶頸時，能做的選擇只有兩個——多開實例（供給）或限速（需求）。

值班時想清楚當下這個瓶頸該用哪一邊，比較容易跳出「再重啟看看」的循環。

Discord 那一次最後是兩條同時做，這也是大多數真實災難恢復裡會選的答案。

事故當下你會發現工程師有一種「我必須做點什麼」的衝動——這種衝動是好的，但要綁定在正確的問題框架上。「increase supply 或 reduce demand」就是這個框架。每一個事故當下的動作，問自己一句：「我這個動作是在增加供給還是減少需求？」答不出來就是在亂打。

把這次事故跟自家系統對照

如果你的團隊跑 Elixir，這次覆盤幾乎是現成的 checklist。

但如果你跑的是其他語言，結構性的教訓也直接搬得過來——只要把「mailbox」換成「channel」、「supervisor」換成「worker pool」、「BEAM scheduler」換成「event loop」，整篇故事都可以重講一遍。

Go 的 channel buffered 滿了之後 sender 會 block。

跟 Erlang mailbox 漲長之後 selective receive 變慢，本質上是同一類問題：訊息傳遞層的反壓沒處理好，全系統一起被拖下水。

Rust 的 tokio mpsc 如果 receiver 處理不過來，sender 端會看到 send 失敗——這時候要不要 retry、要不要 drop，是一個必須在設計時想清楚的決定。

Node 的 event loop 如果有 CPU-bound 任務塞住，所有 socket 都跟著卡——這也是 mailbox 模式的變體。

Java 的 ThreadPoolExecutor 如果 queue 是 unbounded，過載時 queue 會無限長到 OOM——對應於 Erlang 的 mailbox blowup。如果 queue 是 bounded，過載時 RejectedExecutionException 開始往上拋，對應於 tokio 的 send 失敗。每種語言都有同類型的工具，差別只在違反 invariant 時的具體症狀。

Python 的 asyncio Queue、Ruby 的 SizedQueue、C++ 的 lock-free MPMC ring——每一個都會在過載時退化到某種失敗模式。寫 distributed system 的工程師，這些 failure mode 應該都要有 mental model。

service discovery 跟 critical path 共享資源的問題就更普遍了。

Kubernetes 的 readiness probe 如果跟主要的 request handling 共用同一個 thread pool，過載時 readiness probe 失敗，pod 被踢出 endpoint，剩下的 pod 接更多流量——同樣的迴圈，不同的語言。

任何時候 health check 跟業務邏輯走同一條 critical path，都要把這個故事拿出來想一遍。

對於 gRPC server，這意味著 health service 應該跑在獨立的 sub-channel 上；對於 HTTP server，這意味著 health endpoint 應該綁定到專屬 listener 上；對於資料庫 driver，這意味著 health query 應該走專屬 connection。每一層都要單獨想過。

還有一條值得提的：deployment manifest 的人類因素。

這次事故的觸發點不是某個複雜的演算法 bug，也不是某個冷門的 race condition——是一份 Kubernetes manifest 把 replicas 改錯了。

任何依賴「工程師會記得手動把 terminationGracePeriodSeconds 調高」的流程都會在某個時間點失敗。

把這條變成 admission webhook 強制檢查，是一個 organizational scale 的修補——它不只防住這次的特定錯誤，也防住未來所有「工程師忘了某個 best practice」的同類錯誤。

這也是「policy as code」這個概念的價值所在：把 best practice 從文件、從 review 共識、從工程師的記憶力，遷移到 admission control 的 enforcement 裡。文件會被忘記、review 共識會被新人不知道、記憶力會被疲勞磨損。只有 enforcement 不會。

把 Holster.Pool 換成 PartitionSupervisor——結構性的關鍵

如果整篇覆盤要挑一張圖留下，那會是 voice syncers 的 HTTP connection 池在事故前後的結構對比。事故前，所有 connection 的 spawn/terminate 訊息都打到一個 Holster.Pool 的 DynamicSupervisor 的 mailbox 裡；事故後，這個單一 mailbox 被 PartitionSupervisor 切成多個分區，每個分區自己一個 mailbox，selective receive 的 O(n) 也跟著切成 O(n/N)。

切成 N 個分區之所以管用，並不只是「分擔負載」這麼一句話可以概括的。selective receive 的退化是因為 BEAM 的 receive 區塊在 mailbox 長時要做 O(n) 掃描；當 N 個 mailbox 各自獨立，每個的 n 都只是原本的 1/N，掃描時間也跟著降到 1/N。對 voice syncers 的場景而言，這個分母通常是 BEAM scheduler 數，在現代多核 host 上輕鬆達到 16-32。一個 ~100k 的 mailbox 切成 32 份之後變成 ~3k——回到了 selective receive 還算便宜的區間。

把 gun 的額外 supervisor 拿掉是另一個值得學的細節。許多 Erlang/Elixir 函式庫為了「保險」會在自己的 process 樹上再多一層 supervision，理論上是為了把不同責任分離。實務上，多一層 supervisor 就多一個訊號中轉點——對 critical path 而言這是純粹的 overhead。Discord 把 connection lifecycle 直接放回 Holster.Pool 管理，少一層 hop、少一個 mailbox 可能變慢的地方。

從這次故事帶走的——壓回一個句子

如果要把這整篇覆盤壓成一句技術人都能記住的話：一行 Kubernetes manifest 的誤設，會經由 graceful drain 缺位、reconnection storm 跨 zone、Erlang selective receive 在長 mailbox 下退化、service discovery 與 connection management 共享 mailbox、cold-start thundering herd，這一連串平日各自無害的設計選擇，串成一條 3 小時 17 分鐘的全球語音崩潰路徑。

每一個環節單獨來看都不算 critical bug——graceful drain 「應該」會跑完、selective receive 「通常」很快、service discovery 「平常」不會跟 connection 搶資源、reconnection 「一般」不會多到打爆 gateway。但當這些「應該、通常、平常」全部同時失敗，就會變成這次的 3 小時 17 分鐘。分散式系統的故障故事，幾乎永遠是這種「多個獨立 invariant 同時失效」的形狀。

這也是為什麼這類覆盤值得讀得很細：你不會在自己的系統上遇到完全一樣的 Holster.Pool 故障，但你會遇到結構上相似的——某個 supervisor 的 mailbox 太長、某條 critical path 同時承擔了 health check 與業務邏輯、某次部署沒有 admission control 把住、某次救火忽略了上游節流。當那一天到來，你會慶幸自己讀過 Discord 這份覆盤。

The lesson：分散式系統的崩潰幾乎永遠不是「單一 bug」，而是多個各自無害的設計選擇在某個流量峰值下同時失效——你能做的不是消滅 bug，而是把每一條 critical path 上的 invariant 寫成可被 enforce 的契約。
