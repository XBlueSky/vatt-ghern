在 CUDA C++ 裡，__shared__ 陣列就是一塊裸記憶體：誰寫到哪裡、有沒有重疊、是否在 race，完全靠程式設計師「不要寫錯」。cuda-oxide 0.1 換了個切法——把同一塊共享記憶體拆成型別化的 DisjointSlice<T>，要兩個 thread 不重疊地寫，必須在編譯期就能向 borrow checker 證明。

NVlabs 在 2026 年 5 月 7 日把 cuda-oxide 0.1.0 釋出到 GitHub，定位是「實驗性的 Rust → CUDA 編譯器」——把標準 Rust 源碼直接編成 PTX，不經過任何 DSL 或 C++ 中介層，也不需要綁定 thrust／cub。整個設計圍繞一個明確的問題：CUDA SIMT 模型在原生 C++ 之下有大量「型別系統撐不住」的不變量（誰是 warp lead、誰寫共享記憶體哪一格、誰負責 reduction 的根節點），cuda-oxide 嘗試把這些不變量編進 Rust 的所有權／生命期模型，讓編譯器幫忙抓 race。

The rusc backend：from MIR to PTX

cuda-oxide 沒有寫一個獨立的 Rust 前端。它接的是 rustc 的 MIR（mid-level intermediate representation），然後在 MIR → PTX 之間插入一條自製 backend：lower MIR 到 LLVM IR、再走 NVPTX target。這條路徑跟主流 rust-cuda 不同——後者透過 LLVM 的 ptx-builtins 加上手寫 wrapper，而 cuda-oxide 把整個 kernel function 的呼叫慣例（calling convention）也客製化，讓 Rust 函式可以直接被 CUDA driver 當成 PTX entry point 呼叫。

實作意義上的關鍵：rustc 的 MIR 已經是「型別與借用都檢查過」的 IR——race condition 與 use-after-free 在進入 cuda-oxide 之前就被擋下，cuda-oxide 不需要重做。代價是必須跟 rustc 內部 IR 的版本對齊：v0.1.0 鎖在特定 nightly rustc commit 上，這也是文件警告「expect API breakage」的真正來源。

DisjointSlice：borrow-checker meets warp-level memory

共享記憶體（shared memory）是 SIMT 程式設計裡 race 的最大來源。CUDA C++ 的標準寫法是宣告一塊 __shared__ float buf[256]，然後每個 thread 用 threadIdx.x 索引存取——但若兩個 thread 算出相同索引、或某個 thread 寫到別人格子，編譯器什麼都不會說。

cuda-oxide 引入 DisjointSlice<T, N>：把同一塊共享記憶體在型別系統裡切成 N 條互不重疊的 slice，每條 slice 只能由「持有對應 ThreadIndex 證明」的 thread 寫入。在 Rust 的借用模型下，這等於同時持有 N 個獨佔 &mut 借用——但每個 &mut 指向不重疊的記憶體區段，所以借用檢查可以放行。

實務上，這把 SIMT 的「每個 thread 寫自己的格子」從程式設計慣例升級為型別約束。若你嘗試寫 slice[i] = x 而 i 不是你的 ThreadIndex 投影過的值，編譯器會在 borrow check 階段就拒絕——這比 CUDA 的 race detector（compute-sanitizer）執行期偵測要早得多。

ThreadIndex：把 warp identity 變成型別

傳統 CUDA 程式設計裡 threadIdx 是一個 runtime 的 dim3 結構：你必須相信「同一個 thread 在整個 kernel 內看到的 threadIdx 不變」，但這個不變量沒有型別系統的支援。cuda-oxide 把它改成 ThreadIndex<BlockDim>——一個由 #[kernel] entry point 在進入時建構、只能透過 move 傳遞的型別化 token。

有了這個 token，warp-level 操作（shfl_sync、__ballot、__activemask）才能被 type-checked：函式簽名可以要求「呼叫者必須持有同一個 warp 的 ThreadIndex token」，而不是靠註解描述。這把過去藏在 CUDA programming guide 章節裡的 warp synchronicity 規則搬進編譯期。

Where unsafe still earns its place

cuda-oxide 的 README 把標題寫成 safe(ish) 而不是 safe，括弧裡那個 ish 不是謙虛——它劃出一條明確的邊界。三類情境仍然必須走 unsafe block：

第一類：跨 block 的 __shared__ 同步。cuda-oxide 的型別系統只覆蓋單一 block 內的共享記憶體；跨 block 的 atomic、grid-level sync（cooperative_groups::grid_group）仍要程式設計師自己保證。第二類：texture 與 surface memory。這些抽象在 CUDA 內有專屬的 cache 模型，cuda-oxide 0.1 還沒有對應的型別化包裝，只暴露 raw intrinsic。第三類：跨 host／device 的 unified memory。cudaMallocManaged 配出的指標在 CPU 與 GPU 上都可解參照，這跟 Rust 的單一 owner 模型衝突——目前的解法是把 unified pointer 包進 UnsafeCell 風格的容器，存取一律 unsafe。

這條邊界選得相當務實：覆蓋了佔大多數 race bug 的「block 內共享記憶體 + warp 同步」場景，把更難形式化的 cross-grid／texture／unified memory 留在 unsafe。從工程角度看，這是「先把容易摘的果子摘乾淨」的合理路線。

What this enables：把 SIMT race 條件從「執行期靠 compute-sanitizer 偵測」改為「編譯期被借用檢查拒絕」——讓寫 CUDA kernel 的工程師獲得跟寫一般 Rust 一樣的「編譯通過 ≒ 沒有資料競爭」保證，至少在 block-local shared memory 與 warp synchronicity 兩個最常出錯的層面如此。
