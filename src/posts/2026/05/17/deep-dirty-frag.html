第一個 CVE 只是一個 4-byte STORE：透過 xfrm-ESP 的 packet 重組路徑，無特權使用者可以把任意 4 個位元組寫進核心 page cache 的特定位置。第二個 CVE 只是一個 namespace create：透過 RxRPC 的 socket 建立路徑，無特權使用者可以在核心地址空間裡布出一段「可預測」的 page-cache 內容。兩個都是受限原語——但放在一起，就是無條件的 root。

{{ title }}

DirtyFrag 是 2026 年 5 月 7 日公開的一對 Linux 核心漏洞：CVE-2026-43284 位於 IPsec 的 xfrm-ESP（esp4／esp6）子系統，CVE-2026-43500 位於 RxRPC 子系統。兩個 CVE 各自的破壞力都被限制在「能寫核心 page cache 但寫不到任意位置」或「能建立特殊 namespace 但不能改 page 內容」這類受限原語上——直到有人把它們連起來。連起來之後，整條鏈只用到 socket／setsockopt／bind／vmsplice／splice／sendmsg 這幾個標準系統呼叫，依賴的核心模組（esp4、esp6、rxrpc）在所有主流發行版的預設核心包裡都已啟用。

what happened

時間線從一個獨立研究員與 Wiz 安全團隊的內部協作開始。兩個漏洞在 2026 年 3 月底分別被發現，但揭露者一開始也沒看出它們可以鏈起來——直到 4 月中旬有人把兩條 PoC 並列才意識到雙寫原語的組合性。從那一刻起，協同揭露的節奏就明顯比較急：

PoC 公開後幾個小時，Wiz、Sysdig、Tenable 各自發出技術 advisory；Ubuntu、AlmaLinux、Red Hat、SUSE 在 24 小時內把更新推到 stable 通道。Microsoft Defender 團隊在 5 月 8 日報告觀察到實際攻擊試圖載入 esp4 與 rxrpc 模組然後執行雙原語序列——這在所有從未跑 IPsec 或 AFS／RxRPC 的伺服器上都是明顯異常訊號。

why it matters

連鎖型核心漏洞的危險之處不在單一原語的強度，而在「兩條 partial 原語的笛卡兒乘積」。傳統靜態分析、fuzzer、cap-based mitigation 都傾向於評估「每個系統呼叫單獨能造成多大破壞」，但 DirtyFrag 揭示的攻擊面是兩個獨立子系統互不知情的合作。

第二個值得注意的點：兩個漏洞依賴的模組都在「預設核心包」的允許清單裡。esp4 與 esp6 是 IPsec stack 的核心元件，RHEL、Ubuntu、Debian 都預設啟用；RxRPC 雖然只在 AFS／kAFS 場景被實際用到，但因為它是 AF_RXRPC socket family 的提供者，所以也預設可載入。換句話說：絕大多數 Linux 主機從未真正使用過 IPsec 或 RxRPC，卻都暴露在攻擊面上。

第三個面向是容器逃逸的影響。許多公有雲 CSP 把 capability set 限制到 CAP_NET_BIND_SERVICE 之類的最小集合，但 DirtyFrag 完全不需要 capability——它只用標準的 unprivileged socket／splice 系統呼叫，這代表大多數現有 seccomp profile 默認不會擋。Microsoft、Sysdig、Wiz 的 advisory 都把 container escape 列為 high-confidence 後果。

so what

短期緩解最直接的路徑是把三個模組黑名單，然後檢查是否已載入：

用 modprobe -r esp4 esp6 rxrpc 卸載；用 /etc/modprobe.d/dirty-frag-mitigation.conf 加 install esp4 /bin/false 之類的條目阻止後續載入。RxRPC 因為被 kAFS 隱含依賴，若主機沒在跑 AFS／kAFS 客戶端，移除應無副作用；esp4／esp6 則需確認沒有 IPsec VPN 或 strongSwan 之類的服務依賴。

中期應該套用 5 月 10 日後陸續釋出的核心更新：Ubuntu 在 24.04／22.04 推 6.8.0-58、AlmaLinux／RHEL 9 推 5.14.0-503.30.1、SUSE 推 6.4.0-150700.53.34。CloudLinux 與 TuxCare 也釋出了 KernelCare 的 live patch，免重啟。

長期值得反思的是：page-cache write 系列原語在過去 18 個月內出現得相當頻繁——Dirty COW、Dirty Pipe、Dirty Cred、Dirty Frag——每一個都來自不同子系統，但共通模式是「無特權使用者透過某條間接路徑改寫 page cache 的特定位置」。對核心安全研究的暗示是：page-cache 在無特權使用者面前的可寫面遠比 capability 體系所表達的還要寬，未來幾年大概會有更多「Dirty X」浮出水面。

Take-away：DirtyFrag 不是因為任何一個 CVE 特別嚴重，而是因為兩個各自受限的原語放在一起就跨過了核心邊界——若你的 host 從未跑過 IPsec 或 RxRPC，先把 esp4／esp6／rxrpc 黑名單，把預設啟用但未使用的核心模組面積壓到最低，本來就是值得長期維持的姿勢。
