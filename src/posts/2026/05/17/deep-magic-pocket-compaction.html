Magic Pocket 是 Dropbox 的 immutable blob store，EB 級規模、用 erasure coding 取代複本。原本只有一條 compaction pipeline——對「快要滿但還沒滿」的 volume 做 top-off。然後某次事件讓一大批 volume 同時掉到不到 5% 使用率，原本的 pipeline 根本來不及把它們排空。新加的兩條 pipeline 不是優化原有的 L1，而是把 compaction 拆成三種完全不同的工作量。

{{ title }}

Magic Pocket 把資料切成 fragment，加上少量 parity fragment 後散佈到不同的物理 volume。

Volume 是 append-only 的：刪資料只是標記、空間不會立刻釋放。

Compaction 的工作就是把多個半滿 volume 的有效資料搬到較少的滿 volume，然後回收空 volume。

三層 pipeline——L1、L2、L3——對應「volume 稀疏化速度不同」時的三種應對節奏：穩態維持、中度批次重組、極稀疏應急排空。

這個拆法的有趣之處不在演算法本身，而在於 Dropbox 工程師明確拒絕「一個更聰明的 unified compaction」這個方向。

三條 pipeline 共享 volume 視圖、共享 metadata service，但工作的單位、選擇候選的策略、對 metadata system 的壓力，都刻意不同。

理解三層為什麼非得分開，比理解任何一條 pipeline 內部都來得重要。

底層的物理事實是這樣：Magic Pocket 把資料用 erasure coding 切成 k 個 data fragment 加 m 個 parity fragment，散佈到不同 cell、不同機架的物理 volume 上。

任何一個 volume 都不會持有完整 blob——它持有的是 blob 的某個 fragment。

volume 是 append-only 寫入的物理單位，一旦封閉就不再接受新寫入。

刪 blob 只是在 metadata service 把它標成 garbage——對應的 fragment 仍然躺在 volume 裡，占著磁碟空間，等下次 compaction 真的把它們搬走、把整個 volume 回收。

當 Magic Pocket 規模還小、刪除壓力溫和的時候，這種 append-only + 異步回收的模型代價很低。

volume 平均使用率穩定在高位，compaction 只需要對「最近被刪了一點點」的 volume 做小幅整理——把幾個 80% 滿的 volume 合併成 95% 滿的 volume，回收掉幾顆磁碟。

但隨著 EB 規模成長，刪除模式變得不規律：某類客戶大規模 churn、某個內部 lifecycle policy 上線、某次資料遷移完成——這些事件都會讓 volume 稀疏化的速度遠遠超出穩態流程能處理的範圍。

原本的單一 pipeline——現在我們稱為 L1——面對突發稀疏化幾乎沒有反應能力：它的設計前提是「世界是穩態的」。

把所有 compaction 都當作穩態工作來做，會出現一種尷尬的失敗：當大批 volume 同時掉到 5% 以下時，L1 還在慢慢拉那些 80% → 95% 的 volume，極稀疏的那批根本排不上隊。

Dropbox 工程師選擇承認這個失配，把問題拆成三類獨立的工作量——而不是寫一個更複雜的 L1。

L1 穩態維持

L1 是原本就存在的單一 pipeline，現在還在跑——只是不再獨自承擔所有 compaction 工作。

L1 對應的場景：每天有少量 volume 因為日常刪除而從接近 100% 降到 70–80%，L1 把它們重新打回接近滿。

L1 的工作目標是把高使用率的 volume 維持在「該滿就滿」的狀態，不讓中段使用率的 volume 堆積。

從 Dropbox 工程師描述的細節看，L1 的選擇邏輯近似 first-fit decreasing 的近親：選一個已經 highly-filled、但還有 free capacity 的 host volume；從 candidate pool 中挑「live byte 加總剛好塞得進 host 剩餘空間」的幾個 donor volume；把 donor 的 live fragment 搬到 host、回收 donor。

每跑一輪 L1 平均回收不到一整個 volume——這個輸出在穩態時剛好夠抵消當天的稀疏化速度。

L1 的兩個設計約束讓它「只能做這件事」。

第一個是搜尋空間：L1 只看「已經夠滿」的 host 候選池，不嘗試對全域 volume 做最佳化匹配。

這個約束讓 L1 每次決策的 CPU cost 非常低——分鐘級就能跑完一輪，metadata service 的壓力也很輕。

第二個是策略保守：L1 選的合併目標必須讓「寫入放大」夠低，否則乾脆不動。

寫入放大的計算很簡單——donor 的 live byte 必須遠小於 host 的 free byte，否則搬完 donor 之後 host 也才升到 85%，沒比 donor 本來的 70% 好多少。

這兩個約束讓 L1 對突發稀疏化幾乎沒有反應能力。

假設某個 cell 一夜之間有一千個 volume 因為某類客戶 churn 而從 60% 降到 10%，L1 會慢慢地、一個一個地拉回來。

L1 的問題不是它「處理稀疏 volume 的方式錯」——L1 根本不會去看那一千個 10% 的 volume，因為它們都不在 highly-filled host 的候選池裡。

L1 只看到 host pool 還是穩定的，繼續做它那分鐘級的小幅整理。

等到 L1 終於透過 candidate pool 的補貨機制接觸到那些 10% volume 時，新的稀疏化已經堆積成山。

L1 還有一個沒明說但很關鍵的好處：它對 metadata system 的壓力是最低的。

L1 一輪只搬幾個 volume 的 fragment、只更新少量 blob 的 location metadata。

Dropbox 工程師在文章裡點名「metadata capacity turned out to be one of our biggest constraints」——這句話的含意是 compaction 不只是磁碟 I/O 的工作，每一次 fragment 移動都帶來 metadata 更新的成本，而 metadata service 本身是有 throughput cap 的。

L1 的低開銷讓它在穩態長期跑、不會吃光 metadata budget。

有了 L2 與 L3 之後，L1 的角色從「唯一的 compaction」變成「最後一道日常修整」。

L2 把中度稀疏批次處理完之後，volume 的使用率分布回到接近正常，剩下的小幅整理交給 L1。

L3 把極稀疏的尾部排空之後，那批 volume 進入下一輪的 L1 流程，不需要任何特殊處理。

三層的分工讓 L1 終於回到它擅長的事——穩態維持，不被異常情境拖累。

L1 的設計也透露出另一個 production 系統設計的常見模式：「初版演算法不要試圖處理所有情境」。

L1 在 Magic Pocket 早期是唯一的 compaction，但工程師沒有把它寫得太聰明——它就是一個簡單、保守、可預測的 pipeline。

這個保守性給了後來的 L2 與 L3 演化空間：L1 不會去搶 L2 或 L3 該處理的 volume，因為它的 candidate filter 從一開始就嚴格限制在「中高使用率」這個區段。

如果當初的 L1 寫得「能處理所有 volume」，現在加 L2 / L3 就必須先重寫 L1 的調度邏輯——這是 production 系統演化中最常見的成本來源。

L2 動態規劃打包

L2 處理的是「volume 中度稀疏化」的場景：使用率 30–60% 的 volume 大量出現，L1 不會去碰它們（不在 L1 的 candidate pool 裡），但這些 volume 也還沒稀疏到值得用 L3 強力排空。

L2 把這個區段建模成有界 bin packing——目標是「以最少的新 volume 容納多個半滿 donor volume 的全部有效資料」。

實作上 L2 是經典 0/1 knapsack 的動態規劃。

狀態維度是 (volume_index, count, capacity)：第 i 個 volume、目前已選的 volume 數、destination volume 已用掉的容量。

DP 值是「在這個狀態下能塞進 destination 的最大 live byte」。

原始 live byte 數會被一個 granularity factor 縮放——例如以 1 MiB 為一格——把容量維度從 TB 級的格子數壓到幾千格，DP 表的記憶體與計算量都在合理範圍。

L2 的關鍵設計參數有三個：donor pool 大小 N（單次取最多多少 volume 進來算）、destination 容量上限 C、granularity factor G。

N 不能太大——DP 的時間複雜度是 O(N · count · C/G)，N=200 的時候 DP 表約 200 × 32 × 4000 ≈ 25M cell，每個 cell 幾個運算，分鐘級可以跑完；N=1000 的時候 DP 表暴增到 125M cell，分鐘級跑不完，CPU 預算也吃不消。

選 donor pool 的方式同樣關鍵。

L2 從「中度稀疏」bucket 取，例如使用率 30–60% 的 volume；不取極稀疏（< 10%）的 volume——那些是 L3 的範疇。

DP 在中度稀疏 pool 上的解品質很高：candidate volume 的 live byte 加總多半比 destination 容量大，DP 能找到「6 個 50% 滿 volume 的 fragment 剛好打包成 1 個 95% 滿的 destination」這種解。

每一輪 L2 平均回收 5–6 個 volume——相比 L1 的「不到一個 volume」是接近一個數量級的吞吐提升。

Dropbox 工程師在 production 部署 L2 後測到的數字：在啟用 L2 的 test cell，一週內整體 compaction overhead 比純 L1 低了 30–50%；overhead 收斂到 sustainable level 的速度比純 L1 快 2–3 倍。

這兩個數字在 EB 規模上意味深長——每降低 1% 的 compaction overhead，等於回收上百個機架的硬碟容量、減少同等數量級的 metadata service 壓力。

30–50% 的差距讓 Dropbox 不需要為了稀疏化容忍多預留 10–20% 的磁碟。

L2 不是萬能的。

當 candidate pool 全是「使用率 5% 以下」的極稀疏 volume 時，DP 仍然會找到解，但這個解的代價是用一個 destination volume 容納 20 個 donor volume 的 live byte——意味著要寫入 20 個 volume 份的 metadata 更新、每個 blob 都要重新分配 location、Live Coder 還沒派上用場就被 metadata service 卡住。

L2 的設計者對這點很清楚：DP 的搜尋空間以 candidate 數量平方成長（DP 表本身），但實際 I/O 與 metadata cost 跟搬動的 blob 數量線性相關。

極稀疏 candidate 的 live blob 雖然少、但分布散亂、metadata 開銷反而最重。

這就是為什麼極稀疏 volume 需要 L3 那種「streaming pipeline + 攤銷 metadata 開銷」的設計，而不是繼續餵給 L2。

L2 還有一個 Dropbox 工程師沒詳細描述但合理推測的優化：DP 的近似版本。

完整 0/1 knapsack 的最佳解需要完整搜尋；近似版本可以用 greedy + local search，犧牲 1–2% 的打包密度換 10× 的計算速度。

在 production 部署初期，Dropbox 顯然用的是「完整 DP，但 N 與 G 都設保守值」的策略——這讓他們能用「DP 最佳解」這個語言來描述 L2，同時不用擔心 CPU 預算。

L2 的另一個微妙之處是「destination 也是新建的 volume」這個細節。

L1 的 host 是現有的 highly-filled volume，搬 donor 的資料進去填滿 host 剩餘空間；L2 不一樣，L2 通常為打包結果分配一個全新的 destination volume。

原因是 L2 處理的 candidate live byte 加總往往比任何現有 volume 的剩餘空間都大——你不可能在現有 volume 裡塞進 6 個 50% 滿 volume 的內容。

新建 destination 換來「一次填滿到 95%」的乾淨輸出，但也意味著 L2 每跑一輪就會新增一個 volume，回收 6 個，淨回收 5 個——這跟 L1 的「不到一個」是兩種完全不同的工作量。

從 metadata 視角看，L2 的成本約是 L1 的 3 倍：搬動的 fragment 數量大約是 L1 的 5–6 倍，但 L2 每輪只更新一次「新 volume 的 manifest」，攤銷下來每 fragment 的 metadata 開銷比 L1 略高、比 L3 低。

這個位置剛好讓 L2 成為 metadata 預算的「中段消費者」——比 L1 多吃、比 L3 少吃，正好對應它處理的 volume 體積區段。

L3 稀疏 volume 排空

L3 是事件驅動的應急機制。

Dropbox 在引入 L2 之後仍碰到一類事件：某種特定的客戶活動或內部 lifecycle policy 變動，讓一大批 volume 同時掉到 5% 以下的使用率。

對這類「極稀疏 volume 群」，DP 打包仍然太慢——它的搜尋空間以 volume 數量平方計算，幾千個一起算根本算不完；更糟的是即使算完，得到的解需要重寫 20–30 個 destination volume，metadata churn 跟手動下指令一個一個搬沒差多少。

L3 改採完全不同的策略：用 Live Coder service 作為 streaming pipeline 連續吃稀疏 volume，把它們的有效 fragment 直接餵到新建立的目標 volume 裡，erasure coding 在 streaming 過程中即時計算。

L3 不在乎打包是否「最緊」——它在乎的是把空間立刻歸還給整個 cluster。

當 L3 跑完一個 batch，那批極稀疏 volume 就從 cluster 視圖中消失，硬碟空間進入下一輪 L1/L2 的常態流程。

Live Coder 是 Magic Pocket 原本就有的 on-the-fly erasure coding service，用在背景寫入路徑——把新進 blob 累積到 buffer、達到 k 個 fragment 後計算 m 個 parity、寫進 storage。

L3 把 Live Coder 接到 compaction 路徑：稀疏 volume 的 live fragment 經過解碼變回原始 blob，再餵進 Live Coder 的 buffer，等於重做一次「新寫入」流程。

從 Live Coder 的視角，這些 blob 跟剛上傳的新 blob 一模一樣；只是 caller 不是客戶端，而是 compaction job。

這個設計的巧妙之處是「重用既有元件」——Dropbox 沒有為 L3 寫新的 streaming compaction code，他們把 Live Coder 接上 compaction 的輸入端，讓 Live Coder 處理 erasure coding 的所有細節。

這意味著 L3 的開發成本遠低於從零寫 streaming compaction，也意味著 Live Coder 的任何優化（例如 batching、pipelining）都會自動被 L3 享受到。

L3 的優先級策略是「最稀疏優先」。

99% 是垃圾的 volume 排在 95% 是垃圾的前面、再前面是 90% 是垃圾的。

原因很直接：搬動的 blob 數量越少，這個 volume 越快被完全清空、回收磁碟。

極稀疏 volume 的單位 compaction cost（搬一個 blob → 回收幾百個 blob 份的空間）遠高於中度稀疏 volume，這是 L3 在 metadata 預算限制下能最大化 throughput 的方式。

L3 的 metadata 壓力是三層裡最高的。

每搬一個 blob 都需要更新它在 metadata service 裡的 fragment 位置；如果是某些 lifecycle policy 觸發的（例如重新分配 blob identifier），壓力更高。

Dropbox 工程師在文章中明確指出 metadata capacity 是「最大的限制之一」——L3 的 throughput 不是被磁碟 I/O 限制，而是被 metadata service 的處理速率限制。

這也決定了 L3 的部署方式：以 cell 為單位開啟、依當前 metadata 負載動態調整 throttle、跑完批次就收手。

traffic locality 也是 L3 的設計約束之一。

Magic Pocket 的 cell 跨 data center 部署，cross-cluster bandwidth 是稀缺資源。

L3 的 Live Coder pipeline 在 cell 內部運作——稀疏 volume 的 live blob 在 cell 內解碼、在 cell 內重新編碼、寫入 cell 內的目標 volume，不跨 cell 流動。

這個約束讓 L3 即使在大規模啟動時也不會把跨 data center 鏈路打爆。

L3 顯式接受「不是最佳解」的代價。

L3 重寫一個 blob 等於「拿出來再寫一次」，比 L2 的單批搬動多了 erasure coding 的計算開銷。

但 L3 不需要回頭最佳化——目標是讓 cluster 的「極稀疏 volume 隊列」清空，把 cluster 帶回 L1/L2 能應付的狀態。

一旦 L3 完成這個任務，它就停下來，把節奏交回給其他兩層。

這種「短期高開銷換長期回到穩態」的取捨在 distributed system 的演化路徑上是常見模式——不是最佳化任何單一情境，而是讓系統能在不同情境之間切換得夠快。

L3 的觸發條件本身也是一個值得注意的設計：它不是「持續運行」、也不是「定期 scan」，而是 cell 偵測到「極稀疏 volume 的累積量達到某個閾值」時才啟動。

這意味著大部分時間 L3 是休眠的——cell 的 metadata budget 完全留給 L1 與 L2。

當 L3 啟動時，它優先吃 metadata budget，但這個搶占是有時限的（跑完批次就收手），不會長期擠壓 L1/L2。

從這個角度看，L3 跟 L1/L2 的關係比較像 garbage collector 的 full GC 跟 incremental GC——大部分時間用增量機制處理日常負載，需要的時候用全量機制處理累積的垃圾，但要確保全量機制不會長期阻塞增量機制。

三層的協同與「為什麼不是 unified 演算法」

三條 pipeline 表面上各自獨立——不共享 work queue、有各自的調度器與資源預算——但它們對 volume 視圖（哪些 volume 使用率多少、哪些可以動、哪些正在被搬）是同步的。

同一個 volume 不會同時被 L2 與 L3 挑中，因為它們的 candidate filter 不重疊：L2 要求使用率 30–60%，L3 要求 < 5%，L1 要求 50–90%。

三層的候選區段有少量重疊（L1 跟 L2 都看得到 50–60% 的 volume），這部分由更高層的 priority logic 處理——通常是「regime 偵測」：cell 偵測到自己處於穩態還是異常批次，不同 regime 下三層的權重不同。

更有趣的觀察是「為什麼不是一個更複雜的 unified compaction 演算法」。

Dropbox 工程師在文章中明確指出：unified 設計會被「最稀疏的情境」拖累——若要同時最佳化穩態與應急，演算法的搜尋空間爆炸、收斂變慢，反而比三條獨立 pipeline 慢。

把問題拆成三層的本質是承認「不同稀疏化速度需要不同的搜尋策略」，而不是強迫一個演算法處理所有情境。

這個觀察的可推廣性在於：很多 distributed system 的設計都有「regime 切換」的本質。

consensus 演算法在「節點都活著、網路通暢」的 regime 跟「節點失聯、需要選舉新 leader」的 regime 行為完全不同。

memory allocator 的 fast path 跟 slow path 是兩套機制。

compaction 也一樣——「日常維持」跟「應急排空」是兩種 regime。

承認這點、設計兩到三套機制分別處理、用簡單的 dispatch logic 在它們之間切換，比設計一個自適應的單一演算法更穩、也更容易推理。

Dropbox 在 production 部署三層 compaction 後，overhead 數字穩定收斂。

前面提到的「30–50% 降低」是 L2 vs 純 L1 的數字；加入 L3 之後對極稀疏事件的應對能力從「天級慢慢追」變成「天級就能清空」。

對於 EB 規模的 immutable blob store 來說，這意味著不需要為了應對突發稀疏化長期預留 10–20% 的硬碟容量——這部分容量可以拿來服務新資料，等於免費獲得了一定比例的儲存。

把三層放在同一張表裡比較，每一層的「擅長 / 不擅長」很清楚地對應到不同維度：搜尋空間、metadata 壓力、單次回收量、適用 regime。

下表整理了 Dropbox 工程師描述中可量化或可推論的數字——按任一欄排序可以看出三層在那個維度上的相對位置。

這張表的關鍵不是任一欄的絕對值，而是「沒有單一 tier 在所有維度都贏」這個事實。

L1 的 metadata 壓力最低、L3 的回收速率最高——這兩個事實單獨看似乎在說「L1 用太少 metadata 浪費、L3 太貴」，但放在 regime 維度上就變成「在穩態下用 L1 浪費的 metadata 預算 = 0，在大規模極稀疏事件下不啟用 L3 損失的回收速率 = 8×」。

每一層在自己 regime 下都是最佳，跨 regime 比較沒有意義。

unified 演算法的第一個問題是搜尋空間。

一個 unified 演算法要同時最佳化「穩態 top-off」與「應急排空」，意味著它的搜尋空間要涵蓋兩個 regime 的所有可能解。

L1 的搜尋空間是「幾個 host 配幾個 donor」、L3 的搜尋空間是「幾百個極稀疏 volume 排序＋分批」——把這兩個空間合併，得到的不是「更聰明的解」而是「更慢的搜尋」。

distributed system 的核心約束之一是 decision latency——演算法跑太久，等它出結果時情境已經變了。

三條 pipeline 的搜尋空間都被各自的 candidate filter 嚴格限制住，是這個快速反應的前提。

unified 演算法的第二個問題是「regime 偵測」本身就比「regime 內最佳化」簡單。

判斷「現在有沒有大批極稀疏 volume」只需要掃一下使用率分布的直方圖，毫秒級就能完成；判斷「該不該啟動 L3」只是看那個直方圖的尾部是否突出。

把 regime 偵測從「演算法的一部分」抽出來變成「dispatcher 的工作」，讓三條 pipeline 的設計都簡化——L1 不需要知道現在是不是 burst，L3 不需要知道現在是不是穩態。

每條 pipeline 只負責自己 regime 內的最佳化，跨 regime 的協調由更高層的 priority logic 處理。

unified 演算法的第三個問題是 metadata 預算。

unified 演算法很難對「每一輪 compaction 消耗多少 metadata operation」做硬上限——它會根據當前情境動態決定搬多少東西。

三條獨立 pipeline 的好處是：L1 的 metadata 消耗是已知常數、L2 受 N（candidate pool 上限）控制、L3 透過 throttle 控制。

當 metadata service 接近飽和時，可以單獨壓 L3 的 throttle、保留 L1 與 L2 的容量；如果是 unified 演算法，這種精細的資源控制幾乎做不到。

這三個問題的共同主題是「工程系統的設計優先順序通常不是『最佳解』而是『可控、可推理、可調整』」。

在 EB 規模的 production system 裡，一個複雜但 95% 情境表現很好的演算法，往往輸給三個簡單但每個都「在自己 regime 下表現可預測」的演算法。

可推理性帶來的營運價值——能在事件中診斷、能在 dashboard 上看到哪一層在工作、能單獨調整任一層——遠超過理論上「最佳解」的 1–2% 改善。

Dropbox 工程師描述的另一個細節印證這點：L1 仍然每天在跑、L2 不會去碰 L1 已經處理好的 volume、L3 只在偵測到批次條件時啟動。

如果是 unified 演算法，這些「不做某件事」的條件會散落在演算法各處變成 corner case；分成三層之後，「不做」的邏輯就是 candidate filter 的補集——L1 不看 30% 以下的 volume，因為 L2 會看；L2 不看 5% 以下的 volume，因為 L3 會看。

每層的職責邊界是 candidate filter，這比「演算法內部的 if-else」清楚得多。

從更大的角度看，三層 compaction 是「組合性勝過單體性」這個原則的具體案例。

當系統面對多種輸入分布時，把 input space 切分、為每個切片設計專門的處理路徑，往往比設計一個自適應的單體更穩。

這個原則在 compiler、database query planner、network scheduler 都看得到——不同的 input 走不同的快速路徑（fast path），共用同一份 metadata，但 algorithm 完全分開。

Magic Pocket 的三層 compaction 是這個 pattern 在 EB 規模 immutable blob store 上的一個樣本。

動態觀察：三層在不同 regime 下的回收節奏

下面的 canvas widget 把這個 cell 抽象成 80 個 volume 的 fleet 視圖，每一格代表一個 volume，高度代表 live byte。

churn rate 控制日常刪除的速率——拉高會讓更多 volume 稀疏化、推動 sparse backlog 累積。

「inject sparse-burst」按鈕一次注入 60 個 < 5% 的 volume，模擬大規模 lifecycle policy 變動或客戶 churn 事件。

觀察點：L1、L2、L3 各自的計數器在不同 regime 下會以不同速率成長。穩態時 L1 主導；持續中度 churn 時 L2 開始追上；burst 注入後 L3 立刻拉起、清空極稀疏 backlog，然後回到 L1/L2 的常態流程。

這個模擬不是 Dropbox 系統的精確重現——它的常數是為了讓在瀏覽器內幾秒內看到三層分工而調整過的。

但它捕捉到了三層 compaction 的核心動態：每一層的觸發條件是 candidate volume 的使用率分布、每一層的回收速率對應它擅長的 regime、burst 事件會讓 L3 計數器突然拉高然後回到平穩。

把 churn rate 拉到最大可以看到另一個現象：在持續高 churn 下，L1 完全跟不上、L2 變成主力，但 sparse backlog 仍然會緩慢累積——這是穩態 + 中度稀疏 regime 之外的另一種失配，現實中 Dropbox 會用 L3 的低 throttle 慢慢消化這個 backlog，避免讓它累積到觸發 burst 偵測。

互動 widget 的價值在於：靜態圖表能說明「三層各自擅長的 regime」，但只有動態觀察能讓讀者體會「regime 切換時三層的權重變化」這個概念。

從三層看出去：可推廣的設計直覺

把 Magic Pocket 的三層 compaction 抽象成可推廣的設計直覺，可以得到幾條原則。

第一條：當系統的 input 分布是多峰的（multi-modal），不要試圖用單一演算法覆蓋所有峰；為每個峰設計專門路徑、用簡單的 dispatcher 把 input 分流。

這條原則在 cache 系統、queue 系統、scheduler 系統都見過——LRU / LFU / ARC 的組合、priority queue / fair queue / latency queue 的組合，本質都是承認 input 分布多峰之後的回應。

把 input 分流的代價是「需要 dispatcher」，但 dispatcher 的邏輯通常是線性掃描或直方圖比對，遠比設計自適應演算法簡單。

第二條：當搜尋空間隨 input 規模超線性成長時，把 input 預先 bucket 化、限制每個 bucket 的處理範圍。

L2 的 DP 之所以能跑，是因為 candidate pool 被嚴格限制在「中度稀疏」這個 bucket、且單次最多取 N 個。

沒有這兩個限制，DP 的時間複雜度就會爆炸；有了這兩個限制，DP 變成可預測的工作。

這個技巧在 streaming aggregation、distributed sort、graph partitioning 都常見——預先切片，犧牲一點全域最佳性換可控的計算複雜度。

第三條：metadata 是 distributed system 的隱形瓶頸。

Magic Pocket 三層的設計被 metadata capacity 深深影響——L1 之所以省、L2 之所以受 N 限制、L3 之所以需要 throttle，都是因為 metadata service 的處理速率有上限。

許多 distributed system 的設計者把注意力放在資料路徑（datapath）的優化，但 production 規模下 metadata path 往往才是瓶頸所在。

設計新的 storage system 或新的 compaction 機制時，先估算 metadata operation 預算、再回頭看 datapath 設計，比反過來做更省彎路。

第四條：應急機制要顯式設計、不能假設「平時的演算法剛好也能處理」。

L3 的存在本身就是因為 L1 與 L2 在極稀疏事件下都失靈。

Dropbox 沒有試圖把 L3 的功能「擠進 L1 的 candidate filter」或「擠進 L2 的 DP 解」，而是承認這是不同的工作量、做了第三條 pipeline。

在 production system 演化過程中，這種「為應急情境寫一條專門路徑」的決策往往是事後諸葛——某次事件暴露出穩態演算法的盲點，新加的 pipeline 就是對那個盲點的補。

這不是失敗，而是健康的演化。

第五條：把「regime 偵測」放在 dispatcher 層，把「regime 內最佳化」放在 worker 層。

這個分層讓每個 worker 的職責清晰、可單獨測試、可單獨 throttle。

Dropbox 的三層 compaction 在這個結構上是教科書級的——dispatcher 看 cell 的使用率分布、決定該啟動哪些 worker、用什麼 throttle；三條 pipeline 各自處理 candidate filter 內的工作，不知道也不需要知道其他 pipeline 在做什麼。

這種「knowledge sharing 只發生在 dispatcher 層、worker 層保持互相無知」的設計讓系統演化容易——加一條新 pipeline 只需要改 dispatcher，不影響其他 worker。

第六條：「重用既有元件」勝過「為新需求寫新元件」。

L3 沒有為了 streaming compaction 寫一個新的 erasure coding pipeline，而是接到既有的 Live Coder service。

這個決策的好處不只是省開發成本——它讓 Live Coder 的所有優化（batching、pipelining、tail latency 控制）都自動被 L3 享受到。

更重要的是，L3 不會引入新的 erasure coding bug——它跟新寫入路徑共用同一份程式碼，任何 erasure coding 層的 bug 都會在新寫入路徑先被發現、再透過共用程式碼修復到 L3。

這條原則的反面是：當有人提議「為新需求寫個專用元件」時，先檢查能不能讓既有元件多承擔一些責任。

專用元件帶來的維護成本通常被低估——額外的測試、額外的監控、額外的 incident response 路徑，這些長期成本累積起來往往遠超「重用既有元件」的短期不適。

這些原則不是 Magic Pocket 獨有——它們在許多 production-scale system 都看得到。

但 Magic Pocket 的三層 compaction 是一個格外清晰的範例：問題明確（volume sparsification 的多峰分布）、解法明確（三條獨立 pipeline）、量化效果明確（30–50% overhead reduction、2–3× faster convergence）。

當你下次面對「該寫一個聰明的單體還是三個簡單的專用模組」這個問題時，Magic Pocket 的答案是後者——而且不是因為「簡單比聰明好」這種空泛的論述，而是因為可推理性、metadata 預算、regime 偵測的成本，這些具體的工程考量都站在「拆」這一邊。

三層 compaction 也提醒我們：好的系統設計不是一次想出來的。

L1 在 Magic Pocket 早期就存在；L2 是中期加上的；L3 是某次事件之後才追加的。

每一層都是對「上一個版本的演算法處理不了的情境」的回應，而不是預先設計好的完整方案。

這種演化路徑在大型 production system 是常態——預先設計的「完美方案」往往禁不起 production 流量的考驗，事後迭代加上的應急路徑反而成為系統的關鍵能力。

接受這個演化路徑、保留 L1 而不重寫它、為新情境加 L2 / L3 而不試圖把它們塞回 L1，是 Dropbox 工程師在這個系統上展現的工程紀律。

最後值得提一個本文沒有展開但值得讀者注意的議題：三層 compaction 跟 garbage collection 的關係。

Magic Pocket 的 garbage collection 標記哪些 blob 是 unreferenced——這發生在 compaction 之前，是 compaction 的前提。

compaction 的工作是「把仍然 referenced 的 blob 搬走、回收 volume」；GC 的工作是「決定哪些 blob 不再 referenced」。

兩者的耦合在於：GC 標記得越積極，volume 稀疏化得越快、compaction 壓力越大；GC 標記得越保守，volume 維持較高 fill rate，但磁碟上躺著更多其實已經 unreferenced 的資料。

三層 compaction 的存在讓 GC 可以更積極——因為三層能應對 GC 帶來的稀疏化波動，GC 不需要為了 compaction pipeline 的速度而保守。

這是 storage system 設計中的常見耦合：一個元件的優化能力決定另一個元件能放開多少。

Magic Pocket 把 compaction 從單層擴展成三層，等於給了 GC 更大的設計空間——這是「組合 effect」的另一個面向，遠超單純看 compaction 數字所能呈現。

What this enables：三層 compaction 把 Magic Pocket 對「volume 稀疏化速度」的應對能力從「分鐘級的慢慢追」擴展到「天級的批次排空」，整體 compaction overhead 在 EB 規模上降低 30–50%、收斂速度提升 2–3 倍——這個能力讓 immutable blob store 可以承受不規律的刪除模式而不需要超量預留容量，等於把原本被「為突發事件留 buffer」綁住的硬碟容量釋放出來服務新資料。
