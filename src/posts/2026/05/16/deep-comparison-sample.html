這是 comparison archetype 範例。對比兩個 streaming framework 選項：Kafka Streams 與 Apache Flink。對照表先給出 at-a-glance、然後 3 個 dimension 各自展開，最後 how to choose 給決策建議。

Kafka Streams Apache Flink
State backendRocksDB (local)RocksDB + remote checkpoint
Deployment modelLibrary (in app JVM)Cluster (separate runtime)
Latency profile~10-50ms~50-200ms
Exactly-onceYes (within Kafka)Yes (across systems)
Learning curveLow (Java/Scala fluency enough)Medium (需懂 distributed state)

dimension: state management

Kafka Streams 把 state 存在 local RocksDB，重啟時從 changelog topic 重建。Flink 預設也是 RocksDB，但加上 remote checkpoint（HDFS / S3），復原速度更快，但 latency 多 50-100ms。

dimension: operational model

Kafka Streams 是 library，跟你的 app 一起部署，沒有額外 cluster 要管。Flink 是 standalone cluster，需要 JobManager + TaskManager + ZooKeeper 等，但相對地 resource isolation 更好。

dimension: latency vs throughput

Kafka Streams 預設 micro-batch 100ms，latency 低、throughput 受 partition 並行限制。Flink 是真 streaming，latency 較高（checkpoint 開銷）但 throughput 更高（pipeline parallelism + state spilling）。

how to choose

如果你的 pipeline 已經 in-Kafka（input + output 都是 Kafka topic）且 latency 要求 <100ms，選 Kafka Streams——operational simplicity 是真價值。如果你需要 cross-system exactly-once（例如 Kafka in + Postgres out）或單 instance 要處理 >50K events/s，選 Flink——cluster 開銷值得。

Take-away：對 80% 的「我已經在用 Kafka 想加 stream processing」場景，Kafka Streams 是正確選擇；只有 cross-system 或高吞吐才該付 Flink cluster 的 operational tax。
