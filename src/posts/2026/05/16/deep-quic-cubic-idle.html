連線已經穩定傳輸了幾秒鐘，然後發生一次丟包。CUBIC 開始復原。兩個封包送出去、確認回來，bytes_in_flight 歸零——但下一輪傳送後，擁塞窗口依舊卡在兩個封包。再下一輪，還是卡著。六秒七秒後，測試逾時。

CUBIC 的 RFC 9438 §4.2-12 定義了 app-limited exclusion：應用程式閒置期間，CUBIC 不應讓擁塞窗口因為沒有流量而產生不公平的暴衝。2017 年 Linux 核心引入的修補正是要解決這個問題——但當 Cloudflare 在 2020 年把這個修補移植進使用者空間的 QUIC 實作 quiche 時，少了核心的一個回呼，一個靜默的邊緣條件就此埋入。

what happened

故事的起點是 2017 年的一個 Linux CUBIC 缺陷：若應用程式長時間閒置，epoch（參考時間戳記）不更新，導致下次傳送時 delta_t = now − epoch_start 暴增，CUBIC 計算出不切實際的大目標窗口。Eric Dumazet、Yuchung Cheng 和 Neal Cardwell 的修補方案是「將 epoch 向前平移閒置時長」，而非重設，保留了 CUBIC 的增長曲線形狀。這個修補在 TCP 的核心層運作良好，因為核心的 TCP 機制有精確的回呼點可以判斷「真正的閒置」起始。

2020 年，quiche 移植這個修補。使用者空間 QUIC 沒有 TCP 核心層的回呼機制；quiche 選擇在 on_packet_sent() 裡檢查 bytes_in_flight == 0 來判斷閒置起始。問題在於：這個判斷發生在「送出封包之後」，而不是「最後一個 ACK 確認之後」。閒置時長被計算為 now − last_sent_time，實際上捕捉到的是一個完整的 RTT，而不是真正的閒置時間（幾乎為零）。

當一條連線發生丟包、進入 recovery，然後 bytes_in_flight 在兩個封包確認後歸零，接著下一輪 on_packet_sent() 被呼叫，CUBIC 把這個 RTT 誤認為閒置時長，將 recovery 起始時間推到未來。此後每個 ACK 到達時，in_congestion_recovery() 回傳 true，CUBIC 跳過成長計算——擁塞窗口永遠卡在兩個封包的最低點。測試器觀察到每 ~14ms 就在 recovery 和 congestion avoidance 之間切換，999 次狀態轉換只需 6.7 秒，60% 的測試在 10 秒逾時前無法完成下載。

why it matters

這個 bug 的兩個教訓比問題本身更值得記憶。第一個教訓：核心層的「精確語意」不一定能在使用者空間重現。TCP 的 CUBIC 實作依賴核心的回呼時間點——ACK 處理路徑、傳送路徑、計時器觸發——這些邊界在使用者空間 QUIC 裡未必對應相同的程式碼點。把核心補丁直譯成使用者空間代碼，看似等價，實際上語意已經偏移。

第二個教訓：這類 bug 的重現條件極為苛刻——需要真實丟包、處於 congestion avoidance（不是 slow start）、且 cwnd 已被壓縮至最低點。三個條件缺一不可。在正常的 happy path 測試中，這個 bug 完全不會浮現；只有在「連線已有丟包歷史」的壓力測試下，才會以 60% 失敗率現形。

so what

修復非常直接：新增一個 last_ack_time 時間戳記，在 ACK 抵達時更新，idle 起始點改為 max(last_ack_time, last_sent_time)。這樣閒置時長才真正反映「最後一個確認之後到現在」，而不是「最後一次傳送之後到現在」。修復後測試通過率從 40% 回到 100%，cwnd 沿正常 CUBIC 曲線成長，下載在 4-5 秒內完成。

對於在使用者空間實作擁塞控制的工程師，這個故事提供了一個具體的 checklist 項目：每一個依賴「時間點語意」的核心 TCP 修補，在移植時都必須重新確認使用者空間等價的觸發時機。RFC 9438 §4.2-12 描述的行為是正確的；問題永遠在實作對 RFC 的詮釋是否與執行環境的邊界對齊。

Take-away：把核心 TCP 修補移植到使用者空間 QUIC 時，每個「時間點回呼」都必須重新核對語意等價——last_sent_time 和 last_ack_time 差一個 RTT，但那個 RTT 足以讓擁塞窗口永遠卡死。
