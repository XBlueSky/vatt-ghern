凌晨四點，p99 latency 突然從 80ms 跳到 800ms——但 CPU、記憶體、磁碟、網路全都正常。

{{ title }}

每個工程師都遇過這種 incident。表面看一切正常的 metric，卻有某個維度暴增。這篇範例追蹤兩個假設的證偽過程，最後揭示真相。

observation

p99 從 80ms 暴增到 800ms，持續約 20 分鐘後自行恢復。CPU 利用率、記憶體、磁碟 IO、網路頻寬全在正常範圍。錯誤率沒上升、QPS 沒變化。

hypothesis: GC pause cascade

第一個假設：可能是 JVM Full GC 卡住造成 p99 變差。我們檢查了 GC log——確實有 GC 活動，但暫停時間都在 10-20ms，無法解釋 800ms。GC log 反而顯示這 20 分鐘 GC 頻率比平常還低。假設失敗。

hypothesis: downstream slow query

第二個假設：可能是後端某個 DB query 變慢了，把上游也拖慢。我們檢查 DB metrics 與 query log——所有 query latency 都在 base line。沒有 lock contention、沒有 slow log 條目、沒有 connection pool exhaustion。假設失敗。

the truth

真相是 kernel 層級的問題：那 20 分鐘剛好對應到 systemd-journald 在做 log rotation + fsync，因為 disk write back cache 被 flush 干擾了一個與我們服務不直接相關的 cgroup 的 IO 排程，間接影響了 socket buffer flushing。前面的 metrics 看不到是因為它們聚合在 process 層，沒看到 cgroup-level 的 IO scheduling 細節。

Take-away：下次遇到「所有 metric 都看起來正常但 p99 暴增」的情況，先看 cgroup-level 的 IO 排程指標，不要只信 process-level metric。
