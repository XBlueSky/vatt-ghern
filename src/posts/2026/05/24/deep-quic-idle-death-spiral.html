在 6.7 秒裡， 一條 QUIC 連線的 CUBIC 狀態機翻轉了 999 次——平均每 14 毫秒一次， 剛好是一個 RTT 的時間。 封包早就不再遺失了， 網路一片平靜， 但 congestion window 死死卡在兩個封包大小的最小值上， 再也長不起來。 把這個 bug 追到底， 會走到一行 2017 年的 Linux 核心最佳化——一段為了讓 TCP 在閒置後不要重置成長曲線而寫的程式碼， 被原封不動搬進 userspace 之後， 反而成了讓連線餓死自己的引擎。

當 idle 不是 idle——一個 Linux 核心最佳化如何把 QUIC 推進死亡螺旋

Cloudflare 的 quiche——他們開源的 QUIC / HTTP3 函式庫——在一組壓力測試裡出現了一個極不直觀的失敗模式： 大約 61% 的下載在 timeout 之前根本跑不完。 測試本身並不殘酷：10ms RTT、 一個 10 MB 的 HTTP/3 下載、 前兩秒注入 30% 的隨機封包遺失， 兩秒之後網路完全恢復、 零遺失， 整體 10 秒 timeout。 照理說， 前兩秒的丟包會把 cwnd 打下去， 但兩秒一過，CUBIC 應該迅速爬回正常吞吐、 把剩下的位元組灌完。 實際發生的卻是：cwnd 卡在 2,700 bytes——剛好兩個 full-size 封包——再也不動。 連線沒有 crash、 沒有報錯、 吞吐曲線上只是一條貼著地板的平線， 然後 timeout。

這類 bug 是工程上最難抓的一種： 它在正常 dashboard 上完全隱形。 你的 throughput panel、 你的 p50 / p99 latency、 你的 error rate， 在沒有 congestion 的日子裡全都漂亮得很。 只有當網路真的進入嚴重遺失、CUBIC 真的要做 recovery 的時候， 這個 bug 才會引爆——而那恰恰是你最需要 congestion control 正常運作的時刻。 對一個跑在全球 anycast 網路上、 每天要面對各種劣質 last-mile 連線的 edge 平台來說， 「只在 recovery 期爆炸」 幾乎等於「在最該穩的時候最不穩」 。

更值得一個工程 leader 停下來想的是它的來歷。 這不是一個 CUBIC 演算法本身的設計缺陷——RFC 9438 把 CUBIC 寫得清清楚楚。 這也不是一個 quiche 團隊憑空寫錯的 off-by-one。 它是一段在 Linux 核心裡跑了八年、 被千萬台機器驗證過、 完全正確的最佳化程式碼， 在被移植進 userspace 的 QUIC stack 時， 因為兩邊的 timing 語意不同， 而從「正確」 退化成「災難」 。 這篇要拆的就是這條因果鏈： 從 2017 年那個 kernel commit， 到 quiche 裡的不完整移植， 到死亡螺旋的物理機制， 最後到那個只加一個 timestamp 就解決的修正。

螺旋的形狀——cwnd 為什麼回不去

先把現象本身看清楚。CUBIC 的設計目標是： 在遺失發生後，congestion window 沿著一條三次曲線重新成長， 前期快、 接近上次的 cwnd 上限時放緩、 越過上限後再加速探測更高頻寬。 這條曲線的數學形狀正是 CUBIC 名字的由來。 正常情況下， 前兩秒的 30% 遺失會把 cwnd 反覆砍半、 最終壓到最小值， 但只要遺失停止，CUBIC 的三次曲線就會接管， 把 cwnd 在幾百毫秒內拉回可用的吞吐區間。

出 bug 的連線完全不是這樣。 它的 cwnd 在遺失停止之後， 依然死死貼在 2,700 bytes 的地板上。CUBIC 不是「成長得慢」 ， 而是「完全不成長」 。 下面這個模擬把兩種行為並排放在同一個時間軸上——你可以親手切換 broken 跟 fixed、 按 play 看 cwnd 隨時間怎麼走。 注意 broken 模式下那條貼地的平線， 以及右下角那個瘋狂跳動的 recovery 狀態計數器： 它就是那 999 次翻轉的來源。

「999 次狀態翻轉、6.7 秒、 約 14ms 一次」 這組數字本身就是診斷的關鍵線索。14ms 不是隨便一個數——它約等於一個 RTT（10ms） 加上一點點處理時間。 當一個本該是「事件驅動」 的狀態機， 開始以「每個 RTT 翻一次」 的節奏抽搐， 那幾乎可以斷定： 有某個量原本應該反映「應用層真正閒置了多久」 ， 卻意外被綁上了「一個 RTT 的長度」 。 把這個直覺記住， 它就是整條因果鏈的扣環。

這裡值得強調 CUBIC 的最小 cwnd 為什麼是兩個封包而不是一個。 兩個封包是為了讓 ACK clocking 能持續運轉——接收端的 delayed ACK 機制通常等到收到兩個 segment 才回一個 ACK， 如果 cwnd 只剩一個封包， 發送端送完就沒有 in-flight 資料、 收不到能觸發後續傳送的 ACK， 連線會直接 stall。 所以 2,700 bytes（兩個 1,350 byte 封包） 是 CUBIC 刻意設的地板。bug 的殘酷之處在於： 連線確實停在這個「理論上還能動」 的地板上，ACK clocking 也確實在跑， 但每一次 ACK 回來該觸發的成長， 都被那個錯誤的 idle 判斷吃掉了。

2017 年那行核心程式碼——idle 最佳化的血統

要理解 quiche 裡的 bug， 得先理解它移植的那段 Linux 核心程式碼解決的是什麼問題。CUBIC 的成長曲線是「自上次進入 congestion avoidance 的時間原點（epoch） 算起的三次函數」 。 這帶來一個微妙的問題： 如果一條連線送完一波資料後閒置了一段時間（例如 HTTP keep-alive 連線在兩個 request 之間沒有流量） ， 等到下次又有資料要送時， 那個三次函數的時間原點已經被閒置期推得很遠——dtEpoch 很大，cubic 曲線會算出一個高得離譜的 cwnd 目標， 等於讓連線在對網路一無所知的情況下突然爆量送出。

RFC 9438 §4.2 對這種「應用受限（application-limited） 」 的情況有明確規範： 閒置期間不該讓 CUBIC 的曲線繼續往前跑。2017 年 Eric Dumazet、Yuchung Cheng、Neal Cardwell 提交的核心 commit 30927520dbae 就是這個規範的實作——它的做法是在偵測到閒置時， 把 epoch 時間原點往前推， 等於「凍結」CUBIC 曲線的形狀， 讓連線恢復活動時從凍結點繼續、 而不是從一個被閒置期推遠的虛假高點爆發。 這是一個正確、 優雅、 被廣泛驗證的最佳化。

但這個 commit 落地大約一週後， 核心團隊自己又提交了一個 follow-up c2e7204d180f， 承認原版有個 imprecision： 在某些情況下， 量測閒置時間用的是「送出時間（send time） 」 ， 這可能把 recovery 的邊界推到未來去， 導致行為不正確。 換句話說， 核心團隊在原版上線一週內就發現「用 send time 當閒置基準」 這個量測點本身有問題、 並修掉了它。 這個一週的時間差， 後面會變成整個故事的關鍵——因為移植進 quiche 的， 是還沒被這個 follow-up 修正觀念滲透透徹的那套量測邏輯。

把這條血統攤開來看， 每一步都沒有人犯下「愚蠢」 的錯誤。Dumazet 那群人寫的核心程式碼是對的； 核心 follow-up 的修正也是對的；quiche 團隊把一個經過實戰驗證的核心最佳化拿來用， 這個判斷在工程上完全合理——別人花了八年驗證過的東西， 重新發明只會引入更多風險。 錯誤發生在最不起眼的接縫處： 核心的時間語意和 userspace 的時間語意， 在「last_sent_time 到底代表什麼」 這一點上， 悄悄地不一樣了。

idle 量錯了——last_sent_time 與 last_ack_time 的差異

現在拆機制本身。quiche 的 CUBIC 在 on_packet_sent() 裡用 bytes_in_flight == 0 判斷「現在是不是閒置狀態」——這個判斷本身是對的， 沒有 in-flight 資料確實意味著連線當下沒在傳東西。 問題出在下一步： 它量「閒置了多久」 用的是 now - last_sent_time。 在一般情況下這沒問題， 但在 cwnd 卡在最小值（兩個封包） 的特殊情況下， 這個量測會出大事。

想清楚最小 cwnd 下的封包時序：cwnd 只允許兩個封包在路上。 發送端送出這兩個封包後，bytes_in_flight 達到 cwnd 上限， 必須停下來等 ACK。ACK 要等多久？ 一個 RTT。 所以從「送出最後一個封包」 到「收到第一個 ACK、bytes_in_flight 歸零、 可以再送」 之間， 必然隔著一整個 RTT。 此時 now - last_sent_time 量到的是這一整個 RTT（~14ms）——但這段時間應用層根本沒有閒置， 它是被 congestion control 卡住在等 ACK。 真正的 app idle 是 ~0ms： 應用早就準備好下一批資料了。

看懂了量測點的差異， 整個死亡螺旋的機制就清楚了。 在 broken 版本下， 每當 bytes_in_flight 歸零（也就是每個 RTT、 每次剛把那兩個封包送完等到 ACK） ，on_packet_sent() 就會把那 ~14ms 的虛假 idle_delta 拿去推進 epoch_start。epoch 被往前推之後，CUBIC 計算 dtEpoch（自 epoch 起算的時間） 時得到一個接近 0 的值——而 dtEpoch ≈ 0 代入三次曲線， 算出的 cwnd 目標就是最小值附近。 於是 cwnd 不成長。 下一個 RTT， 同樣的事情再發生一次：epoch 又被推前、dtEpoch 又被歸零、cwnd 又不長。 這就是那 999 次翻轉的物理本質——每一次都是一個被人為製造出來的、 不該存在的 FALSE recovery 狀態。

這個機制有一個值得親手感受的性質：broken 版每個 round 把 epoch 往前推的量， 恰好等於一個 RTT——RTT 越大，epoch 被推得越遠、dtEpoch 被壓得越死。 下面這個滑桿讓你掃 RTT， 看 broken 與 fixed 兩種量測下， 每個 round 推進 epoch 的量怎麼隨 RTT 變化。 注意 fixed 版那條恆為 ~0 的線——不管 RTT 多大， 只要量測基準取對了，epoch 就不會被虛假地往前推。

這張圖把「為什麼 broken 版會無限循環」攤成一句話： 只要 idle_delta 跟 RTT 綁在一起， 每個 round 推進 epoch 的量就永遠 ≥ 一個 RTT， 而連線每個 RTT 都會進一次 on_packet_sent()——推進的速率剛好追平甚至超過時間流逝的速率，dtEpoch 因此永遠回不到正值。fixed 版把這條線壓回 0， 時間流逝才終於能累積成 dtEpoch，CUBIC 曲線才能重新接管。

修正之所以只需要「加一個 timestamp」 就足夠， 是因為問題的本質是「量測的參考點選錯了」 ， 而不是「演算法邏輯錯了」 。last_ack_time 在每次收到 ACK 時更新。 在最小 cwnd 的場景裡， 連線剛收到 ACK 才會去送下一批、 才會進到 on_packet_sent()， 所以此刻 last_ack_time 幾乎就是 now。 把閒置基準從 last_sent_time 改成 max(last_ack_time, last_sent_time) 之後，max 會取到那個剛更新的 last_ack_time，idle_delta 算出來 ≈ 0，epoch 不再被推進，CUBIC 的三次曲線正常接管。 為什麼是 max 而不是直接用 last_ack_time？ 因為在真正的應用閒置場景（連線送完資料後沒有新資料、 也沒有新 ACK） ，last_sent_time 才是較晚的那個、 才反映真實閒置的起點——max 同時涵蓋兩種場景。

這裡有一個容易被當成「實作細節」 一筆帶過、 但其實是整個 bug 核心的觀念： 在核心裡， 封包真的是核心自己送出去的，last_sent_time 反映的是「核心 NIC 隊列裡這個 socket 上一次有封包出去的時刻」 ， 而核心對 ACK 的處理跟對 send 的處理在同一個 timing domain 裡， 兩者的時間語意是對齊的。 搬到 userspace 之後，quiche 拿到的 timestamp 來自 userspace 的時鐘讀取，send 與 ack 之間的關係不再有核心那套隱含的對齊保證。 原本在核心裡「last_sent_time 已經足夠近似」 的前提， 在 userspace 的 timing 模型下不再成立——而那個一週後的核心 follow-up， 正是在核心自己的世界裡就已經發現「光用 send time 不夠精確」 。 移植的人沒有把那個一週後的觀念修正也一起帶過來。

數字的形狀——把螺旋量化

把這個案例的關鍵數字放在一起看， 能感受到它的隱蔽性與爆炸性各有多強。 下面這張表整理了測試條件、 失敗特徵、 與修正後的結果。 值得注意的是「失敗率 61%」 這個數字——它不是「偶爾」 ， 而是「多數」 ； 只要進入那組 congestion 條件， 連線更可能餓死自己而不是恢復。 但同樣這套程式碼在沒有遺失的日常流量下， 吞吐 dashboard 永遠是綠的。

14ms 那一行值得單獨再強調。 在 incident 排查裡， 「某個本該是事件驅動的東西， 開始以一個固定的、 約等於某個系統常數的週期抽搐」 ， 幾乎永遠是「有個量被錯誤地綁上了那個常數」 的訊號。 這裡的常數是 RTT。 當你看到狀態翻轉的週期 ≈ RTT， 下一個問題就該是「哪個量本來不該跟 RTT 有關， 卻變成了一個 RTT 長？ 」——答案就是那個被誤量成一整個 RTT 的 idle_delta。 這種「週期匹配某個系統常數」 的模式辨識， 是讀 timing-related bug 時最值得內化的直覺之一。

另一個值得 leader 記住的點是失敗的「形狀」 ： 它不是常態的 5% 降速， 而是條件性的 61% 全滅。 許多 congestion control 的 regression 是「在某些路徑上慢了 10%」 這種漸進式劣化， 可以靠 A/B 與長期 metric 慢慢發現。 這個 bug 不是——它平時完全不存在， 只在遺失夠嚴重、cwnd 被打到地板的那一刻突然出現， 而且一出現就是接近全滅。 這類「平時隱形、 極端條件下災難」 的失敗模式， 恰恰是最需要靠 fault injection 測試（像這次的 30% 隨機丟包） 而非生產 metric 才能抓到的——因為生產環境的 metric 是被「平時一切正常」 的多數樣本稀釋掉的。 把這點翻成排查語言： 當一個失敗只在某個狀態子空間（這裡是 cwnd 觸地）才出現， 聚合 metric 幾乎一定看不見它， 你需要的是能主動把系統逼進那個子空間的測試， 而不是被動等它在生產裡自己發生。

移植核心程式碼這件事——該帶走的不只是程式碼

這個案例真正的 leverage 不在 QUIC、 也不在 CUBIC， 而在「跨環境移植經過驗證的程式碼」 這個普遍動作裡。 把核心的最佳化搬進 userspace、 把 C 的演算法搬進 Rust、 把單執行緒的假設搬進並行環境——每一次這種移植， 工程師都在隱含地假設「原環境成立的前提， 在新環境也成立」 。 這個 bug 的教訓是： 那些前提經常是隱含的、 沒寫在程式碼裡的， 而它們恰恰是最危險的部分。

核心的 CUBIC 程式碼裡， 「last_sent_time 足以近似 idle 起點」 這個前提從來沒被明寫成一行註解或一個 assert——它是核心 timing model 的一個 emergent property， 是「send 與 ack 在同一個 timing domain、 且核心對 NIC 隊列有直接控制」 這些底層事實的副產品。 當你只 port 程式碼、 不 port 這些底層事實時， 前提就靜悄悄地失效了。 更諷刺的是， 核心團隊自己在一週後的 follow-up 裡， 等於已經把「光用 send time 不夠」 這個觀念寫下來了——移植時若連 commit 歷史一起讀， 這個坑本可以避開。

對一個帶團隊的人， 這裡有三條可以直接落地的做法。 第一， 移植任何「跨了 N 年、 被廣泛驗證」 的程式碼時， 把它的完整 commit 歷史也讀一遍——尤其是緊跟在原始 commit 之後的 follow-up 與 bugfix， 那些往往是原作者自己踩過、 又修掉的坑， 是不寫在最終程式碼裡的隱性知識。 第二， 凡是移植涉及 timing、ordering、memory model 的程式碼， 明確寫下原環境的隱含前提， 再逐條檢查新環境是否成立——把 emergent property 顯式化成 assert 或註解。 第三， 為「平時隱形、 極端條件下災難」 這類失敗模式建立 fault injection 測試， 不要只依賴生產 metric——這次若不是有人特地跑 30% 丟包， 這個 bug 可能還躲在 dashboard 的綠色背後很久。

還值得補一句關於「為什麼選擇移植而不是重寫」 的辯護：quiche 團隊拿核心驗證過的 idle 最佳化來用， 這個決定本身是對的。 重新發明一套 application-limited 處理邏輯， 引入新 bug 的機率只會更高。 問題從來不是「不該移植」 ， 而是「移植時對隱含前提的盡職調查不夠」 。 把這個案例讀成「不要抄核心程式碼」 是讀錯了； 正確的讀法是「抄的時候要連同它成立的條件一起抄， 並驗證新環境裡這些條件還在」 。

The lesson： 跨環境移植經過驗證的程式碼時， 真正要帶走的不是那幾行邏輯， 而是讓它成立的隱含前提——當 last_sent_time 在核心裡「足夠近似 idle」 、 到了 userspace 卻量成一整個 RTT， 那條沒被一起搬過來的 timing 語意， 就足以把一個正確的最佳化變成一台讓連線餓死自己的引擎。
