當 idle 不是 idle——一個 2017 年的 Linux 核心最佳化讓 QUIC 的 cwnd 永遠卡在最小值

Cloudflare 的 quiche 把 Linux 核心 2017 年的一個 idle 最佳化（commit 30927520）搬進 CUBIC（RFC 9438），但搬得不完整：idle 時長用 last_sent_time 量，在最小 cwnd 下這個差值抓到的是整整一個 RTT（約 14ms）而不是真正的應用閒置（約 0ms），於是不斷把 recovery 邊界往前推、觸發連續的假 recovery，cwnd 永遠長不起來、卡死在 2,700 bytes。測試裡約 61% 的下載跑不完、6.7 秒內 999 次狀態轉換。修法是加一個 last_ack_time、改用 max(last_ack_time, last_sent_time) 量 idle。這種 bug 在 throughput dashboard 上完全看不見，只在壅塞復原時爆出來。

帳務管線突然變慢——ClickHouse query planner 的隱藏鎖競爭

Cloudflare 把一張超過 2PiB、每秒進數百萬列的 ClickHouse 表，partition key 從 (day) 改成 (namespace, day)（為了做 per-namespace 保留），結果 query 隨 part 數累積愈跑愈慢——一年內每 replica 的 part 從 3 萬漲到 16 萬。profiler 指出 filterPartsByPartition 吃掉 45% 的 CPU、超過一半的 leaf query 時間耗在 MergeTreeData 的 mutex 上：planner 取 exclusive lock、整份 parts vector 複製一遍再過濾，把並發查詢排成單線。三招修：改 std::shared_lock 允許並發讀、共享快取避免複製、利用 namespace 排序前綴做 binary search——query 時間砍半，patch 進 ClickHouse 25.11（PR #85535）。教訓：planner 同步成本是隨「總 part 數」長，不是隨查詢實際讀到的 part 數。
