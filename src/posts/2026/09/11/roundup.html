fp64 拆成餘數，丟給 FP8 tensor core

Satoshi Matsuoka 這篇處理的是用 CRT 餘數系統在 FP8 tensor core 上模擬 fp64 矩陣乘法，重點不在乘法，而在把運算元轉成餘數平面的那段——那是在 tensor 運算開始前就先把資源吃掉的階段。工程手法是 convert-once 的餘數工作區、走整數管線且常數約化剛好兩個 limb 的 GEMM，再把轉換 pipeline 到 MMA 後面藏起來。論文給的是模型推估、不是實測：作者註明每一個數字都還等著被量出來，在這個前提下，NVIDIA Rubin 上 thread-block cluster 之內能貼到約 473 TFLOPS 的算術上限，輸出放大之後則卡在約 235 TFLOPS 的地板；文中提的 Option C 硬體改動是在非同步複製路徑上加一塊固定功能的餘數轉換單元，宣稱能把地板拉回 473。

#04

一個簽章 2,420 位元組，UDP 裝不下

1.1.1.1 開始驗證 ML-DSA-44 的 DNSSEC 簽章，而一個 ML-DSA-44 簽章就是 2,420 位元組、公鑰另外 1,312 位元組，在還沒算進被簽的 RRset、網域名稱、DNS header 與其他 DNSSEC 記錄之前，光簽章本身就超出常見的 1,232 位元組 UDP payload 預算。Cloudflare 的處理不是把回應拆成片段——文中直說分片 UDP 不可靠、應該避免——而是讓權威伺服器回截斷標記，把 resolver 推去 TCP 或其他 transport。這個轉移的代價量得出來：約 85% 的 1.1.1.1 查詢從 UDP 進來，把 Big Pineapple 上所有 DNS 產品一起算則約 60%，其餘走 TCP、DoT 與 DoH。

#07

module specifier 當成真的 URL 來解

Cloudflare 重寫了 workerd 的 module registry，把 module specifier 當成真正的 URL 解析，包含 query string 與 fragment：相對 import 的結果跟 new URL(specifier, base) 一致，import attribute 會被驗證，query string 不同的同一個 URL 會產生不同的 module instance，import.meta 也補上了。舊實作把 specifier 當成檔案系統路徑，而且整包 Worker 事先編譯、每個 V8 isolate 各留一份；新設計一開始就把 laziness 與快取共享放進來，模組改成第一次被 import 時才編譯，isolate 副本之間共用編譯後的程式碼。跟著一起變的是 Node.js 相容 API 預設開啟、應用程式大小上限提到 64 MiB，並以 new_module_registry 這個 compatibility flag 選用。

#08

每個 shard 都還是真的 Postgres

PlanetScale 的 Neki 進入 platform preview，立場寫得很明確——「stick to Postgres, don't work around it, fake it, or turn away from it」，每個 shard 上跑的是真的 Postgres，擴充套件、SQL 支援與行為都保持標準，而不是一個相容實作。應用程式連的是 Neki router，走標準 Postgres wire protocol，由 router 負責解析查詢、規劃分散式執行、緩衝並合併結果；每個 shard 是一個 primary 加上兩個以上 replica、跨三個可用區，shard group 則讓不同的表與工作負載落在不同的 shard 集合上。連線池以 sidecar 同時掌握 router 側與 Postgres 側，量的是實際容量而不是估算值；預覽階段官方明說不建議放上 production 工作負載。
