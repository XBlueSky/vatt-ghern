把 30 層 async 呼叫疊起來丟出一個例外，舊版 .NET 要讓 30 個編譯器生成的 state machine 各自接住、各自存起來，合計 51.302 微秒、配置 84.2 KB。.NET 11 只讓 dispatch loop 走過去接一次，同一組測試掉到 10.721 微秒、5.71 KB。

把 async 搬進 runtime

舊版 C# 的 async/await，把降級這件事完全交給編譯器——編譯期就得把 state machine 的形狀定案：欄位要放哪些值、哪些區域變數必須撐過一次懸掛與恢復，全部得先想清楚才能生出程式碼。.NET 11 的 runtime async 把這一段責任搬進 JIT：編譯器不再自己動手轉換，只在 metadata 裡把方法標成 async、吐出精簡的 IL，真正的降級留給 JIT 在執行期依實際發生的事去做。目前這條路要靠 <Features>$(Features);runtime-async=on</Features> 這個編譯器 feature 開關選擇性打開，還不是預設行為。但它牽動的東西不只 async 一個角落——同一份效能整理裡，JIT 在 escape analysis 跟邊界檢查消除上也各自往前推了一步，三條線收在同一個論點上。

這三條線做的其實是同一件事：找出一層「執行期才能真正確定、編譯器只好先保守處理」的抽象，證明安全之後就把它拆掉。跟傳統效能優化把迴圈寫得更緊、指令排得更密不一樣，這裡動的是抽象本身的位置——從編譯期挪到執行期、從 heap 挪到 stack、從間接呼叫挪到直接呼叫。下面這疊層，由上而下大致對應文章拆掉的幾種保守假設，後面幾節會依序拆開講。

這個順序也解釋了為什麼這份效能整理讀起來跟一般的優化清單不太一樣——它持續在問同一個問題：這一層抽象，JIT 有沒有辦法在執行期自己證明用不到。runtime async 排在最前面，因為它動的範圍最大：幾乎每一支服務端程式碼都寫著 async/await。這也是為什麼 C# 編譯器過去要在編譯期就把 state machine 的欄位、懸掛點通通定案——它沒有機會等到執行期才知道一次呼叫是否真的需要懸掛。

runtime async：state machine 從編譯器搬進 JIT

傳統模型下，一個 async 方法在編譯期就會被整個改寫：方法體依 await 點切成幾段，對應的區域變數挪進一個新生的型別當欄位，呼叫端看到的是一個包著這個型別的 Task。這個轉換的關鍵限制是時機——編譯器沒辦法知道這個方法真正跑起來的時候，await 的東西是不是早就完成了，所以它只能假設「有可能要真的懸掛」，把整套機制先準備好。runtime async 把這個決定挪到 JIT，因為 JIT 看得到的是實際跑起來的樣子：一個 async 方法呼叫另一個 async 方法，JIT 可以直接辨認出這是一次直接呼叫，不必先假設它會經過某個抽象的 awaiter 介面。

這個挪動最先受益的是最常見的情況——呼叫鏈根本沒有真的懸掛。如果一路往下每一層的 awaiter 都已經完成，MoveNext 可以直接同步跑到底，不需要真的鋪一份 continuation，也不需要為了讓呼叫端等待而配置一個 Task。這條快路徑不必開發者多寫一行程式碼去觸發，是 JIT 認出模式之後自動選的路。兩層互相呼叫、全部同步完成的測試裡，runtime async 版本比舊版快三倍以上，而且完全沒有中介的 Task 配置——舊版每一層呼叫，不管最後有沒有真的懸掛，都得先把一個 Task 物件生出來擺著。

這也是為什麼舊模型的成本結構長年被詬病：Task 本身是一個 heap 物件，舊模型底下，那些「只是把結果從一個 async 方法直接搬到下一個」的 Task，一樣得完整配置出來。合理的推測是，一個高並發服務如果每次呼叫鏈都要配置好幾層這種 Task，GC 壓力會隨著 QPS 疊上去，即使每一層最後都同步完成。runtime async 讓 JIT 有足夠資訊避免生出這些純粹搬運用的 Task——先假設會同步完成，真的要懸掛才鋪 continuation、配置 Task。

例外穿過多層 async：一次 catch 取代十次

同步完成路徑省的是常態開銷，例外處理省的是失敗路徑的開銷，而且省得更兇。舊模型裡，每個 async 方法都是獨立的一份 state machine，各自被包進一層 try/catch——這是編譯器要把例外正確地灌回外層那個 Task 的必要手段，不這樣做，呼叫端就看不到方法內部真正丟出的例外。代價是，一個例外如果要穿過十層這樣的 async helper 往上傳，即使沒有一層真的打算處理它，也會被個別丟出、接住、存起來整整十次。runtime async 把這個責任收回到單一個 dispatch loop：例外只在最外層被接住一次，沿路走過那些沒有 handler 的 continuation record，直到真正會被外部觀察到的 root task 上才標記成失敗。

三十層深的測試把這個差距量出來：舊模型 51.302 微秒、配置 84.2 KB；runtime async 10.721 微秒、配置 5.71 KB——時間掉到約五分之一，配置掉到約十五分之一。同一件事——接住例外、往外傳——原本要做三十次，現在只需要做一次。底下這個模擬把兩種機制的動態行為放在一起，播放之後可以看例外往上爬的時候，兩邊各自在做什麼。

沿路走過的那些 continuation record，本質上只是記著這一段暫停在哪裡、要跳回哪個位址繼續執行的一小塊資料，不像舊模型的 state machine 型別要背著完整的例外處理邏輯。dispatch loop 走過去只是比對一下有沒有 handler，沒有就繼續往外，這一步的成本跟真的 catch 一次、把 exception 物件存進欄位裡完全不是同一個量級。

二進位變小的原因

二進位縮小是同一個機制的自然結果。舊模型下，每個 async 方法都要各自生出一份 state machine 型別與相關欄位——方法數量一多，光是這些型別本身的 metadata 與程式碼就佔掉可觀的空間。runtime async 底下，這些型別不再需要在編譯期就生出來：編譯器吐出的 IL 精簡得多，state machine 真正的版面交由 JIT 在執行期依需要鋪陳。十個串接 async 方法的測試 assembly 量出來，編譯器版本是 10,752 bytes，runtime async 版本是 5,632 bytes，幾乎打對折。對容器化部署、或是需要把 assembly 塞進較小映像的場景，這個差距會隨著 async 方法數量線性放大。這個效果如果應用在 Native AOT 這類需要縮小啟動映像的場景，合理的推測是影響會更明顯：AOT 編譯不像 JIT 有執行期可以重新鋪版面，state machine 型別原本就得整份預先產生、整份打進最終產物，runtime async 讓這份產物在編譯當下就變薄。

Deabstraction 第二條線：enumerator 上 stack、GVM 去虛擬化、delegate 少一個欄位

runtime async 是這份效能整理裡結構性最完整的一塊，但不是唯一一塊。同一版 JIT 在 escape analysis 上也往前推了一步，做法是 conditional escape analysis（CEA）。過去 JIT 判斷一個物件會不會逃逸，遇到稍微複雜一點的控制流就容易舉手投降，乾脆假設會逃逸，把它配置在 heap 上——保守但安全，代價是 GC 要多背一個物件。CEA 換了個問法：不是單純判斷「會不會逃逸」，而是去記錄 fast-path 配置跟後面 guard 檢查用到的那個 enumerator 區域變數之間的關係。這讓 JIT 能在更複雜的分支下依然證明「這個配置到不了會讓它逃逸的 fallback 呼叫路徑」——證明成立，就把它直接放上 stack，連帶讓一整段 foreach 迴圈不再碰 GC。foreach 走 IEnumerable<int> 的一個 benchmark 量出這個差距：.NET 10 配置 32 bytes、耗時 13.874 ns；.NET 11 配置直接歸零，耗時降到 2.674 ns。

虛擬呼叫跟泛型共享程式碼都是為了不把同一段邏輯抄好幾份而付的代價：CLR 用一次間接跳轉換來程式碼共用，用一份泛型字典換來型別參數不用在編譯期展開成好幾份組合語言。這個代價平常小到感覺不到，但寫在熱路徑裡、被呼叫幾億次，累積起來就不是小事。去虛擬化要做的，是在能證明這裡型別已知、不需要真的查表的少數情況下，把間接跳轉繞過去。

另一條腿是泛型虛擬方法（GVM）的去虛擬化。虛擬呼叫本來就要多一層跳轉——執行期查表找到真正該呼叫的實作；泛型虛擬方法更麻煩，因為同一份程式碼常常要在多個型別實例之間共用，型別參數要另外傳。有兩個 PR 在拆這層：#122023 先讓 JIT 能對「non-shared」的 GVM 去虛擬化——型別參數編譯期就固定、不需要跨型別共用程式碼的那種情況；#128702 把範圍擴大到「shared」GVM 跟 default interface implementation，涵蓋面更廣。把一個新配置的物件轉型成介面再呼叫其泛型虛擬方法的 benchmark 顯示，去虛擬化後耗時從 6.678 ns 降到 1.764 ns，原本那次配置的 24 bytes 直接消失——物件被 JIT 連帶內聯掉，連配置的理由都不存在了。去虛擬化是連鎖反應的起點：兩次呼叫都被去虛擬化並內聯之後，原本要在執行期才查得到的 Unsafe.SizeOf<T>() 也變成編譯期常數，可以再被摺疊、消去。default interface implementation 這幾年在 C# 生態裡用得越來越多，介面直接帶預設實作，寫起來方便；站在 JIT 的角度，它一樣是一次要查表才能決定該跑哪份程式碼的虛擬呼叫，#122023 跟 #128702 合起來都涵蓋到了。

delegate 的改動看起來瑣碎，邏輯完全一樣。一個 delegate 物件原本要記住目標物件、方法指標之類的幾個欄位才能在呼叫時找到正確的方法；CoreCLR 這次讓每個 delegate 物件少放一個指標大小的欄位，在 64-bit process 上每個 delegate 省下 8 bytes。省的是物件的重量——closed-instance delegate 的配置從 64 bytes 降到 56 bytes，連帶讓比較兩個 delegate 是否相等、算它的雜湊值這類要碰欄位的操作也跟著變快；文章把這一段的效益歸給更新後的版面讓相等比較與雜湊運算更直接取得需要的方法識別資訊。三個改動的方向一致：讓執行期能表達的東西變多，編譯器就不用什麼都往壞處想。delegate 在 .NET 裡幾乎無所不在——LINQ 的每個 lambda、event 的每個 handler、Func/Action 型別的每一次呼叫底層都是它，欄位減少的效益因此攤在整個生態系的記憶體足跡上。底下這張表把幾組數字放在一起看。

邊界檢查消除：同一個論點的第三個例證

第三條線是陣列與 span 的邊界檢查消除，做法是把 JIT 的範圍分析（range analysis）再收緊一輪，而不是換一種指令排列。以前 JIT 原始碼裡有一段註解坦白承認自己放棄：遇到「!= 某個常數」這種條件，它形容成這給不了區間什麼資訊，乾脆跳過。PR #121273 把這段放棄改寫成檢查：這個被排除的常數是不是剛好卡在追蹤範圍的邊界上，是的話就把範圍收緊——這對 C# 的 list pattern 特別有用，因為 pattern matching 產生的分支經常正好長這個樣子。位元運算這邊，PR #122263 補了一段：遇到用遮罩位元欄位算查表索引，像 ((b & 0x03) << 4) | ((b & 0xf0) >> 4) 這種寫法，JIT 現在能從兩個用 OR 接起來的位元運算各自推出上界，證明結果落在小查表的合法範圍內。邊界檢查，就這樣被拿掉了。

另外兩個改動處理的是守衛與傳播順序。PR #125056 讓 (uint)i < span.Length 這種把 index 轉成 unsigned 再比較的寫法，在 true 分支裡記住 index 的精確範圍，連 i - 1 這種衍生運算式的邊界檢查都能一併省掉。PR #121527 則處理同一個 basic block 內部的順序：以前 assertion 要跨 block 才會被記住，新版讓 JIT 依執行順序把同一個 block 裡前面產生的 assertion 往後帶，後面同一個索引的存取就不用重新檢查一次。四個改動分別由不同的 PR 送進 JIT：#121273、#122263、#125056、#121527。

邊界檢查本身不貴——一次比較加一次分支，但陣列與 span 存取在迴圈裡通常是最熱的路徑，一次疊代省一次比較，乘上百萬次疊代就是可觀的差距。範圍分析要做的事情，是在編譯期就把這次存取一定安全的證明鋪好，讓 JIT 敢把這次比較連同分支一起刪掉。

三條線碰的是完全不同的東西——async 呼叫鏈、enumerator、虛擬呼叫、delegate、陣列存取——方法論卻是同一套：先讓 JIT 能證明某個原本保守的假設其實不成立，再把因為那個假設而多付的成本整段拆掉。文章對這個方法論的形容很直接：真正的效能工作就是這樣，一路累積、一個疊一個，直到整體在量測上明顯不一樣。這也是為什麼這份整理裡找不到一條「把某個迴圈重寫得更快」的條目——動的從頭到尾都是抽象本身該擺在哪裡。

這些優化都不是免費的：JIT 要在編譯這段程式碼的當下多跑一輪分析——escape analysis 追蹤配置與 guard 之間的關係，range analysis 沿著 block 把 assertion 收攏，devirtualization 先確認型別是否真的已知。分析證得出來就拆抽象，證不出來就退回原本保守的路徑，不會讓程式跑錯，只是少拿到那一段效能。以 enumerator 為例，CEA 證不出「配置到不了 fallback 呼叫」的情況，物件還是照舊配置在 heap，跟 .NET 10 的行為一樣；GVM 也是同理，non-shared 跟 shared 兩種案例各自有各自的 PR 在處理，本身就是承認並非所有泛型虛擬呼叫都能一視同仁去虛擬化；邊界檢查那邊，範圍分析證不出安全時，JIT 一樣照舊留著那次比較與分支，不會冒險拿掉。runtime async 目前仍是要靠 runtime-async=on 這個編譯器 feature 手動打開，還不是預設值——文章沒有談要不要在正式環境打開這個開關，只確定它現在是選擇性的。

The unlock：寫法完全不用變——async/await 照舊寫、foreach 照舊寫、interface 照舊呼叫，JIT 能證明安全時，直接把 state machine、heap 配置、間接跳轉、邊界檢查這些保守假設拆掉，效能差距是搬掉抽象換來的，不是換一種寫法換來的。升級之後值得檢查的是這些條件——同步完成、不逃逸、型別已知、範圍可證——在自己的服務裡成立的比例有多高，那決定了實際能吃到多少這份差距。
