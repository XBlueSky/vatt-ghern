每個 token 只留 890 位元組

DeepSeek-V4.1-Flash 的 model card 描述的是一顆 40 層的 causal encoder-decoder——20 層 causal encoder 接 20 層 decoder，552B backbone，但 prefill 每個 token 只活化 8B、decode 16B，每個 token 路由 6 個 expert。真正被拿來當賣點的是記憶體：Compressed Sparse Attention 2 把 KV cache 壓到每個 token 890 位元組，官方說法是約 DeepSeek-V4-Flash 的四分之一，另一招 SWA Bounded Replay 只重放最近的 token 來補回缺掉的 SWA KV state，常駐 footprint 再降到大約八分之一。訓練用 45T multimodal token 從頭跑，sparse attention 在 64K 長度上訓練後外推到 1M，推理努力程度做成 1 到 100 連續可調，授權是 MIT。

#07

重算有時候比讀快取快

這篇 9 月 10 日投上 arXiv 的論文做的是 vLLM 外部 KV cache 的效能刻畫，橫跨 GPU、CPU 與 NVMe 三層，用合成負載、長 context benchmark 與 production trace 一起量。作者的說法是快取表現取決於傳輸粒度、中間記憶體用量，以及傳輸在什麼時機進入請求排程，而不只是裝置頻寬。他們寫的 py-kvcache 在 80k token 時從磁碟載入比 LMCache 快 2.0 倍、三層合起來快 1.23 倍，與原生 vLLM KV Offload 實作則差在約 4% 以內，而且在 H100 上很多請求根本跨不過外部快取划算的那道門檻。

#04

GC 不再掃 system image

Julia 1.13 在 9 月 10 日發布，改動集中在延遲：image 物件重新設計之後，GC 不再掃過預先載入的系統程式碼，bare session 的 full collection 從 35ms 掉到 2ms，載入 GLMakie 之後從 187ms 掉到 68ms。hash 從 MurmurHash3 換成純 Julia 寫的 RapidhashNano，長字串從 8.555μs 降到 1.742μs，代價是自訂 hash 方法必須接受 seed 參數、而且不得給預設值。scheduler 這邊 @spawn 改成只叫醒一個 thread 而不是全部閒置 thread，官方量到 16 核 Linux 上 1.1 到 1.6 倍、Windows 上 10 到 300 倍。

#05

翻譯一次，指令數翻倍

Chips and Cheese 把 Windows 11 的 x86-64 轉 ARM64 翻譯層 Prism 產出的程式碼從 translation cache 裡挖出來逐條讀，測試平台是 Snapdragon X2 Elite，對照組是 Neoverse N1 與 N2。作者給的粗略法則是同一份 Geekbench 7 工作負載走過翻譯之後，執行的 aarch64 指令數大約是原生 x86-64 的兩倍，其中 AVX 對應到 NEON 的影片播放負載罰得最重、低 IPC 的導航負載罰得最輕。翻譯本身多半直來直往，漏掉的是迴圈裡沒必要的 register spill 與嚴格 register mapping 逼出來的多餘指令；作者的結論是這條路走不走得通，靠的是硬體本身夠快，不是翻譯器多聰明。

#09

location 後面終於能放變數

NGINX 1.31.5 把 location 從 URL 比對裡解放出來，任何變數都能當成 location 的 traffic modifier，於是 location $vip、location $restricted_methods 這種寫法成立，判斷邏輯搬進 map。搭配 client_body_early_read 提早讀 request body、再用原生的 json_set 取出 JSON 欄位，routing 決策可以建立在 body 內容上，不必再掛一段 script。官方自己把代價講明：body 越大，處理吃的記憶體與 CPU 越多，所以簡單而常見的 predicate location 要擺在前面。

union 上了線，沒有 discriminator

C# 15 的 union 會跟著 .NET 11 一起出，而這篇講的是它撞上 System.Text.Json 之後的實際形狀：JsonSerializer.Serialize(new IntOrString(42)) 序列化出來就是 42，沒有 wrapper、沒有 discriminator，只有在兩個 case 的 JSON 型別不同時反序列化才沒有歧義。兩個 object case 就得掛上 [JsonUnion(TypeClassifier = typeof(JsonUnionTypeStructuralClassifier))] 靠屬性名字分辨，OpenAPI 那一側則是每個 case 一個 anyOf 條目。限制寫得很清楚，只有走 System.Text.Json 的綁定來源能用，query string、route value、header 與 form field 都不行，因為 ?id=42 沒有任何線索說該綁 int 還是 string。
