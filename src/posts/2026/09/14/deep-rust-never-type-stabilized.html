8 月 24 日，Rust 貢獻者 waffle 敲定了 never type ! 的穩定化——這件事本身就花了兩年多；同一天生效的改動裡，還藏著一個連作者自己都沒預料到的 breaking change，跟另一個規則變動疊在一起，方向剛好相反。

Rust 用兩年補齊 never type

八月 24 日這天，Rust 的型別系統補上了最後一塊拼圖——never type ! 完成穩定化，會隨 Rust 1.99 一起發佈。讓這件事拖了兩年多才落地的，不是技術本身多難，而是牽動了一條每個 Rust 使用者天天在用、卻幾乎沒人會去讀規格的隱性規則：型別推斷的 fallback。

從一個沒人敢動的 fallback 開始

never type 在 Rust 裡代表「這裡不可能有值」——panic!()、return、無窮迴圈，這些運算式的型別都是 !。多數時候這件事不會造成困擾，因為 ! 可以隱式轉換成任何其他型別：一個 match 裡有一支手臂回傳整數、另一支手臂 panic!()，整條運算式的型別照樣是整數，! 那一邊直接讓路。真正麻煩的情況是相反的：如果一段程式碼裡，所有分支都是 !，而這個結果本身又完全沒有被用到，編譯器手上沒有任何線索能決定型別，只能套用一條叫做 fallback 的預設規則去猜一個型別出來。

這種「猜出來的型別」會不會外洩，取決於這段程式碼寫得多鬆散。多數時候寫程式碼的人會明確標出回傳值該是什麼型別，fallback 根本沒有出場機會；只有在型別完全交給編譯器自己判斷、而且判斷結果又沒有被拿去做任何要求具體型別的操作時，fallback 才會被觸發。這也是為什麼多數 Rust 開發者對這條規則完全無感——平常寫的程式碼，通常根本不會踩到這條路徑。

這條 fallback 規則的尷尬之處，2024 edition 之前一直存在。遇到這種完全推不出型別的情況，編譯器預設猜的是 ()，也就是 unit type。這個選擇當年是安全的——! 能轉換成任何型別，轉成 () 不會讓已經能編譯的程式碼壞掉。但語意上並不準確：這段運算式明明不可能真的產生一個值，把它當成「產生了一個空值」，等於在型別系統裡留了一個心照不宣的洞。

edition 是 Rust 用來在不打破生態系的前提下逐步調整語言行為的機制——同一份 Rust 編譯器，可以用 2015、2018、2021 或 2024 edition 的規則去編譯同一份 crate，切換 edition 不需要換編譯器版本，也不代表舊 edition 會被丟棄。這個設計原本是為了讓「改變語言預設行為」這件事有台階可下：新寫法先進新 edition，舊程式碼留在舊 edition 也照樣能編。但 fallback 規則恰好是一個 edition 制度也不容易溫柔處理的例外——它不是「新寫法 vs 舊寫法」的選擇，而是「同一段沒有任何顯式標註的寫法，編譯器猜出來的答案變了」。

這也是 Rust team 慣用的手法：真正會改變既有程式碼行為的調整，幾乎都選擇透過新 edition 才生效，而不是直接對所有既有程式碼下手。好處是舊程式碼永遠有退路——只要不升 edition，就不會被新規則影響；代價是同一份工具鏈要同時維護好幾種 edition 的語意，編譯器內部的複雜度只增不減。

這種對回溯相容的堅持，是 Rust 從很早期就刻意選擇的路——語言可以演化，但不能要求使用者被迫跟著每一次演化重寫程式碼。edition 制度、以及像這次為 fallback 規則單獨開一個 edition 的做法，都是這個堅持在實務上的體現：改動可以發生，但永遠是使用者自己選擇要不要接受。

補這個洞為什麼要花兩年多？因為 fallback 是編譯器每次遇到型別完全推不出來時都會悄悄呼叫的規則，動它等於把手伸進所有 Rust 程式碼共同依賴的隱藏機制裡——任何調整都要先確認不會讓現有的、已經編譯通過的程式碼在悄無聲息中變成另一種行為。waffle 8 月 24 日敲下最後一行的時候，距離這件事真正開始已經超過兩年；中間要處理的不是「能不能改」，而是「改了之後，舊程式碼還能不能編過、編過之後行為還一樣嗎」。

這兩年多裡發生的事，時間軸上能標出來的重點其實只有三個：問題開始被認真處理、8 月 24 日 waffle 把穩定化敲定、以及 never type 隨 Rust 1.99 進入穩定版。中間漫長的拉鋸不是圍繞著「這個規則該不該改」，而是圍繞著下一節要講的東西——同一時間點還有第二個改動，兩者疊在一起會發生什麼。

兩個 breaking change 疊在一起會怎樣

讓事情更複雜的是，fallback 規則的改動不是唯一動到的東西。標準函式庫裡的 Infallible——原本是一個沒有任何 variant、理論上不可能有值的獨立 enum，常被用在「這個 Result 不會出錯」的情境——同時要變成 ! 的 type alias。這聽起來像是把兩個本來就等價的東西畫上等號，應該無傷大雅，但這個定義調整本身，被發現是意外的 breaking change：凡是有程式碼把 Infallible 當成一個具體、獨立的型別在用，把它換成別名之後，這些程式碼看到的型別關係就變了。

Infallible 常見的用法是 TryFrom 之類會回傳 Result 的 trait，某些實作「這個轉換不可能失敗」，用 Result<T, Infallible> 讓型別系統把「不可能出錯」直接寫進簽名，呼叫端甚至可以用一段「理論上用不到」的錯誤處理把 impossible case 消掉。這一整套用法能成立，靠的正是 Infallible 是一個有名字、可以被 pattern match 窮舉掉的具體型別；換成 ! 的別名之後，這些寫法在語意上更精確了，但任何依賴 Infallible 這個名字本身、而不是它的語意在做特化的程式碼，就會踩到前面講的意外 breaking change。

要注意的是，edition 是 crate 層級的設定，不是專案層級的——一個工作區裡，可以有一部分 crate 用 2024 edition、另一部分維持在舊 edition，彼此照樣能互相依賴、互相呼叫。這個彈性讓遷移可以分批進行，不需要整個 workspace 一次到位，但也意味著同一個專案裡，fallback 的行為可能因為不同 crate 用了不同 edition 而不一致——這件事本身值得在遷移計畫裡明確寫下來，而不是假設全專案的行為是一致的。

三個標註點合起來說的是同一件事：if 和 else 兩個分支都不可能正常返回，x 的型別完全沒有其他線索可以確定。2024 edition 之前，編譯器對這種情況的答案永遠是 ()；進了 2024 edition，答案變成 ! 本身。差別看起來只是一個型別記號，但對任何靠型別大小做記憶體佈局假設、或是靠 () 這個具體型別做 trait 分派的程式碼，答案換了，行為就可能跟著換。下面這個滑桿把同一段程式碼放進 Rust 目前並存的四個 edition 裡各跑一次，可以直接看到 fallback 猜的型別在哪一個 edition 切換。

這種「答案換了」的風險，在 Rust 社群裡有個專門的名字：silent behavior change——程式碼一樣能編譯，警告也不會冒出來，但執行期的行為跟著型別悄悄變了。對比一般的 breaking change（編譯直接失敗，開發者馬上知道要修），silent behavior change 更難抓，因為 CI 綠燈、測試也可能照樣過，問題往往要到很後面、甚至上線之後才會被發現。這也是為什麼 waffle 花了兩年多而不是幾個月——大部分時間不是花在寫程式碼，而是花在窮舉「還有哪些地方會受 fallback 影響」。

這正是 fallback 改動與 Infallible 別名化「疊在一起」的地方——很多原本會因為 fallback 從 () 換成 ! 而受影響的程式碼，剛好也是那些把 Infallible 當「等同於 ()」在用的地方；Infallible 本來就沒有值，把它改成 ! 的別名，反而讓兩邊的型別對上了。兩個 breaking change 各自看起來都會傷人，湊在一起，傷害面反而比想像中小——但「小」不等於「零」，這一點下一節的 crater 數字會說清楚。下面拖曳分隔線，看 Infallible 的定義實際換了什麼。

具體來說，() 的大小是零，! 理論上也不佔任何 bit——兩者在多數情境下確實可以互換而不出事。真正會出事的是那些用 TypeId、Any::downcast 之類機制在執行期比對「這是不是 ()」的程式碼；fallback 從 () 換成 ! 之後，這類比對的結果會反過來，而編譯器完全不會為此發出任何警告，因為兩種型別都合法、程式碼也都能編過。

crater 掃過 3,300 個 crate 之後

「小」的具體數字，靠的是 crater——把 crates.io 上所有公開函式庫全部拉下來，用新規則重新編譯一次的機制。這次跑完，3,300 個 crate 被列為受這個改動影響。這個數字乍看嚇人，拆開來看卻完全是另一回事：真正因為自己程式碼寫法而完全編不過的，只有 7 個；剩下的絕大多數，只是因為釘住了某個舊版本的函式庫，而那個函式庫後來已經被上游修好了。

crater 這套機制本身值得多說一句：它不是抽樣，而是把 crates.io 上所有能抓到原始碼、能夠成功建置的 crate 全部拉下來，分別用舊工具鏈與新工具鏈各編譯一次，逐一比對結果。這種「整個生態系跑一遍」的驗證方式，代價是每次跑都要花上可觀的機器時間，但換來的是一個實證數字，而不是「理論上應該沒問題」的猜測。3,300 這個數字之所以站得住腳，前提正是它來自這樣一次窮舉，而不是抽樣推估。

換句話說，3,300 這個數字量的是「理論上會被牽動的範圍」，7 這個數字量的才是「真正需要開發者自己動手改程式碼的範圍」。中間那段落差，來自 Rust 生態系一個常見但不太被注意的現象：大量的 crate 並不是自己寫壞了，而是相依鏈裡卡著一個沒人記得去升級的舊版本，新規則一上路，舊版本裡早就修好的問題又重新冒出來。

對付這批「相依舊版而失敗」的 crate，Rust 團隊選擇把修復回頭 backport 到舊版函式庫的分支上，一次救回 1,553 個原本會 failing 的 crate——這些 crate 本身一行程式碼都不用改，只要它們相依的函式庫舊分支被打了補丁就自動過關。但 backport 不是萬靈丹：有些維護者直接拒絕接受回頭修復，理由是那個版本早就已經 EOL，沒有義務再為它發新的補丁。

為什麼會拒絕？合理的推測是，對已經 EOL 的版本來說，接受 backport 意味著要重新啟動一套早就關閉的發布流程——重新切分支、重新跑測試、重新發版，對一個已經沒有主動維護資源的專案，這筆成本往往比「請下游自己升級」更高。文章本身沒有寫出維護者的確切理由，只提到 EOL 是他們給出的說法。

這個模式其實不是第一次出現在 Rust 的版本歷程裡——語言核心規則的調整，最大的不確定性往往不是「新規則對不對」，而是「舊生態系裡到底藏了多少依賴舊行為的角落」。crater 存在的意義，正是把這種不確定性從「猜測」變成「可以事先量到的數字」，讓團隊在真正推出改動之前，就知道要準備多少 backport 資源、要提前警告哪些維護者。

這張表格把三層數字疊在一起看：受影響的範圍、真正壞掉的範圍、修復覆蓋到的範圍——三個數字一個比一個小，但沒有一個小到可以忽略。對一個進入穩定軌道十多年的語言來說，「幾乎所有生態系都不受影響」本來就是任何 breaking change 唯一能拿到及格分的答案；3,300 對 7，是這次改動及格的原因，不是它毫無代價的證明。

留在 1.98，還是往前走

如果你的專案剛好落在那 1,553 個之外——相依鏈裡有一段已經 EOL、沒人要再修的舊版函式庫——升級到 Rust 1.99 就不是跑一次相依更新指令那麼簡單的事。真正會踩到 fallback 差異的程式碼，往往長得很無害：一個沒有標注回傳型別的函式、一段兩個分支都會 panic! 或 return 的邏輯、一個依賴推斷結果剛好是 () 才能通過編譯的巨集展開。這些寫法在舊 edition 下能正常編譯，換了 edition 就不一定。

文章給出的因應方式其實只有三條，沒有第四種：留在 Rust 1.98 觀望，等社群把剩下的坑填得差不多；把所有相依都升級到已經拿到 backport 修復的版本；或者在會被 fallback 影響的位置，自己明確寫出回傳型別，不要把決定權交給編譯器的預設猜測。

三條路各自的成本不一樣，也不是互斥的選項。留在 1.98 最省事，但代價是遲早要補這筆作業，而且拖得越久，往前跳的距離就越遠；升級相依最乾淨，把問題留給上游解決，但前提是每一段相依鏈上都有人願意接手維護，遇到已經 EOL 的分支就卡住；明確標注型別最麻煩，需要一行一行找出可能踩雷的地方，但好處是徹底繞開 fallback 的猜測，往後編譯器再怎麼調整這條規則都影響不到你。下面這個手把把三條路放在同一條線上，拖著看每條路實際要付出什麼。

實際判斷「我會不會中」的做法並不神秘：在升級前針對 2024 edition 先跑一次編譯檢查，把所有「這裡型別推斷可能改變」的警告收集起來，再一個個看是不是真的用在會被使用到的路徑上。這比等正式升級後線上行為跑掉才回頭查，成本低了一個量級。已經在 CI 裡長期鎖定 edition 2021 的專案，這筆檢查可以留到真正決定升級的那一刻再做，不用現在就急。

三條路湊在一起看，其實是同一個提醒的三種寫法：fallback 這種「編譯器幫你猜」的機制，一旦你的程式碼真的走到需要猜的那條路徑，最安全的做法從來都不是祈禱猜對，而是不要讓它有機會猜。

這三條路也不是永遠鎖死——如果之後有更多維護者被說服去更新已經 EOL 的分支，或者社群整理出更完整的「哪些寫法會踩雷」清單，留在 1.98 的成本會隨時間下降。但那是別人手上的進度，不是你現在能控制的變數。

沒被 backport 救到的那批：留在 EOL 版本上的相依鏈不會自己變好，Rust 1.99 上線之後，剩下的選擇就是升級、標注型別，或是接受自己暫時卡在 1.98。
